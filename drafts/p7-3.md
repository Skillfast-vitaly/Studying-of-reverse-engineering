
## П7.6. Виртуальные функции и их таблица

Второй заход начался с П7.5. Теперь — самое важное в C++ для реверсера.

### Одна функция — разные ответы

Посмотри на `talk`:

```cpp
void talk(const Animal *a)
{
    puts(a->name());
    a->speak();
}
```

`talk` получает просто «какое-то животное». Но для собаки печатается
`sobaka` и `gav!`, а для птицы — `ptica` и `...`. Как одна и та же
строка `a->name()` вызывает разные функции?

Всё дело в слове **`virtual`** («виртуальный») перед методом в классе
`Animal`. Оно говорит: «какую функцию вызвать, решай **во время
работы** по настоящему классу объекта, а не по типу указателя».
Наследник может заменить такой метод своим — для этого слово
`override` («заменить»). `Dog` заменил и `name`, и `speak`, а `Bird`
только `name`: птица говорит по-звериному, `...`.

### Таблица виртуальных функций

Как процессор узнает класс объекта? Никак — у процессора нет классов.
Поэтому компилятор делает вот что:

1. Для каждого класса с виртуальными функциями кладёт в `.rdata`
   **таблицу виртуальных функций** — vtable `[ви-тэйбл]`, у Visual
   Studio она называется vftable. Это просто массив адресов функций,
   по 8 байт.
2. В **первые 8 байт каждого объекта** конструктор записывает адрес
   таблицы его класса. Вот что за строку ты видел в П7.4:
   `mov [rax], rcx` с адресом `Dog::'vftable'`.

Таблицы нашей программы у Visual Studio:

```
               Animal::`vftable'      Dog::`vftable'       Bird::`vftable'
ячейка 0, +00  Animal::scalar del.    Dog::scalar del.     Bird::scalar del.
ячейка 1, +08  Animal::name           Dog::name            Bird::name
ячейка 2, +10  Animal::speak          Dog::speak           Animal::speak
```

Ячейка 0 — удаляющий деструктор из П7.4: деструктор у нас виртуальный,
поэтому он тоже в таблице. Порядок остальных — порядок объявления
в `Animal`: `name`, потом `speak`. Наследник сохраняет порядок
и подставляет в ячейки свои функции. У `Bird` своей `speak` нет —
в её таблице стоит адрес `Animal::speak`.

### Виртуальный вызов в листинге

Функция `talk` в сборке с оптимизацией:

```
talk:
    push    rsi
    sub     rsp, 20h
    mov     rsi, rcx                   ; rsi = a
    mov     rax, [rcx]                 ; rax = адрес таблицы из объекта
    call    qword ptr [rax+8]          ; ячейка 1 — name()
    mov     rcx, rax
    call    puts
    mov     rax, [rsi]                 ; снова таблица
    mov     rcx, rsi                   ; this = a
    add     rsp, 20h
    pop     rsi
    jmp     qword ptr [rax+10h]        ; ячейка 2 — speak()
```

Вот она, главная примета C++ в листинге:

```
mov     rax, [rcx]             ; взять таблицу из начала объекта
call    qword ptr [rax+8]      ; вызвать функцию из ячейки
```

Номер ячейки — смещение, делённое на 8: `+8` — ячейка 1, `+10h` —
ячейка 2. Последний вызов стал `jmp` вместо `call`: `speak` — последнее
действие `talk`, и компилятор передал ей управление прыжком. Её `ret`
вернётся сразу туда, откуда звали `talk`.

**Как реверсер узнаёт, что вызвалось.** Прямо из листинга — никак:
адрес в `RAX` появится только во время работы. Поэтому идут обходным
путём: выясняют, объект **какого класса** приходит в `RCX`, находят
таблицу этого класса и смотрят в нужную ячейку. В x64dbg проще:
поставь точку останова на `call qword ptr [rax+8]` и посмотри, куда
пойдёт процессор — глава 13.

### У g++ таблица устроена иначе

```
talk у g++:
    mov     rax, [rcx]
    call    qword ptr [rax+10h]        ; name — ячейка 2, а не 1
    …
    call    qword ptr [rax+18h]        ; speak — ячейка 3
```

У g++ в таблице два деструктора: один только разрушает объект, другой
ещё и освобождает память. Они занимают ячейки 0 и 1, поэтому `name`
сдвинулась на `+10h`. А перед ячейкой 0 лежат ещё две служебные
(о них — в упражнении П7.4). Мысль та же, номера другие — снова
«сначала узнай компилятор».

Заметь ещё: таблица виртуальных функций — это массив указателей на
функции, который ты сам строил в П1.7 для обработчиков. Только здесь
его строит компилятор. Ничего нового: взять адрес из таблицы по номеру
и вызвать по нему — как `table[reason](value)` в П1.7.

## П7.7. Искажённые имена

### Зачем искажать

В C имя функции в файле — просто её имя: `count_legs`. В C++ так нельзя.
У нас три функции `name` — у `Animal`, `Dog` и `Bird`. А ещё C++
разрешает несколько функций с одним именем, но разными аргументами.
Компоновщику (глава 2) же нужно, чтобы каждое имя было единственным.
Поэтому компилятор зашивает в имя класс, аргументы и прочее. Это
называется **name mangling** `[нэйм мэ́нглинг]` — «искажение имён».
Microsoft в своей документации зовёт такие имена **decorated names** —
«украшенные имена».

Имена нашей программы у Visual Studio:

| Искажённое имя | Что это |
|---|---|
| `?name@Dog@@UEBAPEBDXZ` | `public: virtual char const * Dog::name(void) const` |
| `?legs@Animal@@QEBAHXZ` | `public: int Animal::legs(void) const` |
| `?give_bone@Dog@@QEAAXXZ` | `public: void Dog::give_bone(void)` |
| `?count_legs@@YAHPEAPEAVAnimal@@H@Z` | `int count_legs(class Animal **, int)` |
| `??0Dog@@QEAA@XZ` | `public: Dog::Dog(void)` — конструктор |
| `??_GDog@@UEAAPEAXI@Z` | удаляющий деструктор `Dog` |
| `??_7Dog@@6B@` | `const Dog::'vftable'` — таблица |
| `??2@YAPEAX_K@Z` | `operator new(unsigned __int64)` |
| `??3@YAXPEAX_K@Z` | `operator delete(void *, unsigned __int64)` |

Расшифровка — настоящий вывод расшифровщика, слово `__cdecl` я убрал.

### Как читать на глаз

Целиком учить схему не нужно — её расшифровывают программы. Но
несколько примет стоит знать:

- `?` в начале — имя C++. Дальше имена **задом наперёд** до `@@`:
  `name@Dog@@` — это `Dog::name`;
- `??0` — конструктор, `??1` — деструктор, `??_G` — удаляющий
  деструктор, `??_7` — таблица виртуальных функций, `??2` и `??3` —
  `operator new` и `operator delete`;
- после `@@`: `Q` — обычный открытый метод, `U` — открытый
  **виртуальный** метод, `Y` — функция вне класса;
- `QEAA` — метод может менять объект, `QEBA` — не может (`const`);
- типы: `H` — `int`, `X` — `void` (или «нет аргументов»), `D` — `char`,
  `PEA…` — указатель, `V…@@` — класс. `Z` — конец.

Так `?legs@Animal@@QEBAHXZ` читается: метод `legs` класса `Animal`,
открытый (`Q`), не меняет объект (`EBA`), возвращает `int` (`H`),
аргументов нет (`X`), конец (`Z`).

### Кто расшифровывает

- **IDA** и **Ghidra** — сами: в листинге будут человеческие имена;
- в консоли Visual Studio из П7.2 есть программа **undname**
  («разукрашиватель»):

  ```
  undname ?name@Dog@@UEBAPEBDXZ
  ```

  Она ответит строкой вида
  `is :- "public: virtual char const * __cdecl Dog::name(void) const"`
  (так описано в документации Microsoft; точный вид у тебя может чуть
  отличаться).

У **g++** схема другая, её называют Itanium `[айтéйниум]` — по
процессору, для которого её придумали:

| Имя у g++ | Что это |
|---|---|
| `_ZNK3Dog4nameEv` | `Dog::name() const` |
| `_Z4feedP3Dog` | `feed(Dog*)` |
| `_ZN3DogD0Ev` | `Dog::~Dog()` — деструктор, который ещё и освобождает память |
| `_ZTV3Dog` | `vtable for Dog` — таблица |
| `_ZTS3Dog` | `typeinfo name for Dog` — строка `3Dog` |

Начало `_Z` и длины перед именами: `3Dog` — три буквы, `4name` —
четыре. IDA расшифровывает и эту схему.

### Где эти имена встретятся на деле

Честно: в чужом `.exe` из Visual Studio **таблицы символов нет**. Имена
методов живут только в отдельном файле символов `.pdb`, а его обычно
не выдают. Поэтому в чужой программе вместо `Dog::name` будет
`sub_140001230`. Искажённые имена ты встретишь:

- в **экспорте** DLL, написанных на C++: методы классов, которые DLL
  отдаёт наружу, видны в таблице экспорта под своими искажёнными
  именами;
- в **символах Microsoft** для файлов Windows — тех самых, что WinDbg
  качает с сервера (глава 30). IDA тоже умеет их подтянуть;
- в **своих сборках**: g++ оставляет таблицу символов (поэтому IDA
  в П5 знала `main`), а Visual Studio кладёт рядом `.pdb`, если
  собирать с ключом `/Zi`.

А в чужой программе без имён классы всё равно можно опознать —
следующий раздел.

## П7.8. Имена классов в самом файле

У Visual Studio по умолчанию включён ключ `/GR` — **RTTI** `[ар-ти-ти-áй]`,
Run-Time Type Information, «сведения о типах во время работы» (по
документации Microsoft он включён по умолчанию). Это данные, по которым
программа может во время работы узнать класс объекта. Нужны они редко,
а для реверсера это подарок: **имена всех классов с виртуальными
функциями лежат в файле строками**.

В нашей программе, собранной с RTTI, в секции данных нашлись три
строки:

```
.?AVDog@@
.?AVAnimal@@
.?AVBird@@
```

`.?AV` — «класс» (V от class), дальше имя и `@@`. Для структур будет
`.?AU` (U от struct). Поиск строк по `.?AV` — своим `strings.py`
из П6.9 или окном Strings в IDA — выдаёт **список классов программы**.
Даже без единого имени функции.

А как найти таблицу класса? Visual Studio кладёт **прямо перед таблицей**
ещё 8 байт — адрес служебной записи RTTI, а та ведёт к строке с именем.
То есть цепочка такая: строка `.?AVDog@@` ← записи RTTI ← 8 байт перед
таблицей ← сама таблица `Dog` ← конструктор `Dog`, который её
записывает в объект. По перекрёстным ссылкам (клавиша X в IDA, П5.5)
от строки до конструктора — несколько шагов.

Инструменты умеют проходить эту цепочку сами. В Ghidra этим занимается
анализатор **Windows x86 PE RTTI Analyzer** при автоанализе, а скрипт
**RecoverClassesFromRTTIScript** (папка `C++` в Script Manager)
восстанавливает классы целиком (оба названия — из исходников Ghidra
12.1.4). Для IDA тоже есть такие средства. Что IDA 9.2 подпишет
сама, без помощи, я проверить не могу — посмотри в упражнении П7.5
и расскажи мне.
