
## П5.9. Тяжёлая сборка: когда имён нет

Третий заход. В главе 16, раздел 16.6, ты собрал задачу «по-взрослому»:
`make hard`, флаги `-O2 -s`, без имён. Открой `01_strings.hard.exe`
в IDA — это **новая** база, рядом появится свой `.i64`.

### Окно Functions без имён

Открой **Functions** (**Shift+F3**). Картина как в главе 14,
раздел 14.7, только приставка другая: вместо `FUN_…` у Ghidra —
**`sub_…`** у IDA. `sub` — subroutine `[сáбрутин]`, «подпрограмма»,
дальше адрес. Имена остались только у тех, кого IDA узнала сама:

- **`start`** — так IDA называет точку входа из заголовка PE (глава 8);
- **`TlsCallback_0`**, `TlsCallback_1` — TLS-колбэки из главы 13;
- переходники к импортам: `fgets`, `puts` и другие — их имена лежат
  в таблице импорта, без них программа не загрузится (глава 8).

Часть служебных функций библиотеки C IDA может узнать по своим
«отпечаткам» — у них появятся имена, а на полоске навигации они будут
бирюзовыми (раздел П5.4). Какие именно узнает твоя IDA, проверь сам.

### Находим main по строке

Метод тот же, что в главе 16: от того, что программа **обязана**
использовать. Открой **Strings** (**Shift+F12**), дважды щёлкни по
`Vvedite parol:`. В тяжёлой сборке раскладка `.rdata` другая — у меня
так:

```
.rdata:0000000140009000 aVveditePar     db 'Vvedite parol: ',0
.rdata:0000000140009000                                         ; DATA XREF: sub_140007B30+A↑o
```

Ссылка `sub_140007B30+A↑o`: функция по адресу `140007B30`, смещение
`0Ah` от её начала, вид `o` — там берут **адрес** строки (`lea`).
Двойной щелчок — и ты в функции. Это `main`: по главе 16 ты знаешь,
кто печатает приглашение. Дай ей имя сразу: курсор на `sub_140007B30`,
**N**, `main`.

Для сравнения загляни и в `rev_is_fun_2024`: у меня она лежит по
`140009012`. Нажми **X** — ссылок **нет**. Это то самое открытие главы
16: строка в файле осталась, а код её не использует.

### Пароль внутри инструкций

Вот сердце проверки — те же инструкции, что в разделе 16.6, только
в манере IDA (примерно так; адреса — мои, настоящие):

```
.text:0000000140007B89                 mov     rdx, 343230325F6E75h
.text:0000000140007B93                 mov     byte ptr [rsp+rax+20h], 0
.text:0000000140007B98                 xor     rdx, [rsp+28h]
.text:0000000140007B9D                 mov     rax, 665F73695F766572h
.text:0000000140007BA7                 xor     rax, [rsp+20h]
.text:0000000140007BAC                 or      rax, rdx
.text:0000000140007BAF                 jz      short loc_140007BCA
```

(Обращения к стеку у тебя могут выглядеть как `[rsp+68h+var_48]`:
IDA любит считать их от начала кадра функции. Это то же самое место,
просто записанное по-другому.)

Три вещи, знакомые по этому приложению:

- `mov` с длинным числом IDA пишет как обычный `mov` — не `movabs`
  (глава 16 предупреждала, что бывают оба имени);
- числа с `h` на конце: `665F73695F766572h`;
- `jz` вместо `je` — те же «z»-имена, что `jnz` в П5.6.

А теперь приём, ради которого стоит запомнить IDA. **Щёлкни правой
кнопкой по числу `665F73695F766572h`.** В меню IDA предложит показать
его по-другому: десятичным, двоичным — и **как символы**. Рядом с
каждым пунктом написана его клавиша. Выбери символы, и вместо числа
появятся буквы.

Посмотри, в каком порядке IDA их выведет. Если увидишь
`'f_si_ver'` — это не ошибка, а глава 3: IDA читает **число** от
старшего байта к младшему, а в памяти оно лежит младшим байтом вперёд
— `r e v _ i s _ f`. Ту же перестановку ты делал в главе 16 руками.
Теперь IDA делает её за тебя, а тебе надо только узнать знакомую
картину.

Нажми **F5** в этой функции. Декомпилятор покажет условие примерно
такого вида:

```c
if ( !(*(_QWORD *)buf ^ 0x665F73695F766572LL | *(_QWORD *)&buf[8] ^ 0x343230325F6E75LL) )
```

`*(_QWORD *)buf` — «первые 8 байт буфера как одно число» (`_QWORD` —
«четверное слово», 8 байт), `^` — XOR (глава 17), `|` — OR. Та же
логика, что ты читал в листинге: два XOR, объединённые через OR,
и проверка на ноль. Декомпилятор не превратил это обратно
в `strcmp`: он показывает то, что **делает** код, а не то, что
написал автор.

## П5.10. Отладчик IDA — коротко

В IDA есть свой отладчик. Идеи — ровно те же, что в x64dbg (глава 13):
точки останова, шаги, регистры, память. Подробно учить его второй раз
не нужно — достаточно знать, где что лежит.

Сначала выбери, **чем** отлаживать: меню **Debugger → Select debugger**
(«Отладчик → Выбрать отладчик»). Для программы на своей машине —
локальный отладчик Windows (в списке он называется примерно **Local
Windows debugger**). Клавиши — по документации Hex-Rays:

| Действие | x64dbg (глава 13) | IDA |
|---|---|---|
| точка останова | F2 | **F2** |
| запустить / продолжить | F9 | **F9** |
| шаг с заходом | F7 | **F7** |
| шаг с обходом | F8 | **F8** |
| выполнить до возврата из функции | Ctrl+F9 | **Ctrl+F7** |
| выполнить до курсора | F4 | **F4** |
| завершить программу | — | **Ctrl+F2** |

Почти всё совпадает: эти клавиши давно стали общими для отладчиков
Windows. Отличается выход из функции: в IDA это **Ctrl+F7**. Клавиши
x64dbg я сверил с его исходником, клавиши IDA — с таблицей Hex-Rays.

### Опыт: смотрим, куда пойдёт проверка

Возьми обычную сборку `01_strings.exe` (её базу с твоими именами).

1. Встань на строку `test eax, eax` сразу после `call strcmp`
   и нажми **F2**. Строка станет красной — точка поставлена.
2. **F9.** Откроется окно программы — введи `test` и нажми Enter.
3. IDA остановится на `test eax, eax`. Найди окно регистров
   (**General registers** — «общие регистры»): в `RAX` будет
   **не ноль** — `strcmp` сказала «строки разные».
4. Переключись на граф (**пробел**). У блока с `jnz` одна из стрелок
   **мигает** — по ней процессор пойдёт сейчас. Она ведёт к «Neverno».
5. **F9** — программа допишет «Neverno» и закончится.
6. Повтори с паролем `rev_is_fun_2024`. Теперь в `RAX` ноль, и мигает
   стрелка к «Verno».

Ты только что увидел решение программы **глазами**: не вычитал из
адресов, а посмотрел, какая стрелка загорелась. Адреса в отладчике
у тебя будут другими, чем в базе: IDA сдвигает базу туда, куда
Windows загрузила программу (ASLR, глава 13). Имена и комментарии при
этом едут вместе с кодом.
