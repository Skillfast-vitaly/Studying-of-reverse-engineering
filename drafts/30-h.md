
## 30.11. Сверяем часть X: таблицы страниц

В главе 32 ты переводил адрес руками: резал его на четыре индекса
по 9 битов, спускался по дереву PML4 → PDPT → PD → PT, а физические
адреса таблиц я **придумал** — «настоящие видны только из кольца 0,
посмотрим в главе 30 отладчиком ядра». Смотрим.

### !pte: весь спуск одной командой

Возьми адрес своего `DriverEntry` (из строки DebugView или из
`x Hello!DriverEntry`) и попроси WinDbg показать записи таблиц для
него. Драйвер для этого должен быть загружен:

```
!pte Hello!DriverEntry
```

Ответ — примерно так (адреса и числа у тебя будут свои; вид вывода
я даю по памяти о том, как WinDbg печатает его на x64):

```
                                           VA fffff8074e9b1000
PXE at FFFFF6FB7DBEDF80    PPE at FFFFF6FB7DBF00E8    PDE at FFFFF6FB7E01D3A0    PTE at FFFFF6FC03A74D88
contains 0000000004309063  contains 0000000004310063  contains 000000011B64A063  contains 090000012345A021
pfn 4309      ---DA--KWEV  pfn 4310      ---DA--KWEV  pfn 11b64a    ---DA--KWEV  pfn 12345a    ----A--KREV
```

Четыре столбца — **четыре уровня** из главы 32. Имена у WinDbg свои,
исторические:

| WinDbg | Глава 32 | Что это |
|---|---|---|
| **PXE** | запись PML4 | верхний уровень |
| **PPE** | запись PDPT | второй |
| **PDE** | запись PD | третий |
| **PTE** | запись PT | последний — сама страница |

Строки сверху вниз:

1. **`... at FFFFF6FB...`** — виртуальный адрес, по которому Windows
   видит **саму запись** таблицы. Да, ядро держит свои таблицы
   страниц видимыми в собственной памяти — это отдельная хитрость,
   сейчас она нам не нужна;
2. **`contains ...`** — 64 бита записи. Ровно то, что ты разбирал
   в разделе 32.6: младшие 12 битов — флажки, биты 12–51 — физический
   адрес, бит 63 — XD;
3. **`pfn ...`** и буквы — WinDbg разобрал запись за тебя.

**PFN** — Page Frame Number `[пейдж фрейм нáмбер]`, «номер
физической страницы». Это биты 12–51 записи, то есть физический адрес,
делённый на 4096. Чтобы получить адрес, припиши три нуля в hex:
`pfn 4309` → физический адрес `0x4309000`. Вот он, **настоящий**
физический адрес таблицы PDPT, который в главе 32 был выдуман.

### Буквы флажков

По документации Microsoft к `!pte`: заглавная буква — бит стоит,
чёрточка — нет. Каждая буква — бит из таблицы раздела 32.6:

| Буква | Бит записи | Если стоит | Если нет |
|---|---|---|---|
| **V** | 0, P | valid — запись действует | (чёрточка) — страницы нет |
| **W** / **R** | 1, R/W | writeable — можно писать | read-only — только чтение |
| **U** / **K** | 2, U/S | user — можно из кольца 3 | kernel — только ядро |
| **A** | 5 | accessed — обращались | — |
| **D** | 6 | dirty — писали | — |
| **L** | 7, PS | large — большая страница (раздел 32.11) | — |
| **G** | 8 | global — не сбрасывать из TLB | — |
| **C** | 9 | copy on write — пометка Windows в свободном бите | — |
| **E** | 63, XD наоборот | executable — выполнять **можно** | — |

Прочитаем последнюю запись из примера — `----A--KREV`:
**K** — только ядро (U/S = 0: программа сюда не доберётся, глава 27),
**R** — только чтение, **E** — выполнять можно, **V** — страница есть,
**A** — к ней обращались. Страница с кодом драйвера: читать и выполнять,
но не писать. Проверь по числу: `...021` — это биты 0 и 5 (V и A),
бита 1 (R/W) нет; старшая цифра `0` — бит 63 не стоит, значит, XD = 0
и выполнять можно.

Буква **W** у твоего кода или **R**? Это зависит от настроек Windows
(в частности, от «Целостности памяти» из главы 27, которая
в виртуальной машине может быть включена или выключена). Посмотри
у себя — это часть упражнения 30.4.

И заметь то, что в главе 32 называлось «права складываются по всему
пути»: у верхних уровней стоят широкие права (`KWEV`), а сужает
их последняя запись. Процессор побеждает самой строгой.

### DirBase — это CR3

В разделе 30.4 я просил запомнить строку `DirBase` из `!process`.
Теперь разгадка. Останови Windows и сравни:

```
!process -1 0
r cr3
```

`DirBase` у текущего процесса и `cr3` совпадут. Возможно, не до
последней цифры: младшие 12 битов `CR3` могут хранить номер PCID
(глава 32, раздел про TLB), а `DirBase` — это чистый адрес таблицы.
Старшая часть совпадёт обязательно.

**DirBase** — directory table base, «база таблицы каталога» —
физический адрес PML4 этого процесса, то самое значение, которое ядро
пишет в `CR3`, когда переключается на поток этого процесса (глава 32:
«у каждого процесса свой CR3»). Хранится оно в записи процесса.

Это и есть обещание главы 26: «В записи процесса в ядре хранится
ещё одна важная вещь: адрес таблиц перевода адресов этого процесса».
Посмотри, в каком поле:

```
dt nt!_KPROCESS DirectoryTableBase
```

`KPROCESS` — первая часть записи `EPROCESS` (раздел 30.13). По моей
памяти, поле стоит на смещении `+0x028`, но это внутренняя структура,
и Microsoft может сдвинуть её в новой сборке. Что покажет твой
WinDbg — то и правда.

### Спуск для программы

Открой в машине Блокнот. Останови Windows и найди его запись:

```
!process 0 0 notepad.exe
```

В ответе будет строчка `DirBase` — у Блокнота **свой** корень таблиц,
не такой, как у `System`. А поле `Peb` — адрес PEB Блокнота, адрес
в **нижней** половине (глава 26). Переведём его в физический тем же
спуском по чужим таблицам — расширением **`!vtop`** («virtual to
physical», «из виртуального в физический»). Документация Microsoft
велит передать ему **PFN** корня (DirBase без трёх последних нулей)
и виртуальный адрес:

```
!vtop <DirBase без трёх нулей> <адрес Peb>
```

Ответ покажет физический адрес страницы. Сделай это упражнение
вместе с упражнением 32.3 из главы 32 — там ты делал то же самое
на бумаге.

Главное, что тут надо увидеть: **один и тот же** адрес в разных
процессах ведёт в разную физическую память, потому что `CR3` разный.
Когда ты напишешь гипервизор, у тебя появится ещё один уровень
над всем этим — таблицы **гипервизора** (EPT, глава 37). Физический
адрес, который ты сейчас получил, для гипервизора будет всего лишь
«гостевым физическим».

## 30.12. Сверяем часть X: IDT и GDT

### IDT

В главе 34 я обещал: «В главе 30 отладчик ядра покажет всю IDT одной
командой». Вот она:

```
!idt
```

Ответ — длинный список, по строке на вектор: номер вектора в hex,
адрес обработчика и его имя. Примерно так:

```
Dumping IDT: fffff8074a29c000

00:	fffff8074a414100 nt!KiDivideErrorFault
01:	fffff8074a414440 nt!KiDebugTrapOrFault	Stack = 0xFFFFF8074A2A2000
02:	fffff8074a414940 nt!KiNmiInterrupt	Stack = 0xFFFFF8074A29E000
03:	fffff8074a414e00 nt!KiBreakpointTrap
...
06:	fffff8074a415900 nt!KiInvalidOpcodeFault
08:	fffff8074a416100 nt!KiDoubleFaultAbort	Stack = 0xFFFFF8074A298000
...
0d:	fffff8074a417000 nt!KiGeneralProtectionFault
0e:	fffff8074a417340 nt!KiPageFault
...
2e:	fffff8074a41c540 nt!KiSystemService
...
```

Сверь с таблицей из раздела 34.4 — по вектору 0, 3, 6, 8, 13 (`0d`)
и 14 (`0e`). Имена я там приводил по памяти и предупреждал, что может
добавиться `Shadow`. Что увидел ты — пришли мне: это станет правдой
курса.

Ещё три вещи, которые здесь видно:

- **`Stack = ...`** у некоторых векторов — это **IST** из главы 34:
  отдельный, заранее подготовленный стек для самых опасных событий.
  Двойной сбой (8) и NMI (2) — обязательно среди них: для них
  нельзя рассчитывать, что текущий стек в порядке;
- **вектор `2e`** — `KiSystemService`: старая дверь для системных
  вызовов из главы 28 (`int 0x2e`). Она всё ещё на месте;
- **векторы после `0x30`** — прерывания устройств и служебные
  прерывания ядра (глава 34, APIC). Там ты найдёшь имена вроде
  `nt!KiIsrThunk...` или обработчики драйверов.

Команда показывает IDT **всех** процессоров по очереди — у каждого
своя таблица (глава 34). Как правило, они почти одинаковые.

Проверим размер таблицы. Регистры `idtr` и `idtl` — адрес и **предел**
(limit, «граница») IDT этого процессора:

```
r idtr
r idtl
```

По главе 34: 256 векторов по 16 байт = 4096 байт. Предел — это
**последний** допустимый байт, то есть на единицу меньше размера:
ожидаю `idtl=0fff`.

### GDT

Так же — для GDT (глава 33):

```
r gdtr
r gdtl
```

А сами записи показывает команда **`dg`** — display selector,
«показать селектор». Она берёт селектор и печатает дескриптор, на
который он указывает. Можно дать диапазон:

```
dg 10 33
```

Честное предупреждение: документация Microsoft описывает `dg` как
команду для 32-битных машин. На x64 она обычно тоже работает, но
если у тебя ответ окажется странным — пришли, разберёмся. Ожидаю
примерно такое:

```
                                                    P Si Gr Pr Lo
Sel        Base              Limit          Type    l ze an es ng Flags
---- ----------------- ----------------- ---------- - -- -- -- -- --------
0010 00000000`00000000 00000000`00000000 Code RE Ac 0 Nb By P  Lo 0000029b
0018 00000000`00000000 00000000`00000000 Data RW Ac 0 Bg By P  Nl 00000493
0020 ...
0023 00000000`00000000 00000000`ffffffff Code RE Ac 3 Bg Pg P  Nl 00000cfb
002B 00000000`00000000 00000000`ffffffff Data RW Ac 3 Bg Pg P  Nl 00000cf3
0030 ...
0033 00000000`00000000 00000000`00000000 Code RE Ac 3 Nb By P  Lo 000002fb
```

Столбцы, которые нам важны:

- **Type** — `Code RE` («код, чтение и выполнение») или `Data RW`
  («данные, чтение и запись»);
- **Pl** (privilege level, «уровень привилегий») — это **DPL**
  дескриптора из главы 33: `0` у записей ядра, `3` у записей программ;
- **Long** — `Lo` (long, 64-битный код) или `Nl` (not long). Вот он,
  бит L из раздела 33.7: `0010` (ядро) и `0033` (64-битные программы) —
  `Lo`, а `0023` — код **32-битных** программ — `Nl`.

Сравни с таблицей из раздела 33.7 — раскладка та же: `0x10` и `0x18` —
ядро, `0x23`, `0x2B`, `0x33` — программы. Строка за строкой главы 33
подтверждается живым процессором.

Base везде ноль, Limit у 64-битных записей тоже ноль — в длинном режиме
процессор их не смотрит (глава 33: «музей внутри процессора»). Живое
доказательство, что сегментация в 64 битах — почти пустая формальность.
