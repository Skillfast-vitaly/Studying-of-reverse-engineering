
## 30.9. Сверяем часть X: системные регистры

Третий заход. Он весь про одно: в главах 32–34 я много раз писал
«это видно только из кольца 0» и «сверим в главе 30». Теперь у тебя
в руках отладчик ядра — он смотрит на процессор именно из кольца 0.
Сверяем.

Остановись (**Break**). Все команды этого раздела безопасны: они
только **читают**. Ничего не меняй в системных регистрах руками —
WinDbg позволяет, но машина от этого упадёт мгновенно.

Одно замечание про то, **что** ты видишь. Твоя цель — виртуальная
машина. Регистры, которые покажет WinDbg, — это регистры
**виртуального** процессора, какими их видит гостевая Windows. Гипервизор
Hyper-V хранит их для гостя и подставляет, когда гость работает. Держи
эту мысль: в части XI **твой** гипервизор будет так же хранить регистры
своего гостя.

### CR0

В главе 33 я написал: «На 64-битной Windows обычно получается
`80050033`… Это значение я не получил сам… Проверим вместе в главе 30».

```
r cr0
```

Ожидаемый ответ:

```
cr0=0000000080050033
```

Если у тебя именно так — моё обещание сбылось, и ты проверил его
своими руками. Разбор из главы 33 (биты я пересчитал программой):
`80050033` — это биты **0, 1, 4, 5, 16, 18, 31**:

| Бит | Имя | Смысл |
|---|---|---|
| 0 | PE | защищённый режим |
| 16 | **WP** | запрет записи действует и на ядро |
| 31 | **PG** | страничная память включена |
| 1, 4, 5, 18 | — | математический сопроцессор и проверка выравнивания |

Если у тебя число **другое** — не страшно. Пришли его мне, разберём
побитно. Главное должно совпасть в любом случае: биты 0, 16 и 31 —
единицы. Без PE и PG 64-битная Windows не работала бы вовсе, а WP
она держит включённым всегда.

### CR3 и CR4

```
r cr3
r cr4
```

`CR3` — корень таблиц страниц текущего процесса (глава 32). Число
запомни: в разделе 30.11 мы найдём его ещё в одном месте.

`CR4` разбери сам по таблице из раздела 33.3 — это упражнение 30.5.
Что стоит ожидать:

- **PAE (бит 5)** — 1: без него 64 бит не бывает;
- **LA57 (бит 12)** — вот и ответ на вопрос главы 32 «используется ли
  пятый уровень таблиц на твоей Windows». 1 — пять уровней, 0 —
  четыре. Честно: я не знаю, что будет у тебя, — это зависит от
  процессора, версии Windows и того, что Hyper-V показывает гостю.
  Узнаем по твоему числу;
- **VMXE (бит 13)** — внутри гостя, скорее всего, **0**. Рубильник
  VT-x гостевой Windows никто не включал: она не гипервизор;
- **SMEP (бит 20)** — 1, если процессор его умеет. Оба твоих
  процессора умеют.

### EFER

MSR читаются командой **`rdmsr`** (глава 33: номер MSR — в hex):

```
rdmsr c0000080
```

Ожидаемый ответ:

```
msr[c0000080] = 00000000`00000d01
```

`d01` — это биты **0, 8, 10, 11** (проверено программой):

| Бит | Имя | Смысл |
|---|---|---|
| 0 | SCE | работают `syscall`/`sysret` |
| 8 | LME | 64-битный режим разрешён |
| 10 | LMA | 64-битный режим работает |
| 11 | NXE | работает бит XD в таблицах страниц |

Вся «лестница загрузки» из главы 33 одной строчкой: 64-битный режим
включён и работает, системные вызовы через `syscall`, запрет
выполнения данных (DEP из главы 11) — на месте. Бита 12 (**SVME**,
рубильник AMD-V) нет — гостевая Windows AMD-V тоже не включала.

## 30.10. Сверяем часть X: системные вызовы

### LSTAR: куда прыгает syscall

В главе 28 мы остановились на пороге: `syscall` из `ntdll.dll`
уходит в ядро, в обработчик `KiSystemCall64`, — «увидеть это своими
глазами ты сможешь в главе 30». В главе 33 добавилось: адрес
обработчика процессор берёт из MSR **LSTAR** (`C0000082`).

```
rdmsr c0000082
```

Ответ — адрес, примерно так:

```
msr[c0000082] = fffff807`4a4a9180
```

Чей он? Спроси `ln`, как в разделе 30.7:

```
ln fffff807`4a4a9180
```

```
(fffff807`4a4a9180)   nt!KiSystemCall64   |  (fffff807`4a4a9…)   nt!…
Exact matches:
    nt!KiSystemCall64 (void)
```

Справа от черты `|` — следующее имя после этого адреса, оно нам
не важно. `Exact matches` — «точные совпадения». Адрес из LSTAR — это **ровно
начало** `nt!KiSystemCall64`. Главы 28 и 33, сложенные вместе:
программа делает `syscall` → процессор читает LSTAR → прыгает сюда.

Может оказаться, что точное совпадение — **`KiSystemCall64Shadow`**.
Это вариант того же обработчика для процессоров с уязвимостью
Meltdown (2018 год): Windows на них держит для программ отдельные,
«теневые» (shadow) таблицы страниц без ядра. Твои Ryzen 7500F и
Core 13400F — новые процессоры, этой уязвимости у них нет, поэтому
ожидаю обычный `KiSystemCall64`. Проверь.

### Первая инструкция обработчика

```
u nt!KiSystemCall64 L1
```

`u` — unassemble, «дизассемблировать»; `L1` — «одну инструкцию»
(L — length, «длина»). Ожидаемый ответ:

```
nt!KiSystemCall64:
fffff807`4a4a9180 0f01f8          swapgs
```

Вот она, **`swapgs`**, — самая первая инструкция ядра после
`syscall`. В главе 33 я объяснял: пока работала программа, в `GS`
было её значение; ядро первым делом меняет его на своё, чтобы найти
данные своего процессора и свой стек. Теперь ты видишь это не на
схеме, а в настоящем коде ядра. Байты `0f 01 f8` — это и есть
`swapgs` (можешь проверить в документации Intel, приложение П4).

Посмотри дальше — `u nt!KiSystemCall64 L8`. Следующие инструкции
работают с памятью через `gs:` — это ядро, уже со своим `GS`,
сохраняет пользовательский `RSP` и берёт стек ядра. Нам хватит
понимать смысл, разбирать каждую строку не будем.

### STAR: селекторы для syscall и sysret

```
rdmsr c0000081
```

Ожидаемый ответ:

```
msr[c0000081] = 00230010`00000000
```

Разрежем по правилам из документации Intel (страницы `SYSCALL`
и `SYSRET`, том 2 — ты умеешь их читать после приложения П4):

- биты 47–32: `0010`. При **`syscall`** процессор кладёт в `CS`
  это число (**`0x10`**), а в `SS` — его же плюс 8 (**`0x18`**);
- биты 63–48: `0023`. При **`sysret`** в 64-битную программу
  процессор кладёт в `CS` это число плюс 16 (`0x23 + 0x10 = `**`0x33`**),
  а в `SS` — плюс 8 (`0x23 + 8 = `**`0x2B`**), и в обоих случаях
  ставит кольцо 3 в двух младших битах.

Сравни с таблицей GDT из раздела 33.7: `0x10` — код ядра, `0x18` —
данные ядра, `0x33` — код 64-битных программ, `0x2B` — их данные.
**Всё совпало.** И `cs=0033`, который ты видел в x64dbg в главе 27, —
вот откуда он берётся, когда ядро возвращается в программу.

Разбор этого числа — упражнение 30.6: попробуй повторить его сам,
не подглядывая.
