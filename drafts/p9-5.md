
## П9.12. DNS и HTTP: стандартные протоколы

Наш протокол Wireshark не знал и показывал как `Data`. Стандартные
протоколы он раскладывает сам, по полям, с названиями. Посмотрим
два главных. Это уже не петля, а настоящая сеть: записывай на своём
обычном подключении (проводном или Wi-Fi), а не на loopback.

**DNS** `[ди-эн-эс]` (Domain Name System, «система доменных имён») —
телефонная книга интернета. Программа знает имя сайта, а соединяться
нужно по IP-адресу. Кто даёт адрес по имени? DNS-сервер. Запрос
и ответ обычно идут по UDP, порт 53 (П9.2).

Запусти запись на своём подключении. В консоли выполни:

```
nslookup example.com
```

`nslookup` («найти имя») встроен в Windows. Остановив запись, поставь
фильтр `dns`. Останутся пары строк, примерно такие:

```
Standard query 0x1a2b A example.com
Standard query response 0x1a2b A example.com A …
```

Рядом могут быть строки с `AAAA` — то же самое для адреса IPv6 — и
`PTR`: так `nslookup` сначала узнаёт имя своего DNS-сервера.

**Standard query** — «обычный запрос», **response** — «ответ». Число
после них — номер запроса: по нему ответ находит свой запрос, как Seq
и Ack в TCP. **A** — тип записи «адрес IPv4». В ответе после второго
`A` стоят адреса сайта. У тебя они будут свои, адреса больших сайтов
меняются. Раскрой в подробностях **Domain Name System** — увидишь
поля запроса: имя в поле `Name`, тип в поле `Type`. Фильтр по имени:
`dns.qry.name == "example.com"`.

> Если в настройках Windows включён «DNS по HTTPS», обычные программы
> спрашивают адреса по зашифрованному каналу, и фильтр `dns` их
> не покажет. `nslookup` всё равно шлёт обычный запрос, поэтому опыт
> получится.

**HTTP** `[эйч-ти-ти-пи]` (HyperText Transfer Protocol, «протокол
передачи гипертекста») — язык сайтов. Он текстовый: запрос и ответ
можно прочитать глазами. Сайт `example.com` — учебный, его держат
специально для примеров, и по адресу с `http://` он отвечает без
шифрования.

Запусти запись и выполни в консоли:

```
curl.exe http://example.com
```

`curl` встроен в Windows 10 и 11. Пиши именно `curl.exe`: в старой
Windows PowerShell слово `curl` без `.exe` — другая команда.

Фильтр `http`. Останется пара строк: запрос `GET / HTTP/1.1` («дай
главную страницу») и ответ `HTTP/1.1 200 OK` («вот, всё в порядке»).
Выдели запрос и открой **Analyze → Follow → HTTP Stream**
(**Ctrl+Alt+Shift+H**). Получится разговор открытым текстом:

```
GET / HTTP/1.1
Host: example.com
User-Agent: curl/…
Accept: */*

HTTP/1.1 200 OK
Content-Type: text/html
…
<!doctype html>
…
```

Каждая строка запроса — поле **заголовка HTTP**: `Host` — какой сайт,
`User-Agent` — какая программа спрашивает. Пустая строка отделяет
заголовки от содержимого. Помнишь П9.3? HTTP размечает сообщения
не длиной впереди, а **разделителем** — переводом строки, и пустая
строка значит «заголовки кончились».

Для реверсера `User-Agent` — подпись программы. Многие программы
пишут туда своё имя и версию. Вредоносные иногда выдают себя
за браузер, но с ошибкой в мелочи, и по этой мелочи аналитики их
узнают.

## П9.13. TLS: что видно, а что нет

Теперь то же самое, но с `https://`:

```
curl.exe https://example.com
```

С фильтром `http` в списке пусто. Поставь фильтр `tls`. **TLS**
`[ти-эл-эс]` (Transport Layer Security, «защита транспортного
уровня») — шифрование поверх TCP. HTTPS — это HTTP внутри TLS.

Что ты увидишь. После рукопожатия TCP идёт **рукопожатие TLS**.
Первый пакет — **Client Hello** («привет от клиента»): какие шифры
клиент умеет и… имя сайта. Раскрой в подробностях **Transport Layer
Security → Handshake Protocol: Client Hello** и найди расширение
**server_name**. Там написано `example.com`, открытым текстом. Это
поле называют **SNI** `[эс-эн-ай]` (Server Name Indication, «указание
имени сервера»). Найти его сразу во всех разговорах помогает фильтр:

```
tls.handshake.extensions_server_name
```

Дальше сервер отвечает **Server Hello**. После него остаются строки
**Application Data** («данные приложения»). Это и есть наш HTTP,
только зашифрованный: Follow → TCP Stream покажет кашу.

Итог: что видно при TLS, а что нет.

| Видно | Не видно |
|---|---|
| IP-адреса и порты (заголовки IP и TCP) | путь страницы (`GET /…`) |
| имя сайта в Client Hello — SNI | заголовки HTTP, в том числе `User-Agent` |
| когда и сколько байт ушло в каждую сторону | содержимое запросов и ответов |
| версию TLS и шифры, которые выбрали стороны | пароли, файлы, всё остальное |

Две оговорки. В старой версии TLS 1.2 открытым текстом шёл ещё
и **сертификат** сервера — «удостоверение личности» сайта. В TLS 1.3
он уже зашифрован. А новое расширение **ECH** (Encrypted Client Hello,
«зашифрованное приветствие клиента») прячет и имя сайта. Его понимают
Chrome и Firefox, но работает оно только с сайтами, которые сами его
включили.

Как тогда реверсеры смотрят зашифрованный трафик программы? Три пути.
Все они законны только для своих программ и только на своём ПК или
в своей ВМ:

1. **Изнутри, отладчиком** (П9.1). Программа шифрует уже собранное
   сообщение. Точка останова на функции шифрования или на `send`
   показывает сообщение до шифрования. Это главный путь реверсера:
   ему не нужно ничего ломать.
2. **Ключи от своего браузера.** Chrome и Firefox умеют записывать
   ключи своих сессий TLS в файл, если задать переменную окружения
   `SSLKEYLOGFILE`. Wireshark читает этот файл (настройка **(Pre)-Master-
   Secret log filename** в разделе протокола TLS) и показывает
   расшифрованный HTTP. Работает только для программ, которые сами
   пишут ключи. Встроенный `curl.exe` не пишет.
3. **Отладочный прокси** — например, Fiddler или Burp Suite. Он
   встаёт посредником между программой и сайтом и расшифровывает
   трафик. Чтобы программа ему поверила, в систему ставят его
   **корневой сертификат** — «я доверяю этому посреднику». Делай это
   только в учебной ВМ: доверенный посредник видит всё, что идёт
   через него. Некоторые программы проверяют сертификат сайта сами
   и посредника не принимают — это называют **закреплением
   сертификата** (certificate pinning). Тогда остаётся путь 1.

## П9.14. Запись без Wireshark: pktmon

На чужом рабочем ПК Wireshark часто ставить нельзя, а записать трафик
нужно. В Windows есть встроенный инструмент — **pktmon** `[пакет-мон]`
(Packet Monitor, «наблюдатель за пакетами»). Он есть начиная с Windows
10 версии 2004. Нужна консоль **от имени администратора**: pktmon
ставит свой драйвер.

```
pktmon start --capture --pkt-size 0
```

`--capture` — записывать пакеты. `--pkt-size 0` — записывать пакет
целиком. Без этого pktmon по умолчанию берёт только первые 128 байт
каждого пакета, а данные программы как раз в конце. Файл записи
по умолчанию называется `PktMon.etl`.

Сделай то, что хочешь записать, и останови:

```
pktmon stop
```

Wireshark формат `.etl` не открывает. Переведи запись в `.pcapng`:

```
pktmon etl2pcap PktMon.etl --out zapis.pcapng
```

Получившийся файл открывается в Wireshark как обычно, на любом ПК.
Так и работают на практике: пишут встроенным `pktmon` там, где
Wireshark нет, а разбирают дома.

> ❓ **Не проверено.** Ловит ли pktmon разговоры по петле `127.0.0.1`,
> я проверить не смог: pktmon смотрит пакеты на пути через сетевые
> компоненты Windows, а петля, как мы знаем из П9.4, идёт мимо карты.
> Проверь сам на задаче 06 и напиши мне — это упражнение П9.8.

Все команды и ключи pktmon — по документации Microsoft (страницы
`pktmon start` и `pktmon etl2pcap` на learn.microsoft.com, сверено
11.10.2026). Подробная справка — `pktmon start help`.
