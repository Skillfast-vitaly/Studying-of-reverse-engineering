
## 30.6. Структуры ядра своими глазами

В главе 29, в упражнении 29.5, ты считал на бумаге, почему поле
`DriverUnload` лежит на смещении `0x68` от начала `DRIVER_OBJECT`.
Сейчас сверим с отладчиком.

Команда **`dt`** — display type, «показать тип». Она берёт описание
структуры из символов и печатает её поля со смещениями:

```
dt nt!_DRIVER_OBJECT
```

Ожидаемый ответ. Смещения я проверил сам: собрал кросс-компилятором
программу, которая печатает `offsetof` каждого поля по заголовкам
драйверов, — числа совпали с этой таблицей. Структура
документирована Microsoft и от сборки к сборке не меняется:

```
   +0x000 Type             : Int2B
   +0x002 Size             : Int2B
   +0x008 DeviceObject     : Ptr64 _DEVICE_OBJECT
   +0x010 Flags            : Uint4B
   +0x018 DriverStart      : Ptr64 Void
   +0x020 DriverSize       : Uint4B
   +0x028 DriverSection    : Ptr64 Void
   +0x030 DriverExtension  : Ptr64 _DRIVER_EXTENSION
   +0x038 DriverName       : _UNICODE_STRING
   +0x048 HardwareDatabase : Ptr64 _UNICODE_STRING
   +0x050 FastIoDispatch   : Ptr64 _FAST_IO_DISPATCH
   +0x058 DriverInit       : Ptr64     long
   +0x060 DriverStartIo    : Ptr64     void
   +0x068 DriverUnload     : Ptr64     void
   +0x070 MajorFunction    : [28] Ptr64     long
```

Словарик типов WinDbg: `Int2B` — целое на 2 байта (`SHORT`),
`Uint4B` — беззнаковое на 4 байта (`ULONG`), `Ptr64` — 64-битный
указатель, `[28]` — массив из 28 элементов.

`DriverUnload` — `+0x068`. Ровно то, что было в ассемблере главы 29
(`mov [rbx+0x68], rax`) и в твоём расчёте. Бумага, компилятор
и живое ядро сказали одно и то же.

Заметь ещё два поля:

- **`DriverName`** на `+0x038` — это `UNICODE_STRING` **целиком**,
  не указатель: 16 байт (2 + 2 + 4 дыры + 8), поэтому следующее поле
  начинается на `0x38 + 0x10 = 0x48`;
- **`MajorFunction`** — массив из 28 адресов функций. Это «таблица
  обработчиков запросов» драйвера: запрос «открыть», «прочитать»,
  «записать» и так далее — у каждого свой номер и своя ячейка.
  Точно как таблица указателей на функции из приложения П1. Ею мы
  займёмся в главе 31, когда будем разбирать чужие драйверы.

### Настоящий паспорт твоего драйвера

Остановись на `DriverEntry` ещё раз (точка `bu` всё ещё стоит —
`sc stop Hello`, `sc start Hello`). Теперь покажи не описание типа,
а **настоящую** структуру по адресу из `DriverObject`:

```
dt nt!_DRIVER_OBJECT @rcx
```

`@rcx` — «значение регистра RCX». Почему RCX? На первой инструкции
функции её первый параметр ещё лежит в `RCX` — соглашение о вызовах
из главы 12. В ядре оно то же самое. Можно написать и адрес руками —
тот, что показал `dv`.

Ответ — примерно так:

```
   +0x000 Type             : 0n4
   +0x002 Size             : 0n336
   ...
   +0x018 DriverStart      : 0xfffff807`4e9b0000 Void
   +0x020 DriverSize       : 0x7000
   ...
   +0x038 DriverName       : _UNICODE_STRING "\Driver\Hello"
   ...
   +0x068 DriverUnload     : (null)
```

Прочитаем:

- **`0n4`** — `0n` в WinDbg означает «десятичное число» (а `0x` —
  шестнадцатеричное, как везде). `Type = 4` — номер вида объекта
  ядра «драйвер»;
- **`Size = 0n336`** — размер структуры, 336 байт. В hex это `0x150`:
  массив `MajorFunction` начинается на `0x70` и занимает `28 × 8 = 224`
  байта, `0x70 + 0xE0 = 0x150`. Сходится;
- **`DriverStart`** — где в памяти начинается образ `Hello.sys`, его
  база. Сравни с адресом `DriverEntry` из DebugView: он чуть **больше**
  базы — функция лежит внутри образа, в секции `.text` (глава 8);
- **`DriverName`** — `\Driver\Hello`. Так ядро называет твой драйвер
  в своём «пространстве имён» объектов;
- **`DriverUnload: (null)`** — пусто! Потому что мы остановились
  в **самом начале** `DriverEntry`, а строка
  `DriverObject->DriverUnload = HelloUnload;` ещё не выполнена.
  Пройди её по **F10** и повтори команду — там появится адрес
  `Hello!HelloUnload`. Ты своими глазами увидишь, как драйвер вписал
  себя в паспорт.

Есть и короткий путь — расширение **`!drvobj`**:

```
!drvobj Hello
```

Оно печатает главное про драйвер по имени: адрес `DRIVER_OBJECT`
и список его устройств (у нашего устройств нет). С параметром `2`
(`!drvobj Hello 2`) — ещё и таблицу `MajorFunction`. Посмотри:
у драйвера, который обработчиков не ставил, почти все ячейки
указывают на одну и ту же функцию ядра — «запрос не поддерживается».

## 30.7. Падение под отладчиком

В главе 29 ты уронил машину нарочно — записью по адресу 0. Видел
синий экран и название ошибки. Теперь сделаем то же самое, но
с отладчиком — и посмотрим, как он **ловит** падение.

**Перед опытом — снимок!** Верни в `DriverEntry` две строки
из раздела 29.11, перед `return`:

```c
    volatile int *p = NULL;
    *p = 1;   // запись по адресу 0 — в кольце 0
```

Собери, скопируй (`sc stop` → копирование → ничего не запускай пока).
В WinDbg убери старую точку (`bc *`) и отпусти Windows (`g`). В машине:
`sc start Hello`.

Машина **не покажет синий экран**. Она замрёт, а в WinDbg появится
примерно такое:

```
*** Fatal System Error: 0x0000007e
                       (0xFFFFFFFFC0000005,0xFFFFF8074E9B1085,0xFFFFE60C2A4F6F48,0xFFFFE60C2A4F6780)

Break instruction exception - code 80000003 (first chance)

A fatal system error has occurred.
Debugger entered on first try; Bugcheck callbacks have not been invoked.

For analysis of this file, run !analyze -v
nt!DbgBreakPointWithStatus:
fffff807`4a41c0f0 cc              int     3
```

Перевод: «Фатальная системная ошибка: `0x7E`… Произошла фатальная
системная ошибка. Отладчик вошёл с первой попытки; функции, которые
вызываются при аварии, ещё не запущены. Для анализа выполни
`!analyze -v`».

Смысл: Windows **уже решила** сделать bug check (глава 27), но перед
тем как нарисовать синий экран, отдала управление тебе. Машина стоит
в самой точке падения. Всё, что было в памяти, ещё там.

Бывает, что перед этим WinDbg напишет ещё строчку про само исключение —
`Access violation - code c0000005` («нарушение доступа»). Зависит
от того, как именно ядро передавало исключение. Код ошибки в любом
случае будет тем же.

### Четыре числа в скобках

`0x7E` — это `SYSTEM_THREAD_EXCEPTION_NOT_HANDLED`, «необработанное
исключение в системном потоке». Именно его я предсказывал в главе 29:
код выполнялся в системном потоке (раздел 30.5 это доказал стеком).
У каждого кода остановки есть четыре **параметра**. Для `0x7E`
документация Microsoft объясняет их так:

| № | Что это | У нас |
|---|---|---|
| 1 | код исключения, которое никто не обработал | `C0000005` — нарушение доступа (глава 27) |
| 2 | адрес, **где** случилось исключение | адрес внутри `Hello!DriverEntry` |
| 3 | адрес записи об исключении (exception record) | для отладчика |
| 4 | адрес записи контекста (context record) — все регистры в момент ошибки | для отладчика |

Первое число напечатано как `FFFFFFFFC0000005` — 32-битный код
`C0000005`, растянутый до 64 бит (единицы слева — то же расширение
знака, что `movsxd` в главе 20).

Второе число — **адрес виновника**. Проверь, чей он: команда **`ln`**
— list nearest symbols, «ближайшие символы»:

```
ln 0xFFFFF8074E9B1085
```

```
(fffff807`4e9b1000)   Hello!DriverEntry+0x85
```

«Внутри `Hello!DriverEntry`, на `0x85` байт от начала». Это ты.

### !analyze -v: отчёт следователя

Теперь главная команда разбора падений — ровно то, что советует сам
WinDbg:

```
!analyze -v
```

`-v` — verbose, «подробно». Отладчик соберёт отчёт. Он длинный;
вот главные поля (названия полей — как их печатает WinDbg, значения
у тебя будут свои):

```
SYSTEM_THREAD_EXCEPTION_NOT_HANDLED (7e)
This is a very common BugCheck.  Usually the exception address pinpoints
the driver/function that caused the problem.
...
EXCEPTION_CODE_STR:  c0000005

FAULTING_SOURCE_FILE:  C:\Users\ты\source\repos\Hello\Hello.c
FAULTING_SOURCE_LINE_NUMBER:  31

STACK_TEXT:
... Hello!DriverEntry+0x85
... Hello!GsDriverEntry+0x20
... nt!PnpCallDriverEntry+0x4c
...

SYMBOL_NAME:  Hello!DriverEntry+85
MODULE_NAME: Hello
IMAGE_NAME:  Hello.sys
```

Как это читать:

- первая строка — название и код ошибки. Дальше пояснение: «Очень
  частая ошибка. Обычно адрес исключения точно указывает на
  драйвер и функцию, которые её вызвали»;
- **`FAULTING_SOURCE_FILE`** и **`FAULTING_SOURCE_LINE_NUMBER`** —
  «файл и номер строки исходника, где случился сбой». Это возможно
  только потому, что у WinDbg есть твой `.pdb`. Открой `Hello.c`:
  на этой строке стоит `*p = 1;`. Отладчик нашёл строку, которую
  в главе 29 ты мог только угадать по синему экрану;
- **`STACK_TEXT`** — стек в момент падения, как `k`;
- **`MODULE_NAME`**, **`IMAGE_NAME`** — «виновный модуль» и его файл.

Номер строки у тебя будет свой — зависит от того, куда ты вставил
две строки.

А если бы `.pdb` не было? Отчёт всё равно назвал бы модуль `Hello.sys`
и смещение `DriverEntry+0x85` — или, без символов совсем, `Hello+0x1085`.
Этого хватает, чтобы открыть `Hello.sys` в Ghidra (глава 14), перейти
по смещению и прочитать код. Так и разбирают падения в **чужих**
драйверах — это будет глава 31.

Посмотри ещё регистры **в момент ошибки**. Отладчик стоит внутри
обработчика аварии, но в четвёртом параметре лежит адрес сохранённого
контекста. Команда **`.cxr`** (context record — «запись контекста»)
переключает WinDbg на него:

```
.cxr 0xFFFFE60C2A4F6780
r
```

Регистры станут такими, какими были на инструкции `*p = 1`. Найди
в дизассемблере её — что-то вроде `mov dword ptr [rax], 1` — и
посмотри в `r`: регистр с адресом будет равен нулю. Вот оно,
«запись по адресу 0», глазами процессора. Вернуться к обычному
контексту — `.cxr` без параметров.

### Что дальше с упавшей машиной

Если сейчас сказать `g`, Windows продолжит bug check: нарисует синий
экран, запишет дамп и перезагрузится. Так и сделай — дамп нам нужен
в следующем разделе.

### Важное правило: точка останова в коде без отладчика

Для отладки в код драйвера иногда вставляют **остановку прямо
в исходнике** — функцию `DbgBreakPoint()` или `__debugbreak()`
(это `int3` одной инструкцией). Когда отладчик подключён, это удобно:
Windows остановится ровно там.

Но документация Microsoft к ошибке `0x7E` предупреждает: если
отладчик **не подключён**, такая остановка превращается в исключение
`0x80000003` (`STATUS_BREAKPOINT`), которое некому обработать, —
и тот же синий экран `0x7E`. Правило: **`DbgBreakPoint` только
пока подключён отладчик**, и убирай её, как только нашёл, что искал.

## 30.8. Дамп: разбор после смерти

Бывает, что отладчика рядом не было: машина упала ночью, а утром
остался только файл. Для этого Windows пишет **дамп памяти** (глава 29).

После `g` из прошлого раздела машина показала синий экран,
записала дамп и перезагрузилась. По документации Microsoft,
по умолчанию Windows пишет **автоматический дамп памяти** (Automatic
Memory Dump) в файл `%SystemRoot%\MEMORY.DMP` — то есть
`C:\Windows\MEMORY.DMP`. В нём память **ядра** на момент падения
(память программ туда не попадает). Может появиться ещё и маленький
дамп в папке `C:\Windows\Minidump\`.

Проверь, какой дамп пишет твоя машина: **Параметры → Система →
О системе → Дополнительные параметры системы** → вкладка
**Дополнительно** → **Загрузка и восстановление** → **Параметры**
(Startup and Recovery → Settings). Поле **«Запись отладочной
информации»** (Write debugging information) — должно быть
**«Автоматический дамп памяти»**.

### Переносим дамп на хост

Дамп лежит в защищённой папке, Проводник может не дать его
скопировать. В машине, в командной строке **администратора**:

```
copy C:\Windows\MEMORY.DMP C:\drivers\
```

Дальше — как `.sys`, только в обратную сторону: из `C:\drivers\`
машины на рабочий стол основной (расширенный сеанс). Файл может
весить сотни мегабайт — это нормально.

### Открываем

На хосте, в **новом** окне WinDbg (старое можно оставить подключённым):
**File → Start debugging → Open dump file** («открыть файл дампа»),
выбери `MEMORY.DMP`. WinDbg прочитает файл и сам предложит то же,
что и вживую: `!analyze -v`.

Добавь путь к своему `.pdb` (`.sympath+` и `.reload`, как в разделе
30.5) — и отчёт покажет тот же файл и ту же строку.

Ещё полезная команда для дампа — **`.bugcheck`**: печатает код
остановки и четыре параметра, коротко, без анализа.

### Чем дамп отличается от живой отладки

Дамп — это **фотография**. На нём можно смотреть память, регистры,
стек, структуры (`dt`, `k`, `!process`, `lm` работают). Но нельзя:

- **запустить дальше** — `g`, шаги и точки останова бессмысленны,
  машины за снимком нет;
- **читать MSR** — документация Microsoft прямо пишет про `rdmsr`:
  «только живая отладка» (live debugging only). Регистров процессора,
  которых нет в сохранённом контексте, на фотографии просто нет;
- видеть память, которой не было в дампе. Автоматический дамп
  хранит только память ядра. WinDbg в таком месте покажет
  вопросительные знаки `????????`.

Для гипервизора это важно. Если машина с твоим гипервизором упадёт
«намертво», дампа может не быть вовсе — Windows не успеет его записать.
Поэтому главный инструмент разработчика гипервизора — живая отладка
и `DbgPrintEx` с подробным журналом. Дамп — приятный бонус, когда он
есть.

**Верни снимок** «отладка» и убери из кода две опасные строки.
