
Разберём по шагам.

- **Шаг 2.** `VirtualProtect` («защитить виртуальную память») меняет
  права уже выделенной страницы — те же константы, что в таблице 26.8.
  `PAGE_EXECUTE_READ` (`0x20`) — «код»: выполнять и читать можно,
  писать нельзя. `FlushInstructionCache` («сбросить кэш инструкций»)
  документация `VirtualProtect` велит звать после того, как в страницу
  положили код: процессор мог запомнить старое содержимое. `f()`
  прыгает на страницу, `ret` тут же возвращает — строка `1)` напечатана.
- **Шаг 3.** Права снова `PAGE_READWRITE` (`0x04`) — «данные». Тот же
  `f()`, тот же байт `C3`. Но процессор **отказывается даже взять**
  инструкцию со страницы, у которой стоит бит XD. Случается исключение
  `C0000005` — нарушение доступа, твой старый знакомый (главы 13 и 27).
- **Вид доступа 8.** У нарушения доступа Windows кладёт в первую ячейку
  `ExceptionInformation` вид операции: 0 — чтение, 1 — запись,
  **8 — нарушение DEP** (документация структуры `EXCEPTION_RECORD`).
  Во второй ячейке — адрес, к которому обращались: это начало нашей
  страницы. Процессор споткнулся на самой первой инструкции.

Функция `report` — тот же приём, что в программе `rings.c` из главы
27.5: `SetUnhandledExceptionFilter` просит Windows позвать нашу функцию,
если исключение никто не поймал. Если ты до главы 27 ещё не дошёл,
просто запомни: так программа узнаёт о своём падении и успевает
напечатать подробности.

**Посмотри то же в x64dbg.** Открой `dep.exe` и нажми **F9** («Run»).
Под отладчиком наша `report` не вызовется: исключение первым получает
отладчик (глава 13.1). x64dbg остановится и напишет в журнал
(вкладка **Log**) строку вида:

```
First chance exception on 0000022B8E0B0000 (C0000005, EXCEPTION_ACCESS_VIOLATION)!
```

(«первое уведомление об исключении по адресу…» — текст сверен
с исходником x64dbg). Посмотри на `RIP` — он равен адресу страницы.
А в карте памяти (глава 13.13) у этой страницы права `-RW--`, без `E`.
Вот и весь DEP: права страницы плюс бит процессора.

### Где здесь честные программы

Шаги 1–2 — ровно то, что делают **JIT-компиляторы** (just-in-time
`[джаст-ин-тáйм]`, «точно в срок»): движок JavaScript в браузере
и среда .NET переводят код в машинные инструкции прямо во время работы
и кладут их в память. Правильный порядок у них такой же, как у нас:
записать в страницу-данные, потом сделать её кодом и только потом
выполнить. Страница не бывает «записывай и выполняй» одновременно.

Поэтому в 26.8 права `0x40` (`PAGE_EXECUTE_READWRITE`) — повод
присмотреться: программа, которая просит запись и выполнение сразу,
держит дверь, которую DEP старается закрыть.

## П10.7. ASLR: адреса, которых не знаешь заранее

**ASLR** ты встречал трижды: в 4.8 — что это такое, в 13.7 — как
x64dbg показывает сдвиг (младшие четыре hex-цифры не меняются),
в 26.6 — где Windows обычно кладёт `.exe`. Соберём этажи.

**Файл.** Флаг `DYNAMIC_BASE` — «меня можно сдвигать». Но обещание
надо подкрепить: в файле есть абсолютные адреса (например, адрес
строки, записанный прямо в данные). Если файл лёг не по `ImageBase`,
все такие адреса стали неверными. Поэтому в файле есть секция
`.reloc` — **таблица поправок** (relocations `[рилоукéйшенз]`,
«перемещения»). Ты видел её в выводе `pe_info.py` в П6.8. Это список
мест, где лежат абсолютные адреса. Загрузчик Windows проходит по нему
и к каждому месту прибавляет величину сдвига. Без `.reloc` сдвинуть
файл нельзя, и флаг теряет смысл.

**Файл, второй флаг.** `HIGH_ENTROPY_VA` разрешает Windows
пользоваться всеми 64 битами адреса — класть образ и выдавать
память выше 4 ГБ. Документация Microsoft о защите от эксплойтов
говорит, что для 64-битных программ это добавляет 24 бита случайности
к выделению памяти — разброс в 1 ТБ.

**Windows.** Выбирает случайный адрес — но не так часто, как
кажется. Как именно, хорошо описано в исследовании компании Mandiant
«Six Facts about Address Space Layout Randomization on Windows»
(«Шесть фактов об ASLR в Windows», 2020):

- каждый образ — `.exe` или `.dll` — получает случайный адрес,
  **когда его загружают впервые**. Все следующие копии того же файла
  получают **тот же** адрес;
- поэтому **системные библиотеки** — `ntdll.dll`, `kernel32.dll` —
  лежат по **одному адресу во всех процессах**. Причина — экономия:
  страницы образа Windows делит между процессами (26.8), а для этого
  у библиотеки должен быть один адрес у всех;
- когда программа закрылась, Windows 10 и 11 ещё какое-то время
  **помнят** её адрес, особенно у `.exe`. Два запуска подряд часто
  дают одно и то же число. Новый адрес даст копия файла под другим
  именем, а **гарантированно новые** адреса всем образам — только
  перезагрузка;
- у 64-битной программы случайны 17–19 бит адреса образа, у
  32-битной — только 8. Поэтому 64-битную программу угадать
  в сотни раз труднее.

Так что фраза «ASLR сдвигает программу при каждом запуске» —
упрощение. Точнее: **случайно при первой загрузке, надёжно новое —
после перезагрузки**. Стеки и кучи — другое дело: их адреса выбираются
заново для каждого процесса (переключатель «Bottom-up ASLR» ниже).

Отсюда важный урок: если программа хоть раз «выдала» адрес системной
библиотеки, он верен для **всех** процессов до перезагрузки. Утечка
адреса (например, чтение за границей из 4.4) ослабляет ASLR. Поэтому
защиты и работают командой: ASLR прячет адреса, DEP и CFG мешают
воспользоваться ими, даже если адрес узнали.

### Опыт: два запуска

Файл `aslr.c`:

```c
/* aslr.c — где лежит программа: запусти два раза и сравни (П10.7) */
#include <stdio.h>
#include <stdlib.h>
#include <windows.h>

int global = 1;

int main(void)
{
    int local = 2;
    void *heap = malloc(16);
    HMODULE exe = GetModuleHandleA(NULL);          /* база своего .exe */
    HMODULE ntdll = GetModuleHandleA("ntdll.dll"); /* база ntdll.dll */

    printf("exe    %p\n", (void *)exe);
    printf("main   %p\n", (void *)main);
    printf("global %p\n", (void *)&global);
    printf("stack  %p\n", (void *)&local);
    printf("heap   %p\n", heap);
    printf("ntdll  %p\n", (void *)ntdll);
    free(heap);
    return 0;
}
```

`GetModuleHandleA` («дай описатель модуля») возвращает адрес, по
которому загружен модуль: с `NULL` — свой `.exe`, с именем — указанную
библиотеку. Тип `HMODULE` — это и есть адрес начала образа.

Опыт в три шага:

1. Собери и запусти `aslr.exe` **два раза подряд**.
2. Скопируй файл под новым именем — `copy aslr.exe aslr2.exe`
   (в консоли w64devkit: `cp aslr.exe aslr2.exe`) — и запусти копию.
3. Перезагрузи компьютер и запусти `aslr.exe` ещё раз.

Примерно так (числа у тебя свои). Первый запуск:

```
exe    00007ff6c9a20000
main   00007ff6c9a21450
global 00007ff6c9a28010
stack  000000e5a3bff86c
heap   0000020c5a6414a0
ntdll  00007ffd0a3e0000
```

Второй запуск, сразу за первым:

```
exe    00007ff6c9a20000
main   00007ff6c9a21450
global 00007ff6c9a28010
stack  0000008f7c5ffa1c
heap   000001b34e2f1360
ntdll  00007ffd0a3e0000
```

Копия `aslr2.exe`:

```
exe    00007ff70b1c0000
main   00007ff70b1c1450
global 00007ff70b1c8010
stack  000000b1d07ff8ac
heap   0000017a9c3a1440
ntdll  00007ffd0a3e0000
```

Что сравнивать:

1. Второй запуск: `exe`, `main`, `global` — **те же**, Windows
   помнит образ. А `stack` и `heap` — новые: их адреса случайны для
   каждого процесса.
2. Копия: образ получил **новый** адрес — для Windows это другой файл.
   `exe`, `main`, `global` сдвинулись **вместе**, на одну величину:
   ASLR двигает образ целиком. Младшие четыре цифры `main` и `global`
   прежние (13.7).
3. `ntdll` — одинаковый во всех трёх запусках. А после перезагрузки
   новым будет всё, включая `ntdll`.

Вывод я составил по исследованию Mandiant, а не снял на Windows: если
второй запуск у тебя дал **новый** адрес `exe`, это тоже возможно
(прошло время, Windows «забыла» файл). Пришли свои четыре запуска —
сверим и поправим текст.

### Настройки ASLR в Windows

В «Безопасности Windows» (раздел П10.11) у ASLR три переключателя.
Их имена пригодятся, когда встретишь их в статьях:

| Надпись (англ.) | Смысл | По умолчанию |
|---|---|---|
| Force randomization for images (Mandatory ASLR) — «принудительно случайные адреса образов» | сдвигать даже файлы без `DYNAMIC_BASE` | выключено |
| Randomize memory allocations (Bottom-up ASLR) — «случайные адреса выделений памяти» | случайные адреса стеков и куч | включено |
| High-entropy ASLR — «ASLR с высокой энтропией» | 64-битный разброс для файлов с `HIGH_ENTROPY_VA` | включено |

**Энтропия** (entropy `[э́нтропи]`) здесь значит «сколько случайных
бит в адресе»: чем больше, тем труднее угадать. Документация Microsoft
предупреждает: принудительный сдвиг без случайности даёт
**предсказуемый** адрес, поэтому первый переключатель работает только
в паре со вторым. Значения «по умолчанию» сверь у себя: Windows
пишет их прямо в окне, в скобках после «Use default».

**Ядро тоже сдвигается.** У ядра Windows и драйверов свой ASLR —
его называют **KASLR** (Kernel ASLR, «ASLR ядра»). В главе 30 ты увидишь
адрес `ntoskrnl.exe` в WinDbg — после перезагрузки виртуальной машины
он будет другим. Подробнее — в П10.14.
