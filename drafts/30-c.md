
## 30.3. Соединяем хост и цель

Отладчику и связному нужен провод. Документация Microsoft называет
три вида: сеть (Ethernet), USB и старый COM-порт (serial `[сúриал]`,
«последовательный порт»). Для виртуальной машины провод, конечно,
тоже виртуальный. Microsoft советует **сеть** — это быстрее всего.
Способ называется **KDNET** `[кей-ди-нет]` — «KD по сети».

Путь ниже — для Hyper-V, он описан в документации Microsoft
(«Setting Up Network Debugging of a Virtual Machine – KDNET»). Для
VMware — в конце раздела.

### Шаг 1. Сеть, в которой хост и цель видят друг друга

В главе 29 ты подключил машину к **Default Switch** — готовой сети
Hyper-V через основную машину. Microsoft в инструкции для отладки
использует **внешний коммутатор** (external virtual switch
`[экстёрнал вёрчуал свитч]`) — виртуальную сеть, привязанную к твоей
настоящей сетевой карте. Сделаем, как в документации:

1. В **Диспетчере Hyper-V** справа: **Диспетчер виртуальных
   коммутаторов** (Virtual Switch Manager).
2. **Создать виртуальный сетевой коммутатор** → тип **Внешний**
   (External) → **Создать**.
3. Имя — `debug-net`. В списке «Внешняя сеть» выбери свою
   настоящую сетевую карту (проводную или Wi-Fi — ту, через которую
   у тебя интернет).
4. Галочка **«Разрешить управляющей операционной системе
   предоставлять общий доступ к этому сетевому адаптеру»** (Allow
   management operating system to share this network adapter) —
   **включена**. Без неё основная машина потеряет интернет.
5. **Идентификатор VLAN** (VLAN ID) — **не** включай. **OK**.
6. Параметры виртуальной машины → **Сетевой адаптер** (Network
   Adapter) → выбери `debug-net` → **OK**.

Основная машина может на пару секунд потерять сеть — она
перестраивается. Это нормально.

А можно ли остаться на Default Switch? Часто работает, но у него
есть неприятная особенность: его адреса могут меняться после
перезагрузки основной машины. Тогда отладчик перестанет находить
цель, и шаги 2–4 придётся повторить с новым адресом. Внешний
коммутатор надёжнее.

### Шаг 2. Узнать адрес хоста

На **основной** машине открой командную строку и введи:

```
ipconfig
```

Программа покажет все сетевые адаптеры. Найди тот, в названии
которого есть имя твоего коммутатора, — примерно так:

```
Ethernet adapter vEthernet (debug-net):
   ...
   IPv4 Address. . . . . . . . . . . : 192.168.1.23
```

Здесь `IPv4 Address` — «адрес IPv4», сетевой номер хоста. Запиши его.
У тебя цифры будут свои. Адаптеров с похожими именами может быть
несколько — нужен именно тот, где в скобках `debug-net`.

Проверить, что цель видит хост, можно командой `ping 192.168.1.23`
(с твоим адресом) внутри виртуальной машины. Но предупреждаю:
брандмауэр основной машины часто **не отвечает** на `ping`
по умолчанию. Если ответа нет — это ещё не значит, что отладка
не заработает. Решающая проверка — шаг 5.

### Шаг 3. Снимок и два файла в машину

Перед любыми правками настроек загрузки — **снимок** виртуальной
машины (глава 29). Назови его «до отладки».

Потом скопируй с основной машины из папки
`C:\Program Files (x86)\Windows Kits\10\Debuggers\x64` два файла —
`kdnet.exe` и `VerifiedNICList.xml` — в новую папку **`C:\KDNET\`**
внутри виртуальной машины. Копировать удобно через расширенный сеанс,
как `.sys` в главе 29.

Ещё одна вещь из документации: если в виртуальной машине включён
**BitLocker** `[бúтлокер]` (шифрование диска Windows), перед правкой
настроек загрузки его надо приостановить, иначе при следующей загрузке
Windows может попросить ключ восстановления. Проверь: Панель
управления → **Шифрование диска BitLocker** (BitLocker Drive
Encryption). Если там написано «BitLocker отключён» — всё хорошо.
Если включён — нажми **Приостановить защиту** (Suspend protection).
Для машины, поставленной с локальной учётной записью, как в главе 29,
он обычно выключен.

### Шаг 4. Включить отладку внутри цели

**Внутри виртуальной машины** открой командную строку от имени
администратора (как в главе 29) и перейди в папку:

```
cd C:\KDNET
kdnet
```

Без параметров `kdnet` только проверяет, умеет ли сетевая карта
машины работать со связным. Для Hyper-V ответ примерно такой:

```
Network debugging is supported on the following NICs:
busparams=..., Microsoft Hyper-V Network Adapter, ...
This Microsoft hypervisor supports using KDNET in guest VMs.
```

Перевод: «Сетевая отладка поддерживается на следующих сетевых
картах… Этот гипервизор Microsoft поддерживает KDNET в гостевых
машинах». NIC `[эн-ай-си]` — Network Interface Card, «сетевая карта».
Слово **гость** (guest `[гест]`) — это машина, которая работает
под гипервизором. Запомни это слово: с главы 35 оно станет главным.

Теперь включаем. Подставь адрес хоста из шага 2 и **порт** — номер
«двери», через которую будет идти связь. Microsoft советует брать
его из диапазона 50000–50039; возьмём 50005:

```
kdnet 192.168.1.23 50005
```

Ответ — примерно такой:

```
Enabling network debugging on Microsoft Hypervisor Virtual Machine.
Key=3u8smyv477z20.2owh9gl90gbxx.3sfsihzgq7di4.nh8ugnmzb4l7

To debug this vm, run the following command on your debugger host machine.
windbg -k net:port=50005,key=3u8smyv477z20.2owh9gl90gbxx.3sfsihzgq7di4.nh8ugnmzb4l7

Then restart this VM by running shutdown -r -t 0 from this command prompt.
```

Перевод: «Включаю сетевую отладку… Ключ = … Чтобы отлаживать эту
машину, выполни на хосте такую команду… Потом перезагрузи машину
командой `shutdown -r -t 0`».

**Ключ** (key `[ки]`) — длинная строка из четырёх частей через точку.
Это пароль связи: связной будет разговаривать только с тем отладчиком,
который знает ключ. У тебя ключ будет **свой** — не переписывай мой.
Выдели его в окне и скопируй (**Ctrl+C**), а на основной машине
сохрани в файл `key.txt` в Блокноте. Переписывать руками 50 символов
не надо — ошибёшься.

Что сделал `kdnet` на самом деле? То же, что мы делали в главе 29
программой `bcdedit`, — поправил настройки загрузки. Посмотреть их
можно так:

```
bcdedit /dbgsettings
```

Ответ — примерно так:

```
key                     3u8smyv477z20.2owh9gl90gbxx.3sfsihzgq7di4.nh8ugnmzb4l7
debugtype               NET
hostip                  192.168.1.23
port                    50005
dhcp                    Yes
The operation completed successfully.
```

`debugtype NET` — «вид отладки: сеть», `hostip` — адрес хоста,
`port` — порт. Если потеряешь ключ — эта команда покажет его снова.

Перезагружать пока **не надо**. Сначала хост должен начать ждать.

### Шаг 5. WinDbg ждёт, цель перезагружается

На **основной** машине в WinDbg: **File → Start debugging → Attach
to kernel** («подключиться к ядру»). Откроется окно с вкладками;
выбери вкладку **Net** («сеть»). Впиши:

- **Port Number** («номер порта») — `50005`;
- **Key** («ключ») — вставь ключ из `key.txt`.

Нажми **OK**. В окне Command появится примерно:

```
Using NET for debugging
Opened WinSock 2.0
Waiting to reconnect...
```

«Использую сеть для отладки… Жду подключения…»

В первый раз Windows на хосте спросит про **брандмауэр** (firewall
`[фáйрвол]`): «Брандмауэр заблокировал некоторые функции этого
приложения». Документация Microsoft говорит: поставь галочки **на всех
трёх** видах сетей — доменные (Domain), частные (Private) и общественные
(Public) — и нажми **Разрешить доступ** (Allow access). Если поставить
только одну, связь может молча не пойти.

Теперь **в виртуальной машине**, в той же командной строке
администратора:

```
shutdown -r -t 0
```

— «перезагрузка через 0 секунд». Машина перезагрузится, и через
минуту-другую в WinDbg появится примерно:

```
Connected to target 192.168.1.40 on port 50005 on local IP 192.168.1.23
Kernel Debugger connection established.
Windows 10 Kernel Version 26100 MP (4 procs) Free x64
Kernel base = 0xfffff807`4a000000 PsLoadedModuleList = 0xfffff807`4ac134f0
```

Разберём по строчкам:

- **Connected to target** — «подключено к цели»: адрес цели,
  порт, адрес хоста;
- **Kernel Debugger connection established** — «соединение
  с отладчиком ядра установлено». Всё, провод есть;
- **Windows 10 Kernel Version 26100** — не пугайся «Windows 10»:
  ядро Windows 11 называет себя так по старой памяти, а важен номер
  **сборки** — у Windows 11 он пятизначный, вроде `26100`. У тебя
  может быть другой номер — это нормально;
- **MP (4 procs)** — multiprocessor, «многопроцессорная, 4 процессора» —
  те самые четыре, что ты дал машине;
- **Kernel base** — «база ядра»: адрес, куда загружен
  `ntoskrnl.exe`. Верхняя половина адресов, как и положено (глава 32).
  Обрати внимание на запись адреса с апострофом посередине:
  ``fffff807`4a000000``. Это WinDbg так разделяет 16 цифр на две
  половины по 8, чтобы легче читалось. Сам апостроф ничего не значит:
  вводить адреса можно и с ним, и без него.

Windows внутри машины при этом **продолжает работать**: связь есть,
но никто её пока не остановил. Загрузись до рабочего стола.

Если за пять минут ничего не появилось — посмотри «Если не
подключается» в конце раздела.

### Шаг 6. Расширенный сеанс и снимок

Документация Microsoft предупреждает: если оставить машину
**остановленной** в отладчике, окно расширенного сеанса Hyper-V
может отвалиться по тайм-ауту (timeout `[тáймаут]`, «время ожидания
вышло»). Поэтому на время отладки переключай окно машины в обычный
режим: **Вид → Расширенный сеанс** (снять галочку). Для копирования
файлов — включай обратно, пока Windows работает.

И — **снимок** машины: «отладка». С него будут начинаться все
опыты этой главы.

### Если не подключается

По документации Microsoft, почти всегда виновато одно из трёх:

1. **Брандмауэр на хосте.** Проверь: Панель управления → Система
   и безопасность → **Разрешение взаимодействия с приложением через
   брандмауэр Windows** (Allow an app through Windows Firewall).
   Найди в списке строку WinDbg — в документации она называется
   **WinDbg engine process (TCP) (all)** — и поставь галочки на всех
   трёх видах сетей. Перезапусти WinDbg.
2. **Не тот адрес или не тот ключ.** Сравни `bcdedit /dbgsettings`
   в машине с тем, что вписано в WinDbg. Адрес — именно адаптера
   `vEthernet (debug-net)`.
3. **Порт занят.** Возьми другой из диапазона 50000–50039 и повтори
   шаг 4 с новым номером.

Не получается никак — пришли мне вывод `ipconfig` с хоста, вывод
`bcdedit /dbgsettings` из машины и снимок окна WinDbg. Настройка
отладки ядра — одно из мест, где спотыкаются все, и разбирать это
вдвоём быстрее.

### Если у тебя VMware

Сначала попробуй тот же путь: внутри машины `kdnet` без параметров.
Если он покажет, что сетевая карта машины поддерживается, — делай
шаги 4–6 точно так же (сеть у машины VMware в режиме **Bridged**
(«мост») — аналог внешнего коммутатора).

Если `kdnet` ответит, что поддерживаемых карт нет, у Microsoft есть
второй способ — **виртуальный COM-порт** через **именованный канал**
(named pipe `[нэймд пайп]`) — канал связи между программами на одной
машине, у которого есть имя. Кратко:

1. Внутри машины (командная строка администратора):
   `bcdedit /debug on`, затем
   `bcdedit /dbgsettings serial debugport:1 baudrate:115200`.
2. Выключи машину. В VMware: **VM → Settings → Add → Serial Port**
   («добавить последовательный порт») → **Use named pipe** («использовать
   именованный канал»), имя `\\.\pipe\com_1`, «This end is the
   server» («этот конец — сервер»), «The other end is an application»
   («другой конец — программа»).
3. **Запусти WinDbg от имени администратора** (для канала это
   обязательно). File → Start debugging → Attach to kernel → вкладка
   **COM**: галочка **Pipe** («канал»), Port — `\\.\pipe\com_1`,
   Baud Rate («скорость») — `115200`. **OK**.
4. Включи машину.

Документация Microsoft замечает про VMware: если перезагрузить машину
кнопкой сброса VMware, WinDbg надо закрыть и открыть заново. Надписи
в VMware проверь у себя: их переставляют от версии к версии.
