
## П7.9. Исключения: `throw` и `catch`

Третий заход. В C ошибку обычно возвращают числом: `return -1`. В C++
есть ещё один способ — **исключение** (exception, глава 27 — то же
слово, но здесь это механизм языка, а не процессора). Функция
**бросает** (throw `[сроу]`) объект-ошибку, и он летит вверх по цепочке
вызовов, пока его не **поймает** (catch `[кэч]`) блок `try` («попробуй»)
где-то выше.

Файл `exc.cpp`:

```cpp
#include <stdio.h>

struct BadInput {
    int code;
};

int parse(int x)
{
    if (x < 0)
        throw BadInput{ x };
    return x * 2;
}

int safe(int x)
{
    try {
        return parse(x);
    } catch (const BadInput &e) {
        printf("oshibka %d\n", e.code);
        return -1;
    }
}
```

`struct` в C++ — тот же класс, только всё в нём по умолчанию
`public`. `parse(5)` вернёт 10, а `parse(-3)` бросит `BadInput`
с кодом −3, его поймает `safe`, напечатает `oshibka -3` и вернёт −1.

### `throw` в листинге

`parse` у Visual Studio (с оптимизацией):

```
parse:
    sub     rsp, 28h
    test    ecx, ecx
    js      short throw_it             ; x < 0? (знак — глава 9)
    add     ecx, ecx                   ; x * 2
    mov     eax, ecx
    add     rsp, 28h
    retn
throw_it:
    mov     [rsp+24h], ecx             ; объект BadInput{x} на стеке
    lea     rdx, _TI1?AUBadInput@@     ; «паспорт» типа исключения
    lea     rcx, [rsp+24h]             ; адрес объекта
    call    _CxxThrowException
    int     3                          ; сюда управление не вернётся
```

Вот примета: **`throw` — это вызов `_CxxThrowException`**. Первый
аргумент — адрес объекта-ошибки, второй — описание его типа, имя
которого начинается с `_TI` (от throw info, «сведения о броске»).
`_CxxThrowException` не возвращается никогда, поэтому компилятор
ставит после него `int 3` — точку останова из главы 13, просто как
заглушку «сюда не попадаем».

В имени описания снова видно имя типа: `?AUBadInput@@`. И строка
`.?AUBadInput@@` лежит в данных, даже если RTTI выключен ключом `/GR-`:
исключениям она нужна всегда (проверено компилятором). Так поиск
строк `.?AU` и `.?AV` выдаёт и типы ошибок программы.

### `catch` в листинге

Тело `catch` компилятор выносит в **отдельную маленькую функцию**,
а рядом кладёт таблицы: какой кусок кода к какому `try` относится
и где искать обработчик. Читает эти таблицы особая функция библиотеки
C++ — **обработчик кадра** (frame handler). В программах из Visual
Studio 2019 и новее это `__CxxFrameHandler4` из файла
`VCRUNTIME140_1.dll` (так в блоге команды C++ Microsoft: новый формат
таблиц стал примерно на 60% меньше). У clang в облаке —
`__CxxFrameHandler3`, старый формат.

Для реверсера отсюда простое правило. Видишь в импортах
`_CxxThrowException` и `__CxxFrameHandler4` — программа на C++
из Visual Studio, и в ней есть исключения. Разбирать таблицы
руками почти никогда не нужно; как твоя IDA покажет блок `catch`, —
посмотри сам на этом примере (упражнение П7.7).

## П7.10. `std::string` и `std::vector` в памяти

В C++ есть **стандартная библиотека** (standard library) — готовые
классы. Два главных, которые встретятся в любой программе:

```cpp
#include <string>
#include <vector>

std::string s = "sobaka";             // строка, которая сама знает длину
std::vector<int> v = { 1, 2, 3 };     // массив, который растёт сам
```

`std::` — «из стандартной библиотеки» (std — standard). В IDA таких
объектов в программах из Visual Studio будет полно, и выглядят они
просто как куски памяти по 32 и 24 байта. Устройство я взял прямо
из исходников библиотеки Microsoft (`microsoft/STL`, файлы `xstring`,
`vector`, `xmemory`, октябрь 2026). Числа — для сборки Release.

### `std::string` — 32 байта

```
+00  16 байт: либо сам текст (если он не длиннее 15 букв),
              либо адрес текста в куче (если длиннее)
+10  размер — сколько букв сейчас (8 байт)
+18  вместимость — сколько поместится без нового выделения (8 байт)
```

Короткий текст живёт **прямо в объекте**: это экономит обращение
к куче для большинства строк. Такой приём называют **SSO**
`[эс-эс-óу]` — Small String Optimization, «оптимизация коротких
строк». Как понять, что лежит в первых 16 байтах? Смотри на
вместимость: **если она больше 15 — там адрес**, иначе — сам текст.

`std::string s = "sobaka";` в памяти (по исходнику):

```
+00  73 6F 62 61 6B 61 00 00 00 00 00 00 00 00 00 00   "sobaka" и нули
+10  06 00 00 00 00 00 00 00                           размер 6
+18  0F 00 00 00 00 00 00 00                           вместимость 15
```

А строка из 30 букв уже не влезет: первые 8 байт станут адресом
в куче, размер — `1E` (30), вместимость — `1F` (31). Почему 31, а не
30? Библиотека округляет вместимость вверх так, чтобы младшие четыре
бита были единицами: `30 | 15 = 31` (функция `_Calculate_growth`
в `xstring`).

### `std::vector` — 24 байта

```
+00  адрес первого элемента
+08  адрес сразу за последним элементом
+10  адрес конца выделенной памяти
```

Три указателя, и всё. Размер вектора нигде не записан — его
вычисляют: `(второй − первый) / размер элемента`. Для
`std::vector<int> v = {1, 2, 3}` разница первых двух адресов — 12 байт,
`12 / 4 = 3` элемента. В листинге это узнаётся по вычитанию двух
указателей и сдвигу вправо: `sar rax, 2` — деление на 4 (глава 10).

### В отладочной сборке — на 8 байт больше

В сборке Debug у Visual Studio перед полями появляется ещё один
служебный указатель — для проверок ошибок при работе со строками
и массивами (в `xmemory` это `_Container_base12` и его `_Myproxy`).
Тогда строка занимает 40 байт, вектор — 32, и все смещения сдвигаются
на 8. Ещё одна причина сначала понять, что перед тобой: Debug
или Release.

### У g++ строка устроена иначе

Библиотека g++ (libstdc++) тоже кладёт короткие строки в объект, но
порядок полей другой: сначала **всегда** указатель на текст (для
короткой строки он указывает внутрь самого объекта), потом длина, потом
16 байт буфера. Тоже 32 байта, но читать их надо по-другому. Снова
правило: сначала узнай компилятор.
