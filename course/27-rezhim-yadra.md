# Глава 27. Kernel mode и user mode

> **Часть VIII. Windows изнутри (Windows Internals)**
> Предыдущая глава: [26. Процессы, потоки, память глазами системы](26-processy-i-potoki.md)

В конце главы 26 остались открытыми три вопроса:

1. Программе **запрещено** читать верхнюю половину адресов, где живёт
   ядро. А кто, собственно, запрещает?
2. Спящий поток «уходит в ядро». Что значит «уйти в ядро», если поток
   один и тот же?
3. Почему код Windows может то, чего не может твоя программа? Ведь и то
   и другое — просто инструкции x86-64, те самые `mov`, `cmp`, `call`
   из главы 10.

Ответ на все три один, и он лежит **в самом процессоре**. Процессор
всегда знает, **насколько доверять** коду, который он сейчас выполняет.
Коду программы — мало. Коду ядра — полностью. Этот уровень доверия
называется **режимом** (mode `[мóуд]`), и у Windows их два: **режим
пользователя** и **режим ядра**.

Для твоей цели это одна из самых важных глав всего трека. Гипервизор —
это третий уровень, ниже ядра. Чтобы понять, как устроен «этаж под
полом», сначала надо твёрдо понять, как устроены сам пол и потолок.

После главы ты будешь уметь:

- объяснять, что такое кольца защиты и почему Windows использует
  только два из четырёх;
- находить номер текущего кольца в регистре `CS` — и в x64dbg, и из
  своей программы;
- узнавать **привилегированные** инструкции, которые программе
  запрещены, и коды исключений, которыми кончается попытка их выполнить;
- перечислять три «двери», через которые поток попадает в ядро;
- измерять, сколько времени твой поток провёл в ядре, а сколько — у себя;
- отличать файлы ядра от обычных программ по заголовку PE;
- объяснять, почему ошибка в драйвере роняет всю систему, и что такое
  «кольцо −1», где будет жить твой гипервизор.

## 27.1. Кто запрещает: не Windows, а процессор

Начнём с аналогии. Представь офисное здание с турникетами. У каждого
сотрудника пропуск, и на пропуске записан уровень доступа. Кто следит,
чтобы уборщик не зашёл в серверную? Не директор: он не может стоять
у каждой двери. Следят **турникеты** — сами, автоматически, у каждой
двери, каждую секунду. Директор только **настроил** их: вот этим
пропускам сюда можно, а этим нельзя.

В компьютере всё так же:

| В здании | В компьютере |
|---|---|
| директор, который настраивает правила | **ядро Windows** |
| турникеты, которые проверяют каждый проход | **процессор** |
| пропуск с уровнем доступа | **текущий уровень привилегий** кода |
| серверная, куда пускают не всех | память ядра, особые инструкции |

Главное в этой таблице — вторая строка. Проверку делает **железо**,
на каждой инструкции, без участия Windows. Программа не может
«договориться» с процессором или обойти проверку хитростью в коде:
проверка встроена в саму схему процессора.

Почему нельзя было поручить проверку программе-сторожу? Потому что
сторож тоже был бы просто кодом. Если бы защиту делал код, другой код
мог бы её испортить. Надёжная граница возможна, только если её держит
тот, кого нельзя переписать, — процессор.

Отсюда и порядок, в котором Windows просыпается при включении
компьютера. Первым работает код ядра с **полным** доступом. Он
раскладывает память, настраивает правила для процессора и только потом
запускает программы — уже с урезанным доступом. Программа рождается
в мире, где правила написаны до неё.

## 27.2. Кольца защиты

Инженеры Intel ещё в 1980-х годах придумали для процессора **четыре**
уровня привилегий. Их принято рисовать как вложенные кольца, поэтому
они называются **кольца защиты** (protection rings `[протéкшен рингз]`):

```
        ┌─────────────────────────────────┐
        │  кольцо 3 — меньше всего прав   │
        │   ┌─────────────────────────┐   │
        │   │  кольцо 2               │   │
        │   │   ┌─────────────────┐   │   │
        │   │   │  кольцо 1       │   │   │
        │   │   │   ┌─────────┐   │   │   │
        │   │   │   │ кольцо 0│   │   │   │
        │   │   │   │ все     │   │   │   │
        │   │   │   │ права   │   │   │   │
        │   │   │   └─────────┘   │   │   │
        │   │   └─────────────────┘   │   │
        │   └─────────────────────────┘   │
        └─────────────────────────────────┘
```

Чем **меньше** номер, тем **больше** прав. Не перепутай: кольцо 0 —
самое главное, кольцо 3 — самое слабое. Кольцо по-английски — ring
`[ринг]`, поэтому говорят «ринг ноль» и «ринг три», пишут ring 0
и ring 3.

Задумка была такая: ядро в кольце 0, драйверы в кольцах 1 и 2,
программы в кольце 3. Но на практике операционные системы выбрали
простоту. **Windows использует только два кольца:**

| Кольцо | Как называется в Windows | Англ. | Кто там работает |
|---|---|---|---|
| **0** | режим ядра | kernel mode `[кёрнел мóуд]` | ядро Windows и драйверы |
| **3** | режим пользователя | user mode `[юзер мóуд]` | все программы: Блокнот, браузер, твой `threads.exe` |

Кольца 1 и 2 в Windows пустуют. Поэтому «ring 0» и «режим ядра» —
синонимы, так же как «ring 3» и «режим пользователя». Встретишь в статье
любое из этих названий — речь об одном и том же.

Слово «пользователь» здесь сбивает с толку. Оно **не** про человека
за компьютером и **не** про учётную запись. Программа, запущенная от
имени администратора, всё равно работает в кольце 3. Администратор
может больше в смысле **правил Windows** (какие файлы открыть, какие
настройки поменять), но для **процессора** его программа — такой же
код кольца 3, как любой другой.

Уровень, на котором процессор работает в данный момент, называется
**текущим уровнем привилегий** — CPL (Current Privilege Level
`[кáррент прúвилидж лéвел]`, читается «си-пи-эл»). Это просто число
от 0 до 3. Процессор сверяется с ним перед каждой «опасной» инструкцией
и при каждом обращении к памяти.

Где процессор хранит это число? В очень старом регистре, про который
ты уже слышал.

## 27.3. Эксперимент: в каком кольце моя программа

В главе 13 x64dbg показывал перед адресами приписки `ss:` и `ds:`,
и я сказал: это сегментные регистры, наследие старых процессоров,
пока не обращай внимания. Пришло время обратить внимание на один
из них.

Сегментных регистров шесть: `CS`, `DS`, `SS`, `ES`, `FS`, `GS`. Каждый
занимает 16 бит. В 64-битном режиме от их прежней работы почти ничего
не осталось — подробно это разберём в главе 33. Но один регистр
по-прежнему очень важен:

- **`CS`** (Code Segment `[коуд сéгмент]` — «сегмент кода»).

**Два младших бита `CS` — это и есть номер текущего кольца.** Документация
Intel прямо говорит: CPL хранится в битах 0 и 1 регистров `CS` и `SS`.

### Смотрим в x64dbg

Открой в x64dbg любую программу, например `threads.exe` из главы 26,
и дождись остановки. Посмотри на панель регистров справа. Под флагами
и строками `LastError`, `LastStatus` есть блок из шести сегментных
регистров:

```
GS 002B   FS 0053
ES 002B   DS 002B
CS 0033   SS 002B
```

Числа в x64dbg, как всегда, в hex без `0x` (глава 13). Нас интересует
`CS = 0x33`. Переведём в двоичную систему, как в главе 3:

```
0x33 = 0011 0011
               ^^
               два младших бита: 11 = 3
```

**Кольцо 3.** Процессор выполняет код твоей программы в режиме
пользователя. Проверь заодно `SS = 0x2B = 0010 1011` — младшие биты
тоже `11`, тоже кольцо 3. Всё сходится.

А какое значение в `CS`, когда работает ядро? В 64-битной Windows это
`0x10`:

```
0x10 = 0001 0000
               ^^
               два младших бита: 00 = 0
```

Кольцо 0. Увидеть `CS = 0010` своими глазами ты сможешь только
в главе 30, когда подключишь отладчик к самому ядру: x64dbg живёт
в кольце 3 и видит только кольцо 3.

### Спрашиваем из своей программы

То же самое можно узнать без отладчика. В Windows есть документированная
функция `RtlCaptureContext` («снять контекст»). Она заполняет структуру
`CONTEXT` — **контекст** потока из главы 26, то есть снимок всех его
регистров. В этой структуре есть поле `SegCs` — значение регистра `CS`.

Файл `C:\reverse\work\rings.c`. Пока набери его целиком — остальные
части программы понадобятся в разделе 27.5:

```c
#include <windows.h>
#include <stdio.h>
#include <string.h>

/* Сюда Windows передаст управление, если программа упадёт */
LONG WINAPI on_crash(EXCEPTION_POINTERS *info)
{
    printf("Exception %08lx at %p\n",
           info->ExceptionRecord->ExceptionCode,
           info->ExceptionRecord->ExceptionAddress);
    fflush(stdout);
    ExitProcess(1);
    return EXCEPTION_EXECUTE_HANDLER;
}

int main(int argc, char **argv)
{
    CONTEXT ctx;

    RtlCaptureContext(&ctx);             /* снимок регистров своего потока */
    printf("CS = %04x, ring %d\n", ctx.SegCs, ctx.SegCs & 3);

    SetUnhandledExceptionFilter(on_crash);

    if (argc < 2)
        return 0;

    if (strcmp(argv[1], "hlt") == 0) {
        printf("Trying hlt...\n");
        __asm__ volatile ("hlt");        /* привилегированная инструкция */
        printf("hlt worked?!\n");
    }

    if (strcmp(argv[1], "read") == 0) {
        volatile char *p = (volatile char *)0xFFFF800000000000;
        printf("Trying to read %p...\n", (void *)p);
        printf("Got %d\n", *p);          /* чтение из половины ядра */
    }
    return 0;
}
```

Сейчас нас интересуют только первые строки `main`:

- `RtlCaptureContext(&ctx)` — заполнить `ctx` регистрами текущего потока;
- `ctx.SegCs & 3` — оставить от `CS` два младших бита. Знак `&` — это
  побитовое И, инструкция `and` из главы 10. Число 3 в двоичной
  системе — `11`, поэтому `& 3` обнуляет все биты, кроме двух младших.
  Такой приём называется **маской** (mask `[маск]`): число 3 работает
  как трафарет, через который видны только нужные биты.

Остальное — функцию `on_crash` и две ветки `if` — разберём
в разделе 27.5.

Собери и запусти **без аргументов**:

```
gcc -O0 -o rings.exe rings.c
./rings.exe
```

Вывод:

```
CS = 0033, ring 3
```

Это число не зависит ни от адресов, ни от компьютера: в любой 64-битной
Windows любая 64-битная программа работает с `CS = 0x33`. Твой код,
Блокнот, браузер, x64dbg — все в кольце 3.

## 27.4. Что запрещено в кольце 3

Процессор проверяет уровень привилегий в двух случаях: когда выполняет
**особую инструкцию** и когда обращается **к памяти**.

### Привилегированные инструкции

Почти все инструкции, которые ты знаешь, — `mov`, `add`, `cmp`, `jmp`,
`call`, `push` — одинаково работают в любом кольце. Но есть небольшая
группа инструкций, которые меняют **настройки самого процессора** или
общаются с **железом**. Их может выполнить только кольцо 0. Они
называются **привилегированными** (privileged instructions
`[прúвилиджд инстрáкшенс]`).

Вот главные. Не учи их наизусть — просто посмотри, сколько знакомых
слов будет в следующих главах:

| Инструкция | Что делает | Где встретим |
|---|---|---|
| `hlt` | остановить процессор до следующего события | эта глава |
| `cli`, `sti` | запретить / разрешить прерывания | глава 34 |
| `mov cr3, rax` и другие `mov` с `CR0`–`CR4` | поменять управляющие регистры процессора | главы 32 и 33 |
| `rdmsr`, `wrmsr` | прочитать / записать особые регистры настроек (MSR) | глава 33 |
| `lgdt`, `lidt` | загрузить адрес системных таблиц GDT и IDT | главы 33 и 34 |
| `invlpg` | сбросить запомненный перевод адреса одной страницы | глава 32 |
| `in`, `out` | обменяться данными с устройством напрямую | — |

Если бы программа могла выполнить любую из них, защите пришёл бы конец.
Например, `cli` отключает прерывания — и планировщик из главы 26 больше
не смог бы отнять у программы процессор: одна программа захватила бы
ядро навсегда. А `mov cr3, rax` подменил бы **таблицы перевода адресов**
(глава 26, раздел 26.12) — и программа увидела бы чужую память.

Строго говоря, `cli`, `sti`, `in` и `out` проверяются чуть сложнее —
по отдельному полю в регистре флагов. Но Windows настраивает это поле
так, что для программ результат тот же: в кольце 3 они запрещены.

А вот что разрешено в кольце 3, хотя звучит «системно»:

| Инструкция | Что делает | Зачем разрешена |
|---|---|---|
| `cpuid` | сообщить модель и возможности процессора | программам нужно знать, что умеет процессор |
| `rdtsc` | прочитать счётчик тактов процессора | точные замеры времени |
| `syscall` | **перейти в ядро** по правилам | это и есть законная дверь в ядро — глава 28 |

Запомни `cpuid`. В обычной Windows её может выполнить кто угодно. А под
гипервизором на процессорах Intel эта безобидная инструкция **всегда**
передаёт управление гипервизору — и он сам решает, что ответить.
(На AMD — если гипервизор попросил её перехватывать.) Это будет первый
перехват в твоём гипервизоре (глава 38).

### Страницы ядра

Второй случай — память. В главе 26 мы говорили, что у каждой страницы
есть права: чтение, запись, выполнение. Есть и ещё одна пометка, про
которую я тогда промолчал: **чья страница**. Каждая страница помечена
как **пользовательская** (её можно трогать из кольца 3) или как
**страница ядра** (только из кольца 0).

При **каждом** обращении к памяти процессор делает две проверки:

1. Разрешено ли такое действие (чтение, запись, выполнение)?
2. Разрешено ли оно **из текущего кольца**?

Страницы верхней половины адресов помечены как страницы ядра. Поэтому
код ядра может читать их сколько угодно, а твоя программа — нет. Вот
и ответ на первый вопрос главы: **запрещает процессор**, сверяя CPL
с пометкой страницы. Где именно лежит эта пометка — в записи о странице
в таблицах перевода адресов. Как устроены эти таблицы, разберём
в главе 32. А пока достаточно знать: пометка есть, и её проверяет железо.

Важная асимметрия: кольцо 0 **может** трогать и свои страницы, и
пользовательские. Код ядра видит память текущего процесса целиком:
и нижнюю половину, и верхнюю. Кольцо 3 видит только нижнюю.

## 27.5. Эксперимент: нарушаем правила

Проверим обе защиты на деле. Для этого в `rings.c` есть две ветки,
которые включаются аргументом командной строки. Аргументы — это слова,
которые пишут после имени программы. В C они приходят в `main` через
`argc` («сколько слов») и `argv` («сами слова»):

- `./rings.exe hlt` — выполнить инструкцию `hlt`;
- `./rings.exe read` — прочитать байт по адресу `0xFFFF800000000000`
  из половины ядра (тот самый адрес, который я предлагал попробовать
  в главе 26).

Помнишь параметры `_Argc` и `_Argv`, которые Ghidra показала у `main`
в главе 14? Это они и есть. `argv[0]` — имя самой программы, `argv[1]` —
первое слово после него. А `argc < 2` значит «слов после имени нет».
Функция `strcmp` сравнивает две строки и возвращает 0, если они равны —
её мы встречали в главе 7, в проверке пароля.

**Как попасть в ассемблер из C.** Строка `__asm__ volatile ("hlt");` —
это **ассемблерная вставка** (inline assembly `[инлайн эссéмбли]`). Так
gcc позволяет вписать одну инструкцию прямо в код на C. Слово `volatile`
(«изменчивый») запрещает компилятору выбрасывать или переставлять
вставку. В `.exe` она превратится ровно в один байт — `F4`, опкод `hlt`
(опкоды — глава 10). То же слово стоит у указателя `p` в ветке
`read`: `volatile char *p` значит «каждое чтение через `p` выполняй
по-настоящему, не выкидывай его». Без этого компилятор с оптимизацией
мог бы решить, что чтение лишнее.

**Как узнать, что программа упала.** Функция `SetUnhandledExceptionFilter`
(«установить фильтр необработанных исключений») говорит Windows: если
в программе случится исключение и его никто не обработает, вызови мою
функцию `on_crash`. Windows передаст ей структуру с описанием
исключения. Мы печатаем два поля:

| Поле | Перевод | Что там |
|---|---|---|
| `ExceptionCode` | код исключения | **что** случилось — число вроде `C0000005` |
| `ExceptionAddress` | адрес исключения | **на какой инструкции** это случилось |

Потом `fflush(stdout)` выталкивает на экран всё напечатанное, а
`ExitProcess(1)` завершает процесс (глава 26) с кодом 1.

### Опыт 1: привилегированная инструкция

```
./rings.exe hlt
```

Примерно так (у тебя адрес будет другим):

```
CS = 0033, ring 3
Trying hlt...
Exception c0000096 at 00007FF7A3B815DC
```

Строки `hlt worked?!` нет: до неё дело не дошло. Код `C0000096`
в документации Microsoft называется `STATUS_PRIVILEGED_INSTRUCTION` —
«привилегированная инструкция». Процессор отказался выполнять `hlt`
в кольце 3.

Проверь адрес. База образа всегда кончается на `0000` — это
гранулярность из главы 26. Поэтому четыре последние hex-цифры
напечатанного адреса — это и есть RVA инструкции: у меня `15DC`.
Открой свой `rings.exe` в Ghidra, нажми **G** и введи базу Ghidra
плюс свои четыре цифры — у меня `1400015dc` (база `140000000`,
глава 14). Там будет инструкция `HLT`.

### Опыт 2: чтение памяти ядра

```
./rings.exe read
```

Примерно так:

```
CS = 0033, ring 3
Trying to read FFFF800000000000...
Exception c0000005 at 00007FF7A3B8163E
```

`C0000005` — старый знакомый из главы 26: **access violation**,
нарушение доступа. Адрес в сообщении — это адрес **инструкции**, которая
пыталась читать, а не адрес `FFFF800000000000`: так устроено поле
`ExceptionAddress`. В моей сборке это RVA `0x163E`, и там стоит
`movzx eax, byte ptr [rax]` — чтение одного байта по адресу из `RAX`
(`movzx` — глава 10). Строки `Got` нет.

Заметь, что программе всё равно, есть ли по этому адресу что-то
в ядре на самом деле. Лежат там данные ядра или пустота — из кольца 3
результат один: нельзя.

### Опыт 3: то же самое под x64dbg

Открой `rings.exe` в x64dbg и дождись **первой** остановки — программа
ещё не дошла до `main`. Чтобы передать ей аргумент, выбери в меню
**File** («Файл») → **Change Command Line** («Изменить командную
строку»). В конец строки, после кавычки с путём к файлу, допиши через
пробел `hlt` и нажми **OK**. Во вкладке **Log** появится `New command
line: …` — «новая командная строка». Программа прочитает её, когда
дойдёт до `main`.

Жми **F9**, пока программа не остановится на исключении. Внизу,
во вкладке **Log** («Журнал»), появится строка:

```
First chance exception on 00007FF7A3B815DC (C0000096, EXCEPTION_PRIV_INSTRUCTION)!
```

«Исключение первого шанса по адресу … (код, название)». Первый шанс
(first chance `[фёрст чанс]`) — Windows сначала показывает исключение
отладчику, до самой программы (глава 13). Окно CPU стоит ровно на
инструкции `hlt`.

Нажми **F9** ещё раз. Под отладчиком наш `on_crash` не сработает:
Windows вызывает такой фильтр, только когда программу никто не
отлаживает. Вместо этого появится строка `Last chance exception…` —
«исключение последнего шанса»: программа не справилась, и отладчик
получает исключение второй раз, перед её гибелью.

### Что произошло на самом деле

Разберём путь исключения по шагам. Здесь кроется ответ на второй
вопрос главы.

1. Процессор дошёл до `hlt` в кольце 3 и отказался её выполнять.
2. **Процессор сам переключился в кольцо 0** и прыгнул в код ядра,
   который обрабатывает такие случаи. Адрес этого кода ядро заранее
   записало в специальную таблицу процессора (глава 34).
3. Ядро посмотрело: откуда пришла беда? Из кольца 3, из программы.
   Значит, это проблема программы, а не системы.
4. Ядро упаковало описание — код `C0000096`, адрес, все регистры —
   и **вернуло поток в кольцо 3**, но не на `hlt`, а в специальную
   функцию `ntdll.dll`, которая раздаёт исключения обработчикам.
   Её имя — `KiUserExceptionDispatcher` («раздатчик исключений
   пользователю»). Иногда ты увидишь его в стеке вызовов x64dbg.
5. Если программу отлаживают, Windows сначала сообщает отладчику. Если
   нет — ищет обработчик, и в конце концов вызывает наш `on_crash`.

То есть **каждое** исключение — это путешествие в кольцо 0 и обратно.
В том числе исключения, которые ты видел в главе 13: `int3` точки
останова и шаги с флагом `TF`. Вот почему отладчик не может работать
сам по себе, а работает **через Windows**: о любом исключении сначала
узнаёт ядро, и только оно решает, кому его показать.

> **Связь с гипервизором.** Посмотри на шаг 2: «процессор сам
> переключился в более привилегированный режим и прыгнул в заранее
> указанный код». Когда работает гипервизор, всё происходит так же,
> только уровнем ниже. Гостевая Windows выполняет что-то, что
> гипервизор велел перехватывать, — процессор сам переключается
> в гипервизор и прыгает по адресу, который тот заранее записал.
> Этот переход называется **VM exit** — «выход из виртуальной машины».
> Механика та же, что ты только что видел. Глава 35.

## 27.6. Три двери в ядро

Мы выяснили: программа не может ни выполнить привилегированную
инструкцию, ни прочитать память ядра. Но ведь программы **постоянно**
пользуются услугами ядра: открывают файлы, создают потоки, выделяют
память. Значит, из кольца 3 в кольцо 0 можно как-то попасть. Как?

Вернёмся к офисному зданию. В серверную нельзя пройти через турникет,
но можно подойти к **окошку** и отдать заявку. Сотрудник за окошком
(у него доступ есть) проверит заявку, сделает работу и вернёт ответ.
Ты ни разу не переступил порог, а работа сделана.

У процессора таких «окошек» ровно три вида:

| Дверь | Англ. | Кто открывает | Пример |
|---|---|---|---|
| **системный вызов** | system call `[сúстем кол]` | программа, **сама и нарочно** | `CreateFileW` доходит до инструкции `syscall` |
| **исключение** | exception `[иксéпшен]` | процессор — **из-за инструкции программы** | `hlt`, чтение ядра, `int3`, деление на ноль |
| **аппаратное прерывание** | hardware interrupt `[хáрдвэр интерáпт]` | **устройство**, в любой момент | тикнул таймер, нажата клавиша, пришёл сетевой пакет |

Разберём каждую.

**Системный вызов** — вежливая просьба. Программа кладёт в регистры,
что ей нужно, и выполняет инструкцию `syscall` — она, как ты видел
в таблице раздела 27.4, в кольце 3 **разрешена**. Процессор переходит
в кольцо 0 и прыгает в ядро. Ядро выполняет просьбу (если она
законная) и возвращается обратно. Вся глава 28 — про эту дверь.

**Исключение** — ты только что прошёл через эту дверь в разделе 27.5.
Добавлю одну вещь, которая свяжет эту главу с прошлой. В главе 26 мы
узнали: выделенная страница получает настоящую, физическую память
только при **первом обращении**. Как Windows узнаёт, что обращение
первое? Через исключение! Процессор видит, что под страницей пока нет
физической памяти, и вызывает исключение **страничного сбоя** (page
fault `[пейдж фолт]`). Ядро в кольце 0 тихо находит свободную
физическую страницу, подставляет её — и возвращает поток на ту же
инструкцию. Во второй раз всё проходит. Программа ничего не заметила:
это исключение ядро обработало само и программе не показало.

То есть исключение — это не всегда «ошибка». Это просто «процессор
не может продолжить сам, пусть разберётся кольцо 0». Иногда ядро
разбирается молча, иногда передаёт беду программе.

**Аппаратное прерывание** — стук снаружи. Его вызывает не программа,
а устройство: таймер, клавиатура, диск, сетевая карта. Оно приходит
в **любой** момент, между любыми двумя инструкциями программы.
Процессор откладывает текущий поток, переходит в кольцо 0 и выполняет
код ядра, который обслуживает это устройство.

Помнишь **квант** из главы 26? Планировщик отнимает процессор у потока,
когда квант кончился. Но как, если поток крутит бесконечный цикл и
ни о чём не просит ядро? Ответ — третья дверь. Таймер регулярно
вызывает прерывание, процессор переходит в ядро, ядро видит, что квант
кончился, и переключает контекст. Без аппаратных прерываний
планировщик был бы бессилен против одной жадной программы.

### Кто выбирает, куда именно войти

Вот самое важное свойство всех трёх дверей. Программа может **постучать**,
но не может **выбрать**, в какой код ядра попадёт. Адреса, куда процессор
прыгает при `syscall`, при исключении и при прерывании, **ядро записало
заранее**, при загрузке Windows. Записало — в регистры и таблицы
процессора, которые можно менять только из кольца 0 (помнишь `wrmsr`
и `lidt` в таблице привилегированных инструкций?).

Если бы программа могла сказать «перейди в кольцо 0 и прыгни вот сюда,
в мой код», защита не значила бы ничего. Поэтому граница устроена как
окошки, а не как двери с кодовым замком: за каждым окошком сидит тот,
кого посадило туда ядро, и мимо него не пройти.

### И обратно

Возвращается ядро тоже особыми инструкциями: после системного вызова —
как правило, `sysret` `[сис-рет]`, после исключения и прерывания —
`iretq` `[ай-рет-кью]`. Обе — привилегированные: переключить процессор из
кольца 0 в кольцо 3 может только кольцо 0. Их ты увидишь в главе 28
и снова в главе 34.

## 27.7. Один поток — два режима

Теперь второй вопрос главы: что значит «поток ушёл в ядро»?

Легко представить так: программа передала работу «потоку ядра»,
а сама ждёт. Это **неправильная** картинка. На самом деле в ядро уходит
**тот же самый поток**. Тот же TID, то же место в планировщике. Он
просто переключился в кольцо 0 и выполняет теперь код ядра. Сделал
работу — вернулся в кольцо 3 и продолжил код программы.

Одно отличие всё же есть: в ядре поток работает **на другом стеке**.
У каждого потока **два** стека:

| Стек | Где лежит | Кто пользуется |
|---|---|---|
| **пользовательский** | в нижней половине адресов | код программы (это его ты видел в x64dbg) |
| **стек ядра** | в верхней половине | тот же поток, пока он в кольце 0 |

Зачем второй стек? Пользовательский стек — во власти программы.
Программа может испортить `RSP` (глава 11) или положить его на мусор.
Ядро не может доверять ничему, что контролирует программа, поэтому
сразу при входе в кольцо 0 `RSP` переключается на стек ядра. При
исключениях и прерываниях это делает **сам процессор**. При `syscall`
процессор этого не делает — стек меняют самые первые инструкции ядра,
ещё до того, как они что-либо положат на стек. Подробности в главе 28.

### Разгадка из главы 26

В главе 26 ты смотрел на рабочие потоки `threads.exe` в x64dbg, и их
`RIP` указывал куда-то внутрь `ntdll.dll`. Я обещал объяснить.

Запусти `threads.exe` под x64dbg ещё раз, дойди до `getchar` (как
в разделе 26.5) и дважды щёлкни рабочий поток во вкладке **Threads**.
Окно CPU покажет место в `ntdll.dll`. Посмотри на инструкцию **прямо
над** текущей строкой:

```
syscall
ret          <- здесь RIP
```

Поток выполнил `syscall` и **ушёл в ядро**. Там, в кольце 0, он и
спит — ядро поставило его в очередь ожидающих, пока не кончится `Sleep`.
x64dbg из кольца 3 не видит, что делает поток в ядре. Он показывает
последнее, что поток делал в кольце 3: адрес, **куда поток вернётся**,
когда ядро его отпустит. Это инструкция сразу после `syscall`.

Как именно устроены эти несколько инструкций вокруг `syscall` в
`ntdll.dll` — разберём по байтам в главе 28.

### Эксперимент: сколько времени поток провёл в ядре

Раз поток один, а режимов два, Windows может посчитать, сколько времени
поток провёл в каждом. Спросим её функцией `GetThreadTimes` («получить
времена потока»). Файл `modetime.c`:

```c
#include <windows.h>
#include <stdio.h>

/* FILETIME считает время порциями по 100 наносекунд. Переводим в миллисекунды */
double ms(FILETIME ft)
{
    ULARGE_INTEGER t;

    t.LowPart  = ft.dwLowDateTime;
    t.HighPart = ft.dwHighDateTime;
    return t.QuadPart / 10000.0;
}

void report(const char *stage)
{
    FILETIME created, exited, kernel, user;

    GetThreadTimes(GetCurrentThread(), &created, &exited, &kernel, &user);
    printf("%-11s kernel %6.0f ms   user %6.0f ms\n",
           stage, ms(kernel), ms(user));
}

int main(void)
{
    HANDLE ev = CreateEventA(NULL, TRUE, FALSE, NULL);
    unsigned long long sum = 0;
    int i;

    report("start");

    for (i = 0; i < 500000000; i++)      /* только арифметика в своей памяти */
        sum += i;
    report("math");

    for (i = 0; i < 2000000; i++)        /* каждый вызов — просьба к ядру */
        ResetEvent(ev);
    report("ResetEvent");

    printf("sum = %llu\n", sum);
    CloseHandle(ev);
    return 0;
}
```

Что здесь нового:

| Что | Смысл |
|---|---|
| `GetThreadTimes` | заполнить четыре структуры `FILETIME`: когда поток создан, когда завершился, **сколько работал в ядре**, **сколько у себя** |
| `GetCurrentThread` | дескриптор «мой поток» |
| `FILETIME` | время в виде двух 32-битных половинок; вместе — 64-битное число порций по 100 нс |
| `ULARGE_INTEGER` | помощник: склеивает две половинки в одно 64-битное число `QuadPart` |
| `CreateEventA` | создать **событие** (event `[ивéнт]`) — простейший объект ядра, флажок «поднят / опущен» |
| `ResetEvent` | опустить флажок события |

Про события подробнее поговорим, когда понадобятся. Сейчас важно
одно: событие живёт **в ядре** (программа получает только его
дескриптор, глава 12), поэтому **каждый** вызов `ResetEvent` — это
системный вызов, поход через первую дверь.

Почему делим на `10000`? В одной миллисекунде 1 000 000 наносекунд,
то есть 10 000 порций по 100 нс. Документация Microsoft приводит
пример: секунда в ядре — это число 10 000 000.

Программа проходит три этапа и после каждого печатает **накопленные**
времена: этап `math` — полмиллиарда сложений, этап `ResetEvent` — два
миллиона просьб к ядру.

```
gcc -O0 -o modetime.exe modetime.c
./modetime.exe
```

Честное предупреждение: я пишу курс там, где Windows нет, поэтому
цифры ниже — иллюстрация, а не мой замер. У тебя они будут другими,
и от запуска к запуску будут немного плавать. Но **соотношение** будет
таким:

```
start       kernel      0 ms   user      0 ms
math        kernel      0 ms   user    547 ms
ResetEvent  kernel    453 ms   user    641 ms
sum = 124999999750000000
```

Последняя строка от компьютера не зависит, она будет точно такой.
Читаем остальное — помни, что числа **накапливаются**, и смотри на
то, **насколько они выросли** за этап:

1. **Этап `math`.** Выросло почти только время `user`. Сложение чисел
   в своей памяти — чистое кольцо 3, ядро не нужно.
2. **Этап `ResetEvent`.** Теперь основной прирост — у `kernel`: поток
   раз за разом уходил через `syscall` в ядро. `user` тоже чуть
   подрос: по дороге к `syscall` поток проходит несколько функций
   в системных библиотеках (`kernel32.dll`, `ntdll.dll` и других),
   а они работают в кольце 3.

Время `kernel` — это время **этого же потока**, другого исполнителя
здесь нет. Поток по очереди был то в кольце 3, то в кольце 0.

### То же в инструментах

- **x64dbg:** во вкладке **Threads** есть столбцы **User Time** и
  **Kernel Time** — то же разделение для каждого потока отдельно.
  А столбец **Wait Reason** («причина ожидания») говорит, почему поток
  стоит. У спящих рабочих потоков `threads.exe` из главы 26 там будет
  `DelayExecution` — «отложенное выполнение», то есть `Sleep`.
- **Process Explorer:** двойной щелчок по процессу → вкладка
  **Performance** («Производительность»). Там строки **Kernel Time**
  («время в ядре») и **User Time** («время в режиме пользователя»).
- **Диспетчер задач:** вкладка **Производительность** → **ЦП**. Щёлкни
  правой кнопкой по графику и выбери **Show kernel times** («Показать
  время ядра»; в русской версии надпись может быть чуть другой). На
  графике появится второй, более тёмный слой — доля времени, которую
  процессор провёл в кольце 0.

Открой браузер с тяжёлым сайтом, запусти копирование большого файла —
посмотри, как меняется тёмный слой. Копирование файла — почти всё
работа ядра и драйверов диска.

## 27.8. Кто живёт в кольце 0

Кто работает по ту сторону окошка? Нарисуем Windows слоями, сверху вниз:

```
кольцо 3   твоя программа (threads.exe, rings.exe)
           kernel32.dll, kernelbase.dll — функции WinAPI (глава 12)
           ntdll.dll — последняя остановка перед ядром
═══════════════════ syscall — граница колец ═══════════════════
кольцо 0   ntoskrnl.exe — ядро Windows
           драйверы (.sys) — диски, сеть, видео, клавиатура…
           hal.dll — слой, прячущий различия между компьютерами
────────────────────────────────────────────────────────────────
           железо: процессор, память, устройства
```

`kernelbase.dll` ты уже встречал — в стеке вызовов Process Monitor
в главе 15. В неё Microsoft перенесла большую часть кода
`kernel32.dll`, поэтому по дороге к ядру вызов обычно проходит через
обе библиотеки.

**Ловушка в названии.** `kernel32.dll` — «ядро-32» — **не ядро**. Это
обычная библиотека кольца 3, она загружена в твой процесс и работает
с `CS = 0x33`. Название осталось с тех времён, когда Windows была
устроена иначе. Настоящее ядро — файл `ntoskrnl.exe`.

Пройдёмся по кольцу 0:

| Файл | Произношение | Что это |
|---|---|---|
| `ntoskrnl.exe` | `[эн-ти-оу-эс-кёрнел]` | NT OS Kernel — **ядро Windows**. Планировщик, менеджер памяти, объекты, процессы и потоки — всё из главы 26 работает здесь |
| `*.sys` | `[сис]` | **драйверы** (driver `[дрáйвер]`) — модули, которые подгружаются в ядро и умеют работать с конкретными устройствами или добавляют ядру новые возможности |
| `hal.dll` | `[хэл]` | HAL (Hardware Abstraction Layer — слой абстракции оборудования): прячет от ядра различия между материнскими платами. В 64-битной Windows его код встроен прямо в `ntoskrnl.exe`, а файл остался ради совместимости со старыми драйверами |

Драйверы лежат в папке `C:\Windows\System32\drivers\`. Загляни туда —
там сотни файлов `.sys`. Каждый из них, когда загружен, работает
в кольце 0 **наравне с ядром**. Запомни эту мысль, она понадобится
в разделе 27.9.

Process Monitor из главы 15, кстати, тоже ставит свой драйвер — поэтому
и просит права администратора. Без кольца 0 он не мог бы видеть
обращения к файлам всех процессов сразу.

### Эксперимент: ядро — это тоже PE-файл

Открой в PE-bear (глава 8) файл `C:\Windows\System32\ntoskrnl.exe`.
Только смотрим, ничего не сохраняем.

Первое открытие: у ядра Windows **тот же формат**, что у твоего
`hello.exe`. DOS-заголовок с `MZ`, PE-заголовок, таблица секций,
`.text` с кодом — всё, что ты разбирал в главе 8. Реверсить ядро
можно теми же приёмами.

Теперь найди на вкладке **Optional Hdr** поле, которое мы в главе 8
пропустили, — **Subsystem** («подсистема»). Оно говорит Windows, для
какого мира собран файл:

| Значение | Название | Что значит |
|---|---|---|
| `1` | Native `[нéйтив]` — «родной» | работает **без** WinAPI: ядро, драйверы и несколько самых ранних системных программ |
| `2` | Windows GUI — Graphical User Interface, графический интерфейс | программа с окнами, как Блокнот |
| `3` | Windows CUI — Console User Interface, консольный интерфейс | консольная программа, как все наши |

У `ntoskrnl.exe` будет `1` — Native. У твоего `rings.exe` — `3`
(проверь). У `notepad.exe` — `2`.

Посмотри теперь **импорты** ядра (вкладка **Imports**). Там **нет**
`kernel32.dll`. И это логично: `kernel32.dll` — это кольцо 3, она сама
просит ядро о помощи. Ядру просить некого — помощь это оно.

Открой в PE-bear какой-нибудь драйвер из `C:\Windows\System32\drivers\`,
например `null.sys` или `beep.sys` (если их нет — любой маленький файл
`.sys`). Subsystem снова `1`. А в импортах ты найдёшь **`ntoskrnl.exe`**:
драйверы берут функции прямо у ядра, как программы берут их
у `kernel32.dll`.

Имена функций ядра начинаются с **приставок**. По приставке сразу ясно,
к какой части ядра обращается драйвер. Это пригодится в главе 31, когда
будешь реверсить чужие драйверы:

| Приставка | Часть ядра | Пример функции |
|---|---|---|
| `Io` | ввод-вывод, устройства | `IoCreateDevice` |
| `Ke` | сердцевина ядра | `KeBugCheckEx` |
| `Mm` | менеджер памяти | `MmGetSystemRoutineAddress` |
| `Ex` | исполнительная система | `ExAllocatePool2` |
| `Ob` | менеджер объектов | `ObReferenceObjectByHandle` |
| `Ps` | процессы и потоки | `PsGetCurrentProcessId` |
| `Rtl` | вспомогательная библиотека | `RtlInitUnicodeString` |

Помнишь из главы 26 записи **E**PROCESS и **E**THREAD? Буква E там —
от Executive, та же исполнительная система, что в приставке `Ex`.

## 27.9. Почему ошибка в ядре роняет всё

Когда падает твоя программа, закрывается только она. Когда падает
драйвер, падает **весь компьютер**. Почему такая разница?

Документация Microsoft отвечает прямо. Каждая программа живёт в своём
адресном пространстве, поэтому её падение не задевает ни другие
программы, ни систему. А **весь код режима ядра делит одно общее
адресное пространство** (помнишь из главы 26: верхняя половина одна на
всех). Драйвер не изолирован ни от других драйверов, ни от самой
Windows. Если он по ошибке запишет не туда, он может испортить данные
ядра или чужого драйвера. И дальше цитата: если драйвер режима ядра
падает, падает вся операционная система.

Посмотри на это с точки зрения раздела 27.5. Исключение в программе
ловит ядро — оно стоит **выше** программы и может её аккуратно
закрыть. А кто поймает исключение в самом ядре? **Выше никого нет.**
Ядро не может «закрыть себя» и продолжить. Если в кольце 0 случилось
то, чего быть не должно, продолжать работу опасно: данные ядра, может
быть, уже испорчены, и следующий шаг испортит диск. Поэтому Windows
делает единственное безопасное — **останавливает всё**.

Эта остановка называется **bug check** `[баг чек]` — «проверка на
ошибку»; так её зовёт документация для разработчиков драйверов.
Выполняет её та самая функция `KeBugCheckEx` из таблицы выше. В народе
это «синий экран смерти», BSOD (Blue Screen of Death `[блю скрин оф
дэс]`). В Windows 11 начиная с версии 24H2 экран стал **чёрным**,
но суть та же: надпись «Your device ran into a problem and needs to
restart» (перевод: «с устройством случилась проблема, его нужно
перезагрузить») и **код остановки** (stop code `[стоп коуд]`).

Сравни два случая — одна и та же ошибка, разные кольца:

| Чтение по плохому адресу | Что происходит |
|---|---|
| в программе (кольцо 3) | исключение `C0000005`, программа закрывается, ты это видел |
| в драйвере (кольцо 0) | bug check с кодом вроде `PAGE_FAULT_IN_NONPAGED_AREA` — «страничный сбой в неподкачиваемой области», компьютер перезагружается |

Отсюда три правила, которые определят следующую часть курса:

1. **Windows пускает в ядро не каждого.** Драйвер должен быть подписан
   цифровой подписью, иначе 64-битная Windows его не загрузит. Как
   с этим живут разработчики драйверов и как загрузить свой учебный
   драйвер — глава 29.
2. **Все опыты с ядром — только в виртуальной машине.** Твой первый
   драйвер почти наверняка уронит систему, и это нормально. Пусть
   падает виртуальная машина, а не твой рабочий компьютер. 32 ГБ
   памяти для этого хватит с запасом.
3. **Останавливать ядро изнутри нельзя.** Если остановить ядро точкой
   останова, остановится и сам отладчик — он ведь тоже работает под
   этим ядром. Поэтому ядро отлаживают **с другой машины** — или
   из основной системы, подключившись к виртуальной. Это глава 30.

## 27.10. Ниже нуля: кольцо −1

Кольцо 0 — самое привилегированное из четырёх. Казалось бы, ниже
некуда. Но в середине 2000-х годов Intel и AMD добавили в процессоры
**аппаратную виртуализацию** — у Intel она называется **VT-x**, у AMD —
**AMD-V** (или SVM). Оба варианта есть в твоих процессорах: Intel
Core i5-13400F и AMD Ryzen 5 7500F.

Идея такая. Процессор получает ещё один, **новый режим**, по правам
старше всех четырёх колец. Поэтому его и рисуют **под** кольцом 0 —
«под полом». Код в этом режиме — **гипервизор**
(hypervisor `[хáйпервайзер]`). А под ним работает целая операционная
система, **гость** (guest `[гест]`), со всеми своими кольцами:

```
                 ┌──────────────────────────────────┐
                 │  гостевая Windows                │
                 │    кольцо 3 — программы          │
                 │    кольцо 0 — ядро гостя         │
                 └──────────────┬───────────────────┘
                   VM exit ↓    │    ↑ VM entry
                 ┌──────────────┴───────────────────┐
                 │  гипервизор — «кольцо −1»        │
                 └──────────────────────────────────┘
                              железо
```

Гостевое ядро думает, что оно в кольце 0 и главное на машине. Его
`CS` честно показывает кольцо 0, и почти все инструкции выполняются
на полной скорости, прямо на процессоре. Но когда гость делает что-то,
что гипервизор велел перехватывать, процессор **сам** переключается
в гипервизор — это **VM exit** `[ви-эм экзит]`, «выход из виртуальной
машины». Гипервизор разбирается и возвращает управление гостю — это
**VM entry** `[ви-эм энтри]`, «вход в виртуальную машину».

Узнаёшь схему? Это ровно то, что ты видел в разделе 27.5 с `hlt`, только
этажом ниже: программа → исключение → ядро разбирается → обратно.
Гость → VM exit → гипервизор разбирается → обратно.

Название «кольцо −1» (ring −1 `[ринг мáйнус уан]`) — **неофициальное**.
Так говорят в статьях и докладах, потому что гипервизор «ниже нуля».
В документации Intel этот режим называется **VMX root operation**
(root `[рут]` — «корневой»), режим гостя — **VMX non-root operation**
(«некорневой»). У AMD — host mode и guest mode, «режим хозяина» и
«режим гостя».
Эти слова ты будешь встречать с главы 35.

### Возможно, твоя Windows уже гость

Вот неожиданная вещь. На многих компьютерах с Windows 11 гипервизор
**уже работает** — гипервизор Microsoft, Hyper-V. Его включает функция
**безопасности на основе виртуализации** — VBS (Virtualization-Based
Security `[вёрчуалайзéйшен бейст сек'юрити]`). Тогда вся твоя Windows,
включая ядро `ntoskrnl.exe`, работает **гостем** под гипервизором
Microsoft — особым, привилегированным, но всё же гостем. VBS с помощью гипервизора выделяет изолированную область
памяти, куда не может заглянуть даже ядро Windows, и оттуда, например,
проверяет код драйверов перед запуском. Эта функция называется
**целостность памяти** (memory integrity).

Проверь свой компьютер. Нажми `Win+R`, введи `msinfo32` и нажми Enter.
Откроется окно «Сведения о системе» (System Information). На первой
странице найди строки:

| Строка (англ.) | Перевод | Что значит |
|---|---|---|
| Virtualization-based security: **Running** | безопасность на основе виртуализации: **выполняется** | VBS включена, под Windows работает Hyper-V |
| A hypervisor has been detected. Features required for Hyper-V will not be displayed. | обнаружен гипервизор, компоненты для Hyper-V не будут показаны | гипервизор уже работает прямо сейчас |

В русской Windows надписи будут по-русски, и точные слова могут
отличаться от моего перевода — ищи по смыслу. Параметр «целостность
памяти» лежит здесь: **Безопасность Windows** → **Безопасность
устройства** → **Изоляция ядра** → **Целостность памяти**. Сейчас
ничего не выключай — только посмотри и запомни, что там.

Что это значит для твоей цели? Если место «ниже нуля» уже занято
гипервизором Microsoft, свой гипервизор прямо на этом компьютере
не запустить. Поэтому разрабатывать и испытывать его мы будем
**в виртуальной машине**, которой внешний гипервизор разрешает тоже
пользоваться VT-x или AMD-V. Это называется **вложенной
виртуализацией** (nested virtualization `[нéстид вёрчуалайзéйшен]`).
Как её настроить — расскажу, когда дойдём до части XI.

## 27.11. Что запомнить

1. Границу между программой и ядром держит **процессор**, а не код
   Windows. Ядро только настраивает правила, а проверяет их железо —
   на каждой инструкции.
2. У процессора x86-64 **четыре кольца**. Windows использует два:
   **кольцо 0** — режим ядра (kernel mode), **кольцо 3** — режим
   пользователя (user mode). Меньше номер — больше прав.
3. Текущее кольцо (**CPL**) — это **два младших бита `CS`**. У программ
   в 64-битной Windows `CS = 0x33` (кольцо 3), у ядра — `0x10` (кольцо 0).
   Права администратора кольцо не меняют.
4. В кольце 3 запрещены **привилегированные инструкции** (`hlt`, `cli`,
   `mov cr3`, `wrmsr`, `lidt`…) — исключение `C0000096` — и **страницы
   ядра** — исключение `C0000005`.
5. В ядро ведут **три двери**: системный вызов (`syscall`), исключение,
   аппаратное прерывание. Куда именно попадёт процессор, ядро записало
   заранее — программа не выбирает.
6. Исключение — не всегда ошибка. Страничный сбой при первом обращении
   к памяти ядро обрабатывает молча.
7. В ядро уходит **тот же поток**, только на свой **стек ядра**. Windows
   считает его время отдельно: `kernel` и `user`.
8. `kernel32.dll` — **не ядро**, это кольцо 3. Ядро — `ntoskrnl.exe`,
   рядом с ним драйверы `.sys`. У них Subsystem = `1` (Native), а
   драйверы импортируют функции у `ntoskrnl.exe`.
9. Весь код ядра делит **одно адресное пространство**, выше него никого
   нет. Поэтому ошибка драйвера — это **bug check** (синий, а теперь
   чёрный экран), и опыты с ядром — только в виртуальной машине.
10. Ниже кольца 0 есть **гипервизор** — неофициально «кольцо −1».
    Гость работает со всеми своими кольцами, а особые события уводят
    процессор в гипервизор: **VM exit**, и обратно: **VM entry**.
11. Если в Windows 11 включена **VBS**, под твоей Windows уже работает
    гипервизор Microsoft. Проверка — `msinfo32`.

---

## Что дальше

Ты узнал, **где** проходит граница между программой и ядром и **кто**
её держит. Теперь ясно, почему программа не может сама прочитать файл
с диска: диск — это устройство, работа с устройствами — привилегированная,
значит, без ядра никак.

Из трёх дверей в ядро одна особенная. Исключения и прерывания случаются
«сами», а **системный вызов** программа делает **нарочно** — это её
законный способ попросить ядро о помощи. Через него проходит каждое
открытие файла, каждое создание потока, каждый `VirtualAlloc`. В
[главе 28](28-sistemnye-vyzovy.md) пройдём этот путь целиком: от
`CreateFileW` в твоём коде через `kernel32.dll` и `ntdll.dll` до
инструкции `syscall` — и узнаем, что делает процессор в тот миг, когда
её выполняет. А заодно разберём те самые несколько инструкций вокруг
`syscall`, на которых спали рабочие потоки `threads.exe`.

Глава 28 закроет часть VIII. Ещё немного — и ты начнёшь писать код,
который сам работает в кольце 0.
