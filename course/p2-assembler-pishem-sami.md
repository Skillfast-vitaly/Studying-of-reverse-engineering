# Приложение П2. Ассемблер: пишем сами

> **Приложения к курсу**
> Когда проходить: после [приложения П1](p1-si-pishem-sami.md) и **до
> части XI** (гипервизор). Опирается на главы [10](10-assembler.md),
> [11](11-stek-i-funkcii.md), [12](12-soglashenie-o-vyzovah.md)
> и [13](13-x64dbg.md).

Брат, это второе приложение из проверки курса на полноту. Пробел здесь
такой же, как с C в П1: **главы 10–12 учат читать ассемблер, но не
писать на нём.** Для реверса этого хватает. Ты смотришь в x64dbg на
чужой код и понимаешь, что он делает.

Но в гипервизоре есть несколько мест, где C не справится и придётся
написать несколько десятков строк на ассемблере **самому**. И там
не прощают ни одной ошибки: забыл вернуть один регистр — и Windows
падает через секунду в совершенно другом месте, а ты не понимаешь
почему.

Хорошая новость: нового здесь почти нет. Инструкции ты знаешь
(глава 10), стек — тоже (глава 11), правила вызова — тоже (глава 12).
В главе 12 ты смотрел на эти правила **снаружи**, глазами того, кто
читает чужую функцию. Здесь ты посмотришь **изнутри**, глазами того,
кто пишет функцию, которую будут вызывать другие.

После приложения ты будешь уметь:

- писать функцию на ассемблере в отдельном файле и вызывать её из C;
- объяснять, какие регистры твоя функция может портить, а какие
  обязана вернуть как было;
- находить ошибку «забыл сохранить регистр» по её странным
  последствиям;
- вызывать функции C из ассемблера: теневое пространство и
  выравнивание стека;
- описывать пролог функции для Windows, чтобы отладчик и система
  могли пройти по стеку;
- писать свои обёртки для инструкций `cpuid` и `rdtsc`;
- сохранять все регистры в структуру C и разбирать их на C — это
  основа будущего обработчика в гипервизоре;
- переводить свой код с синтаксиса w64devkit на MASM из Visual Studio.

Приложение длинное, около 1150 строк. Проходи **в три захода**:

| Заход | Разделы | О чём |
|---|---|---|
| 1 | П2.1–П2.3 | первая функция, как C её находит |
| 2 | П2.4–П2.7 | правила вызова изнутри, забытый регистр, вызов C, пролог |
| 3 | П2.8–П2.13 | свои `cpuid` и `rdtsc`, снимок регистров, проект, MASM |

Правило то же, что в П1: **каждый пример набирай руками**. Ассемблер
учится пальцами ещё сильнее, чем C.

## П2.1. Зачем писать на ассемблере самому

Ты вправе спросить: мы весь курс писали на C, компилятор сам делает
ассемблер, и делает хорошо. Зачем писать руками?

Есть три причины, и все три — про гипервизор и драйверы.

**1. В Visual Studio для x64 нет вставок ассемблера.** В главе 34 ты
видел ассемблерные вставки прямо в коде C — так умеет компилятор
`gcc`. Драйверы для Windows собирают компилятором Microsoft из
Visual Studio (глава 29), а он для 64-битного кода вставки **не
поддерживает**. В документации Microsoft так и написано: «Inline
assembly is not supported on the ARM and x64 processors» — «вставки
ассемблера не поддерживаются на процессорах ARM и x64». Вместо них
Microsoft предлагает два пути:

- **встроенные функции** (intrinsics `[интрúнсикс]`) — ты уже
  пользовался `__cpuidex` в главе 33;
- **отдельный файл на ассемблере** — файл `.asm`, который собирается
  вместе с файлами `.c`. Этому и учит приложение.

**2. Встроенных функций хватает не на всё.** Для многих инструкций они
есть. Но бывают места, где нужен **целый кусок** ассемблера, а не одна
инструкция. Например, место, где надо сохранить все регистры процессора
разом, и сделать это **до того**, как любой код на C успеет их
испортить. Компилятор C не даёт тебе управлять регистрами напрямую:
он сам решает, в каком регистре держать переменную.

**3. Реверсеру это полезно само по себе.** Когда ты хоть раз написал
функцию руками и она упала, потому что стек сдвинулся на 8 байт, ты
навсегда начинаешь видеть такие вещи в чужом коде.

Сразу скажу честно, чтобы не пугать: ассемблера в твоём гипервизоре
будет **мало**. Сотни строк на C и несколько десятков на ассемблере.
Но эти несколько десятков должны быть **идеальными**.

## П2.2. Первая функция: `add3`

Начнём с самой простой функции: сложить три числа.

```c
uint64_t add3(uint64_t a, uint64_t b, uint64_t c);   // вернуть a + b + c
```

Вспомни главу 12: первые четыре аргумента приходят в регистрах `RCX`,
`RDX`, `R8`, `R9`, а ответ функция кладёт в `RAX`. Значит, при входе
в `add3`: `a` лежит в `RCX`, `b` — в `RDX`, `c` — в `R8`. Нужно
сложить их в `RAX` и вернуться.

Открой консоль w64devkit (глава 6), перейди в свою рабочую папку и
создай файл:

```
notepad add.s
```

Набери в нём:

```
.intel_syntax noprefix          # синтаксис Intel, как в x64dbg
.text                           # дальше идёт код

.globl add3                     # имя видно другим файлам
add3:                           # uint64_t add3(a, b, c)
    mov  rax, rcx               # rax = a
    add  rax, rdx               # rax = a + b
    add  rax, r8                # rax = a + b + c
    ret                         # ответ уже в rax
```

Разберём каждую строку.

- **`.s`** — так для `gcc` называется файл на ассемблере (s — от
  source, «исходник»). Строчки, которые начинаются с точки, —
  **директивы** (directive `[дирéктив]`, «указание»). Это не инструкции
  процессора, а команды самому **ассемблеру** — программе, которая
  переводит текст в машинный код.
- **`.intel_syntax noprefix`** — «пиши в синтаксисе Intel, без значков
  `%` перед регистрами». У ассемблера из `gcc` по умолчанию другой
  синтаксис (его называют AT&T), в нём операнды стоят в обратном
  порядке. Мы берём синтаксис Intel: он такой же, как в x64dbg
  (глава 13) и в документации Intel. Эта строка — первая в каждом
  нашем файле.
- **`.text`** — «дальше идёт код». Помнишь секцию `.text` из главы 8?
  Это она: ассемблер положит наши инструкции именно туда.
- **`.globl add3`** — «имя `add3` видно снаружи этого файла»
  (globl — сокращение от global, «глобальный»). Без этой строки
  функцию никто, кроме самого файла, не найдёт. Проверим в П2.3.
- **`add3:`** — **метка** (label `[лéйбл]`), как в главе 10. Имя
  с двоеточием — это просто адрес следующей инструкции. Имя функции
  в ассемблере — это и есть метка.
- **`#`** — начало **комментария** до конца строки. Внимание:
  у ассемблера `gcc` комментарий начинается с `#`, а не с `;`, как
  в x64dbg. Точка с запятой здесь означает «следующая инструкция
  на той же строке». Если по привычке написать `; комментарий`,
  ассемблер попробует понять твой комментарий как инструкцию
  и выдаст ошибку.
- Инструкции `mov`, `add`, `ret` — из главы 10, ничего нового.

Теперь программа на C, которая вызывает нашу функцию. Файл `main_add.c`:

```c
#include <stdio.h>
#include <stdint.h>

uint64_t add3(uint64_t a, uint64_t b, uint64_t c);   // живёт в add.s

int main(void)
{
    uint64_t r = add3(1, 20, 300);
    printf("add3(1, 20, 300) = %llu\n", (unsigned long long)r);
    return 0;
}
```

Строка с `add3` без тела — это **прототип** (prototype `[прóутотайп]`)
из П1.6: обещание компилятору «такая функция есть, с такими
аргументами, её тело найдётся при сборке». Приведение к
`unsigned long long` и `%llu` — из П1.1: так 64-битное число
печатается правильно на любом компиляторе.

Собери оба файла **одной** командой и запусти:

```
gcc -Wall -o add.exe main_add.c add.s
./add.exe
```

```
add3(1, 20, 300) = 321
```

Этот вывод настоящий: я собрал тот же код и проверил логику
на облачном сервере (подробнее — в П2.10).

Что сделал `gcc`? Файл `.c` он скомпилировал, файл `.s` отдал
ассемблеру, а потом **компоновщик** (linker `[лúнкер]`, глава 2)
склеил оба куска машинного кода в один `.exe`.

Открой `add.exe` в x64dbg и найди `add3` способом из главы 13.
Выбери **Search for** («Искать») → **Current Module** («Текущий
модуль») → **String references** («Ссылки на строки»), найди строку
`add3(1, 20, 300) = %llu` и дважды щёлкни по ней. Чуть выше
увидишь `call` — это вызов `add3`, ведь его результат потом уходит
в `printf`. Поставь на этот `call` точку останова (**F2**), запусти
(**F9**) и зайди внутрь (**F7**). Ты увидишь ровно свои четыре
инструкции:

```
mov rax,rcx
add rax,rdx
add rax,r8
ret
```

Компилятор ничего не переставил и не добавил. Всё, что ты написал
в `.s`, попадает в `.exe` **ровно так**. Это главное отличие от C:
никто не будет за тебя думать. И никто не будет исправлять твои
ошибки.

## П2.3. Как C находит функцию

Зачем была строчка `.globl add3`? Сделаем опыт: удали её из `add.s`
и собери снова. Компоновщик выдаст:

```
undefined reference to `add3'
collect2: error: ld returned 1 exit status
```

Перевод: «неопределённая ссылка на `add3`… `ld` (компоновщик)
завершился с кодом 1». Ассемблер собрал функцию, но оставил её имя
**внутри файла**, а `main_add.c` искал его снаружи. Это самая частая
ошибка новичка в ассемблере. Запомни её вид, и в следующий раз
починишь за секунду. Верни строчку на место.

Как это работает. Каждый собранный файл (его называют **объектным**,
object file, `.o`) несёт с собой список имён:

- «какие имена **есть у меня** и видны снаружи» — `.globl add3`
  в `add.s`;
- «какие имена **мне нужны** от других» — вызов `add3` в `main_add.c`.

Компоновщик сводит эти списки. Нашёл пару — подставил адрес в `call`.
Не нашёл — `undefined reference`. Это та же идея, что с импортом
функций из DLL в главе 8, только на этапе сборки, а не запуска.

А теперь опаснее. Компоновщик сверяет **только имя**. Типы аргументов
он не проверяет. Напиши в прототипе

```c
uint64_t add3(uint64_t a, uint64_t b);   // забыл третий аргумент
```

и вызови `add3(1, 20)`. Программа соберётся без единого
предупреждения. А в `R8` при входе в `add3` будет лежать **то, что
там осталось** от предыдущего кода, и функция честно прибавит этот
мусор. Ответ будет случайным.

Отсюда правило: **прототип — это договор, и следишь за ним ты сам.**
C не видит, что написано в `.s`. Поэтому прототип и комментарий над
функцией в `.s` держи одинаковыми и меняй всегда вместе. В проекте
П2.10 мы положим прототипы в отдельный файл `.h`, как в П1.6, чтобы
договор хранился в одном месте.

> **Конец первого захода.** Ты написал функцию на ассемблере, собрал
> её вместе с C и видел её в x64dbg. Проверь себя: напиши функцию
> `uint64_t mul2(uint64_t x)`, которая возвращает `x * 2`, одной
> инструкцией `lea` из главы 10 и одной `ret`. Дальше — правила,
> которые нельзя нарушать.

## П2.4. Правила из главы 12, теперь изнутри

В главе 12 (раздел 12.3) ты выучил, что регистры делятся на две
группы. Тогда ты смотрел на это глазами **вызывающего**: «после `call`
какие регистры могли измениться?». Теперь ты пишешь функцию сам, и та
же таблица читается как **список твоих обязанностей**:

| Регистры | Как они называются | Что тебе можно |
|---|---|---|
| `RAX`, `RCX`, `RDX`, `R8`, `R9`, `R10`, `R11` | volatile `[вóлатайл]`, «летучие» | портить как угодно, ничего не возвращать |
| `RBX`, `RBP`, `RDI`, `RSI`, `R12`–`R15` | non-volatile `[нон-вóлатайл]`, «сохраняемые» | трогать можно, но **перед `ret` вернуть** каждый как было |
| `RSP` | указатель стека | к `ret` он обязан указывать туда же, куда при входе |

Ещё одна мысль, которая сильно упрощает жизнь: **для вызывающего
летучие регистры — это черновик**. Он знает, что после `call`
в них может оказаться что угодно, и ничего важного там не хранит.
А в сохраняемых регистрах он как раз держит самое ценное: счётчик
цикла, указатель на структуру. Он **уверен**, что после `call` они
на месте. Если ты их испортишь, вызывающий об этом не узнает. Он
просто продолжит работать с неправильными числами.

Как вернуть сохраняемый регистр? Самый простой способ ты знаешь
из главы 11: `push` в начале функции, `pop` перед `ret`, в обратном
порядке:

```
    push rbx                # сохранить
    push rsi
    ...                     # здесь rbx и rsi можно портить
    pop  rsi                # вернуть — в обратном порядке!
    pop  rbx
    ret
```

Стек — стопка тарелок: что положил последним, снимаешь первым.
Перепутаешь порядок `pop` — `RBX` и `RSI` поменяются значениями, и
это опять ошибка, которую никто не заметит сразу.

И последнее правило, про стек. По правилам Windows перед каждым
`call` значение `RSP` должно делиться на 16 (глава 12). Инструкция
`call` кладёт на стек адрес возврата — 8 байт. Значит, **в момент
входа в твою функцию** `RSP` делится на 16 **с остатком 8**. Запомни
это число: в П2.6 мы по нему будем считать выравнивание.

## П2.5. Опыт: забытый `RBX`

Правило «верни сохраняемый регистр» легко выучить и легко нарушить.
Давай нарушим его нарочно и посмотрим, как это выглядит. Тогда,
если такое случится с тобой по-настоящему, ты узнаешь симптомы.

Нам нужна инструкция, которая сама портит `RBX`. Такая есть, и ты её
знаешь: **`cpuid`** из главы 33. Она кладёт ответ в `EAX`, `EBX`,
`ECX`, `EDX`. А `RBX` — сохраняемый регистр! Напишем функцию-обёртку
для `cpuid` и **забудем** его сохранить. Файл `bad.s`:

```
.intel_syntax noprefix
.text

# void bad_cpuid(uint32_t leaf, uint32_t out[4]) — ОШИБКА: rbx не сохранён
.globl bad_cpuid
bad_cpuid:
    mov  r8, rdx
    mov  eax, ecx
    xor  ecx, ecx
    cpuid
    mov  [r8],      eax
    mov  [r8 + 4],  ebx
    mov  [r8 + 8],  ecx
    mov  [r8 + 12], edx
    ret
```

Что делают строки, подробно разберём в П2.8. Пока важно одно: после
`cpuid` в `RBX` лежит не то, что было при входе.

Программа `main_bad.c` — простой цикл на три шага:

```c
#include <stdio.h>
#include <stdint.h>

void bad_cpuid(uint32_t leaf, uint32_t out[4]);   // bad.s

int main(void)
{
    uint32_t r[4];
    for (int i = 0; i < 3; i++) {
        bad_cpuid(0, r);
        printf("i = %d\n", i);
    }
    printf("done\n");
    return 0;
}
```

Собери **с оптимизацией** `-O2` (глава 5) и запусти:

```
gcc -O2 -o bad.exe main_bad.c bad.s
./bad.exe
```

Ожидаешь `i = 0`, `i = 1`, `i = 2`, `done`. А получишь вот это,
бесконечно, пока не нажмёшь **Ctrl+C**:

```
i = 1970169159
i = 1970169159
i = 1970169159
i = 1970169159
...
```

Это настоящий вывод: я проверил его на облачном сервере, у которого
процессор Intel. На твоём Intel будет то же число. На Ryzen число будет
другим: `1752462657`. Сейчас поймёшь почему.

**Расследование.** Как настоящий реверсер, откроем `bad.exe` и
посмотрим, как компилятор сделал цикл. Вот `main`, настоящий
дизассемблер той самой сборки `-O2` (я убрал только адреса).
Это листинг в том виде, как его показывает x64dbg, поэтому
комментарии здесь через `;`, а не через `#`:

```
push rdi
push rsi
push rbx                    ; main сам бережёт rbx своего вызывающего
sub  rsp,0x30
xor  ebx,ebx                ; i = 0 — счётчик живёт в EBX!
lea  rsi,[строка "i = %d\n"]
call __main
lea  rdi,[rsp+0x20]         ; rdi = адрес массива r
цикл:
mov  rdx,rdi                ; второй аргумент: r
xor  ecx,ecx                ; первый аргумент: 0
call bad_cpuid
mov  edx,ebx                ; второй аргумент printf: i
mov  rcx,rsi                ; первый: строка
add  ebx,0x1                ; i++
call printf
cmp  ebx,0x3                ; i == 3?
jne  цикл
```

Видишь? Компилятор положил счётчик `i` в `EBX`. Он имел на это полное
право: `RBX` сохраняемый, значит, после `call bad_cpuid` он обязан
остаться прежним. Компилятор **доверился** правилам. А наша функция
их нарушила: `cpuid` с листом 0 положил в `EBX` первые четыре буквы
имени производителя.

Проверим. На Intel имя — `GenuineIntel`, первые четыре буквы `Genu`.
Байты этих букв в ASCII: `G` = `47`, `e` = `65`, `n` = `6E`, `u` = `75`.
Порядок little-endian (глава 3) — младший байт первым, поэтому число
в регистре — `756E6547`. В десятичной системе это `1970169159`. Вот
оно, наше «`i`». На AMD имя — `AuthenticAMD`, первые буквы `Auth`,
число `68747541` = `1752462657`.

Дальше цикл делает `i++`, сравнивает `1970169160` с тройкой — не равно,
идём по кругу. Снова `bad_cpuid`, снова `EBX = 1970169159`. Бесконечно.

Посмотри, какие здесь **симптомы**, это главное в опыте:

- ошибка в **нашей** функции, а сломался **чужой** код — цикл в `main`;
- программа не упала, не выдала ошибку — она **тихо** считала неправильно;
- без `-O2` (в режиме `-O0`) компилятор держит `i` в памяти, а не
  в регистре, и программа печатает правильно. Но ошибка никуда
  не делась: `RBX` всё так же испорчен, просто сейчас в нём не лежит
  ничего важного. Ошибка **прячется** и проявится при оптимизации.

Запомни эту тройку. Если твой код на C «сходит с ума» сразу после
вызова ассемблерной функции, и только в `-O2` (или только в сборке
Release в Visual Studio), — первым делом проверь, возвращает ли
функция все сохраняемые регистры.

**Исправление** — две строчки:

```
bad_cpuid:
    push rbx                # сохранить
    mov  r8, rdx
    ...
    mov  [r8 + 12], edx
    pop  rbx                # вернуть
    ret
```

С ними программа печатает `i = 0`, `i = 1`, `i = 2`, `done`.

## П2.6. Вызываем C из ассемблера

Теперь наоборот: наша функция на ассемблере сама вызывает функцию,
написанную на C. Тут включаются правила, которые в главе 12 ты видел
в чужих функциях: **теневое пространство** (shadow space) и
**выравнивание стека**.

Задача: функция `apply_twice(fn, x)` получает указатель на функцию
(П1.7) и число, и возвращает `fn(fn(x))`. Файл `twice.s`:

```
.intel_syntax noprefix
.text

# uint64_t apply_twice(uint64_t (*fn)(uint64_t), uint64_t x)
# вернуть fn(fn(x))
.globl apply_twice
.seh_proc apply_twice
apply_twice:
    push rbx                    # rbx чужой: сохранить
    .seh_pushreg rbx
    sub  rsp, 32                # 32 байта теневого пространства
    .seh_stackalloc 32
    .seh_endprologue

    mov  rbx, rcx               # fn -> rbx: переживёт вызов
    mov  rcx, rdx               # первый аргумент = x
    call rbx                    # rax = fn(x)
    mov  rcx, rax               # первый аргумент = fn(x)
    call rbx                    # rax = fn(fn(x))

    add  rsp, 32                # вернуть стек
    pop  rbx                    # вернуть rbx как было
    ret
.seh_endproc
```

Строчки с `.seh_` пока пропусти, их разберём в П2.7. Смотри на всё
остальное.

**Почему указатель `fn` лежит в `RBX`?** Нам нужно вызвать `fn` дважды.
При входе `fn` лежит в `RCX`. Но `RCX` летучий: первый же `call`
может его испортить, ведь функция `fn` вправе делать с ним что угодно.
Значит, `fn` надо переложить туда, где он **переживёт** вызов, —
в сохраняемый регистр. Мы взяли `RBX`. Но раз мы его трогаем, мы
обязаны его сохранить и вернуть. Отсюда `push rbx` в начале и
`pop rbx` в конце. Правила П2.4 работают в обе стороны: `fn` обязана
вернуть нам `RBX`, мы обязаны вернуть `RBX` тому, кто вызвал нас.

**Почему `sub rsp, 32`?** Это теневое пространство из главы 12: перед
каждым `call` вызывающий обязан оставить на стеке 32 байта, куда
вызванная функция может сохранить свои четыре аргумента. Функция `fn`
написана на C, и компилятор вправе записать туда что угодно. Не
оставишь места — она затрёт то, что лежит выше: наш сохранённый `RBX`
и адрес возврата.

**Почему 32, а не 40, как в главе 12?** Посчитаем, это главный
навык раздела. Считаем остаток от деления `RSP` на 16:

| Момент | Что случилось | `RSP` mod 16 |
|---|---|---|
| вход в `apply_twice` | `call` положил адрес возврата | 8 (П2.4) |
| после `push rbx` | ещё 8 байт | 0 |
| после `sub rsp, 32` | 32 делится на 16 | 0 |
| перед `call rbx` | — | **0** — правило выполнено |

В главе 12 функция не сохраняла ни одного регистра, поэтому ей
приходилось добавлять к 32 ещё 8 байт «на выравнивание» — отсюда 40.
У нас эти 8 байт уже добавил `push rbx`. Если бы мы сохраняли **два**
регистра, остаток снова стал бы 8, и понадобилось бы `sub rsp, 40`.

Правило на всю жизнь: **после всех `push` и `sub` перед `call` сумма
должна быть «8 + что-то кратное 16»**. То есть 8 байт от адреса
возврата плюс всё, что положила сама функция, должны делиться на 16.

Что будет, если ошибиться? Большинство функций работают и с кривым
стеком. Но некоторые инструкции (например, `movaps`, которую
компилятор любит для копирования структур и чисел с плавающей
точкой) требуют, чтобы адрес делился на 16, и падают с исключением
0xC0000005 (глава 34), если это не так. Поэтому ошибка выравнивания
особенно коварна: всё работает неделю, а потом падает в чужой функции,
которая только что начала пользоваться такой инструкцией.

Программа `main_twice.c`:

```c
#include <stdio.h>
#include <stdint.h>

uint64_t apply_twice(uint64_t (*fn)(uint64_t), uint64_t x);   // twice.s

uint64_t times10(uint64_t v) { return v * 10; }
uint64_t plus7(uint64_t v)   { return v + 7; }

int main(void)
{
    printf("times10 twice: %llu\n", (unsigned long long)apply_twice(times10, 3));
    printf("plus7 twice:   %llu\n", (unsigned long long)apply_twice(plus7, 3));
    return 0;
}
```

```
gcc -Wall -O2 -o twice.exe main_twice.c twice.s
./twice.exe
```

```
times10 twice: 300
plus7 twice:   17
```

`3 × 10 × 10 = 300`, `3 + 7 + 7 = 17`. Вывод настоящий.

## П2.7. Пролог для Windows: директивы `.seh_`

Вернёмся к строчкам с `.seh_`. Они не превращаются ни в одну
инструкцию. Я проверил: в `twice.exe` функция `apply_twice` —
это ровно десять инструкций, от `push rbx` до `ret`. Зачем тогда
эти строчки?

Вспомни главу 8. В `.exe` для Windows есть секции `.pdata` и `.xdata`,
«данные для обработки исключений». Там для каждой функции записано:
где она начинается и кончается и что её **пролог** (prologue
`[прóлог]`, «вступление» — первые инструкции функции) сделал со
стеком. Например: «сначала `push rbx`, потом отнял от `RSP` 32 байта».

Кому это нужно? Всем, кто ходит **по стеку назад**:

- **x64dbg** — чтобы в окне **Call Stack** («стек вызовов») показать,
  кто кого вызвал;
- **Windows** — чтобы при исключении найти обработчик в одной из
  вызывающих функций (глава 34);
- **отладчик ядра** (глава 30) — чтобы после синего экрана показать,
  в какой функции какого драйвера всё сломалось.

Чтобы пройти от функции к её вызывающему, нужно знать, где на стеке
лежит адрес возврата. А это зависит от того, что пролог положил на
стек. Без записи в `.pdata` система видит только адрес и не знает,
сколько байт снять. Поиск по стеку ломается на твоей функции.

Директивы `.seh_` (SEH — Structured Exception Handling, «структурная
обработка исключений») как раз и **описывают пролог** для этой
таблицы:

| Директива | Что говорит |
|---|---|
| `.seh_proc имя` | здесь начинается функция |
| `.seh_pushreg rbx` | «сейчас пролог сделал `push rbx`» |
| `.seh_stackalloc 32` | «сейчас пролог отнял от `RSP` 32 байта» |
| `.seh_endprologue` | пролог закончен |
| `.seh_endproc` | здесь функция кончается |

Каждая директива стоит **сразу после** инструкции, которую описывает.
Это важно: так ассемблер точно знает, на каком байте функции случилось
каждое действие.

Я собрал `twice.exe` дважды, с директивами и без них, и сравнил. С ними
в `.pdata` есть запись для `apply_twice`, и в ней ровно два действия:
«отнял 32 байта» и «`push rbx`». Без них для `apply_twice` записи нет
вообще. Программа при этом работает одинаково, разницу видят только
отладчик и система.

Когда директивы нужны? Правило Microsoft: запись в таблице нужна
**каждой функции, которая выделяет место на стеке, вызывает другие
функции или сохраняет сохраняемые регистры**. Функции вроде `add3`,
которые ничего не кладут на стек и никого не вызывают, называются
**листовыми** (leaf function `[лиф фáнкшен]`, «функция-листок»: на ней
дерево вызовов кончается). Им таблица не нужна: адрес возврата у них
всегда лежит прямо на вершине стека.

Для программы из командной строки это кажется мелочью. Но в драйвере,
а потом в гипервизоре, пролог без описания — это синий экран, который
отладчик не может нормально показать. Поэтому привычку ставим сразу:
**функция трогает стек — пиши `.seh_`.**

> **Конец второго захода.** Проверь себя: функция сохраняет `RBX`,
> `RSI` и `RDI` и вызывает функцию на C. Сколько байт ей надо отнять
> от `RSP`, чтобы и теневое пространство было, и выравнивание? (Ответ
> посчитай по таблице из П2.6, потом сверься с упражнением П2.3.)

## П2.8. Инструкции, которых нет в C: свои `cpuid` и `rdtsc`

Третий заход. Теперь сделаем полезные вещи: свои обёртки для двух
инструкций. Для обеих у компилятора есть встроенные функции, так что
по-настоящему они тебе не нужны. Но на них отлично видно, как думать,
когда пишешь обёртку для **любой** инструкции, в том числе для тех,
у которых встроенной функции нет.

### `my_cpuid`

```
# void my_cpuid(uint32_t leaf, uint32_t out[4])
#   rcx = leaf, rdx = out
.globl my_cpuid
.seh_proc my_cpuid
my_cpuid:
    push rbx                    # cpuid портит rbx, а он чужой
    .seh_pushreg rbx
    .seh_endprologue
    mov  r8, rdx                # out -> r8: cpuid затрёт rdx
    mov  eax, ecx               # номер листа -> eax
    xor  ecx, ecx               # подлист 0
    cpuid                       # ответ в eax, ebx, ecx, edx
    mov  [r8],      eax         # out[0]
    mov  [r8 + 4],  ebx         # out[1]
    mov  [r8 + 8],  ecx         # out[2]
    mov  [r8 + 12], edx         # out[3]
    pop  rbx
    ret
.seh_endproc
```

Когда пишешь обёртку, задай себе три вопроса. Это и есть метод.

**1. Где инструкция берёт данные?** `cpuid` берёт номер листа из `EAX`
и номер подлиста из `ECX` (глава 33). А наш аргумент `leaf` пришёл
в `ECX`. Значит, сначала переложить `ECX` → `EAX`, а потом обнулить
`ECX`. Порядок важен: если сначала обнулить `ECX`, номер листа
пропадёт. `xor ecx, ecx` — привычный способ обнулить регистр
(глава 10).

**2. Что инструкция портит?** Все четыре: `EAX`, `EBX`, `ECX`, `EDX`.
Из них `RBX` сохраняемый — значит, `push rbx` / `pop rbx` (П2.5 —
ты уже знаешь, что бывает без них). А `RDX` летучий, его портить
можно. Но в нём лежит наш второй аргумент — адрес `out`! Поэтому
**до** `cpuid` переложим его в регистр, который `cpuid` не трогает, —
в `R8`. Он летучий, сохранять его не надо.

**3. Куда положить результат?** `out` — массив из четырёх `uint32_t`
(глава 4). Каждый элемент — 4 байта, значит, адреса элементов —
`out + 0`, `out + 4`, `out + 8`, `out + 12`. Запись `mov [r8 + 4], ebx`
кладёт 4 байта, потому что `EBX` — 32-битный регистр: размер записи
ассемблер берёт из размера регистра.

Функция трогает стек (`push`), поэтому у неё есть директивы `.seh_`
(П2.7). Место на стеке она не выделяет и никого не вызывает, поэтому
`sub rsp` ей не нужен.

### `my_rdtsc`

```
# uint64_t my_rdtsc(void)
.globl my_rdtsc
my_rdtsc:
    rdtsc                       # edx:eax = счётчик
    shl  rdx, 32                # старшая половина вверх
    or   rax, rdx               # склеить в rax
    ret
```

`rdtsc` (Read Time-Stamp Counter `[рид тайм-стэмп кáунтер]`,
«прочитать счётчик тактов») читает счётчик, который процессор
увеличивает с постоянной частотой, пока компьютер включён. Им удобно
мерить, сколько времени заняла работа: прочитал до, прочитал после,
вычел. У компилятора для неё есть встроенная функция `__rdtsc`,
а мы напишем свою. Счётчик у неё
64-битный, но по традиции ещё из 32-битных времён она отдаёт его
**двумя половинами**: младшие 32 бита в `EAX`, старшие — в `EDX`.
Такую пару пишут через двоеточие: `EDX:EAX`. Верхние половины `RAX`
и `RDX` она при этом обнуляет.

Склеить две половины в одно 64-битное число — это рецепт из П1.2:

```
RDX = 0000000000000123      старшая половина
RAX = 00000000ABCDEF00      младшая половина

shl rdx, 32   →  RDX = 00000123 00000000     сдвинули на 32 бита влево
or  rax, rdx  →  RAX = 00000123 ABCDEF00     сложили без переносов
```

На C это была бы строчка `((uint64_t)hi << 32) | lo`. Та же мысль,
только руками.

Эта функция — **листовая**: ничего не кладёт на стек и никого не
вызывает. Портит только летучие `RAX` и `RDX`. Поэтому ни `push`,
ни директив `.seh_` ей не нужно.

## П2.9. Снимок регистров: ассемблер сохраняет, C разбирает

Самая важная функция приложения. Она сохраняет **все 16 регистров
общего назначения** в структуру C:

```
# void snapshot(REGS *out)
#   rcx = out
.globl snapshot
snapshot:
    mov  [rcx + 0x00], rax
    mov  [rcx + 0x08], rcx
    mov  [rcx + 0x10], rdx
    mov  [rcx + 0x18], rbx
    lea  rax, [rsp + 8]         # rsp до call (без адреса возврата)
    mov  [rcx + 0x20], rax
    mov  [rcx + 0x28], rbp
    mov  [rcx + 0x30], rsi
    mov  [rcx + 0x38], rdi
    mov  [rcx + 0x40], r8
    mov  [rcx + 0x48], r9
    mov  [rcx + 0x50], r10
    mov  [rcx + 0x58], r11
    mov  [rcx + 0x60], r12
    mov  [rcx + 0x68], r13
    mov  [rcx + 0x70], r14
    mov  [rcx + 0x78], r15
    ret
```

А вот структура на C, в которую она пишет:

```c
typedef struct {
    uint64_t rax, rcx, rdx, rbx, rsp, rbp, rsi, rdi;
    uint64_t r8,  r9,  r10, r11, r12, r13, r14, r15;
} REGS;
```

Главное здесь — **договор о смещениях**. Вспомни П1.4: поле структуры —
это «база плюс смещение». Шестнадцать полей по 8 байт, без дырок
(все одного размера, выравнивать нечего), значит:

| Поле | Смещение | В `snapshot` |
|---|---|---|
| `rax` | `0x00` | `[rcx + 0x00]` |
| `rcx` | `0x08` | `[rcx + 0x08]` |
| `rdx` | `0x10` | `[rcx + 0x10]` |
| … | +8 на каждое поле | … |
| `r15` | `0x78` = 120 | `[rcx + 0x78]` |

`sizeof(REGS)` = 16 × 8 = **128** байт. Ассемблер ничего не знает
о структуре C, он просто пишет по адресам. Если порядок полей
в структуре и порядок смещений в `.s` разойдутся, C прочитает `RBX`
там, где лежит `RSI`, и никто тебя не предупредит. Это тот же
«договор», что с прототипом в П2.3.

Три тонких места, над которыми стоит подумать.

**1. Почему `RAX` сохраняется первым?** Потому что дальше мы
используем `RAX` как черновик для `RSP`. Правило снимка: **сначала
сохрани регистр, потом пользуйся им**. Сохранили бы `RAX` после
`lea rax, ...` — в снимок попал бы не настоящий `RAX`, а наш черновик.

**2. Почему `[rsp + 8]`?** В момент, когда работает `snapshot`, на
вершине стека лежит адрес возврата, который туда положил `call`
(глава 11). А нам интересно, каким `RSP` был у **вызывающего** —
до `call`. Это на 8 байт выше.

**3. Что лежит в `rcx`?** Адрес самой структуры: `RCX` — это наш
аргумент `out`. Звучит забавно, зато это отличная **проверка**: если
в снимке `rcx` совпал с адресом структуры, значит, смещения
в порядке и мы пишем туда, куда думаем.

Зачем всё это? Представь место, куда процессор передаёт управление
**сам**, а не через `call` из твоего кода. Например, обработчик
прерывания из главы 34: процессор прыгнул туда посреди чужой работы,
и все регистры ещё хранят значения того кода, который прервали. Если
первая же строчка на C их испортит, прерванный код не сможет
продолжить. Поэтому такой обработчик всегда начинается с кусочка
на ассемблере, который **сначала сохраняет все регистры** в
структуру, **потом** зовёт функцию на C и передаёт ей адрес этой
структуры, а **после** возвращает все регистры на место.

`snapshot` — первая половина такого кусочка. В твоём гипервизоре
будет место ровно такого рода, и ты напишешь его по этому образцу.

## П2.10. Проект: свой маленький `intrin.h`

Соберём всё в программу из трёх файлов, как в П1.6.

**`cpu.h`** — договор, то есть прототипы и структура:

```c
// cpu.h — наши функции на ассемблере (живут в cpu.s)
#pragma once
#include <stdint.h>

// Снимок регистров общего назначения — в том порядке,
// в котором их сохраняет snapshot()
typedef struct {
    uint64_t rax, rcx, rdx, rbx, rsp, rbp, rsi, rdi;
    uint64_t r8,  r9,  r10, r11, r12, r13, r14, r15;
} REGS;

void     my_cpuid(uint32_t leaf, uint32_t out[4]); // EAX, EBX, ECX, EDX
uint64_t my_rdtsc(void);                           // счётчик тактов
void     snapshot(REGS *out);                      // все 16 регистров
```

**`cpu.s`** — первая строка `.intel_syntax noprefix`, потом `.text`,
потом три функции из П2.8 и П2.9 подряд.

**`main.c`** — пробует все три:

```c
#include <stdio.h>
#include <string.h>
#include "cpu.h"

int main(void)
{
    uint32_t r[4];
    char vendor[13];

    // 1. Свой cpuid: имя производителя (как в главе 33)
    my_cpuid(0, r);
    memcpy(vendor + 0, &r[1], 4);   // EBX
    memcpy(vendor + 4, &r[3], 4);   // EDX
    memcpy(vendor + 8, &r[2], 4);   // ECX
    vendor[12] = 0;
    printf("vendor  %s\n", vendor);

    // 2. Свой rdtsc: сколько тактов идёт один printf
    uint64_t t0 = my_rdtsc();
    printf("hello\n");
    uint64_t t1 = my_rdtsc();
    printf("printf  %llu ticks\n", (unsigned long long)(t1 - t0));

    // 3. Снимок регистров
    REGS g;
    snapshot(&g);
    printf("rcx     %016llx\n", (unsigned long long)g.rcx);
    printf("&g      %016llx\n", (unsigned long long)(uintptr_t)&g);
    printf("rsp     %016llx\n", (unsigned long long)g.rsp);
    printf("sizeof  %d\n", (int)sizeof(REGS));
    return 0;
}
```

`%016llx` — печать в шестнадцатеричном виде ровно 16 знаками,
с ведущими нулями. Так адреса удобно сравнивать глазами.

Собери и запусти:

```
gcc -Wall -O0 -o cpu.exe main.c cpu.s
./cpu.exe
```

Вот **настоящий** вывод той же программы на облачном сервере. Запустить
`.exe` там нельзя, поэтому я собрал копию под Linux. В ней объявления
функций помечены так, чтобы вызов шёл **по правилам Windows**, и
файл `.s` тот же самый, так что проверена именно твоя логика:

```
vendor  GenuineIntel
hello
printf  5070 ticks
rcx     00007fff0f924960
&g      00007fff0f924960
rsp     00007fff0f924930
sizeof  128
```

Что проверяем по выводу:

- `vendor GenuineIntel` — наш `cpuid` работает и `RBX` читается
  правильно. На Ryzen будет `AuthenticAMD`.
- `printf ... ticks` — число зависит от всего на свете. У тебя будет
  другое, в консоли Windows, скорее всего, больше. Запусти несколько
  раз и посмотри, как оно скачет.
- `rcx` **равен** `&g` — смещения в `snapshot` совпадают со структурой.
  Если бы они разошлись, в поле `rcx` оказалось бы значение другого
  регистра, и ты сразу увидел бы разницу.
- `rsp` чуть **меньше** `&g`. Это логично: `g` — локальная переменная
  `main`, она лежит в кадре стека `main` (глава 11), а `RSP` указывает
  на его нижний край. Стек растёт вниз.
- `sizeof 128` — как мы и посчитали.

У тебя адреса будут другими: Windows сама выбирает, где будет стек.
Но `rcx` и `&g` обязаны **совпасть**, а `rsp` — оказаться чуть ниже.

## П2.11. Как отлаживать свой ассемблер

Когда функция на ассемблере не работает, лучший друг — x64dbg
(глава 13). Самый простой способ остановиться в своей функции —
**поставить точку останова прямо в коде**. Временно допиши первой
строкой функции:

```
my_cpuid:
    int3                        # ВРЕМЕННО: остановиться здесь
    push rbx
    ...
```

`int3` — та самая инструкция точки останова из глав 13 и 34 (вектор 3).
Запусти `cpu.exe` в x64dbg и жми **F9**: программа остановится прямо
на твоей функции. Дальше по шагам (**F7**/**F8**) смотри на панель
регистров справа. Что проверять:

1. **При входе:** аргументы там, где ты думаешь? `RCX` — первый,
   `RDX` — второй.
2. **Перед `ret`:** `RSP` такой же, как был при входе? Каждый
   сохраняемый регистр, который ты трогал, вернулся к прежнему
   значению? Запиши их значения при входе на бумажку и сравни.
3. **После возврата:** в `RAX` твой ответ?

Проверка пункта 2 ловит обе самые частые ошибки этого приложения:
забытый `pop` (П2.5) и сдвинутый стек (П2.6).

Не забудь **убрать `int3`**, когда закончишь. Без отладчика эта
инструкция вызовет исключение `0x80000003` (глава 34), и программа
закроется.

## П2.12. То же самое в MASM для Visual Studio

Всё приложение мы писали в синтаксисе ассемблера `gcc` из w64devkit:
он у тебя уже стоит (глава 6), и всё можно проверить сразу. Драйверы
же собирают в **Visual Studio** (глава 29), и там ассемблер другой —
**MASM** (Microsoft Macro Assembler `[мáкроу эсéмблер]`, «макро-ассемблер
Microsoft»). Для 64-битного кода его программа называется `ml64.exe`,
а файлы — `.asm`. Инструкции те же самые, отличается только
«обвязка».

Вот `my_cpuid` в MASM:

```
; my_cpuid.asm — MASM, Visual Studio
.code

; void my_cpuid(uint32_t leaf, uint32_t out[4])
my_cpuid PROC FRAME
    push rbx                    ; cpuid портит rbx, а он чужой
    .pushreg rbx
    .endprolog
    mov  r8, rdx                ; out -> r8: cpuid затрёт rdx
    mov  eax, ecx               ; номер листа -> eax
    xor  ecx, ecx               ; подлист 0
    cpuid
    mov  [r8],      eax
    mov  [r8 + 4],  ebx
    mov  [r8 + 8],  ecx
    mov  [r8 + 12], edx
    pop  rbx
    ret
my_cpuid ENDP

END
```

Словарь перевода:

| w64devkit (`gcc`, файл `.s`) | MASM (`ml64`, файл `.asm`) | Что значит |
|---|---|---|
| `.intel_syntax noprefix` | не нужно: MASM всегда в синтаксисе Intel | синтаксис |
| `# комментарий` | `; комментарий` | комментарий |
| `.text` | `.code` | начинается код |
| `.globl имя` + `имя:` | `имя PROC` … `имя ENDP` | функция, видная снаружи |
| `.seh_proc` … `.seh_endproc` | `PROC FRAME` … `ENDP` | функция с описанием пролога |
| `.seh_pushreg rbx` | `.pushreg rbx` | пролог сделал `push rbx` |
| `.seh_stackalloc 32` | `.allocstack 32` | пролог отнял 32 байта |
| `.seh_endprologue` | `.endprolog` | пролог закончен |
| `0x20` | `20h` | шестнадцатеричное число |
| — | `END` в конце файла | конец файла |

Как видишь, директивы `.seh_` у `gcc` и директивы пролога у MASM —
это одно и то же, только по-разному написано. Оба ассемблера строят
из них одну и ту же таблицу `.pdata`.

Как добавить файл `.asm` в проект Visual Studio — по документации
Microsoft:

1. В меню **Project** («Проект») выбери **Build Customizations**
   («Настройки сборки»).
2. В окне поставь галочку **masm(.targets,.props)** и нажми **OK**.
3. **Project** → **Add New Item** («Добавить новый элемент»), выбери
   **C++ File (.cpp)**, но в поле **Name** («Имя») напиши имя
   с расширением `.asm` вместо `.cpp`.
4. Пиши код. При сборке Visual Studio сама вызовет `ml64.exe` и
   склеит результат с остальным проектом.

Одна оговорка для C++: если проект на C++, а не на C, прототип надо
пометить `extern "C"`, иначе C++ исказит имя функции и компоновщик
её не найдёт. В проектах на C этого не нужно.

Честно: MASM-вариант я сверил с документацией Microsoft, но собрать
его в контейнере нечем, там нет Visual Studio. Когда в главе 29
у тебя появится Visual Studio, собери этот файл первым делом. Если
ассемблер на что-то ругнётся, пришли мне сообщение, разберём.

## П2.13. Что запомнить

1. Функцию на ассемблере пишут в отдельном файле (`.s` для `gcc`,
   `.asm` для MASM). В Visual Studio для x64 это **единственный**
   способ: вставок там нет.
2. Файл начинается с `.intel_syntax noprefix` и `.text`. Имя функции —
   метка, снаружи её видно только после `.globl`. Комментарии в `.s` —
   через `#`.
3. `undefined reference` — компоновщик не нашёл имя. Проверь `.globl`.
4. Прототип в C — договор. Компоновщик сверяет только имя, аргументы
   не проверяет никто, кроме тебя.
5. Летучие регистры (`RAX`, `RCX`, `RDX`, `R8`–`R11`) можно портить.
   Сохраняемые (`RBX`, `RBP`, `RDI`, `RSI`, `R12`–`R15`) — вернуть
   к `ret`, `pop` в обратном порядке.
6. Забытый сохраняемый регистр ломает **чужой** код, **тихо**, и часто
   **только с оптимизацией**.
7. При входе в функцию `RSP` mod 16 = 8. Перед `call`: 8 + всё, что
   положила функция, должно делиться на 16. Теневое пространство —
   32 байта.
8. Функция трогает стек — описывай пролог директивами `.seh_`
   (в MASM — `PROC FRAME`, `.pushreg`, `.allocstack`, `.endprolog`).
   Листовой функции это не нужно.
9. Обёртка для инструкции — три вопроса: откуда она берёт данные,
   что портит, куда класть результат.
10. Снимок регистров: сначала сохранить, потом пользоваться. Смещения
    в `.s` и поля структуры в C обязаны совпадать.
