# Глава 2. Что такое программа

> **Часть I. Фундамент**
> Предыдущая глава: [1. Как устроен компьютер](01-kak-ustroen-kompyuter.md)

В прошлой главе мы выяснили, что процессор исполняет числа. Теперь разберёмся,
откуда эти числа берутся — то есть как исходный код превращается в `.exe`.

Это самая важная глава первой части. Реверс-инжиниринг — это движение
**назад** по конвейеру компиляции. Чтобы идти назад, надо сначала понять,
как идут вперёд.

---

## 2.1. Что такое программа на самом деле

Открой любой `.exe` в текстовом редакторе — увидишь мусор:

```
MZ......ÿÿ..¸.......@...................................€...
º..´.Í!¸.LÍ!This program cannot be run in DOS mode.
```

Это не поломка. Это и есть программа — байты, которые редактор честно пытается
показать как текст. Большинство из них текстом не являются, отсюда каракули.

> **Программа — это файл, в котором лежат числа. Часть этих чисел процессор
> будет исполнять как инструкции, часть программа будет читать как данные.**

Всё. Никакой другой магии в `.exe` нет.

## 2.2. Зачем нужны языки программирования

Можно ли писать программу прямо числами? Можно. Так и делали в 1950-х.
Выглядело это примерно так:

```
8d 04 11 c3
```

Четыре байта, которые складывают два числа и возвращают результат. Работает
отлично. Проблема одна: **человек так писать не может**. Точнее, может, но со
скоростью одна строка в час и с ошибкой в каждой третьей.

Поэтому придумали слои посредников.

**Ассемблер** — те же самые инструкции, но записанные словами:

```asm
lea eax, [rcx+rdx]
ret
```

Уже читаемо. Каждая строка — ровно одна машинная инструкция, перевод
однозначен в обе стороны. Но всё ещё очень мелко: чтобы написать что-то
полезное, нужны тысячи строк.

**Языки высокого уровня** — C, C++, Python — позволяют писать смыслом,
а не инструкциями:

```c
int add(int a, int b)
{
    int result = a + b;
    return result;
}
```

Четыре строки вместо десятков. Понятно с первого взгляда. Но процессор этого
не понимает — нужен переводчик.

## 2.3. Конвейер компиляции

Переводчик называется **компилятор** (compiler). Работает он не одним махом,
а конвейером из четырёх станков:

```
   твой код
   add.c
      │
      ▼
┌─────────────────┐
│ 1. ПРЕПРОЦЕССОР │   подставляет #include, разворачивает #define
│  (preprocessor) │   результат — тот же C, но «развёрнутый»
└────────┬────────┘
         ▼
┌─────────────────┐
│ 2. КОМПИЛЯТОР   │   переводит C в ассемблер
│   (compiler)    │   здесь же происходит ОПТИМИЗАЦИЯ
└────────┬────────┘
         ▼
┌─────────────────┐
│ 3. АССЕМБЛЕР    │   переводит ассемблер в машинный код
│   (assembler)   │   результат — объектный файл .o / .obj
└────────┬────────┘
         ▼
┌─────────────────┐
│ 4. КОМПОНОВЩИК  │   склеивает объектные файлы и библиотеки,
│    (linker)     │   расставляет адреса, добавляет заголовок PE
└────────┬────────┘
         ▼
    add.exe
```

Запомни слово **linker** `[линкер]` — компоновщик. Он делает вещь, важную для
нас: берёт куски кода и **расставляет им окончательные адреса**. До линковки
код ещё «плавает», после — прибит к конкретным адресам.

## 2.4. Смотрим своими глазами

Вот та самая функция из 2.2:

```c
int add(int a, int b)
{
    int result = a + b;   /* складываем и возвращаем */
    return result;
}
```

Попросим компилятор остановиться на шаге 2 и показать ассемблер. Вот что
он выдаёт **без оптимизации**:

```asm
add:
    push  rbp                      ; сохранить старую точку опоры
    mov   rbp, rsp                 ; поставить новую
    sub   rsp, 16                  ; выделить 16 байт под локальные данные
    mov   DWORD PTR [rbp+16], ecx  ; сохранить аргумент a
    mov   DWORD PTR [rbp+24], edx  ; сохранить аргумент b
    mov   edx, DWORD PTR [rbp+16]  ; загрузить a обратно
    mov   eax, DWORD PTR [rbp+24]  ; загрузить b обратно
    add   eax, edx                 ; сложить
    mov   DWORD PTR [rbp-4], eax   ; сохранить в переменную result
    mov   eax, DWORD PTR [rbp-4]   ; загрузить result обратно
    add   rsp, 16                  ; вернуть выделенную память
    pop   rbp                      ; восстановить точку опоры
    ret                            ; вернуться
```

Тринадцать инструкций вместо одной строки на C. Сейчас ты не обязан понимать
каждую — разберём в части IV. Обрати внимание на другое: компилятор
**буквально** выполнил то, что написано. Создал переменную `result`, положил
в неё сумму, потом прочитал обратно. Бессмысленная возня, зато один в один
по исходнику.

А теперь то же самое **с оптимизацией**:

```asm
add:
    lea   eax, [rcx+rdx]   ; сложить два аргумента прямо в результат
    ret                    ; вернуться
```

**Две** инструкции. В машинном коде — четыре байта:

```
8d 04 11    lea eax,[rcx+rdx]
c3          ret
```

Компилятор понял, что переменная `result` не нужна, что сохранять аргументы
в память незачем, что всю операцию можно сделать одной инструкцией. Результат
тот же, кода в восемь раз меньше.

> Сравни размеры: без оптимизации функция занимает **33 байта**,
> с оптимизацией — **4 байта**. Один и тот же исходник.

Вот первый практический вывод для реверса:

> **По машинному коду нельзя восстановить исходник. Можно восстановить только
> смысл.**

Обе версии выше — это `return a + b`. Но выглядят они совершенно по-разному,
и обратно к одной и той же строке C ты придёшь только головой, а не
инструментом.

## 2.5. Что теряется при компиляции — главное в главе

Посмотри ещё раз на исходник и на результат. Что исчезло?

**1. Комментарии.** `/* складываем и возвращаем */` не превратился ни во что.
Комментарии существуют только для человека, компилятор их выбрасывает
на первом же шаге. **Восстановить невозможно в принципе.**

**2. Имена.** Функция `add` в примере имя сохранила, но переменные `a`, `b`,
`result` исчезли бесследно — вместо них адреса `[rbp+16]`, `[rbp+24]`,
`[rbp-4]`. В реальном `.exe` обычно исчезают и имена функций: вместо
`check_password` ты увидишь `sub_401A20` — «функция по адресу 401A20».

**3. Типы.** В исходнике было `int`. В машинном коде типов нет вообще —
есть только размеры. Число `5` и буква `5` выглядят одинаково; отличить
их можно только по тому, что программа с ними делает.

**4. Структура.** Границы функций, вложенность циклов, где кончался `if` —
всё это в машинном коде не отмечено. Есть только переходы по адресам.
Дизассемблер восстанавливает структуру **догадками**, и иногда ошибается.

Итого:

```
        ┌──────────────────────────────────────┐
        │  Исходный код на C                   │
        │  • имена • типы • комментарии        │
        │  • структура • намерение автора      │
        └───────────────┬──────────────────────┘
                        │  компиляция
                        │  ⟹ необратимая потеря
                        ▼
        ┌──────────────────────────────────────┐
        │  Машинный код                        │
        │  • инструкции • адреса • числа       │
        └──────────────────────────────────────┘
```

Компиляция — это как перевести книгу на другой язык, потом сжечь оригинал.
Смысл сохранился, авторский стиль — нет.

**Поэтому реверс-инжиниринг — работа творческая, а не механическая.**
Инструмент вернёт тебе инструкции. Понять, что `sub_401A20` — это проверка
пароля, и назвать её так, можешь только ты.

## 2.6. Отладочная информация

Есть исключение из «имена теряются». Компилятор умеет складывать имена
переменных, номера строк исходника и структуру функций в отдельный файл —
**отладочную информацию** (debug info). В Windows это файлы `.pdb`.

Если разработчик случайно выложил `.pdb` вместе с программой, анализ
упрощается в разы: ты видишь настоящие имена. Это редкая удача, но проверять
стоит всегда.

Внутри компании такие файлы есть всегда — иначе невозможно разбираться
в сбоях у пользователей. Наружу их обычно не отдают.

## 2.7. Почему `hello.exe` весит 250 килобайт

Смотри на реальные числа. Берём самую маленькую программу на свете:

```c
#include <stdio.h>
int main(void) { printf("Hello\n"); return 0; }
```

Исходник — **63 байта**. Собранный `.exe` — **249 671 байт**. В четыре тысячи
раз больше. Откуда?

Потому что `printf` ты не писал. Эту функцию написали до тебя, она лежит
в **библиотеке** (library), и компоновщик вкладывает её в твою программу.
А `printf` тянет за собой обработку форматов, работу с буферами, и так далее.

Есть два способа подключать чужой код:

**Статическая линковка** (static linking) — чужой код **копируется внутрь**
твоего `.exe`. Файл толстый, зато самодостаточный: работает на любой машине.

**Динамическая линковка** (dynamic linking) — внутрь кладётся только
**список нужных функций**, а сам код берётся при запуске из `.dll`. Файл
маленький, но без нужных `.dll` не запустится.

Windows использует в основном второй способ: `kernel32.dll`, `user32.dll` и
их родня лежат в системе и общие для всех программ.

Для нас это важно вот чем:

> Список импортируемых функций — **лучшая подсказка о том, что программа
> делает**. Видишь `CreateFileW` — работает с файлами. `RegOpenKeyExW` —
> лезет в реестр. `socket`, `connect` — ходит в сеть.

Это первое, что смотрят при анализе. Займёмся этим в главе 8.

И ещё: те же 250 КБ после удаления таблицы символов (`strip`) сжимаются
до **39 424 байт**. Шесть седьмых файла были именами и отладочными данными —
то есть подарком реверсеру, который разработчик обычно не делает.

## 2.8. Компилируемые и интерпретируемые языки

Не все языки проходят через конвейер целиком.

**Компилируемые** (C, C++, Rust, Go) — превращаются в машинный код заранее.
Результат — обычный `.exe`, процессор исполняет его напрямую. **Это наша
основная цель в курсе.**

**Интерпретируемые** (Python, JavaScript, PHP) — не компилируются.
Программа-интерпретатор читает исходник и выполняет его на ходу. Реверсить
там нечего: исходник и так перед тобой.

**Промежуточные** (C#, Java) — компилируются не в машинный код, а в
**байт-код** — инструкции выдуманного процессора, который исполняет
виртуальная машина. Это важный случай: байт-код хранит гораздо больше
информации, чем машинный код, и восстанавливается почти до исходника.
Для C# есть инструмент dnSpy, который показывает практически оригинальный код.

Практический вывод:

| Чем написано | Сложность реверса |
|---|---|
| C, C++, Rust, Go | **Высокая** — работаем с машинным кодом |
| C#, Java | Низкая — байт-код восстанавливается почти дословно |
| Python, JS | Почти нулевая — исходник открыт |

Если тебе однажды дадут `.exe`, а внутри окажется C# — считай, повезло.
Определять это научимся в главе 7 (инструмент Detect It Easy).

## 2.9. Что всё это значит для реверса

Соберём выводы главы:

1. **Программа — это числа в файле.** Часть исполняется, часть читается.
2. **Компиляция необратима.** Комментарии, имена, типы и структура теряются
   навсегда.
3. **Один исходник даёт разный машинный код** в зависимости от компилятора и
   уровня оптимизации. Не ищи «тот самый» правильный вид.
4. **Оптимизированный код не похож на исходник.** Компилятор переставляет,
   выбрасывает и сливает куски. Это главная причина, почему реверс тяжёлый.
5. **Смысл восстановить можно.** Он никуда не делся — программа же работает.
6. **Импорты — самая быстрая подсказка** о назначении программы.

И главная мысль, к которой стоит вернуться через пару месяцев:

> Задача реверсера — не «получить исходный код обратно». Такой цели не
> существует. Задача — **понять, что программа делает**, и записать это
> понимание так, чтобы им можно было пользоваться.
