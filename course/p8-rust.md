таблицы виртуальных функций, длинные имена. Теперь второй большой
язык системного программирования — **Rust** `[раст]` («ржавчина»).
Он молодой: первая стабильная версия вышла в 2015 году. Rust обещает

Программы на Rust, в том числе вредоносные, попадаются всё чаще,

Честно о работе. В двенадцати вакансиях hh.ru, которые мы разбирали
(П9), Rust не просил никто. Ты попросил его сам, и это разумно
на будущее. Поэтому учим в объёме «читаю код и узнаю в дизассемблере»,
а писать на Rust большие программы не будем.

После приложения ты будешь уметь:

- читать простой код на Rust: переменные, функции, `match`, `Option`,
  `Result`;
- узнавать в листинге **срез** — два регистра, адрес и длину —
  и проверку границ с вызовом **паники**;
- знать, как в памяти лежат `Vec` и `String`, и почему их порядок

  версию компилятора;
- читать имена функций Rust в двух видах: старом `_ZN…E` и новом `_R…`;
- находить свой `main` за стартовым кодом Rust.

Приложение длинное. Проходи его **в три захода**:

1. **П8.1–П8.4** — зачем, чем собирать, язык на пальцах, владение

2. **П8.5–П8.8** — срез в машинном коде, `Vec` и `String` в памяти,

3. **П8.9–П8.13** — имена функций, путь до `main`, строки и сравнения,

Как я проверял. Весь машинный код в приложении выдал настоящий
компилятор **rustc 1.99.0** (вышел 1 октября 2026) на сайте godbolt.org
для цели `x86_64-pc-windows-msvc` — это Windows x64, как у тебя.
Вывод программ проверен их запуском там же. Собрать `.exe` целиком

предупреждение. Компилятор Rust меняет машинный код от версии к версии
заметнее, чем gcc. Листинг в главе — «так было у rustc 1.99», у тебя
он может отличаться в мелочах. Приметы, по которым узнают Rust, —
два регистра у среза, вызов паники, строки без нуля в конце — от версии
не зависят.

## П8.1. Зачем реверсеру Rust

Главное отличие Rust от C — не в синтаксисе, а в том, **когда**
ловятся ошибки с памятью.

- В C программист сам следит, чтобы не выйти за границу массива
  и не прочитать освобождённую память. Ошибся — программа молча портит
  память. Иногда это просто сбой, а иногда — дыра, через которую
  захватывают программу (глава 11.8).
- В Rust большую часть таких ошибок ловит **компилятор** ещё при сборке.
  А то, что можно проверить только во время работы, — например, номер
  элемента массива, — программа проверяет сама и при ошибке
  **паникует** — panic `[пэ́ник]`: аккуратно останавливается
  с сообщением, вместо того чтобы портить память.

Что из этого следует для реверсера:

| Особенность Rust | Что ты увидишь в дизассемблере |
|---|---|
| проверка границ при обращении к элементу | `cmp` с длиной и прыжок к вызову `panic_bounds_check` |
| паника вместо порчи памяти | много вызовов функций `core::panicking::…` и строки сообщений |
| стандартная библиотека вшита в файл | даже «привет, мир» весит больше сотни килобайт |
| свои правила хранения строк | строки лежат **без нуля** в конце, подряд |
| свои имена функций | `_ZN…17h…E` у старых версий, `_R…` у новых |

Пример из жизни. Исследователь нашёл ошибку в том самом
`win32kbase_rs.sys`: выход за границу массива. На C такая ошибка могла
бы стать дырой для захвата системы. В Rust сработала проверка границ,
`panic_bounds_check` — и Windows упала с синим экраном
`SYSTEM_SERVICE_EXCEPTION`. Неприятно, но безопасно: память
не испорчена, захватить нечего. Об этом рассказывал Марк Руссинович,
технический директор Microsoft Azure, на конференции RustConf 2025.
Через пару разделов ты увидишь этот самый вызов `panic_bounds_check`
своими глазами.

## П8.2. Чем собирать

Rust ставится программой **rustup** `[раст-ап]`. Качай её только
с официального сайта **rustup.rs** (правило из главы 6.2), файл
`rustup-init.exe`.

Rust для Windows пользуется компоновщиком Microsoft (глава 2: компоновщик
собирает `.exe` из частей). Поэтому `rustup-init` сначала проверит,
есть ли у тебя Visual Studio. Если нет — **сам предложит её поставить**:
бесплатную Community, с набором **Desktop Development with C++**
(«разработка классических приложений на C++»). Соглашайся. Если Visual
Studio у тебя уже стоит после главы 29 — ничего доставлять не нужно.

Проверка, что всё встало, в новой консоли:

```
rustc --version
cargo --version
```

**rustc** `[раст-си]` — сам компилятор. **cargo** `[кáрго]` («груз») —
сборщик проектов: создаёт папки, собирает, скачивает библиотеки.
Им и пользуются почти всегда.

Первый проект:

```
cargo new zadacha_rust
cd zadacha_rust
cargo build
```

`cargo new` создаёт папку с файлом настроек `Cargo.toml` и исходником
`src\main.rs` — там уже лежит «привет, мир». `cargo build` собирает
**отладочную** сборку в `target\debug\zadacha_rust.exe`. Команда
`cargo build --release` собирает **релизную** — с оптимизацией —
в `target\release\`. Разница между ними для реверсера большая, её мы
разберём в П8.11.

Попробовать без установки можно и на godbolt.org, как в главе 5:
язык **Rust**, компилятор **rustc 1.99.0**, флаги
`--target x86_64-pc-windows-msvc -C opt-level=0`. Для отдельной функции
без `main` допиши `--crate-type lib`.

## П8.3. Язык на пальцах

Ты знаешь C, поэтому покажу Rust через него:

| На C | На Rust | Что значит |
|---|---|---|
| `int x = 5;` | `let x: i32 = 5;` | переменная. В Rust её **нельзя менять**, пока не скажешь иначе |
| `int y = 5; y++;` | `let mut y = 5; y += 1;` | `mut` (mutable, «изменяемая») — менять можно |
| `uint8_t`, `uint32_t` | `u8`, `u32` | числа без знака, цифра — сколько бит |
| `int64_t` | `i64` | число со знаком, 64 бита |
| `size_t` | `usize` | размер или номер элемента, на x64 — 8 байт |
| `int add(int a, int b) { return a + b; }` | `fn add(a: i32, b: i32) -> i32 { a + b }` | функция. Последнее выражение без `;` — то, что она возвращает |
| `for (i = 0; i < n; i++)` | `for i in 0..n` | `0..n` — от 0 до `n`, **не включая** `n` |
| `switch` | `match` | выбор по значению, разберём ниже |
| `printf("%d\n", x);` | `println!("{}", x);` | печать. `!` — это **макрос**, а `{}` — место для значения |

Типы можно не писать: в `let mut y = 5;` компилятор сам решил, что `y` —
это `i32`. А вот `match` стоит разобрать:

```rust
fn name(code: u8) -> &'static str {
    match code {
        1 => "privet",
        2 => "vopros",
        _ => "neizvestno",
    }
}
```

Читается так: «посмотри на `code`; если 1 — верни `"privet"`, если 2 —
`"vopros"`, иначе — `"neizvestno"`». `_` — «всё остальное», как `default`
в `switch` (глава 20). Компилятор требует, чтобы `match` покрывал **все**
случаи. Забыл `_` — программа не соберётся. `&'static str` — тип
«ссылка на строку, которая живёт всю программу». Такие строки лежат
в файле, в секции данных только для чтения (глава 4).

## П8.4. Владение и заимствование

Это главное, чем Rust отличается от C. Объясню на пальцах, полный
разбор — в книге «The Rust Programming Language» (П8.13).

**Владение.** У каждого значения ровно один **владелец** — переменная.
Когда владелец выходит из своего блока `{ … }`, Rust сам освобождает
его память. Как деструктор из П7.4, только его не нужно писать.
В машинном коде ты увидишь в конце функций вызовы освобождения —
`__rust_dealloc` — и функции с именами вроде `drop_in_place`
или `drop_glue` («склейка удаления»).

**Заимствование.** Иногда значение нужно дать посмотреть, не отдавая
насовсем. Для этого есть **ссылки**:

- `&x` — «дай посмотреть»: читать можно, менять нельзя;
- `&mut x` — «дай поменять».

Правило простое: в каждый момент может быть **либо сколько угодно
читателей, либо один писатель**. Нарушил — программа не соберётся.

```rust
fn total(v: &Vec<u32>) -> u32 {
    let mut s = 0;
    for x in v {
        s += x;
    }
    s
}
```

Функция берёт вектор (П8.6) «посмотреть», складывает элементы
и возвращает сумму. Для `vec![1, 2, 3]` получится 6 — я запустил.

А теперь самое важное для реверсера. **Все эти правила проверяет
только компилятор, при сборке.** В готовом `.exe` от них не остаётся
ничего: `&v` — это просто адрес в регистре, как указатель в C (глава 4).
Владельцев и заимствований в машинном коде нет. Зато есть то, что
Rust проверяет **во время работы**, — к этому и переходим.

## П8.5. Срез в машинном коде

**Срез** — slice, как в П6, — это кусок массива: «отсюда, столько-то
элементов». В Rust он записывается `&[u32]` (срез чисел)
или `&str` (срез текста). Внутри срез — это **два числа**: адрес
начала и длина. Не одно, как указатель в C, а два. Отсюда главная
примета Rust в листинге.

Функция, которая берёт третий элемент среза (счёт с нуля, поэтому
номер 2):

```rust
pub fn third(v: &[u32]) -> u32 {
    v[2]
}
```

Релизная сборка, rustc 1.99, Windows x64:

```
third:
        sub     rsp, 40
        cmp     rdx, 3                   ; длина < 3?
        jb      .LBB6_2                  ; да — паника
        mov     eax, dword ptr [rcx + 8] ; v[2]: адрес + 2 × 4 байта
        add     rsp, 40
        ret
.LBB6_2:
        lea     r8, [rip + …]            ; где в исходнике ошибка
        mov     ecx, 2                   ; какой номер просили
        call    core::panicking::panic_bounds_check
        ud2
```

Читаем по главе 12. Первый аргумент пришёл в `RCX`, второй — в `RDX`.
Но аргумент у функции один — срез! Rust разложил его на два регистра:
`RCX` — **адрес начала**, `RDX` — **длина**.

Дальше — **проверка границ** (bounds check). Чтобы взять элемент
номер 2, в срезе должно быть хотя бы 3 элемента. Длина меньше трёх —
прыжок `jb` к панике. Иначе — чтение `[rcx + 8]`: элемент номер 2
лежит через 2 × 4 = 8 байт от начала (глава 4: адрес элемента =
начало + номер × размер).

Ветка паники передаёт `panic_bounds_check` три аргумента, и их
полезно узнавать: в `ECX` — номер, который просили (2), в `RDX` —
длина, в `R8` — адрес записи «где в исходнике» (П8.8). А `ud2`
после вызова — инструкция, которая всегда вызывает сбой «неверная
инструкция» (глава 34, вектор 6, `#UD`). Сюда выполнение не доходит:
`panic_bounds_check` не возвращается. Компилятор ставит `ud2`
как пометку «дальше пути нет». Помнишь `int 3` после
`_CxxThrowException` в П7.9? Та же идея.

В отладочной сборке та же проверка выглядит длиннее, но узнаётся
так же:

```
        mov     eax, 2
        cmp     rax, rdx                 ; номер 2 >= длины?
        jae     .LBB8_2                  ; да — паника
```

**Рисунок, который надо узнавать в лицо:** `cmp` регистра длины
с числом → условный прыжок вперёд → `call …panic_bounds_check` →
`ud2`. Увидел — перед тобой обращение к элементу по номеру, а номер
и длина видны в регистрах.

С текстом то же самое. `&str` — тоже адрес и длина, и функция,
которая **возвращает** строку, отдаёт её в двух регистрах — `RAX`
и `RDX`:

```rust
pub fn greet() -> &'static str {
    "Privet"
}
```

```
greet:
        lea     rax, [rip + …]           ; адрес букв
        mov     edx, 6                   ; длина — 6 букв
        ret
```

А сами буквы лежат в файле так:

```
        .ascii  "Privet"
```

`.ascii`, а не `.asciz`: **нуля в конце нет**. В C строка кончается
байтом 0 (глава 4.4), в Rust — нет, длина хранится отдельно. Поэтому
строки программы на Rust лежат в файле вплотную, одна к другой,
и окно строк в DIE или IDA часто показывает их слипшимися:
`Otkazano.Dostup razreshon!…`. Это не ошибка инструмента, а примета
Rust.

## П8.6. Vec и String в памяти

**Vec** `[век]` (vector, «вектор») — массив, который умеет расти,
как `std::vector` из П7.10. **String** `[стринг]` — строка, которая
умеет расти. Внутри `String` — это `Vec` байтов, поэтому устроены они
одинаково: три числа по 8 байт.

| Поле | Что это |
|---|---|
| ptr | адрес, где лежат сами элементы (в куче, глава 4.7) |
| len | сколько элементов сейчас |
| cap | на сколько элементов выделено место (capacity, «вместимость») |

А **в каком порядке** они лежат? Тут Rust ведёт себя не как C.
Порядок полей Rust не обещает: компилятор волен расставлять их как
удобнее и менять расстановку между версиями. Поэтому порядок
не заучивают, а **проверяют по коду**. Вот три функции, которые
читают по одному полю:

```rust
pub fn vcap(v: &Vec<u32>) -> usize { v.capacity() }
pub fn vptr(v: &Vec<u32>) -> *const u32 { v.as_ptr() }
pub fn vlen(v: &Vec<u32>) -> usize { v.len() }
```

```
vcap:   mov     rax, qword ptr [rcx]        ; +0
vptr:   mov     rax, qword ptr [rcx + 8]    ; +8
vlen:   mov     rax, qword ptr [rcx + 16]   ; +16
```

У rustc 1.99 вышло: **вместимость на +0, адрес на +8, длина на +16**.
Не тот порядок, который подсказывает здравый смысл, и не тот,
что у `std::vector` в П7.10. Отсюда правило: встретил в листинге
`[rcx + 16]` у `Vec` или `String` — это длина, но только если ты
проверил это для своей версии компилятора, как сейчас. Так в реверсе
работают со всем, что не закреплено стандартом.

`String` читается точно так же: `len()` строки у rustc 1.99 — тоже
`[rcx + 16]`.

Сравни три вида «текста» в Rust:

| Тип | Сколько байт | Что внутри | Где буквы |
|---|---|---|---|
| `&str` | 16 | адрес, длина | где угодно: в файле или в куче |
| `String` | 24 | вместимость, адрес, длина (rustc 1.99) | в куче, своя память |
| `&String` | 8 | адрес самой `String` | — |

## П8.7. Option и Result

В Rust нет `NULL`. Если значения может не быть, это говорят типом
**Option** `[óпшн]` («вариант»): `Some(x)` — «есть, вот оно»
или `None` — «нет». Если операция может не получиться — тип
**Result** `[ризáлт]` («результат»): `Ok(x)` — «получилось»
или `Err(e)` — «ошибка, вот какая».

Разобрать их помогает `match` из П8.3:

```rust
match v.iter().find(|&&e| e == 7) {
    Some(x) => println!("nashel {}", x),
    None => println!("net"),
}
```

А короткий путь — `.unwrap()` («распаковать»): «дай значение, а если
его нет — паникуй». Его любят в маленьких программах, и в машинном
коде он заметен сразу.

Как это выглядит внутри. Две находки, обе с rustc 1.99.

**Option от ссылки — просто указатель.** Функция ищет число в срезе
и возвращает ссылку на него или `None`:

```rust
pub fn find(v: &[u32], x: u32) -> Option<&u32> {
    v.iter().find(|&&e| e == x)
}
```

```
find:
        test    rdx, rdx                 ; длина 0?
        je      .LBB1_5
        mov     rax, rcx                 ; rax — текущий элемент
        shl     rdx, 2                   ; длина × 4 = байт осталось
.LBB1_2:
        cmp     dword ptr [rax], r8d     ; элемент == x?
        je      .LBB1_6                  ; да — вернуть его адрес
        add     rax, 4
        add     rdx, -4
        jne     .LBB1_2                  ; цикл назад (глава 5)
.LBB1_5:
        xor     eax, eax                 ; None — это 0
.LBB1_6:
        ret
```

`Some(адрес)` — это сам адрес, `None` — это 0. Ссылка в Rust никогда
не бывает нулём, поэтому ноль свободен и означает «нет». Хитрость
называют **нишей** (niche): лишняя метка не нужна, `Option<&u32>`
занимает столько же, сколько указатель. В листинге такая функция
неотличима от функции на C, которая возвращает `NULL`.

**Option от числа — пара: метка и значение.** У `u32` свободного
значения нет: годится любое число, и 0 тоже. Поэтому `Option<u32>`
хранит отдельно метку: 1 — `Some`, 0 — `None`.

```rust
pub fn un(o: Option<u32>) -> u32 {
    o.unwrap()
}
```

```
un:
        sub     rsp, 40
        cmp     ecx, 1                   ; метка: Some?
        jne     .LBB0_2                  ; нет — паника
        mov     eax, edx                 ; да — значение из EDX
        add     rsp, 40
        ret
.LBB0_2:
        lea     rcx, [rip + …]           ; где в исходнике
        call    core::option::unwrap_failed
        ud2
```

Метка пришла в `ECX`, значение — в `EDX`, хотя в исходнике аргумент
один. Это **внутреннее соглашение Rust**: свои функции Rust вызывает
по своим правилам и раскладывает пары по двум регистрам. Правила
главы 12 Rust строго соблюдает только для функций, помеченных
`extern "C"`, — тех, что вызывают из C или из Windows. Для остальных
внутреннее соглашение не обещано и может меняться. Читай по коду,
как сейчас.

`unwrap` на `Result` выглядит так же, только вызывает
`core::result::unwrap_failed`.

## П8.8. Паники: что они рассказывают о программе

Каждая проверка в Rust ведёт к панике, а каждая паника знает, **где**
она случилась: файл, строку и столбец исходника. Эти сведения лежат
в файле программы рядом с кодом. Для реверсера это подарок.

Посмотри ещё раз на `lea r8, [rip + …]` перед `panic_bounds_check`.
Там лежит запись из трёх полей — компилятор называет её `Location`
(«место»):

```
        .quad   <адрес имени файла>       ; 8 байт: адрес текста
        0f 00 00 00 00 00 00 00           ; 8 байт: длина имени — 15
        01 00 00 00                        ; 4 байта: строка 1
        33 00 00 00                        ; 4 байта: столбец 0x33 = 51
```

Это байты из листинга godbolt, числа младшим байтом вперёд — глава 3.7.
Строка 1, столбец 51 — ровно место `v[2]` в файле, который я собирал:
там функция записана в одну строку и перед ней стоит пометка
`#[inline(never)]` («не встраивать»), поэтому столбец такой большой. А по
адресу из первого поля лежит имя файла. У меня на godbolt это
`/app/example.rs`, а в твоей программе, собранной `cargo`, будет
`src\main.rs`.

Что ещё говорят строки паник:

| Строка в файле | Что она выдаёт |
|---|---|
| `src\main.rs`, `src\…` | программа на Rust и имена её файлов |
| `/rustc/` и 40 шестнадцатеричных цифр, дальше `library\core\src\…` | пути к стандартной библиотеке. 40 цифр — номер сборки компилятора |
| `called \`Option::unwrap()\` on a \`None\` value` | в программе есть `unwrap` на `Option` |
| `called \`Result::unwrap()\` on an \`Err\` value` | `unwrap` на `Result` |
| `index out of bounds: the len is ` | проверки границ |
| `attempt to add with overflow` | отладочная сборка (П8.11) |

Про 40 цифр стоит запомнить. Это хеш — номер изменения в исходниках
компилятора. Свой хеш ты увидишь командой `rustc -vV`, в строке
`commit-hash`. У rustc 1.99.0 на godbolt хеш начинается с `b940084d`.
Встретил его в чужой программе — знаешь, каким компилятором её
собрали, и можешь собрать тем же для сравнения.

Строки паник переживают и релизную сборку, и удаление имён.
В программе на C после удаления имён подсказок остаётся мало,
а в программе на Rust — пути файлов и номера строк. Как называть функции, подскажут сами
сообщения.

## П8.9. Имена функций Rust

Как у C++ в П7.7, у Rust свои **искажённые имена**: в них зашито, где
функция лежит. Вот одна и та же функция `zadacha::zamok::proverka`
(функция `proverka` в модуле `zamok` программы `zadacha`) у двух
версий компилятора. Оба имени настоящие:

| Компилятор | Имя в файле |
|---|---|
| rustc 1.96 и старше | `_ZN7zadacha5zamok8proverka17hfcd155372e8f6368E` |
| rustc 1.97 и новее | `_RNvNtCskLUh0hM8zwv_7zadacha5zamok8proverka` |

**Старый вид** похож на имена g++ из П7.7: начало `_ZN`, конец `E`,
внутри куски с длиной впереди — `7zadacha`, `5zamok`, `8proverka`.
Хвост `17h…` — это 17 знаков: буква `h` и 16 шестнадцатеричных цифр.
Это хеш, отпечаток функции, а не часть имени. Читать его не нужно.

**Новый вид** — v0 — начинается с `_R`. Rust перешёл на него
в версии 1.97 (июль 2026). Правило чтения то же: число перед словом —
его длина. `Nv` значит «функция», `Nt` — «модуль или тип»,
а `Cs…_` перед именем программы — её отпечаток.

Что делать на практике:

- в IDA и Ghidra имена обычно расшифровываются сами. В Ghidra
  за это отвечает анализатор **Demangler GNU**, у него есть формат
  **rust**. Если имена остались `_R…`, проверь его настройки.
  Как у тебя покажет IDA 9.2, я проверить не могу — пришли мне;
- если имена есть — тебе повезло, это отладочная сборка или рядом
  лежит файл `.pdb` (П7.8). В чужой релизной программе имён обычно
  нет, и выручают строки паник из П8.8;
- увидел имя с `_R` или с `17h…E` — перед тобой Rust, даже если DIE
  этого не сказал.

## П8.10. Где начинается твой main

В C путь до `main` ты прошёл в главе 13: стартовый код библиотеки C,
потом `main`. В Rust между ними есть ещё одна ступенька. Вот функция
`main`, которую rustc ставит в `.exe`, — **не твоя**, а служебная
(rustc 1.99, отладочная сборка):

```
main:
        sub     rsp, 40
        mov     r8, rdx
        movsxd  rdx, ecx
        lea     rcx, [rip + example::main]   ; адрес ТВОЕГО main
        xor     r9d, r9d
        call    std::rt::lang_start::<()>
        nop
        add     rsp, 40
        ret
```

Цепочка такая:

1. стартовый код библиотеки C (как в главе 13) вызывает `main`;
2. служебный `main` отдаёт адрес **твоей** функции в `std::rt::lang_start`
   («запуск языка»), в релизной сборке — сразу в
   `std::rt::lang_start_internal`;
3. `lang_start` готовит стандартную библиотеку — обработку паник,
   аргументы — и только потом вызывает твой `main`.

Без имён вторая ступенька узнаётся так: короткая функция, которая
грузит `lea` адрес другой функции и сразу вызывает третью. Адрес
из `lea` — это и есть твой `main`. Но обычно быстрее путь из главы 16:
найди строку программы и пройди по перекрёстной ссылке. Строки
у программы на Rust есть всегда.

## П8.11. Отладочная и релизная сборка

У `cargo build` и `cargo build --release` разница больше, чем у `-O0`
и `-O2` в gcc. Отладочная сборка Rust **проверяет переполнение**
чисел, релизная — нет. Функция

```rust
pub fn add(a: u32, b: u32) -> u32 {
    a + b
}
```

в отладочной сборке:

```
        mov     ecx, eax
        add     ecx, edx                 ; сложили
        mov     dword ptr [rsp + 44], ecx
        cmp     ecx, eax                 ; сумма меньше слагаемого?
        jb      .LBB0_2                  ; да — переполнение, паника
        …
.LBB0_2:
        lea     rcx, [rip + …]
        call    core::panicking::panic_const::panic_const_add_overflow
        ud2
```

в релизной — одна инструкция:

```
        lea     eax, [rcx + rdx]
        ret
```

Проверка «сумма меньше слагаемого» — классический признак переполнения
без знака: если при сложении число перевалило через максимум, оно стало
меньше (глава 3.6). Видишь много таких `cmp`/`jb` с вызовами
`panic_const_…_overflow` — это отладочная сборка Rust.

Сравнение строк тоже меняется. Возьмём проверку пароля:

```rust
fn check(s: &str) -> bool {
    s == "rust_ne_strashen"
}
```

**Отладочная сборка** честно вызывает функцию сравнения:

```
        lea     rcx, [rsp + 40]          ; наша строка: адрес и длина
        lea     rdx, [rip + …]           ; образец: адрес и длина
        call    <&str as core::cmp::PartialEq>::eq
```

Пароль лежит среди строк файла, и способ 1 из главы 16 его находит.

**Релизная сборка** проверяет длину и сравнивает все 16 байт одной
инструкцией SSE — **pcmpeqb** («сравнить упакованные байты на
равенство»):

```
        cmp     r9, 16                   ; длина 16?
        …
        pcmpeqb xmm0, xmmword ptr [rip + __xmm@6e656873617274735f656e5f74737572]
```

Имя константы `__xmm@6e65…7572` — её содержимое, 16 байт числом.
Прочитай его по главе 3.7, младшим байтом вперёд: `72 75 73 74 5f 6e
65 5f 73 74 72 61 73 68 65 6e`. А это `rust_ne_strashen`. Пароль
спрятался в имени константы, и это уже уровень «тяжёлой сборки»
из главы 16.6.

И ещё одна примета релизной сборки. Строку ввода программа обрезала
методом `trim()` — «убрать пробелы по краям». В машинном коде это
длинная функция со сравнениями с числами **133**, **5760**, **12288**.
Это пробельные символы Unicode: U+0085, U+1680 и U+3000. Встретил
эту тройку чисел — рядом обработка пробелов, а значит, ввод
пользователя.

## П8.12. Практика: Rust в IDA

Создай проект `cargo new zadacha_rust` и запиши в `src\main.rs`:

```rust
fn check(s: &str) -> bool {
    s == "rust_ne_strashen"
}

fn main() {
    let mut line = String::new();
    std::io::stdin().read_line(&mut line).unwrap();
    if check(line.trim()) {
        println!("Dostup razreshon!");
    } else {
        println!("Otkazano.");
    }
}
```

Собери обе сборки: `cargo build` и `cargo build --release`. Проверь,
что программа работает: `target\debug\zadacha_rust.exe`, ввод
`rust_ne_strashen` — ответ `Dostup razreshon!`.

Теперь задание. Открой **релизную** сборку в IDA. Когда IDA предложит
загрузить файл `.pdb` с именами, откажись: представь, что программа
чужая. Сделай по шагам:

1. **Опознание.** Что скажет DIE (глава 7)? Какой у файла размер?
2. **Строки.** Найди `Dostup razreshon!` и `Otkazano.`. Слиплись ли
   они с соседними строками (П8.5)? Есть ли среди строк пароль?
3. **Пути.** Найди строки с `/rustc/`. Какой у твоего компилятора хеш?
   Сверь с `rustc -vV`.
4. **main.** По перекрёстной ссылке со строки `Dostup razreshon!` выйди
   на свою функцию `main`. Найди служебный `main` и `lang_start`
   (П8.10).
5. **Сравнение.** Найди проверку длины `16` и сравнение 16 байт.

Потом открой **отладочную** сборку, уже с `.pdb`. Сравни: как IDA

## П8.13. Rust на дороге к гипервизору

Драйверы на Rust — уже не эксперимент. Набор **windows-drivers-rs**
от Microsoft подключает Rust к WDK из главы 29: `cargo-wdk` создаёт
проект драйвера, `wdk-sys` даёт прямой доступ к функциям ядра, `wdk` —
обёртки поудобнее. Значит, и гипервизор, который загружается драйвером
(глава 35), можно написать на Rust. Такие проекты есть.

Что из этого приложения тебе там пригодится:

- в ядре стандартной библиотеки нет: код пишут с пометкой `#![no_std]`,
  без `String` и `println!`;
- паника в ядре — это синий экран, как с `win32kbase_rs.sys` в П8.1.
  Поэтому в коде ядра ошибки возвращают через `Result`, а не через
  `unwrap`;
- взаимодействие с Windows идёт через `extern "C"` и `extern "system"`:
  там действуют правила главы 12, а не внутреннее соглашение Rust.

Писать гипервизор будем на C, как и задумано в курсе. Но читать
чужие драйверы и гипервизоры на Rust ты теперь сможешь.

**Где учить язык дальше.** Официальная книга «The Rust Programming
Language» бесплатна на сайте **doc.rust-lang.org/book**. Есть её
русский перевод «Язык программирования Rust» — **doc.rust-lang.ru/book**. Для чтения кода хватит глав
о владении, о `struct` и `enum`, об обработке ошибок.

## Что запомнить

- **Срез** (`&[T]`, `&str`) — два значения: адрес и длина. В аргументах —
  два регистра, у `&str` нет нуля в конце, строки лежат вплотную.
- **Проверка границ**: `cmp` с длиной → прыжок → `panic_bounds_check` →
  `ud2`. В `ECX` — номер, в `RDX` — длина.
- **Vec и String** — три поля по 8 байт. Порядок не обещан:
  у rustc 1.99 вместимость +0, адрес +8, длина +16. Проверяй по коду.
- **Option<&T>** — указатель или 0. **Option<u32>** — метка и значение.
  `unwrap` → `unwrap_failed` и паника.
- **Паники** оставляют в файле `src\…`, `/rustc/<хеш>/…` и строки
  сообщений — подсказки даже без имён.
- **Имена**: старые `_ZN…17h…E`, с версии 1.97 — `_R…`. Числа перед
  словами — длины.
- **main**: служебный `main` → `lang_start` → твой `main`.
- **Отладочная сборка** проверяет переполнение (`panic_const_…_overflow`),
  релизная сжимает код: 16 байт сравниваются одной `pcmpeqb`.
- Правила главы 12 Rust соблюдает для `extern "C"`. Свои функции
  он вызывает по своим правилам — читай по коду.
