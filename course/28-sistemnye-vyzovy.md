# Глава 28. Системные вызовы

> **Часть VIII. Windows изнутри (Windows Internals)**
> Предыдущая глава: [27. Kernel mode и user mode](27-rezhim-yadra.md)

В главе 27 мы нашли три двери в ядро и выяснили, что одна из них
особенная. Исключения и прерывания случаются «сами». А **системный
вызов** программа делает **нарочно** — это её законный способ попросить
ядро о помощи. Через эту дверь проходит каждое открытие файла, каждый

В этой главе мы пройдём через эту дверь по шагам. Возьмём одну строчку

По дороге разберём по байтам ту маленькую заглушку в `ntdll.dll`,
на которой в главе 26 спали рабочие потоки, и узнаем, что делает
процессор в тот миг, когда выполняет `syscall`.

Эта глава закрывает часть VIII. После неё ты будешь понимать, как
программа разговаривает с ядром, — а значит, будешь готов в части IX

После главы ты будешь уметь:

## 28.1. Путь одной строчки

Вот строчка, которую мы проследим:

```c
h = CreateFileA("no_such_file.txt", GENERIC_READ, 0, NULL,
                OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
```

Программа просит открыть файл `no_such_file.txt` для чтения. Файла нет —
нарочно: так мы увидим, как ядро сообщает об ошибке. Аргументы
`CreateFileA` мы разбирали в главе 12, а слово `OPEN_EXISTING` значит
«открыть только существующий файл, новый не создавать».

Открыть файл программа сама не может — это работа с диском, то есть
с устройством (глава 27). Значит, вызов должен дойти до ядра. Вот его
путь сверху вниз — та же слоёная картинка, что в разделе 27.8, только
теперь с именами функций:

```
кольцо 3   nofile.exe       main
              ↓ call
           kernel32.dll     CreateFileA      — переходник, сразу передаёт дальше
              ↓
           kernelbase.dll   CreateFileA      — переводит имя из ANSI в UTF-16
              ↓
           kernelbase.dll   CreateFileW      — готовит всё для ядра
              ↓
           ntdll.dll        NtCreateFile     — заглушка: syscall
═══════════════════════════ syscall ═══════════════════════════════
кольцо 0   ntoskrnl.exe     обработчик системных вызовов
              ↓
           ntoskrnl.exe     NtCreateFile     — настоящая работа
              ↓
           драйверы файловой системы и диска
```

Уже знакомое по главе 15: в стеке вызовов Process Monitor были строки
`U ntdll.dll NtCreateFile` и `U KERNELBASE.dll CreateFileW`, а выше —
строки `K`, которые я тогда просил пока не трогать. Теперь ясно, что
это: `U` — кольцо 3, `K` — кольцо 0, а граница между ними — **ровно
здесь**, на `syscall` внутри `ntdll.dll`. К строкам `K` вернёмся
в разделе 28.7.

**Зачем столько слоёв?** Каждый слой делает свою часть работы:

1. **`kernel32.dll`** — исторический адрес. Программы десятилетиями
   импортируют функции из `kernel32.dll`, и Microsoft не может это
   сломать. Поэтому `kernel32.dll` осталась, но код многих функций
   переехал в `kernelbase.dll`, а в `kernel32.dll` на их месте стоят
   короткие переходники: одна инструкция `jmp` в `kernelbase.dll`.
   Переход `jmp` — не `call`, адреса возврата он не оставляет (глава 11).
   Поэтому в стеке Process Monitor из главы 15 между программой и
   `KERNELBASE.dll` строки `kernel32.dll` нет.
2. **`kernelbase.dll`** — удобства для программиста. Суффиксы `A` и `W`
   (глава 12): ядро Windows работает со строками UTF-16, поэтому
   `CreateFileA` переводит имя в UTF-16 и зовёт `CreateFileW`. А
   `CreateFileW` превращает понятные параметры вроде `OPEN_EXISTING`
   в то, что ждёт ядро, а имя `no_such_file.txt` — в путь в формате
   ядра.
3. **`ntdll.dll`** — последняя остановка. Здесь живут заглушки: по одной
   на каждую просьбу к ядру. Каждая заглушка — несколько инструкций,
   главная из которых — `syscall`.
4. **Ядро** делает настоящую работу.

## 28.2. Родной язык Windows: Native API

Функции, которые мы вызывали весь курс, — `CreateFileW`, `VirtualAlloc`,
`Sleep`, — называются **WinAPI** или **Win32 API** (глава 12). Это
«внешний» язык Windows, для программистов. Microsoft описывает его
подробно и обещает не менять.

Но у Windows есть и **свой, внутренний** язык — набор функций, которые
понимает само ядро. Он называется **Native API** `[нéйтив эй-пи-áй]` —
«родной API». Его функции начинаются с приставок **`Nt`** или **`Zw`**:

| WinAPI (что зовёт программа) | Native API (что уходит в ядро) |
|---|---|
| `CreateFileW` | `NtCreateFile` |
| `ReadFile` | `NtReadFile` |
| `CloseHandle` | `NtClose` |
| `VirtualAlloc` | `NtAllocateVirtualMemory` |
| `Sleep` | `NtDelayExecution` |
| `ResetEvent` | `NtClearEvent` |

В `ntdll.dll` каждая такая функция экспортируется **дважды**: под именем
`NtCreateFile` и под именем `ZwCreateFile`. В кольце 3 это **одна и та же**
заглушка по одному адресу — документация Microsoft прямо говорит, что
для вызовов из режима пользователя версии `Nt` и `Zw` ведут себя
одинаково. Разница появляется только внутри ядра — о ней в разделе 28.8.

Native API Microsoft документирует лишь частично: часть функций описана
в заголовочном файле `winternl.h`, но с предупреждением, что они могут
измениться. Поэтому программы пишут на WinAPI, а Native API — это язык,
который **реверсер** должен понимать: в отладчике и в Process Monitor
ты видишь именно его.

### Два вида кодов ошибок

У двух языков — два способа сообщать об ошибках. Это надо различать
с первого взгляда.

**Код ошибки Win32** — небольшое число. Функция WinAPI возвращает
«не получилось» (например, `INVALID_HANDLE_VALUE` или `FALSE`), а
подробности кладёт в TEB потока, откуда их достаёт `GetLastError`
(глава 26, раздел 26.12). Примеры:

| Код | Имя | Смысл |
|---|---|---|
| `2` | `ERROR_FILE_NOT_FOUND` | файл не найден |
| `3` | `ERROR_PATH_NOT_FOUND` | путь не найден |
| `5` | `ERROR_ACCESS_DENIED` | доступ запрещён |
| `6` | `ERROR_INVALID_HANDLE` | неверный дескриптор |

**Код `NTSTATUS`** `[эн-ти стéйтус]` — 32-битное число, которое
возвращает **каждая** функция Native API в регистре `RAX`. Он устроен
так же, как коды исключений из главы 27 (да это и есть та же система
кодов):

| Первая цифра | Значит | Пример |
|---|---|---|
| `0` | успех | `00000000` — `STATUS_SUCCESS` |
| `4` | сведения — успех с примечанием | встречается редко |
| `8` | предупреждение | `80000003` — точка останова |
| `C` | ошибка | `C0000034` — `STATUS_OBJECT_NAME_NOT_FOUND`, «имя не найдено» |

Кто переводит один код в другой? `kernelbase.dll`. Когда `NtCreateFile`
вернула `C0000034`, `CreateFileW` переводит этот код в Win32 —
получается `2`, «файл не найден» — и записывает **оба** в TEB. Для
перевода есть документированная функция `RtlNtStatusToDosError`
(«перевести NTSTATUS в код ошибки DOS»; DOS — так исторически называют
коды Win32).

x64dbg показывает оба кода прямо на панели регистров — это те самые
строки `LastError` и `LastStatus`, мимо которых мы проходили в главе 27.
В эксперименте мы увидим в них `2` и `C0000034`.

## 28.3. Заглушка в ntdll.dll по байтам

Теперь главный герой главы. Каждая функция `Nt…` в `ntdll.dll` — это
крошечная **заглушка** (stub `[стаб]`) из восьми коротких инструкций. У всех
заглушек одинаковый вид, различается только одно число. Вот как
выглядит заглушка `NtCreateFile` в 64-битных Windows 10 и 11 —
байты и инструкции:

```
смещение  байты                      инструкция
+00       4C 8B D1                   mov  r10, rcx
+03       B8 55 00 00 00             mov  eax, 0x55
+08       F6 04 25 08 03 FE 7F 01    test byte ptr [0x7FFE0308], 1
+10       75 03                      jne  +15
+12       0F 05                      syscall
+14       C3                         ret
+15       CD 2E                      int  0x2E
+17       C3                         ret
```

Смещения — в hex, от начала функции. Байты я проверил, собрав эти
инструкции ассемблером. Число `0x55` во второй строке — **номер**
системного вызова, о нём ниже; в твоей версии Windows он может быть
другим. Разберём строки по одной.

**`mov r10, rcx`** — скопировать первый аргумент из `RCX` в `R10`.
Зачем, если он уже лежит в `RCX` по соглашению о вызовах (глава 12)?
Потому что инструкция `syscall` **затирает** регистр `RCX` — кладёт туда
свой адрес возврата (раздел 28.5). Ядро знает об этом и берёт первый
аргумент из `R10`. Остальные аргументы остаются где были: второй
в `RDX`, третий в `R8`, четвёртый в `R9`, пятый и дальше — на стеке.

> **Любопытная деталь.** Если ты сам напишешь `mov r10, rcx` и соберёшь
> gcc, получишь байты `49 89 CA`, а не `4C 8B D1`. Обе записи —
> одна и та же инструкция. У `mov` есть два кода операции: `89` —
> «записать регистр в регистр или память» и `8B` — «загрузить регистр
> из регистра или памяти». Когда оба операнда — регистры, подходит
> любой. Компилятор Microsoft обычно выбирает `8B`, ассемблер GNU — `89`
> (вспомни `48 89 e5` — `MOV RBP,RSP` в прологе из листинга Ghidra
> в главе 14). Так что по байтам иногда можно угадать, **каким**
> компилятором собран код.

**`mov eax, 0x55`** — положить в `EAX` **номер системного вызова**
(system service number `[сúстем сёрвис нáмбер]`, сокращённо SSN).
У каждой функции Native API свой номер: `NtClose` — один, `NtCreateFile` —
другой. По этому номеру ядро поймёт, чего от него хотят. Запомни заодно
правило x86-64: запись в 32-битную половину `EAX` (глава 9) **обнуляет**
верхнюю половину `RAX`. Поэтому после `mov eax, 0x55` весь `RAX`
равен `0x55`.

**`test byte ptr [0x7FFE0308], 1`** — проверить один бит в памяти
по адресу `0x7FFE0308`. Узнаёшь адрес? Это `0x7FFE0000 + 0x308` —
внутри той самой страницы `KUSER_SHARED_DATA` из главы 26, которую ядро
кладёт по одному адресу во все процессы. По смещению `0x308` ядро
держит флажок «каким способом входить в ядро». `test` — это `and`,
который не сохраняет результат, а только ставит флаги (глава 10).

**`jne +15`** — если флажок поднят, прыгнуть на смещение `+15`, к старому
способу. Обычно флажок сброшен, и прыжка нет.

**`syscall`** — та самая дверь. Процессор уходит в кольцо 0. Когда ядро
закончит, выполнение продолжится со следующей инструкции.

**`ret`** — вернуться к тому, кто вызвал заглушку. Результат ядра уже
лежит в `RAX` — это код `NTSTATUS`.

**`int 0x2E` и ещё один `ret`** — **старая** дверь в ядро: программное
прерывание номер `0x2E`. Так Windows входила в ядро много лет назад,
до быстрых инструкций вроде `syscall`. Путь оставлен на случай, если
ядро поднимет флажок
по адресу `0x7FFE0308`. Реверсеру достаточно узнавать эти байты
(`CD 2E`) в лицо.

Теперь понятна загадка из главы 27. Рабочие потоки `threads.exe` спали
на `ret`, строчкой ниже `syscall`: они ушли в ядро через заглушку
`NtDelayExecution` и ждали, пока ядро их отпустит.

### Почему номер нельзя запомнить

Номер в `EAX` — это просто порядковый номер строки в таблице ядра.
Microsoft добавляет новые функции, таблица сдвигается, и номера
**меняются от версии к версии Windows**. Номер `NtCreateFile` долго
держался одним и тем же, а у других функций номера менялись даже между
крупными обновлениями.

Поэтому честная программа **никогда** не вставляет номер сама. Она
вызывает функцию `ntdll.dll` той же системы — а в ней номер всегда
правильный: Microsoft собирает `ntdll.dll` и ядро вместе.

Отсюда правило для реверсера, в духе «`0x40` — присмотрись» из главы 26:
если последовательность `mov r10, rcx` / `mov eax, число` / `syscall`
встречается **не** в `ntdll.dll`, а в коде самой программы, —
присмотрись. Обычной программе незачем ходить в ядро в обход
`ntdll.dll`. Так делают некоторые системы защиты программ и
вредоносный код, который хочет пройти мимо чужого наблюдения.

## 28.4. Эксперимент: проходим системный вызов в отладчике

Хватит смотреть на чужие байты — пройдём системный вызов своими руками.
Файл `C:\reverse\work\nofile.c`:

```c
#include <windows.h>
#include <stdio.h>

int main(void)
{
    HANDLE h;

    printf("Press Enter to open the file\n");
    getchar();                           /* пауза: успеть поставить точку останова */

    h = CreateFileA("no_such_file.txt", GENERIC_READ, 0, NULL,
                    OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);

    if (h == INVALID_HANDLE_VALUE)
        printf("CreateFileA failed, GetLastError = %lu\n", GetLastError());
    else {
        printf("File opened?!\n");
        CloseHandle(h);
    }
    return 0;
}
```

`INVALID_HANDLE_VALUE` — особое значение дескриптора «не получилось»,
в 64-битной программе это `0xFFFFFFFFFFFFFFFF` (то есть −1). Именно
с ним сравнивает результат `CreateFileA`.

Собери и запусти без отладчика:

```
gcc -O0 -o nofile.exe nofile.c
./nofile.exe
```

Нажми Enter. Вывод от адресов не зависит, он будет точно таким:

```
Press Enter to open the file

CreateFileA failed, GetLastError = 2
```

`2` — `ERROR_FILE_NOT_FOUND`, как и ждали. Теперь посмотрим, что было
между.

### Шаг 1. Дойти до паузы

Открой `nofile.exe` в x64dbg и жми **F9**, пока в консольном окне
программы не появится `Press Enter to open the file`. Программа ждёт
Enter внутри `getchar` — пока не нажимай.

Зачем пауза? Функцию `NtCreateFile` вызывает не только наша программа:
загрузчик и библиотеки тоже открывают файлы при запуске. Если поставить
точку останова сразу, отладчик остановится на чужом вызове. А сейчас
запуск уже позади.

### Шаг 2. Точка останова на заглушке

Введи в строку **Command**:

```
bp ntdll:NtCreateFile
```

— как `bp msvcrt:getchar` в главе 26. Теперь переключись в окно
программы и нажми **Enter**. x64dbg остановится в начале `NtCreateFile`.
Окно CPU покажет заглушку — сравни с таблицей из раздела 28.3. Номер
в `mov eax, …` запиши: это номер `NtCreateFile` в **твоей** Windows.

Посмотри на регистры. Заглушка ещё ничего не сделала, аргументы лежат
по соглашению о вызовах: в `RCX` — первый аргумент `NtCreateFile`, это
адрес переменной, куда ядро должно записать дескриптор файла.

### Шаг 3. До двери

Нажми **F7** четыре раза — пройди `mov r10, rcx`, `mov eax, …`, `test`
и `jne`. Теперь `RIP` стоит на `syscall`. Проверь:

- `R10` равен `RCX` — первый аргумент скопирован;
- `RAX` равен номеру из `mov eax, …`;
- прыжок `jne` не сработал — значит, флажок по адресу `7FFE0308`
  сброшен и Windows пользуется инструкцией `syscall`.

Запомни значение `RIP` — адрес инструкции `syscall`.

### Шаг 4. Через дверь

Нажми **F8** — «шаг с обходом». x64dbg выполнит `syscall` целиком:
процессор уйдёт в кольцо 0, ядро попробует найти файл, не найдёт и
вернёт управление. Для отладчика всё это — **одна** инструкция: x64dbg
живёт в кольце 3 и не видит, что было в ядре (глава 27).

Теперь `RIP` стоит на `ret`. Смотри на регистры — здесь три открытия:

| Регистр | Что там | Почему |
|---|---|---|
| `RAX` | `C0000034` | ответ ядра: `STATUS_OBJECT_NAME_NOT_FOUND`, «объект с таким именем не найден» |
| `RCX` | адрес инструкции `ret` — `RIP` из шага 3 плюс 2 | `syscall` сам записал сюда, куда вернуться (раздел 28.5) |
| `R11` | копия регистра флагов | туда `syscall` сохранил `RFLAGS` |

Вот и ответ на вопрос «зачем `mov r10, rcx`»: старое значение `RCX`
пропало, на его месте адрес возврата. Если бы заглушка не сохранила
первый аргумент в `R10`, ядро бы его не получило.

(Адрес `ret` на 2 больше адреса `syscall`, потому что `syscall` занимает
два байта: `0F 05`.)

### Шаг 5. Обратно в программу

Нажми **Alt+F9** — **Debug** → **Run to user code** («Отладка» →
«Выполнить до пользовательского кода»). x64dbg выполнит всё, что
осталось в `ntdll.dll` и `kernelbase.dll`, и остановится, как только
вернётся в код `nofile.exe` — сразу после `call` к `CreateFileA`.
В моей сборке это RVA `0x1532`, инструкция `mov qword ptr [rbp-8], rax`.

Посмотри на панель регистров:

- `RAX` = `FFFFFFFFFFFFFFFF` — это `INVALID_HANDLE_VALUE`, «не получилось»;
- строка **`LastError`** — `00000002` (`ERROR_FILE_NOT_FOUND`);
- строка **`LastStatus`** — `C0000034` (`STATUS_OBJECT_NAME_NOT_FOUND`).

Это те два кода из раздела 28.2, оба уже в TEB. `kernelbase.dll`
получила `C0000034` от ядра, перевела в `2` и записала оба. Нажми **F9** —
программа напечатает `GetLastError = 2`.

Весь путь одного системного вызова ты прошёл своими руками: `main` →
`kernel32.dll` → `kernelbase.dll` → заглушка `ntdll.dll` → **`syscall`** →
ядро → обратно → перевод кода ошибки → `main`.

## 28.5. Что делает процессор в миг syscall

В шаге 4 x64dbg выполнил `syscall` как одну инструкцию. Разберём, что
процессор успел сделать за эту «одну инструкцию». Описание взято из
документации Intel; у AMD то же самое.

**Когда процессор выполняет `syscall`:**

1. `RCX` ← адрес следующей инструкции. Это наш `ret` — адрес возврата.
2. `R11` ← `RFLAGS`. Копия регистра флагов.
3. `RIP` ← значение из особого регистра **`LSTAR`**. Здесь ядро заранее,
   при загрузке, записало адрес своего обработчика системных вызовов.
4. `CS` и `SS` ← значения для кольца 0, тоже из особого регистра
   (`STAR`). С этого момента **CPL = 0** — процессор в режиме ядра.
5. В `RFLAGS` сбрасываются флаги, которые ядро перечислило в третьем
   особом регистре (`FMASK`). Windows сбрасывает, среди прочих,
   **`IF`** — разрешение прерываний — и **`TF`** — пошаговый режим
   из главы 13.

**Чего процессор НЕ делает:** не трогает `RSP` и ничего не кладёт
на стек. Никакого `push` — в отличие от `call` из главы 11. Процессор
в кольце 0, а стек всё ещё пользовательский!

`LSTAR`, `STAR` и `FMASK` — это **MSR** (Model-Specific Registers
`[мóдел спесúфик рéджистерс]`, «регистры, зависящие от модели»),
особые регистры настроек процессора. Их пишут инструкцией `wrmsr`,
а она привилегированная (глава 27). Вот почему программа не может
подменить адрес обработчика: записать `LSTAR` можно только из кольца 0.
Это и есть правило «программа стучит, но не выбирает», теперь с именем
конкретного регистра. Подробнее об MSR — в главе 33.

### Ответ на обещание из главы 27

В главе 27 я сказал: при `syscall` стек на ядерный меняет не процессор,
а первые инструкции ядра. Теперь видно почему: процессор просто этого
не умеет, `syscall` не трогает `RSP`. Поэтому обработчик ядра первым
делом:

1. запоминает пользовательский `RSP` в надёжном месте;
2. загружает в `RSP` адрес **стека ядра** текущего потока.

Где ядро берёт адрес стека ядра, если ещё ничего не загружено? У ядра
есть запись о каждом процессоре, и оно дотягивается до неё через
сегментный регистр `GS` — особой инструкцией `swapgs`, которая
переключает `GS` между «пользовательским» и «ядерным» значением.
Подробности — в главе 33.

И теперь понятно, зачем процессор сбросил флаг `IF`. Пока ядро не
переключило стек, оно работает на стеке программы. Если бы в этот миг
пришло аппаратное прерывание, процессор положил бы данные ядра на
пользовательский стек — в память, которую контролирует программа.
С выключенными прерываниями этого случиться не может. Как только стек
переключён, ядро включает прерывания обратно инструкцией `sti`.

А сброс `TF` нужен, чтобы флаг пошагового режима, который поднял
отладчик программы (глава 13), не сработал на первой же инструкции
ядра. Пошаговый режим программы должен остаться в кольце 3.

### И обратно: sysret

Закончив работу, ядро возвращает пользовательский `RSP`, кладёт
в `RCX` адрес возврата, в `R11` — флаги и выполняет **`sysret`**
(глава 27). Процессор делает обратное:

- `RIP` ← `RCX`;
- `RFLAGS` ← `R11`;
- `CS` и `SS` ← значения для кольца 3, **CPL = 3**.

Вот почему в шаге 4 ты увидел в `RCX` адрес `ret`, а в `R11` — флаги:
с этими значениями `sysret` и вернул поток в программу.

Отсюда же практическое правило соглашения о вызовах: после заглушки
`ntdll.dll` значения `RCX` и `R11` испорчены. Для обычного кода это
не новость: по правилам Microsoft x64 эти регистры и так **изменчивые**
(volatile — глава 12), и вызывающий код их не бережёт.

## 28.6. Внутри ядра

Что происходит в кольце 0 между `syscall` и `sysret`? Увидеть это
своими глазами ты сможешь в главе 30, отладчиком ядра. Пока — карта,
чтобы было что узнавать.

Обработчик системных вызовов 64-битной Windows называется
**`KiSystemCall64`** `[кей-ай сúстем кол сикстú-фор]`. Приставка `Ki` —
внутренняя функция ядра (сравни с таблицей приставок из главы 27).
По шагам он делает вот что:

1. **Переключает стек** на стек ядра (раздел 28.5).
2. **Сохраняет регистры программы** — `RIP` (из `RCX`), `RFLAGS`
   (из `R11`), `RSP` и другие — в структуру на стеке ядра. Она называется
   **ловушечный кадр** (trap frame `[трэп фрейм]`). Это тот же
   «контекст» из главы 26: всё, что нужно, чтобы потом вернуть поток
   ровно туда, откуда он пришёл.
3. **Включает прерывания** (`sti`).
4. **Находит функцию по номеру.** Номер из `EAX` — это индекс в таблице
   системных сервисов (System Service Descriptor Table `[сúстем сёрвис
   дискрúптор тэйбл]`, SSDT). В строке таблицы — где лежит
   `nt!NtCreateFile` внутри ядра. Запись `nt!` читается как «в модуле
   ядра» — так имена ядра пишет WinDbg.
5. **Копирует аргументы со стека.** Первые четыре аргумента пришли
   в регистрах `R10`, `RDX`, `R8`, `R9`. Остальные лежат на **пользовательском**
   стеке, и ядро копирует их на свой. Копирует осторожно: если программа
   подсунула испорченный `RSP`, ядро поймает ошибку и вернёт код ошибки,
   а не упадёт.
6. **Вызывает `nt!NtCreateFile`.**
7. **Возвращается** через `sysret` с кодом `NTSTATUS` в `RAX`.

### Ядро не верит программе

Самое интересное — шаг 6. `NtCreateFile` в ядре получает аргументы
от программы, и **ни одному из них не верит**.

Почему? Представь, что ядро верит. Первый аргумент `NtCreateFile` —
адрес, куда записать дескриптор файла. Программа передаёт вместо своего
адреса адрес **внутри ядра**. Ядро послушно пишет туда число — и портит
собственные данные. Программе запрещено трогать память ядра (глава 27),
но она заставила бы ядро сделать это **за себя**. Защита колец потеряла
бы смысл.

Поэтому ядро запоминает, **откуда** пришёл вызов. Это поле потока
называется **`PreviousMode`** `[прúвиэс мóуд]` — «предыдущий режим».
При входе через `syscall` из кольца 3 оно равно `UserMode`. И тогда
`NtCreateFile`:

- **проверяет каждый указатель**: лежит ли он в пользовательской
  половине адресов и можно ли туда писать. Для этого у ядра есть функции
  `ProbeForRead` и `ProbeForWrite` («прощупать для чтения / записи»);
- **проверяет права**: разрешено ли пользователю, от имени которого
  работает процесс (глава 26: контекст безопасности), открыть этот файл
  так, как он просит;
- **ищет дескриптор в таблице процесса**, а не в таблице ядра.

Документация Microsoft говорит об этом прямо: когда вызов пришёл из
режима пользователя, функция считает все параметры пришедшими из
**ненадёжного** источника и тщательно проверяет их, прежде чем
использовать.

Запомни этот принцип — он главный для твоей будущей работы в ядре:
**всё, что пришло из кольца 3, — враг, пока не проверено**. В части IX
ты напишешь драйвер, который получает данные от программы, и тогда эта
проверка станет **твоей** обязанностью.

Дальше `NtCreateFile` передаёт работу менеджеру ввода-вывода (приставка
`Io` из главы 27), тот — драйверу файловой системы. Файловая система —
это способ раскладывать файлы и папки по диску; основная в Windows
называется NTFS `[эн-ти-эф-эс]`, на ней обычно и стоит диск `C:`.
Драйвер ищет файл, не находит — и вверх по цепочке
возвращается код `C0000034`.

## 28.7. Строки «K» в Process Monitor

В главе 15 ты видел стек вызовов в Process Monitor и смотрел только на
строки `U`. Теперь пора прочитать строки `K`.

Запусти Process Monitor, поставь фильтр **Process Name** is
`nofile.exe` (как в главе 15), запусти `nofile.exe` и нажми Enter.
Найди событие `CreateFile` с путём, кончающимся на `no_such_file.txt`,
в столбце **Result** («Результат») будет `NAME NOT FOUND` — «имя не
найдено». Узнаёшь? Это `STATUS_OBJECT_NAME_NOT_FOUND`, наш `C0000034`,
только словами. Procmon показывает **ответ ядра**, а не код Win32.

Дважды щёлкни событие → вкладка **Stack**. Строки `K` будут примерно
такими (сверху — самое глубокое; если Procmon подгрузил символы
Microsoft, будут имена функций, если нет — `ntoskrnl.exe + число`):

```
K  FLTMGR.SYS     …                  менеджер фильтров файловой системы
K  ntoskrnl.exe   IofCallDriver      передать запрос драйверу
K  ntoskrnl.exe   …                  менеджер объектов ищет имя
K  ntoskrnl.exe   NtCreateFile       настоящая NtCreateFile, в ядре
K  ntoskrnl.exe   KiSystemServiceCopyEnd
U  ntdll.dll      NtCreateFile       заглушка
U  KERNELBASE.dll …                  несколько строк: CreateFileW, CreateFileA
U  nofile.exe     nofile.exe + 0x1532
…
```

Читаем снизу вверх, и теперь каждая строка понятна:

- `nofile.exe + 0x1532` — адрес возврата в `main`, тот самый, куда
  x64dbg пришёл по **Alt+F9** в шаге 5;
- `ntdll.dll NtCreateFile` — заглушка. **Здесь проходит граница колец**:
  ниже — `U`, выше — `K`;
- `KiSystemServiceCopyEnd` — место внутри обработчика системных вызовов,
  сразу после копирования аргументов (шаг 5 из раздела 28.6), откуда ядро
  и вызывает нужную функцию;
- `ntoskrnl.exe NtCreateFile` — **тёзка** заглушки, настоящая функция
  в ядре;
- `IofCallDriver` — `Io`, менеджер ввода-вывода, передаёт запрос
  драйверу;
- `FLTMGR.SYS` — менеджер фильтров файловой системы. Через него, кстати,
  и Process Monitor узнаёт об обращениях к файлам — его драйвер
  подключается к этой цепочке фильтром.

Две функции с именем `NtCreateFile` — в `ntdll.dll` и в `ntoskrnl.exe` —
не путай. Первая — окошко, вторая — сотрудник за окошком.

## 28.8. Nt и Zw внутри ядра

В разделе 28.2 я сказал: в кольце 3 `NtCreateFile` и `ZwCreateFile` —
одно и то же. В ядре они разные, и для твоего будущего драйвера это
важно.

Драйвер работает в кольце 0 и тоже может попросить ядро открыть файл.
Ему не нужен `syscall` — он и так в ядре. Но какую функцию звать?

- **`NtCreateFile`** в ядре смотрит на `PreviousMode` потока. Если поток
  пришёл в ядро из программы (а драйвер часто работает именно в таком
  потоке), `PreviousMode = UserMode` — и функция начнёт проверять
  указатели драйвера как пользовательские. Буфер драйвера лежит в
  верхней половине — проверку он не пройдёт.
- **`ZwCreateFile`** в ядре сначала устанавливает `PreviousMode =
  KernelMode`, то есть говорит: «параметры пришли из ядра, им можно
  верить». И только потом зовёт настоящую функцию.

Документация Microsoft формулирует правило так: драйвер вызывает
версию `Zw`, когда параметры пришли из надёжного источника в режиме
ядра. Поэтому в драйверах ты почти всегда будешь видеть **`Zw`**:
`ZwCreateFile`, `ZwClose`, `ZwReadFile`. Встретишь в чужом драйвере
(глава 31) — будешь знать, что это за функции.

А откуда странное `Zw`? Microsoft в документации отвечает, что эти
буквы ничего не значат: их выбрали, чтобы приставка не совпала ни с
какой другой.

## 28.9. Системные вызовы для окон и графики

Не все системные вызовы идут в `ntoskrnl.exe`. Окна, кнопки, рисование
на экране обслуживает отдельная часть ядра — драйвер **`win32k.sys`**
(в современных версиях он разделён на несколько файлов с именами
`win32k…sys`). Путь такого вызова:

```
кольцо 3   твоя программа   MessageBoxA          (глава 12)
           user32.dll        …                   функции окон
           win32u.dll        NtUser…             заглушки для графики
══════════════════════ syscall ══════════════════════
кольцо 0   win32k…sys        NtUser…             окна и графика в ядре
```

**`win32u.dll`** — это «`ntdll.dll` для графики»: в ней такие же
заглушки с `syscall`, только для функций с приставками `NtUser`
(окна, ввод) и `NtGdi` (рисование). Узнать такой вызов можно по номеру
в `EAX`: у графических вызовов он **от `0x1000` и больше**. Ядро по
этому признаку понимает, что номер относится ко второй таблице —
таблице `win32k`.

## 28.10. Связь с гипервизором

Системный вызов — главный путь, которым программа меняет мир: файлы,
память, процессы, сеть. Поэтому тот, кто видит системные вызовы,
видит почти всё, что делает программа.

Process Monitor видит их изнутри Windows — через свой драйвер.
А гипервизор может видеть их **снаружи**, ниже ядра, так что гостевая
Windows об этом даже не узнает:

- гипервизор умеет перехватывать обращения гостя к регистрам MSR —
  в том числе к `LSTAR`, где записан адрес обработчика из раздела 28.5.
  Это настраивается в самом гипервизоре (глава 36);
- с помощью EPT (глава 37) гипервизор может замечать, когда гость
  выполняет определённую страницу кода, например обработчик системных
  вызовов.

На этом построены **песочницы** (sandbox `[сэндбокс]`) для
исследования вредоносных программ:
подозрительный файл запускают в виртуальной машине, а гипервизор
записывает каждый его системный вызов. Изнутри гостя такое наблюдение
увидеть гораздо труднее, чем драйвер Process Monitor. Как это устроено,
разберём в главе 39.

## 28.11. Что запомнить

1. Путь вызова: программа → `kernel32.dll` (переходник) →
   `kernelbase.dll` (удобства, перевод строк) → **`ntdll.dll`** (заглушка
   с `syscall`) → ядро → обратно.
2. **WinAPI** — язык для программистов, документирован и стабилен.
   **Native API** (`Nt…`, `Zw…`) — родной язык ядра, документирован
   частично. В кольце 3 `Nt` и `Zw` — одна заглушка.
3. Функции Native API возвращают **`NTSTATUS`** в `RAX`: `0` — успех,
   `8…` — предупреждение, `C…` — ошибка. `kernelbase.dll` переводит его
   в код Win32 для `GetLastError`. В x64dbg оба видны: `LastStatus`
   и `LastError`.
4. Заглушка: `mov r10, rcx` / `mov eax, номер` / проверка флажка
   в `KUSER_SHARED_DATA` / `syscall` / `ret`, запасной путь — `int 0x2E`.
5. **Номер** системного вызова меняется от версии к версии Windows.
   Поэтому программы ходят в ядро только через `ntdll.dll`. Заглушка
   с `syscall` в коде самой программы — повод присмотреться.
6. При `syscall` процессор: `RCX` ← адрес возврата, `R11` ← флаги,
   `RIP` ← `LSTAR`, CPL = 0, часть флагов (в том числе `IF` и `TF`)
   сброшена. **`RSP` не меняется** — стек переключает само ядро.
7. `mov r10, rcx` нужен потому, что `syscall` затирает `RCX`.
8. `LSTAR` — регистр MSR, писать его можно только из кольца 0
   (`wrmsr`). Программа стучит, но не выбирает.
9. Ядро сохраняет регистры программы в **ловушечный кадр**, находит
   функцию по номеру в **SSDT**, копирует аргументы и вызывает её.
10. Ядро **не верит** параметрам из кольца 3 (`PreviousMode = UserMode`):
    проверяет указатели и права. Драйверы зовут **`Zw…`**, чтобы ядро
    знало, что параметры из ядра.
11. Графические вызовы идут через **`win32u.dll`** в **`win32k…sys`**,
    их номера — от `0x1000`.
12. Системные вызовы видны снаружи из гипервизора — на этом построены
    песочницы.
