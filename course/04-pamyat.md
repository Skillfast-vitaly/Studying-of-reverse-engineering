# Глава 4. Память, адреса, указатели

> **Часть I. Фундамент**
> Предыдущая глава: [3. Числа, которыми говорит машина](03-chisla.md)

Последняя глава фундамента. Разбираемся, как программа раскладывает данные
в памяти — и почему именно здесь живёт большинство уязвимостей на свете.

После этой главы ты будешь понимать, что происходит, когда программа падает
с ошибкой, и почему адрес `0x00000000` считается дурной приметой.

---

## 4.1. Переменная — это кусок памяти с именем

Когда программист пишет на C:

```c
int age = 25;
```

происходит следующее:

1. Компилятор находит свободное место в памяти — четыре байта, потому что
   `int` занимает четыре.
2. Записывает туда число 25.
3. Запоминает: «когда в коде написано `age`, речь про эти четыре байта».

В памяти это выглядит так (little-endian, как мы выучили в главе 3):

```
адрес:    ... 0x1000  0x1001  0x1002  0x1003 ...
байт:     ...   19      00      00      00   ...
                └──────────────────────────┘
                   переменная age = 0x19 = 25
```

Само имя `age` **в программу не попадает**. Оно нужно только компилятору.
В машинном коде останется адрес — `0x1000`, и всё.

Вот почему в реверсе вместо осмысленных имён ты видишь адреса. Не потому что
кто-то их спрятал, а потому что имён там никогда и не было.

## 4.2. Указатель

Раз адрес — это число, его можно положить в переменную. Такая переменная
называется **указателем** (pointer).

```c
int age = 25;      // переменная, в ней лежит 25
int *p = &age;     // указатель, в нём лежит АДРЕС переменной age
```

Значок `&` читается «адрес чего-то». Значок `*` при объявлении означает
«это указатель».

В памяти:

```
        ┌─────────────────┐
0x1000  │   25            │   ← переменная age
        └─────────────────┘
               ▲
               │  указывает
        ┌──────┴──────────┐
0x2000  │   0x1000        │   ← указатель p, в нём лежит адрес age
        └─────────────────┘
```

Обрати внимание: в `p` лежит **не 25**, а `0x1000`. Само число 25 лежит
в другом месте.

Чтобы добраться до значения по адресу, указатель **разыменовывают** —
тот же значок `*`, но уже в коде:

```c
printf("%d", *p);   // напечатает 25 — сходили по адресу и взяли значение
printf("%d", p);    // напечатает 4096 — сам адрес (0x1000)
```

### Зачем это нужно

Три причины, по которым без указателей не обходится ни одна программа:

**1. Передать много данных дёшево.** Функция, принимающая массив из миллиона
чисел, получает не миллион чисел, а один адрес — 8 байтов.

**2. Изменить чужую переменную.** Функция обычно работает с копиями
аргументов. Получив адрес, она может изменить оригинал.

**3. Запросить память по ходу работы.** Заранее неизвестно, сколько данных
придёт, — программа просит память у системы и получает адрес.

### Почему это опасно

Указатель — это просто число. Ничто не мешает записать в него что угодно и
пойти читать по случайному адресу.

```c
int *p;              // указатель создан, но никуда не направлен
*p = 42;             // пишем по адресу, которого не знаем
```

Что будет — зависит от того, какой мусор оказался в `p`. Варианты: программа
упадёт, испортит собственные данные или испортит чужие. Отладить такое тяжело,
потому что сбой проявляется далеко от места ошибки.

Особый случай — **нулевой указатель**:

```c
int *p = NULL;       // NULL — это адрес 0
*p = 42;             // обращение по адресу 0
```

Windows специально держит первую страницу памяти (адреса `0x0`–`0xFFF`)
недоступной. Любое обращение туда → мгновенное аварийное завершение.
Это сделано нарочно: лучше честно упасть, чем тихо испортить данные.

Отсюда и примета: увидел в отладчике попытку обращения по адресу около нуля —
значит, где-то указатель остался неинициализированным или функция вернула
`NULL`, а результат не проверили.

## 4.3. Массивы: данные подряд

Массив — это несколько значений одного типа, лежащих **вплотную**:

```c
int numbers[5] = {10, 20, 30, 40, 50};
```

```
адрес:   0x1000   0x1004   0x1008   0x100C   0x1010
        ┌────────┬────────┬────────┬────────┬────────┐
        │   10   │   20   │   30   │   40   │   50   │
        └────────┴────────┴────────┴────────┴────────┘
          [0]      [1]      [2]      [3]      [4]
```

Каждый `int` занимает 4 байта, поэтому адреса идут через 4.

Формула адреса элемента:

```
адрес элемента [i] = адрес начала + i × размер элемента
```

Эту формулу ты будешь узнавать в ассемблере постоянно. Увидел что-то вроде
`mov eax, [rbx + rcx*4]` — это обращение к массиву четырёхбайтовых элементов:
`rbx` — начало, `rcx` — индекс, `4` — размер. Множитель сразу говорит, с
данными какого размера работает программа.

### Проверки границ нет

Вот место, где C отличается от современных языков:

```c
int numbers[5];
numbers[10] = 999;    // элемента [10] не существует
```

Компилятор это пропустит. Программа посчитает адрес `начало + 10×4` и
запишет туда. А там лежат **чужие данные**.

```
        ┌────┬────┬────┬────┬────┐╌╌╌╌╌╌╌╌╌╌┬──────────┐
        │[0] │[1] │[2] │[3] │[4] │ ...      │ ЧУЖОЕ    │
        └────┴────┴────┴────┴────┘╌╌╌╌╌╌╌╌╌╌┴──────────┘
                                             ▲
                                       сюда запишет [10]
```

Это называется **выход за границы буфера** (buffer overflow) — и это
главная уязвимость в истории вычислительной техники. Из неё выросли черви,
взломы игровых консолей и львиная доля всего, что чинят обновлениями
безопасности.

Почему так сделано: проверка границ стоит времени. C создавался в 1972 году,
когда каждый такт был на счету, и решили доверять программисту. Через
пятьдесят лет счёт последствиям идёт на миллиарды долларов.

Для реверсера это означает: **места работы с массивами и строками надо
смотреть внимательно**. Если размер данных приходит извне, а проверки нет —
это находка.

## 4.4. Строки в C

Строка в C — это массив байтов, заканчивающийся нулём:

```c
char name[] = "Reverse";
```

```
адрес:  0x1000  ...
       ┌────┬────┬────┬────┬────┬────┬────┬────┐
       │ 52 │ 65 │ 76 │ 65 │ 72 │ 73 │ 65 │ 00 │
       └────┴────┴────┴────┴────┴────┴────┴────┘
         R    e    v    e    r    s    e   конец
```

Это ровно задание 3.В из прошлой главы.

Ключевая особенность: **длина нигде не хранится**. Чтобы узнать, сколько
в строке символов, программа читает байты подряд, пока не встретит `0x00`.

Последствия:

1. Узнать длину строки — это пройти её целиком. Не мгновенно.
2. Если нуля нет, чтение уйдёт за пределы строки и утащит чужие данные.
   Так работала знаменитая уязвимость Heartbleed.
3. Строка не может содержать нулевой байт внутри себя.

В Windows чаще используется UTF-16, где каждый символ — два байта, а
признак конца — два нуля подряд. Поэтому в hex-редакторе английский текст
из `.exe` часто выглядит с «дырками»:

```
48 00 65 00 6C 00 6C 00 6F 00 00 00      →  "Hello"
 H     e     l     l     o    конец
```

Узнавать это в лицо — полезный навык, пригодится с первого же вскрытия.

## 4.5. Карта памяти программы

Когда Windows запускает `.exe`, она раскладывает его в памяти по областям.
Вот карта — адреса настоящие, взяты из `.exe`, собранного для этого курса.

Сверху вниз, от высоких адресов к низким:

| Область | Что лежит | Права |
|---|---|---|
| Системные библиотеки | `ntdll.dll`, `kernel32.dll` и прочие | чтение + исполнение |
| Стек (stack) | локальные переменные, адреса возврата | чтение + запись |
| Куча (heap) | данные, запрошенные по ходу работы | чтение + запись |
| `.bss` — `0x14000C000` | переменные, начинающиеся с нуля | чтение + запись |
| `.rdata` — `0x140009000` | неизменяемые данные: **текстовые строки**, таблица импортов | только чтение |
| `.data` — `0x140008000` | изменяемые глобальные переменные | чтение + запись |
| `.text` — `0x140001000` | **машинный код программы** | чтение + исполнение |
| Нулевая страница — `0x0` | ничего, обращение запрещено | нет доступа |

Разбор того, что здесь важно.

**`0x140000000` — база образа** (image base). Это адрес, по которому Windows
загружает сам `.exe`. Значение `0x140000000` — стандартное для 64-битных
программ. Все секции лежат выше него.

**Секции идут через `0x1000`.** Посмотри на адреса: `...1000`, `...8000`,
`...9000`, `...A000`. Все кратны `0x1000` = 4096 байт. Это ровно тот размер
страницы памяти, про который была речь в главе 3. Windows раздаёт память
страницами и назначает права тоже страницами, поэтому каждая секция начинается
с новой страницы.

**Права важнее, чем кажется.** Обрати внимание: у `.text` есть право
исполнения, но нет права записи. У `.data` наоборот. Это защита: программа
не может случайно (или намеренно) переписать собственный код, а данные не
могут стать кодом.

Отсюда следует практическая вещь: **чтобы пропатчить программу в памяти,
сначала нужно снять защиту от записи** с нужной страницы. Отладчики делают
это сами, но знать механику полезно.

**Куда смотреть в первую очередь.** Когда ты откроешь `.exe` в инструменте:

- ищешь **код** — иди в `.text`;
- ищешь **текстовые строки** (сообщения, пароли, пути) — иди в `.rdata`;
- ищешь **что программа умеет** — таблица импортов, тоже `.rdata`.

## 4.6. Стек

Стек (stack) — особая область, без которой не работает ни одна функция.
Название точное: он работает как стопка тарелок. Кладёшь сверху, берёшь
сверху. Последним положил — первым взял.

Две операции:

- **push** `[пуш]` — положить значение на вершину;
- **pop** `[поп]` — снять значение с вершины.

Процессор всё время помнит, где вершина, — адрес хранится в специальном
регистре `RSP` (stack pointer, указатель стека).

### Странность: стек растёт вниз

Вопреки картинке со стопкой тарелок, стек растёт **в сторону уменьшения
адресов**:

```
  до push:   RSP = 0x1000
  push 42
  после:     RSP = 0x0FF8   ← адрес УМЕНЬШИЛСЯ на 8
```

Причина историческая: стек и куча растут навстречу друг другу с
противоположных концов памяти, чтобы свободное место между ними доставалось
тому, кому оно нужнее.

Первое время это путает: «положил на стек» означает «записал по меньшему
адресу». Привыкается.

### Что хранится на стеке

1. **Локальные переменные** функций.
2. **Аргументы**, переданные функции (частично — часть идёт в регистрах).
3. **Адрес возврата** — куда вернуться, когда функция закончится.

Последнее — самое интересное для нас. Когда выполняется инструкция `call`,
процессор кладёт на стек адрес следующей инструкции. Когда выполняется
`ret` — снимает его со стека и прыгает туда.

То есть **адрес возврата лежит в обычной памяти, рядом с обычными данными** —
и его можно перезаписать, если рядом что-то выйдет за свои границы.

### Переполнение буфера

Соединим два факта главы: адрес возврата лежит на стеке, а у локальных
переменных нет проверки границ.

```c
void check_password(void)
{
    char buf[16];      // 16 байт на стеке
    gets(buf);         // читаем ввод БЕЗ ограничения длины
}
```

Что лежит на стеке, от вершины вглубь:

| Смещение | Содержимое | Размер |
|---|---|---|
| `RSP+0`  | `buf[0..15]` — сюда пишется ввод | 16 байт |
| `RSP+16` | сохранённый `RBP` | 8 байт |
| `RSP+24` | **адрес возврата** | 8 байт |

Ввёл 16 символов — всё нормально. Ввёл 32 — лишние 16 байт легли поверх
сохранённого `RBP` и поверх адреса возврата.

Теперь, когда функция выполнит `ret`, процессор снимет со стека **не тот
адрес, который туда положил `call`, а тот, который ввёл пользователь** —
и прыгнет по нему.

Вот и весь механизм. Тот, кто управляет вводом, получает управление над `RIP`
— а это, как мы выяснили в главе 1, означает управление всей программой.

Современная Windows защищается от такого сразу несколькими способами
(канарейки на стеке, DEP, ASLR), и разберём мы их в части VII. Но понимать
исходную механику надо сейчас, потому что на ней стоит половина реверса.

## 4.7. Куча

Стек хорош для мелочи, но у него два ограничения: он невелик (обычно
1 МБ на поток) и данные на нём живут только пока работает функция.

Когда нужно больше или дольше, память просят у системы — эта область
называется **куча** (heap).

```c
char *buf = malloc(1000);   // попросили 1000 байт, получили адрес
free(buf);                  // вернули обратно
```

Отличия от стека:

| | Стек | Куча |
|---|---|---|
| Размер | небольшой, фиксированный | большой |
| Скорость | очень быстро | медленнее |
| Освобождение | автоматически | **вручную** |
| Адреса | предсказуемые | разные при каждом запуске |

Слово «вручную» — источник ещё двух классов ошибок: забыли освободить
(утечка памяти) и освободили дважды либо пользуются уже освобождённым
(use-after-free). Последнее особенно ценится атакующими.

## 4.8. Почему у всех программ одинаковые адреса

Странность, которую стоит закрыть сразу. База образа `0x140000000` —
одна и та же у всех программ. Как они не сталкиваются в памяти?

Ответ: **адреса ненастоящие**. Каждая программа видит свою собственную,
выдуманную для неё память — это называется **виртуальная память**
(virtual memory).

Windows держит таблицу соответствия: «виртуальный адрес `0x140001000`
программы A → физическая ячейка номер такой-то». У программы B тот же
виртуальный адрес ведёт совсем в другое место.

Отсюда три следствия:

1. Программы не могут залезть в память друг друга — у них просто нет
   способа назвать чужой адрес.
2. Адреса в `.exe` можно записывать заранее, не зная, что ещё запущено.
3. Всё, что ты видишь в отладчике, — виртуальные адреса. Где оно лежит
   физически, не знает и сама Windows в момент выполнения.

Добавка к этому — **ASLR** (Address Space Layout Randomization): Windows
намеренно сдвигает базу образа при каждом запуске, чтобы атакующий не мог
заранее знать адреса. Поэтому в отладчике адреса будут отличаться от тех,
что записаны в файле. Это нормально и разбирается в главе 8.

## 4.9. Что запомнить из этой главы

1. **Переменная — это адрес.** Имена существуют только в исходнике.
2. **Указатель — это число, хранящее адрес.** Ошибка в нём роняет программу
   или тихо портит данные.
3. **Массивы лежат подряд**, адрес элемента считается по формуле
   `начало + индекс × размер`. Множитель в ассемблере выдаёт размер элемента.
4. **Проверок границ в C нет.** Отсюда переполнения буфера.
5. **Строки кончаются нулевым байтом**, длина нигде не хранится.
6. **Память разбита на области** с разными правами: `.text` исполняется,
   `.rdata` только читается, `.data` пишется.
7. **Стек растёт вниз** и хранит адреса возврата рядом с данными.
8. **Адреса виртуальные**, у каждой программы свои.

Если из всей главы останется одно — пусть это будет: **в памяти нет
перегородок**. Код, данные, адреса возврата — всё лежит в одном
пронумерованном ряду байтов. Границы между ними существуют только пока
программа их соблюдает.

## Упражнения

**4.1.** В `p` лежит `0x1000`, по адресу `0x1000` лежит число 25. Что
напечатает `printf("%d", p)`, а что — `printf("%d", *p)`?

**4.2.** Массив `short values[10]` начинается с адреса `0x2000`. `short`
занимает 2 байта. По какому адресу лежит `values[6]`?

**4.3.** В ассемблере встретилось `mov eax, [rbx + rcx*8]`. Что можно сказать
о размере элементов массива? Какого типа данные там, скорее всего, лежат?

**4.4.** Почему обращение по адресу `0x00000000` гарантированно роняет
программу, хотя это обычный адрес?

**4.5.** Строка в памяти: `41 42 43 44 45`. Дальше идут чужие данные.
Что произойдёт при попытке напечатать эту строку и почему?

**4.6.** Программа выделила память через `malloc`, но забыла `free`.
Что случится, если повторить это миллион раз?

**4.7.** У секции `.text` нет права на запись. Как тогда отладчик умудряется
ставить точки останова, ведь для этого нужно изменить байт в коде?
