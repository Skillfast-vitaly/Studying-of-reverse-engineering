# Приложение П3. Гонки и блокировки

> **Приложения к курсу**
> Когда проходить: после [главы 26](26-processy-i-potoki.md)
> и [приложения П1](p1-si-pishem-sami.md). Драйвер не нужен: все опыты —
> обычные программы. Опирается также на главы
> [10](10-assembler.md), [33](33-sistemnye-registry.md)
> и [34](34-preryvaniya.md).

Брат, это третье приложение из проверки курса на полноту. Пробел здесь
вот какой. Во всём курсе мы думали о коде так, будто он выполняется
**один**: инструкция за инструкцией, как в x64dbg по F7. А у твоего
Ryzen 5 7500F двенадцать логических процессоров, у Core i5-13400F —
шестнадцать. И все они работают **одновременно**.

В главе 26 ты уже создавал потоки и видел, что глобальная переменная
`shared` у всех одна. Тогда потоки её только печатали. А если они
начнут её **менять** — одновременно? Начнутся странные вещи: числа
теряются, программа то работает, то нет, и отладчик ничего не
показывает.

Для гипервизора это не теория. Гипервизор включается на **каждом**
логическом процессоре, и один и тот же код обработчика работает на всех
сразу. Если два ядра одновременно полезут в одну переменную, ошибка
будет ровно той, что мы сегодня увидим. Только в ядре она кончается
синим экраном.

Хорошая новость: всё можно изучить в обычной программе, без драйвера
и без риска. Правила одни и те же.

После приложения ты будешь уметь:

- своими глазами показать **гонку данных** и объяснить, почему
  `counter++` в двух потоках теряет прибавления;
- пользоваться **атомарными операциями** Windows (`InterlockedIncrement`,
  `InterlockedExchange`, `InterlockedCompareExchange`) и узнавать их
  в ассемблере по префиксу `lock`;
- написать свою **спин-блокировку** и знать её правила;
- находить **взаимную блокировку** (deadlock) и не допускать её;
- раскладывать данные «у каждого ядра своё» и понимать, почему
  соседние байты мешают друг другу;
- запускать свой код на **каждом** логическом процессоре по очереди.

Приложение около 900 строк. Проходи **в три захода**:

| Заход | Разделы | О чём |
|---|---|---|
| 1 | П3.1–П3.4 | гонка своими глазами, атомарные операции |
| 2 | П3.5–П3.7 | сравнить-и-обменять, спин-блокировка, взаимная блокировка |
| 3 | П3.8–П3.10 | у каждого ядра своё, код на каждом ядре, итоги |

## П3.1. Один код — много ядер

Вспомни главу 26: **поток** — это исполнитель, у которого свои регистры
и свой стек, а память у всех потоков процесса общая. Планировщик
Windows раздаёт потокам логические процессоры. Если потоков больше,
чем процессоров, они работают по очереди, квантами. Если процессоров
хватает, потоки работают **по-настоящему одновременно**: в одну и ту же
наносекунду на разных ядрах выполняются инструкции разных потоков.

Отсюда первое правило приложения:

> Всё, что **своё** у потока (регистры, стек, локальные переменные), —
> безопасно. Всё, что **общее** (глобальные переменные, память из
> `malloc`, любые данные по одному адресу), — опасно, как только его
> меняют два потока сразу.

Как это будет в гипервизоре. Твой обработчик — одна функция в памяти.
Когда гость на ядре 3 выполнит `cpuid`, процессор ядра 3 прыгнет в эту
функцию. В ту же секунду гость на ядре 7 выполнит `cpuid` — и процессор
ядра 7 прыгнет в **ту же** функцию. Функция одна, исполнителей два,
как с `worker` в главе 26. Всё, что обработчик хранит в общих
переменных, — поле для гонки.

## П3.2. Опыт: гонка своими глазами

Напишем программу, где четыре потока прибавляют единицу к одному
общему счётчику, каждый по 10 миллионов раз. Ответ должен быть
40 миллионов. Проверим. И сразу сравним с двумя способами защиты,
которые разберём дальше.

Файл `race.c`:

```c
#include <windows.h>
#include <stdio.h>

#define N       10000000        // сколько раз каждый поток прибавит 1
#define THREADS 4               // сколько потоков

LONG counter;                   // общий счётчик: один на весь процесс
LONG busy;                      // блокировка: 0 — свободно, 1 — занято
int  mode;                      // 0 — просто ++, 1 — Interlocked, 2 — блокировка

void lock(LONG *l)
{
    while (InterlockedExchange(l, 1) != 0)   // было занято? ждём
        YieldProcessor();                    // инструкция pause
}

void unlock(LONG *l)
{
    InterlockedExchange(l, 0);               // освободить
}

DWORD WINAPI worker(LPVOID param)
{
    for (int i = 0; i < N; i++) {
        if (mode == 0) {
            counter++;                       // без защиты
        } else if (mode == 1) {
            InterlockedIncrement(&counter);  // атомарно
        } else {
            lock(&busy);
            counter++;                       // под блокировкой
            unlock(&busy);
        }
    }
    return 0;
}

int main(void)
{
    const char *names[3] = { "counter++", "Interlocked", "spinlock" };
    HANDLE t[THREADS];

    for (mode = 0; mode < 3; mode++) {
        counter = 0;
        ULONGLONG t0 = GetTickCount64();
        for (int i = 0; i < THREADS; i++)
            t[i] = CreateThread(NULL, 0, worker, NULL, 0, NULL);
        WaitForMultipleObjects(THREADS, t, TRUE, INFINITE);
        ULONGLONG t1 = GetTickCount64();
        for (int i = 0; i < THREADS; i++)
            CloseHandle(t[i]);
        printf("%-12s %9ld of %d  %5llu ms\n",
               names[mode], counter, THREADS * N, t1 - t0);
    }
    return 0;
}
```

Что тут знакомо и что нового:

- `CreateThread`, `CloseHandle`, функция потока `DWORD WINAPI worker(LPVOID)` —
  из главы 26.
- **`LONG`** — тип Windows, 4 байта со знаком (П1.1: в Windows `long` —
  4 байта). Атомарные функции Windows работают именно с ним.
- **`WaitForMultipleObjects(THREADS, t, TRUE, INFINITE)`** — «жди, пока
  **все** (`TRUE`) потоки из массива `t` закончат работу, сколько
  угодно долго (`INFINITE`)». В главе 26 мы ждали через `Sleep` и
  `getchar`, здесь нужна точность: считать ответ можно только когда
  все закончили.
- **`GetTickCount64`** — сколько миллисекунд прошло с включения
  компьютера. Разница двух вызовов — время работы.
- `InterlockedIncrement`, `InterlockedExchange`, `YieldProcessor` —
  главные новые герои, о них разделы П3.4–П3.6.
- Три прогона в одном запуске: `mode` = 0, 1, 2.

Собери **без оптимизации** и запусти:

```
gcc -Wall -O0 -o race.exe race.c
./race.exe
```

Почему `-O0`: с оптимизацией компилятор может догадаться, что цикл
просто прибавляет `N`, и заменить десять миллионов шагов одним
сложением. Тогда гонки не будет видно. Нам нужна честная работа
шаг за шагом.

Вот **настоящий** вывод, три запуска подряд. Я собрал копию под Linux
на облачном сервере с четырьмя логическими процессорами: функции
Windows там подменены функциями Linux, а логика та же:

```
counter++     12744593 of 40000000    101 ms
Interlocked   40000000 of 40000000   1226 ms
spinlock      40000000 of 40000000   8271 ms

counter++     11488276 of 40000000     94 ms
Interlocked   40000000 of 40000000   1303 ms
spinlock      40000000 of 40000000   8205 ms

counter++     11131083 of 40000000     99 ms
Interlocked   40000000 of 40000000   1219 ms
spinlock      40000000 of 40000000   7775 ms
```

Смотри на первую строку каждого запуска. Четыре потока честно
прибавили по 10 миллионов, а в счётчике — **11–12 миллионов**. Больше
двух третей прибавлений **пропало**. И каждый раз пропадает разное
количество: программа одна, а ответы разные.

У тебя числа будут другими: у тебя больше ядер, другая частота, другая
Windows. Третий прогон может идти секунд десять, подожди. Но картина
будет та же: первая строка неправильная и каждый раз новая, две
другие — ровно 40 000 000. Запусти несколько раз и убедись сам.

Эта ошибка называется **гонка данных** (data race `[дэ́йта рейс]`):
два потока без договорённости меняют одни данные, и результат зависит
от того, кто «прибежал» первым. Отсюда и слово «гонка».

## П3.3. Куда пропадают прибавления

Чтобы понять, откройся ассемблеру. Вот что компилятор сделал из одной
строки `counter++` (настоящий дизассемблер `race.exe`, адреса убраны):

```
mov  eax, dword ptr [rip+...]   ; прочитать counter из памяти в EAX
add  eax, 1                     ; прибавить 1 в регистре
mov  dword ptr [rip+...], eax   ; записать EAX обратно в counter
```

Одна строка C — **три** инструкции: прочитать, изменить, записать.
Между ними процессор ничего не обещает. И вспомни главу 26: регистры
у каждого потока **свои**. `EAX` первого потока и `EAX` второго — разные
ячейки, даже если потоки выполняют одну функцию.

Разыграем, как два потока на двух ядрах теряют прибавление. Пусть
в `counter` сейчас 5:

| Шаг | Ядро 1 (поток A) | Ядро 2 (поток B) | `counter` в памяти |
|---|---|---|---|
| 1 | `mov eax, [counter]` → EAX = 5 | | 5 |
| 2 | | `mov eax, [counter]` → EAX = 5 | 5 |
| 3 | `add eax, 1` → EAX = 6 | | 5 |
| 4 | | `add eax, 1` → EAX = 6 | 5 |
| 5 | `mov [counter], eax` | | **6** |
| 6 | | `mov [counter], eax` | **6** |

Два потока прибавили по единице, а счётчик вырос на одну. Поток B
прочитал 5 **до того**, как A записал 6, и затёр его работу своей
шестёркой. Одно прибавление потеряно. За десятки миллионов шагов такое
случается миллионы раз.

Почему каждый раз по-разному? Потому что порядок шагов в таблице
никто не задаёт. Он зависит от того, когда планировщик запустил потоки,
что ещё делает компьютер, когда пришли прерывания (глава 34).
Поэтому гонку так трудно ловить: она проявляется **иногда**, и в
отладчике, где ты идёшь по шагам, её почти никогда не видно. Отладчик
сам меняет расписание.

Важный вывод на всю жизнь: **«у меня работает» — не доказательство**,
когда в коде есть общие данные. Корректность здесь доказывают
рассуждением, а не запуском.

А если поток **один**? Тогда шаги идут строго по очереди: прочитал,
прибавил, записал, и только потом следующее прочитал. Ничего не
теряется. Гонка возможна только там, где есть хотя бы два исполнителя
и хотя бы один из них **пишет**. Если все только читают, как `shared`
в главе 26, гонки нет.

## П3.4. Атомарные операции: `lock`

Выход — сделать «прочитать, изменить, записать» **одним неделимым**
действием. Такое действие называют **атомарным** (atomic `[этóмик]`;
атом по-гречески — «неделимый»). Пока одно ядро выполняет атомарную
операцию над ячейкой памяти, никакое другое ядро не может вклиниться
в её середину.

У x86 для этого есть **префикс `lock`** (lock `[лок]` — «запереть»).
Его ставят перед инструкцией, которая читает и пишет память, и
процессор выполняет её так, что другие ядра видят либо «до», либо
«после», но никогда не «посередине».

Писать `lock` руками не нужно. В Windows есть готовые функции, а
компилятор превращает их прямо в одну инструкцию (это встроенные
функции, intrinsics, из главы 33). Вот что стало с
`InterlockedIncrement(&counter)` в нашем `race.exe`:

```
mov  edx, 1
lock xadd dword ptr [rax], edx  ; атомарно: counter += 1
```

`xadd` (exchange and add `[иксчéйндж энд эд]`, «обменять и сложить»)
прибавляет число к памяти и заодно отдаёт старое значение. С префиксом
`lock` всё это — один неделимый шаг. Байт `F0` в машинном коде перед
инструкцией — это и есть префикс `lock`. Увидишь `F0` или слово `lock`
в x64dbg — знай: здесь код рассчитан на несколько ядер.

Главные атомарные функции Windows:

| Функция | Что делает атомарно | Инструкция |
|---|---|---|
| `InterlockedIncrement(&x)` | `x = x + 1`, вернуть новое `x` | `lock xadd` |
| `InterlockedDecrement(&x)` | `x = x - 1`, вернуть новое `x` | `lock xadd` |
| `InterlockedExchange(&x, v)` | записать `v`, вернуть **старое** `x` | `xchg` |
| `InterlockedCompareExchange(&x, v, c)` | если `x == c`, записать `v`; всегда вернуть старое `x` | `lock cmpxchg` |
| `InterlockedIncrement64(&x)` | то же для 8-байтового `LONG64` | `lock xadd` |

Interlocked `[интерлóкт]` — «сцепленный, взаимно заблокированный».

Теперь вторая строка вывода: `Interlocked 40000000 of 40000000`.
Ровно, каждый раз. Гонка побеждена.

Но посмотри на время: **1226 мс против 101**. Атомарная операция в
двенадцать раз медленнее обычной. Почему — поймёшь в П3.8, когда
поговорим о кэше. Пока запомни: **атомарность стоит дорого**, поэтому
её применяют только к данным, которые действительно общие.

> **Конец первого захода.** Проверь себя: объясни другу без
> компьютера, почему два потока, прибавляющие по единице, могут вместе
> прибавить только одну. Если получится нарисовать таблицу из П3.3 по
> памяти — ты понял главное.

## П3.5. Сравнить и обменять: кто первый, тот и взял

Второй заход. Самая мощная атомарная операция —
**`InterlockedCompareExchange`**, «сравнить и обменять». На ней можно
построить почти всё остальное. Её смысл в одной фразе:

> «Если в `x` всё ещё лежит то, что я ожидаю (`c`), — положи туда `v`.
> В любом случае скажи, что там лежало на самом деле».

Проверка и запись — один неделимый шаг. Никто не сможет изменить `x`
между «я посмотрел» и «я записал».

Классическая задача: несколько потоков, и **ровно один** должен
сделать что-то первым. Например, в гипервизоре первое ядро, дошедшее
до места, готовит общие таблицы, а остальные ими пользуются. Файл
`once.c`:

```c
#include <windows.h>
#include <stdio.h>

#define THREADS 8

LONG owner = 0;                 // 0 — никто ещё не взял

DWORD WINAPI worker(LPVOID param)
{
    LONG me = (LONG)(DWORD_PTR)param;              // номер потока: 1..8
    LONG was = InterlockedCompareExchange(&owner, me, 0);
    if (was == 0)
        printf("thread %ld: I am the first\n", me);
    else
        printf("thread %ld: too late, owner is %ld\n", me, was);
    return 0;
}

int main(void)
{
    HANDLE t[THREADS];
    for (int i = 0; i < THREADS; i++)
        t[i] = CreateThread(NULL, 0, worker, (LPVOID)(DWORD_PTR)(i + 1), 0, NULL);
    WaitForMultipleObjects(THREADS, t, TRUE, INFINITE);
    for (int i = 0; i < THREADS; i++)
        CloseHandle(t[i]);
    printf("owner = %ld\n", owner);
    return 0;
}
```

Номер потока мы передаём прямо в указателе `param`: приводим число
к `LPVOID` и обратно. Так часто делают, когда потоку нужно одно число,
а не целая структура. `DWORD_PTR` — целое размером с указатель
(8 байт), через него приведение проходит без предупреждений.

Каждый поток пытается записать в `owner` свой номер, но только если
там ещё 0. Настоящий вывод на сервере:

```
thread 1: I am the first
thread 3: too late, owner is 1
thread 4: too late, owner is 1
thread 2: too late, owner is 1
thread 5: too late, owner is 1
thread 6: too late, owner is 1
thread 7: too late, owner is 1
thread 8: too late, owner is 1
owner = 1
```

Потоки печатают в случайном порядке: 1, 3, 4, 2… Это снова
расписание, которое никто не задаёт. Первым может оказаться любой
поток, и у тебя, скорее всего, окажется другой. Но **первый всегда
ровно один**, и все остальные знают, кто он. Запусти десять раз —
«I am the first» будет ровно одна строка на каждый запуск.

В ассемблере это инструкция **`lock cmpxchg`** (compare and exchange
`[кэмпéр энд иксчéйндж]`). Как она работает:

```
; EAX = ожидаемое (c), ECX = новое (v)
lock cmpxchg dword ptr [rdx], ecx
; если [rdx] == EAX:  [rdx] = ECX, флаг ZF = 1
; иначе:              EAX = [rdx], флаг ZF = 0
```

После инструкции флаг `ZF` (глава 9) говорит, получилось или нет.
Узнавай её в чужом коде: `lock cmpxchg` почти всегда значит «здесь
кто-то аккуратно делит общие данные между потоками или ядрами».

А что было бы **без** атомарности? Напиши «проверил — записал»
обычным `if`:

```c
if (owner == 0)     // проверил...
    owner = me;     // ...записал
```

Два потока могут оба увидеть 0, оба решить «я первый» и оба записать
свой номер. Между проверкой и записью — окно, в которое пролезает
другой поток. Это та же гонка из П3.3, только в другой одежде. Её так
и называют: «проверил, потом сделал» (check-then-act).

## П3.6. Спин-блокировка своими руками

Атомарной операцией можно защитить **одну** ячейку. А если нужно
поменять несколько вещей согласованно? Например, в журнале гипервизора
записать строку в буфер **и** сдвинуть указатель конца. Если два ядра
сделают это одновременно, строки перемешаются.

Для этого нужна **блокировка** (lock): участок кода, куда в одну
секунду может войти только **один** поток. Такой участок называют
**критической секцией** (critical section `[крúтикал сéкшен]`). Все
остальные ждут у входа.

Простейшая блокировка — **спин-блокировка** (spinlock `[спинлок]`,
spin — «крутиться»): ожидающий поток не засыпает, а крутится в цикле
и всё время проверяет, не освободилось ли. Она уже была в `race.c`:

```c
void lock(LONG *l)
{
    while (InterlockedExchange(l, 1) != 0)   // было занято? ждём
        YieldProcessor();                    // инструкция pause
}

void unlock(LONG *l)
{
    InterlockedExchange(l, 0);               // освободить
}
```

Как она работает. Переменная `busy`: 0 — свободно, 1 — занято.

- **Вход.** `InterlockedExchange(l, 1)` атомарно записывает 1 и
  возвращает то, что было. Было 0 — значит, свободно было, и мы только
  что заняли: выходим из цикла, мы внутри. Было 1 — занято кем-то
  другим. Наша запись единицы ничего не испортила, там и так была
  единица. Крутимся дальше.
- **Выход.** Записать 0. Один из ждущих на следующем круге увидит 0
  и войдёт.

Ключевой момент: два потока не могут одновременно получить 0 из
`InterlockedExchange`. Обмен атомарный. Кто первым обменял 0 на 1,
тот и вошёл, второй уже получит 1.

Вот что стало с `lock` в `race.exe` (настоящий дизассемблер, самое
главное):

```
pause                           ; YieldProcessor()
...
xchg dword ptr [rax], edx       ; InterlockedExchange: обмен с памятью
test eax, eax                   ; было 0?
jne  ...                        ; нет — снова на pause
```

Здесь нет слова `lock`, но оно не нужно: инструкция `xchg` с памятью
**всегда** атомарна, процессор ставит ей `lock` сам. Это исключение
из правила, запомни его.

**`pause`** — особая инструкция для таких циклов ожидания. Она говорит
процессору: «я кручусь в ожидании». Документация Intel называет две
выгоды. Первая: когда ожидание кончится, процессор выйдет из цикла без
большого штрафа, который иначе платит за такие циклы. Вторая: пока
цикл крутится, процессор тратит заметно меньше энергии. Правило из
той же документации: **в каждом цикле ожидания — `pause`**.
Отсюда и имя функции Windows: `YieldProcessor` — «уступить процессор».

Теперь третья строка вывода: `spinlock 40000000` — ровно, но **8 секунд**
против 1,2 у `Interlocked`. Блокировка — самый дорогой способ. Каждый
вход и выход — две атомарные операции, а ещё потоки подолгу крутятся
в ожидании. Поэтому её берут, только когда без неё нельзя: когда
нужно менять **несколько** вещей согласованно.

### Правила спин-блокировки

1. **Держи коротко.** Пока ты внутри, все остальные ядра, которым
   нужна эта блокировка, крутятся впустую. Внутри — несколько
   инструкций, а не цикл на миллион шагов.
2. **Внутри не засыпай и не жди.** Никаких `Sleep`, `printf` в файл,
   ожиданий диска. Если поток уснёт с блокировкой в руках, все
   остальные будут крутиться, пока он не проснётся.
3. **Всегда освобождай.** Забытый `unlock` — вечная блокировка: все,
   кто придёт следом, будут крутиться до конца времён.
4. **Не входи дважды.** Спин-блокировка не помнит, **кто** её занял.
   Если поток, уже держащий блокировку, снова вызовет `lock`, он будет
   ждать сам себя вечно.

Правило 4 особенно коварно в ядре и в гипервизоре. Представь:
обработчик взял блокировку журнала, и тут пришло прерывание (глава 34),
а его обработчик тоже пишет в журнал. Он вызывает `lock` на том же
ядре — и ядро зависает навсегда. Поэтому в ядре Windows спин-блокировку
берут функцией `KeAcquireSpinLock`, которая заодно поднимает IRQL до
`DISPATCH_LEVEL` (глава 34). Прерывания ниже этого уровня не
прервут владельца блокировки. Это будет в главах про драйверы.

А в самом гипервизоре функции Windows вызывать нельзя вообще (почему —
увидишь в главе 38). Поэтому там спин-блокировку пишут **сами**,
ровно такую, как наша, из `InterlockedExchange` и `pause`.

## П3.7. Взаимная блокировка

Когда блокировок больше одной, появляется новая беда. Пусть есть две:
`A` (для журнала) и `B` (для таблицы). И два куска кода:

```c
void first(void)                  void second(void)
{                                 {
    lock(&A);                         lock(&B);
    lock(&B);                         lock(&A);
    ...                               ...
    unlock(&B);                       unlock(&A);
    unlock(&A);                       unlock(&B);
}                                 }
```

Поток 1 вызвал `first` и взял `A`. В ту же секунду поток 2 вызвал
`second` и взял `B`. Теперь поток 1 ждёт `B`, которую держит поток 2,
а поток 2 ждёт `A`, которую держит поток 1. Оба будут ждать вечно.

Это **взаимная блокировка** (deadlock `[дэ́длок]`, «мёртвый замок»).
Программа не падает и не выдаёт ошибку, она просто замирает. Два
ядра крутятся в `pause` на 100 % и никогда не выйдут.

Лекарство простое и строгое: **всегда брать блокировки в одном и том
же порядке**. Договорились «сначала `A`, потом `B`» — значит, во всей
программе, в каждой функции, только так. Тогда вечного ожидания
не будет: чтобы держать `B`, поток сначала обязан был взять `A`.
Значит, положения «один держит `A`, другой держит `B` и ждёт `A`»
просто не бывает.

А лучше всего — чтобы блокировок было как можно **меньше**. Как
обойтись совсем без них — следующий раздел.

> **Конец второго захода.** Проверь себя: зачем в спин-блокировке
> именно `InterlockedExchange`, а не обычное `*l = 1`? (Подсказка:
> вспомни `if (owner == 0) owner = me;` из П3.5.)

## П3.8. У каждого ядра своё

Третий заход. Лучший способ победить гонку — **не делить данные
вообще**. Если у каждого ядра свой счётчик, свой буфер, своя структура,
то никто ни с кем не пересекается, и никакие блокировки не нужны. Это
называют данными **«на процессор»** (per-CPU `[пер-си-пи-ю́]`).

Гипервизор устроен именно так. У каждого логического процессора
**свои** управляющие структуры, свой стек обработчика, свои счётчики.
Общие данные — только там, где без них никак, и они защищены.

Проверим, насколько это быстрее. Каждый поток прикрепим к своему ядру
(как — объясню в П3.9) и сравним три способа посчитать события:

1. один общий счётчик через `InterlockedIncrement64`;
2. у каждого ядра своя ячейка в массиве, ячейки идут вплотную;
3. у каждого ядра своя ячейка, но каждая «раздута» до 64 байт.

Файл `percpu.c`:

```c
#include <windows.h>
#include <stdio.h>

#define N    20000000           // событий на каждое ядро
#define MAXC 64

typedef struct {
    LONG64 count;               // 8 байт полезных данных
} SLOT_TIGHT;

typedef struct {
    LONG64 count;
    char   pad[56];             // добить до 64 байт: своя строка кэша
} SLOT_PADDED;

SLOT_TIGHT  tight[MAXC];
SLOT_PADDED padded[MAXC];
LONG64      shared;
int         mode;               // 0 — общий Interlocked, 1 — tight, 2 — padded

DWORD WINAPI worker(LPVOID param)
{
    int me = (int)(DWORD_PTR)param;
    SetThreadAffinityMask(GetCurrentThread(), (DWORD_PTR)1 << me);
    for (int i = 0; i < N; i++) {
        if (mode == 0)      InterlockedIncrement64(&shared);
        else if (mode == 1) tight[me].count++;
        else                padded[me].count++;
    }
    return 0;
}

int main(void)
{
    const char *names[3] = { "shared Interlocked", "own slot, tight", "own slot, padded" };
    SYSTEM_INFO si;
    GetSystemInfo(&si);
    int n = si.dwNumberOfProcessors < MAXC ? (int)si.dwNumberOfProcessors : MAXC;
    HANDLE t[MAXC];

    for (mode = 0; mode < 3; mode++) {
        ULONGLONG t0 = GetTickCount64();
        for (int i = 0; i < n; i++)
            t[i] = CreateThread(NULL, 0, worker, (LPVOID)(DWORD_PTR)i, 0, NULL);
        WaitForMultipleObjects(n, t, TRUE, INFINITE);
        ULONGLONG t1 = GetTickCount64();
        for (int i = 0; i < n; i++)
            CloseHandle(t[i]);

        long long sum = shared;
        if (mode == 1) { sum = 0; for (int i = 0; i < n; i++) sum += tight[i].count; }
        if (mode == 2) { sum = 0; for (int i = 0; i < n; i++) sum += padded[i].count; }
        printf("%-20s %11lld  %5llu ms\n", names[mode], sum, t1 - t0);
    }
    printf("sizeof tight %d, padded %d\n", (int)sizeof(SLOT_TIGHT), (int)sizeof(SLOT_PADDED));
    return 0;
}
```

`GetSystemInfo` заполняет структуру `SYSTEM_INFO` сведениями о
компьютере; поле `dwNumberOfProcessors` — число логических
процессоров. `LONG64` — 8-байтовый `LONG`. Ячейки `tight[me]` и
`padded[me]` — у каждого потока своя, по номеру ядра `me`. Гонки там
нет: никто не трогает чужую ячейку. Итог складываем в конце, когда все
потоки закончили.

Настоящий вывод на сервере с четырьмя логическими процессорами, два
запуска:

```
shared Interlocked      80000000   2556 ms
own slot, tight         80000000    198 ms
own slot, padded        80000000     53 ms
sizeof tight 8, padded 64

shared Interlocked      80000000   2377 ms
own slot, tight         80000000    200 ms
own slot, padded        80000000     55 ms
sizeof tight 8, padded 64
```

Все три ответа верные: 4 × 20 000 000 = 80 000 000. Но время!

- Общий счётчик: **2,5 секунды**.
- Свои ячейки вплотную: **0,2 секунды** — в двенадцать раз быстрее.
- Свои ячейки по 64 байта: **0,05 секунды** — ещё в четыре раза быстрее.

Первое понятно: нет атомарных операций, нет очереди к одной ячейке.
Но почему **второй** способ в четыре раза медленнее третьего? Ведь
и там и там у каждого своя ячейка, никто не делит данные.

### Строка кэша

Ответ — в устройстве памяти. В главе 32 ты видел TLB — маленький
быстрый кэш внутри процессора, который помнит переводы адресов.
Точно так же у каждого ядра есть **кэш памяти** (cache `[кэш]`): там
лежат копии недавно тронутых байтов, чтобы не ходить каждый раз в
медленную оперативную память.

Но кэш хранит байты не по одному, а **кусками по 64 байта**. Такой
кусок называют **строкой кэша** (cache line `[кэш лайн]`). Прочитал
один байт — в кэш ядра приехали все 64 соседних.

А теперь главное. Если одно ядро **пишет** в строку, копии этой строки
в кэшах **других** ядер становятся устаревшими, и процессор их
отбирает. Следующее ядро, которое захочет эту строку, будет ждать,
пока она к нему «переедет».

Посмотри на `tight`: ячейки по 8 байт вплотную. Все четыре ячейки
лежат в **одной** строке кэша (4 × 8 = 32 байта меньше 64). Потоки
пишут каждый в свою ячейку, но для кэша это **одна** строка. Она
непрерывно переезжает от ядра к ядру. Данные не общие, а строка
общая. Это называют **ложным разделением** (false sharing `[фолс
шэ́ринг]`).

В `padded` каждая ячейка — ровно 64 байта: 8 полезных и 56 байт
«набивки» (П1.4). Каждая ячейка — своя строка кэша, и ядра друг
другу не мешают. Отсюда четырёхкратная разница.

И теперь понятно, почему `InterlockedIncrement` в П3.4 был
в двенадцать раз медленнее `counter++`: атомарная операция сначала
забирает строку кэша себе в исключительное пользование, и только
потом меняет её. Все ядра стоят к одной строке в очередь.

Правило для гипервизора: **данные разных ядер — в разные строки кэша**.
Проще всего — у каждого ядра своя большая структура, выровненная
по 64 байта или даже по странице (4 КБ). Тогда ложного разделения
не будет.

## П3.9. Код на каждом ядре по очереди

В П3.8 мы прикрепили каждый поток к своему ядру. Как это работает?

**`SetThreadAffinityMask(поток, маска)`** — «разрешить потоку работать
только на этих логических процессорах». Маска — число, где бит номер
`i` означает «процессор `i` разрешён» (битовые маски — П1.2). Маска
`1 << 5` — только процессор 5. Если поток вызывает эту функцию для
себя (`GetCurrentThread()`) и сейчас работает на другом процессоре,
Windows тут же переносит его куда надо.

**`GetCurrentProcessorNumber()`** — номер логического процессора,
на котором поток работает **прямо сейчас**.

Этим способом можно пройти по **всем** ядрам и выполнить на каждом
свой кусочек кода. Гипервизору нужно ровно это: включить режим
гипервизора на ядре 0, потом на 1, потом на 2… на каждом. Попробуем
в обычной программе: на каждом ядре спросим у процессора его
**номер APIC** (глава 34: APIC — контроллер прерываний, у каждого ядра
свой). Он лежит в `cpuid`, лист 1, биты 31–24 регистра `EBX`.

Файл `cores.c`:

```c
#include <windows.h>
#include <intrin.h>
#include <stdio.h>

DWORD WINAPI on_core(LPVOID param)
{
    int want = (int)(DWORD_PTR)param;
    int r[4];

    SetThreadAffinityMask(GetCurrentThread(), (DWORD_PTR)1 << want);  // только это ядро
    __cpuid(r, 1);                                  // лист 1
    int apic = (r[1] >> 24) & 0xFF;                 // EBX, биты 31..24

    printf("asked %2d   running on %2lu   APIC ID %3d\n",
           want, GetCurrentProcessorNumber(), apic);
    return 0;
}

int main(void)
{
    SYSTEM_INFO si;
    GetSystemInfo(&si);
    printf("logical processors: %lu\n", si.dwNumberOfProcessors);

    for (DWORD i = 0; i < si.dwNumberOfProcessors; i++) {
        HANDLE t = CreateThread(NULL, 0, on_core, (LPVOID)(DWORD_PTR)i, 0, NULL);
        WaitForSingleObject(t, INFINITE);           // по очереди: вывод не смешается
        CloseHandle(t);
    }
    return 0;
}
```

`__cpuid(r, 1)` — встроенная функция из `intrin.h`, как `__cpuidex`
в главе 33, только без подлиста. `WaitForSingleObject` — то же, что
`WaitForMultipleObjects`, для одного потока. Мы ждём каждый поток,
прежде чем запускать следующий, поэтому строки идут по порядку.

Настоящий вывод на сервере:

```
logical processors: 4
asked  0   running on  0   APIC ID   0
asked  1   running on  1   APIC ID   1
asked  2   running on  2   APIC ID   2
asked  3   running on  3   APIC ID   3
```

У тебя строк будет **12** на Ryzen и **16** на Core i5-13400F. Главное,
что надо проверить: в каждой строке `asked` равно `running on` —
значит, поток действительно работал там, куда его послали. А номера
APIC у тебя могут идти **с пропусками** и не совпадать с номерами
Windows. Особенно на 13400F: у него ядра двух видов, производительные
и энергоэффективные, и процессор нумерует их по своим правилам. Это
нормально. Номер Windows — порядковый, номер APIC — «адрес» ядра
для прерываний. **Пришли мне вывод с обоих компьютеров**, посмотрим
на них вместе. Это ещё одна разведка перед частью XI.

В драйвере то же самое делают другими средствами. Например,
в наборе для разработки драйверов есть функция `KeIpiGenericCall`,
которая запускает указанную функцию на **всех** процессорах сразу
через межпроцессорное прерывание (IPI, глава 34). Это будет в главе 38.

## П3.10. Что запомнить

1. Общие данные, которые кто-то **меняет**, в многопоточном коде
   опасны. Своё у потока (регистры, стек) — безопасно.
2. `counter++` — это три инструкции: прочитать, изменить, записать.
   Два потока могут прочитать одно значение и потерять прибавление.
   Это **гонка данных**.
3. Гонка проявляется иногда и почти не видна в отладчике. «У меня
   работает» — не доказательство.
4. **Атомарные** операции (`Interlocked…`) неделимы. В ассемблере —
   префикс `lock` (байт `F0`), а `xchg` с памятью атомарна всегда.
5. `InterlockedCompareExchange` — «если там ещё то, что я жду, запиши
   новое». Основа почти всех хитрых приёмов. Инструкция `lock cmpxchg`.
6. **Спин-блокировка**: вход через `InterlockedExchange(l, 1)` в цикле
   с `pause`, выход — записать 0. Держать коротко, внутри не спать,
   всегда освобождать, не входить дважды.
7. **Взаимная блокировка**: два потока ждут друг друга вечно. Лечится
   одним порядком взятия блокировок везде.
8. Лучшая защита — не делить данные: **у каждого ядра своё**.
9. Кэш работает строками по **64 байта**. Данные разных ядер в одной
   строке мешают друг другу — ложное разделение.
10. `SetThreadAffinityMask` + `GetCurrentProcessorNumber` — пройти по
    всем ядрам. В гипервизоре так включают режим на каждом ядре.

третьей? Предскажи и проверь.

**П3.7.** *(практика)* Запусти `cores.exe` на **обоих** своих
компьютерах и пришли мне вывод. Сколько логических процессоров на
каждом? Совпадают ли номера Windows и номера APIC? Есть ли пропуски?

**Тренажёр.** Закрепи приложение в
[тренажёре](https://claude.ai/artifact/2UULEnh9wsTTKAgk9So5Xf), кнопка
«П3»: гонки по шагам, атомарные инструкции, правила блокировок и
строки кэша.

## Что дальше

Теперь ты знаешь, что код живёт не в одиночестве. Ты видел, как
теряются данные, и умеешь это предотвратить: атомарными операциями,
спин-блокировкой или лучше всего — раскладкой «у каждого ядра своё».
И ты уже умеешь пройти по всем ядрам и выполнить на каждом свой код.

Всё это понадобится в драйвере (часть IX) и особенно в гипервизоре
(часть XI): там твой обработчик будет работать на всех ядрах сразу,
и каждая общая переменная должна быть под защитой.

Вернись к основному курсу, к той главе, на которой ты сейчас.
