# Глава 15. Наблюдение за поведением

> **Часть V. Инструменты**
> Предыдущая глава: [14. Ghidra](14-ghidra.md)

Два главных инструмента у тебя уже есть: **Ghidra** показывает программу
целиком, **x64dbg** — живьём, по одной инструкции. Оба требуют лезть
внутрь, в код.

Есть третий взгляд, самый простой: **смотреть снаружи**. Не читать
инструкции, а наблюдать, что программа **делает с системой**: какие файлы
открывает, что пишет в реестр, какие процессы запускает, куда подключается
по сети. Это называется **анализ поведения** (behavioral analysis
`[бихéйвьерал анáлисис]`).

Звучит скромно, но на практике с этого часто начинают. За пять минут
наблюдения можно понять, где программа хранит настройки, почему не
запускается и что она делает на самом деле. И только потом решать, какую
функцию разбирать в Ghidra.

После главы ты будешь уметь:

- записывать всё, что программа делает с файлами и реестром, в Process
  Monitor;
- отсеивать лишнее фильтрами и читать результат каждой операции;
- от события в журнале переходить к коду, который его вызвал;
- смотреть открытые программой файлы и загруженные библиотеки
  в Process Explorer;
- записывать вызовы функций Windows вместе с аргументами прямо в x64dbg.

## 15.1. Программа как чёрный ящик

Вспомни главу 12: всё, что выходит за пределы вычислений в собственной
памяти, программа делает **через Windows**. Прочитать файл, записать
в реестр, открыть сетевое соединение — это всегда просьба к системе.

А раз просьбы проходят через систему, **систему можно попросить
рассказать о них**. Этим и занимаются инструменты этой главы. Им не нужно
понимать код программы: они стоят «на проходной» и записывают, кто что
пронёс.

Отсюда сильные и слабые стороны метода:

| Плюс | Минус |
|---|---|
| быстро, не нужно читать код | видно **что** сделано, но не **почему** |
| работает с любой программой, на любом языке | видно только то, что случилось при этом запуске (как и у отладчика) |
| сразу показывает файлы, ключи реестра, адреса | программу приходится **запускать** |

Последний минус важен. В главе 7 мы договорились: незнакомую программу
не запускают на своей основной системе. Анализ поведения чужих программ
делают в **виртуальной машине**. Сегодня мы наблюдаем за своей учебной
программой, поэтому можно прямо на основной Windows.

## 15.2. Подопытная программа

Как обычно, начнём со своей программы, чтобы сверять увиденное
с исходником. Она делает три типичные для настоящих программ вещи: ищет
файл настроек, считает свои запуски в реестре и пишет файл.

Создай в `C:\reverse\work\` файл `behave.c` (`notepad behave.c`):

```c
#include <windows.h>
#include <stdio.h>

int main(void)
{
    HANDLE h;
    HKEY key;
    DWORD runs = 0, size = sizeof runs, written;

    /* 1. Ищем файл настроек */
    h = CreateFileW(L"config.ini", GENERIC_READ, 0, NULL,
                    OPEN_EXISTING, 0, NULL);
    if (h == INVALID_HANDLE_VALUE) {
        printf("No config.ini, using defaults\n");
    } else {
        printf("Found config.ini\n");
        CloseHandle(h);
    }

    /* 2. Считаем запуски в реестре */
    if (RegCreateKeyExW(HKEY_CURRENT_USER, L"Software\\ReverseCourse", 0, NULL,
                        0, KEY_READ | KEY_WRITE, NULL, &key, NULL) == ERROR_SUCCESS) {
        RegQueryValueExW(key, L"Runs", NULL, NULL, (BYTE *)&runs, &size);
        runs++;
        RegSetValueExW(key, L"Runs", 0, REG_DWORD, (const BYTE *)&runs, sizeof runs);
        RegCloseKey(key);
    }
    printf("Run number %lu\n", runs);

    /* 3. Пишем заметку и держим файл открытым, пока не нажмут Enter */
    h = CreateFileW(L"notes.txt", GENERIC_WRITE, 0, NULL,
                    CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
    if (h != INVALID_HANDLE_VALUE)
        WriteFile(h, "hello from behave\r\n", 19, &written, NULL);

    printf("Press Enter to exit\n");
    getchar();

    if (h != INVALID_HANDLE_VALUE)
        CloseHandle(h);
    return 0;
}
```

Знакомые по главе 12 функции: `CreateFileW` открывает файл, `WriteFile`
пишет, `CloseHandle` закрывает дескриптор. Новые — функции реестра:

| Функция | Что делает |
|---|---|
| `RegCreateKeyExW` | открыть раздел реестра, а если его нет — создать |
| `RegQueryValueExW` | прочитать значение из раздела |
| `RegSetValueExW` | записать значение |
| `RegCloseKey` | закрыть раздел |

**Реестр** (registry `[рéджистри]`) — это большая база настроек Windows
и программ. Устроен как дерево папок: **разделы** (keys) и в них
**значения** (values). `HKEY_CURRENT_USER`, сокращённо `HKCU`, — ветка
настроек текущего пользователя. Наша программа создаёт в ней раздел
`Software\ReverseCourse` и хранит там число `Runs`.

Собери:

```
gcc -O0 -o behave.exe behave.c
```

Функции реестра лежат в `advapi32.dll` (глава 12). Отдельно указывать
её gcc не нужно — он подключает её сам.

**Пока не запускай.** Сначала подготовим наблюдателя.

## 15.3. Process Monitor

**Process Monitor** `[прóцесс мóнитор]`, сокращённо **Procmon**, —
бесплатный инструмент Microsoft из набора **Sysinternals** `[сисинтéрналс]`.
Это главный инструмент наблюдения в Windows. Он записывает каждое
обращение каждой программы к файлам, реестру, процессам и сети.

**Установка:**

1. Официальная страница: **learn.microsoft.com/sysinternals** → раздел
   Process Monitor. Архив называется `ProcessMonitor.zip`.
2. Распакуй в `C:\reverse\tools\procmon\`.
3. Запускай `Procmon64.exe` — версию для 64-битной Windows.

> На момент написания главы свежая версия — **4.11** от 10 сентября 2026
> года. Официально она работает на Windows 11 и новее. Проверь
> актуальность на сайте.

Procmon попросит **права администратора** — Windows покажет окно «Разрешить
этому приложению вносить изменения?». Соглашайся. Права нужны не просто так:
чтобы видеть обращения **всех** программ, Procmon загружает в ядро Windows
свой **драйвер** — модуль, работающий на самом низком уровне системы.
Запомни это: в главе 29 ты напишешь свой драйвер, а в главе 31 научишься
разбирать чужие.

При первом запуске покажут лицензионное соглашение — **Agree**
(«Согласен»). Потом сразу откроется окно фильтра. Пока закрой его
кнопкой **OK** — вернёмся к нему через минуту.

И ты увидишь **лавину**. Тысячи строк в секунду: Windows и все запущенные
программы постоянно что-то читают и пишут. Это нормально. Без фильтров
Procmon бесполезен, а с фильтрами — незаменим.

Три кнопки, которые нужны сразу:

| Клавиши | Действие |
|---|---|
| `Ctrl+E` | включить или выключить запись (capture — «захват») |
| `Ctrl+X` | очистить список |
| `Ctrl+L` | открыть фильтр |

Нажми `Ctrl+E`, чтобы остановить запись, и `Ctrl+X`, чтобы очистить
экран.

## 15.4. Фильтр: оставляем только нашу программу

Нажми `Ctrl+L` — откроется окно **Process Monitor Filter** («Фильтр»).
В нём строится правило из четырёх частей:

```
[ Process Name ▼ ]  [ is ▼ ]  [ behave.exe      ]  then  [ Include ▼ ]
   что проверяем       как         значение                  что делать
```

Читается как фраза: «если **имя процесса** (Process Name) **равно** (is)
`behave.exe`, **то показать** (Include)». Заполни так, нажми **Add**
(«Добавить»), потом **OK**.

Заметь: программу можно ещё не запускать. Фильтр ждёт процесс с этим
именем и покажет его, как только тот появится.

Остальные варианты пригодятся позже:

| Поле | Перевод | Пример |
|---|---|---|
| `Process Name` | имя процесса | `behave.exe` |
| `Path` | путь к файлу или ключу | `contains` (содержит) `ReverseCourse` |
| `Operation` | вид операции | `is` `RegSetValue` |
| `Result` | результат | `is` `NAME NOT FOUND` |
| `Exclude` | вместо Include — «скрыть» | убрать надоевший шум |

Совет: любую строку в списке можно щёлкнуть **правой кнопкой** и выбрать
**Include** или **Exclude** — Procmon сам добавит в фильтр правило по
значению под курсором. Так шум убирается за пару кликов.

## 15.5. Запускаем и читаем

Включи запись (`Ctrl+E`) и запусти программу из консоли w64devkit,
находясь в `C:\reverse\work\`: `./behave.exe`. Программа напечатает:

```
No config.ini, using defaults
Run number 1
Press Enter to exit
```

Пока **не нажимай Enter** и посмотри в Procmon. Строк будет несколько
сотен. Большая часть — служебная работа: загрузка библиотек, чтение
системных настроек. Среди неё найдутся **наши** операции. Вот они, без
служебных строк (у тебя время и порядок соседних строк могут
отличаться):

| Operation | Path | Result |
|---|---|---|
| `CreateFile` | `C:\reverse\work\config.ini` | `NAME NOT FOUND` |
| `RegCreateKey` | `HKCU\Software\ReverseCourse` | `SUCCESS` |
| `RegQueryValue` | `HKCU\Software\ReverseCourse\Runs` | `NAME NOT FOUND` |
| `RegSetValue` | `HKCU\Software\ReverseCourse\Runs` | `SUCCESS` |
| `RegCloseKey` | `HKCU\Software\ReverseCourse` | `SUCCESS` |
| `CreateFile` | `C:\reverse\work\notes.txt` | `SUCCESS` |
| `WriteFile` | `C:\reverse\work\notes.txt` | `SUCCESS` |

Сверь с исходником — каждая строка на своём месте:

1. Программа попыталась открыть `config.ini` и получила `NAME NOT FOUND` —
   «имя не найдено», файла нет. Поэтому она напечатала `No config.ini`.
2. Открыла (создала) раздел реестра.
3. Попыталась прочитать `Runs` — значения ещё нет, `NAME NOT FOUND`.
   Поэтому `runs` осталось нулём, а после `runs++` стало единицей.
4. Записала `Runs`. В столбце **Detail** («Подробности») будет
   `Type: REG_DWORD, Length: 4, Data: 1` — тип, размер и само значение.
5. Закрыла раздел, создала `notes.txt` и записала в него 19 байт.

`CloseFile` для `notes.txt` пока нет: программа держит файл открытым
и ждёт Enter. Нажми Enter в её окне — строка `CloseFile` появится.

**Запусти программу второй раз.** Теперь `RegQueryValue` вернёт `SUCCESS`
с `Data: 1`, а записано будет уже `Data: 2`. Procmon показывает и то, что
программа прочитала, и то, что записала.

### Главный приём: `NAME NOT FOUND`

Первая строка таблицы — самая интересная. **Программа искала файл,
которого нет.** В настоящем анализе такие строки ценнее всего: они
рассказывают, **что программа ожидает найти**. Файл настроек, ключ
реестра с параметрами, библиотеку, которую она пытается загрузить.

Проверь сам. Создай пустой файл — в консоли w64devkit это команда `touch`
(«коснуться»):

```
touch config.ini
```

и запусти программу снова (`./behave.exe`). Она скажет `Found config.ini`,
а в Procmon у `CreateFile` будет `SUCCESS`. Ты изменил поведение программы, не
заглянув в её код, — только подсмотрев, что она ищет.

Отсюда рабочий приём: **отфильтруй `Result` → `is` → `NAME NOT FOUND`**
и посмотри, чего программе не хватает.

### Словарь результатов

Столбец **Result** («Результат») — главный. Самые частые значения:

| Result | Перевод | Что значит |
|---|---|---|
| `SUCCESS` | успех | операция прошла |
| `NAME NOT FOUND` | имя не найдено | файла или значения реестра нет |
| `PATH NOT FOUND` | путь не найден | нет папки или раздела на пути |
| `ACCESS DENIED` | доступ запрещён | не хватает прав |
| `BUFFER OVERFLOW` | буфер переполнен | см. ниже |
| `END OF FILE` | конец файла | дочитали до конца |

Про `BUFFER OVERFLOW` — важная оговорка. В главе 11 переполнение буфера
было атакой. **Здесь это не атака.** Программа спросила, например,
значение реестра, но дала слишком маленький буфер. Windows ответила:
«не влезает, вот сколько нужно». Программа выделяет буфер побольше
и спрашивает снова. Обычная вежливая переписка, не пугайся.

## 15.6. От события — к коду

Procmon сказал, **что** случилось. Теперь узнаем, **какой код** это
сделал.

Дважды щёлкни по строке `CreateFile` с `config.ini`. Откроется окно
**Event Properties** («Свойства события») с тремя вкладками. Нас интересует
вкладка **Stack** («Стек»). Там — **стек вызовов** в момент события,
та самая цепочка кадров из главы 11: кто кого вызвал, чтобы дело дошло
до открытия файла.

Выглядит она примерно так (сверху — самое глубокое):

```
K  ...                          (функции ядра Windows)
U  ntdll.dll       NtCreateFile
U  KERNELBASE.dll  CreateFileW
U  behave.exe      behave.exe + 0x152c
U  behave.exe      behave.exe + 0x...  (стартовый код)
U  KERNEL32.DLL    BaseThreadInitThunk
U  ntdll.dll       RtlUserThreadStart
```

`K` — kernel, код ядра; `U` — user, пользовательский код. Сейчас смотри
на строки `U`.

Читаем снизу вверх: система запустила поток, стартовый код вызвал `main`,
`main` вызвала `CreateFileW`, та — `NtCreateFile` из `ntdll`, дальше —
ядро. Строка **`behave.exe + 0x152c`** — место в **нашей** программе.
Число `0x152c` — это **RVA** (глава 8), смещение от начала образа.

Это не адрес `call`, а **адрес возврата** — инструкция сразу после вызова
(глава 11). В Ghidra перейди на `140000000 + 152c = 14000152c` (клавиша
**G**) и посмотри на одну инструкцию выше:

```
140001519  LEA   RAX,[u_config.ini_140009000]
140001520  MOV   RCX,RAX
140001523  MOV   RAX,qword ptr [__imp_CreateFileW]
14000152a  CALL  RAX
14000152c  MOV   qword ptr [RBP + local_10],RAX      ← адрес возврата
```

(Это настоящий листинг Ghidra 12.1.4. `u_` в имени строки — значит
строка в UTF-16, «широкая», как и положено для функции с суффиксом `W`
из главы 12.)

Вот он, вызов `CreateFileW`, который искал `config.ini`.

Заодно ты встретил **третью форму вызова функции Windows**. В главе 12
было `call [адрес в таблице импортов]`, в главе 13 — `call <JMP.&getchar>`
через переходник. Здесь адрес сначала загружается из таблицы импортов
в `RAX`, а потом `call rax`. Суть одна: адрес берётся из таблицы импортов.
Какую форму выберет компилятор, зависит от его версии и настроек.

**Цепочка «событие → стек → RVA → Ghidra»** — очень сильный приём.
В большой программе на десятки тысяч функций он за минуту приводит
к коду, который пишет в интересующий тебя файл или ключ реестра.

## 15.7. Process Explorer: что у процесса внутри

Procmon записывает **события** — что происходило во времени. А иногда
нужен **снимок**: что у процесса есть прямо сейчас. Какие библиотеки
загружены, какие файлы открыты. Для этого — **Process Explorer** из того же
набора Sysinternals.

**Установка:** та же страница Sysinternals → Process Explorer, архив
`ProcessExplorer.zip`. Распакуй в `C:\reverse\tools\procexp\` и запусти
`procexp64.exe`. На момент написания главы свежая версия — **17.14**.

Главное окно — дерево всех процессов: кто кого запустил. Это как
Диспетчер задач, только честнее и подробнее.

Запусти `behave.exe` и **не нажимай Enter** — программа будет ждать
с открытым файлом `notes.txt`. Найди `behave.exe` в дереве (скорее всего,
он будет «ребёнком» консоли w64devkit) и выдели его.

Теперь включи нижнюю панель: меню **View** («Вид») → **Show Lower Pane**
(«Показать нижнюю панель»), клавиши `Ctrl+L`. В ней два режима:

| Клавиши | Режим | Что показывает |
|---|---|---|
| `Ctrl+D` | DLLs | все загруженные библиотеки процесса |
| `Ctrl+H` | Handles | все открытые **дескрипторы** (глава 12) |

Включи **Handles** (`Ctrl+H`). В списке среди прочего найдётся строка:

```
Type: File     Name: C:\reverse\work\notes.txt
```

Вот он, дескриптор, который вернула `CreateFileW`. В главе 12 мы говорили:
дескриптор — это номер открытого объекта в системной таблице. Process
Explorer показывает эту таблицу для процесса целиком. Нажми Enter в окне
программы — строка исчезнет: сработал `CloseHandle`.

Переключись на **DLLs** (`Ctrl+D`). Там `kernel32.dll`, `advapi32.dll`,
`msvcrt.dll` — те самые библиотеки, что были в импортах (главы 7 и 8),
плюс их собственные зависимости.

Ещё две возможности Process Explorer, которые пригодятся позже:

- **Двойной щелчок по процессу** → вкладка **Strings** («Строки»). Внизу
  переключатель **Image** / **Memory**: строки из файла на диске или из
  памяти работающего процесса. Во втором случае видны строки, которые
  программа расшифровала во время работы. Вспомни об этом, когда дойдёшь
  до главы 17.
- **Фиолетовый цвет** строки процесса означает, что Process Explorer
  подозревает **упакованный** файл (глава 24).

## 15.8. Запись вызовов WinAPI с аргументами

Procmon показывает операции на уровне системы. Но часто хочется видеть
именно **вызовы функций Windows**: какая функция, с какими аргументами.
Например, все вызовы `CreateFileW` с именами файлов.

Для этого долго был популярен **API Monitor** (сайт rohitab.com). Честно
о нём: последняя версия — v2 r13, **2013 года**, и та с пометкой «альфа».
Официально он поддерживает системы до Windows 8. На Windows 11 он иногда
работает, иногда нет. Если захочешь попробовать — качай только
с официального сайта. А мы освоим способ, который работает точно, и
в инструменте, который у тебя уже есть.

### Точка останова, которая не останавливает

В главе 13 точка останова останавливала программу. Но x64dbg умеет больше:
точка может **не останавливать**, а только **записать сообщение в журнал**
и пустить программу дальше.

Открой `behave.exe` в x64dbg. На первой остановке (системная точка
останова, глава 13) введи в строку **Command** внизу окна три команды,
каждую с Enter:

```
bp kernel32:CreateFileW
bpcond kernel32:CreateFileW, 0
bplog kernel32:CreateFileW, "CreateFileW: {utf16@rcx}"
```

Разберём:

1. **`bp kernel32:CreateFileW`** — поставить точку останова на начало
   функции `CreateFileW` из `kernel32.dll`. Запись `модуль:функция` x64dbg
   понимает сам — адрес искать не нужно.
2. **`bpcond ..., 0`** — условие остановки (break condition): `0`, то есть
   «никогда не останавливаться».
3. **`bplog ..., "..."`** — текст для журнала. `{utf16@rcx}` значит:
   «возьми адрес из `RCX` и напечатай строку UTF-16, которая там лежит».

Почему `RCX`? Мы стоим на **первой инструкции** `CreateFileW`, когда она
только что вызвана. По соглашению о вызовах (глава 12) первый аргумент —
в `RCX`, а первый аргумент `CreateFileW` — имя файла. Почему UTF-16?
Потому что суффикс `W` (тоже глава 12).

Нажми **F9** и дай программе поработать. Потом открой вкладку **Log**
(`Alt+L`):

```
CreateFileW: config.ini
CreateFileW: notes.txt
```

Программа ни разу не остановилась, а журнал записал каждый вызов вместе
с именем файла. Кроме наших двух, могут мелькнуть служебные вызовы
системных библиотек — это нормально.

То же можно сделать мышкой: поставь точку клавишей F2, щёлкни по строке
правой кнопкой → **Breakpoint** → **Edit** («Изменить»). В окне **Edit
breakpoint** заполни поля **Break Condition** («Условие остановки»)
и **Log Text** («Текст для журнала»), нажми **Save** («Сохранить»).

По этому образцу записывается любая функция: достаточно знать, в каком
регистре лежит нужный аргумент. Документация Microsoft даёт порядок
параметров, соглашение о вызовах — регистры. Ты собрал из двух глав
собственный мини-API-монитор.

## 15.9. Сеть

У Procmon есть и сетевые события. На панели инструментов пять кнопок-фильтров
по классам событий: реестр, файлы, **сеть**, процессы и потоки,
профилирование. Сетевые операции выглядят как `TCP Connect`
(«подключение»), `TCP Send` («отправка»), `TCP Receive` («получение»),
а в столбце **Path** — адреса: откуда и куда, с номерами портов.

Для живой картины всех соединений в системе есть ещё одна утилита
Sysinternals — **TCPView**: таблица «какой процесс с каким адресом сейчас
соединён». Наши учебные программы в сеть не ходят, поэтому здесь только
упоминаем её: когда понадобится — ты знаешь, где искать.

## 15.10. Какой инструмент когда

| Вопрос | Инструмент |
|---|---|
| Какие файлы и ключи реестра программа трогает? | **Process Monitor** |
| Что программа ищет и не находит? | Procmon, фильтр `NAME NOT FOUND` |
| Какой код сделал эту операцию? | Procmon → **Stack** → RVA → Ghidra |
| Что у процесса открыто и загружено сейчас? | **Process Explorer** |
| Какие строки в памяти работающей программы? | Process Explorer → Strings → Memory |
| С какими аргументами вызывается функция WinAPI? | **x64dbg**, точка с журналом |
| С кем программа соединяется по сети? | Procmon (сеть), **TCPView** |

Типичный порядок работы с незнакомой программой теперь выглядит так:
**глава 7** (первое вскрытие, без запуска) → **глава 15** (понаблюдать
снаружи, в виртуальной машине) → **глава 14** (найти интересный код
в Ghidra) → **глава 13** (проверить догадки в x64dbg).

## 15.11. Что запомнить

1. **Анализ поведения** — наблюдение снаружи: что программа делает
   с файлами, реестром, процессами и сетью. Быстро, но показывает **что**,
   а не **почему**. Чужие программы — только в виртуальной машине.
2. **Process Monitor** записывает все обращения к системе. Без **фильтра**
   (`Ctrl+L`) бесполезен: оставляй `Process Name is имя.exe`.
3. Главный столбец — **Result**. `NAME NOT FOUND` показывает, что
   программа **ищет и не находит**, — ценная подсказка.
   `BUFFER OVERFLOW` в Procmon — не атака, а просьба дать буфер побольше.
4. Вкладка **Stack** в свойствах события ведёт к коду: `модуль + RVA` —
   это адрес возврата, сам вызов стоит на инструкцию выше.
5. Функции Windows вызываются тремя способами: `call [таблица импортов]`,
   `call <JMP.&имя>` через переходник и `mov rax,[таблица импортов]` +
   `call rax`. Суть одна.
6. **Process Explorer** — снимок процесса: дерево процессов, открытые
   дескрипторы (`Ctrl+H`), библиотеки (`Ctrl+D`), строки в памяти.
7. **x64dbg** записывает вызовы WinAPI с аргументами: точка останова
   с условием `0` и текстом для журнала, аргументы — по регистрам
   из главы 12.
8. **Реестр** — база настроек: разделы и значения, `HKCU` — ветка
   текущего пользователя.

## Упражнения

Упражнения 15.4 и 15.5 — практические.

**15.1.** Почему анализ поведения чужой программы делают в виртуальной
машине, хотя Procmon сам по себе безопасен?

**15.2.** Ты наблюдаешь за незнакомой программой и видишь в Procmon:

```
CreateFile  C:\Users\user\AppData\Roaming\Tool\settings.json   NAME NOT FOUND
RegOpenKey  HKCU\Software\Tool                                  NAME NOT FOUND
CreateFile  C:\Users\user\AppData\Roaming\Tool\settings.json   SUCCESS
WriteFile   C:\Users\user\AppData\Roaming\Tool\settings.json   SUCCESS
```

Что можно сказать о программе? Что, скорее всего, произойдёт при втором
запуске?

**15.3.** В Procmon у операции `RegQueryValue` стоит результат
`BUFFER OVERFLOW`. Кто-то атакует программу? Что на самом деле
произошло и что ты, скорее всего, увидишь в следующей строке?

**15.4.** *(практика)* Во вкладке **Stack** у события `RegSetValue` видно
`behave.exe + 0x1632`. Найди это место в Ghidra. Какая инструкция стоит
по этому адресу и где сам вызов? Как убедиться, что вызывается именно
`RegSetValueExW`?

**15.5.** *(практика)* Настрой в x64dbg запись вызовов `RegSetValueExW`
так, чтобы в журнале было видно **имя** записываемого значения. В каком
регистре его искать? Для любознательных: пятый аргумент — указатель на
сами данные. Где он лежит в момент входа в функцию и как напечатать
4 байта по этому указателю?

**15.6.** Ghidra показала в `behave.exe` такой вызов:

```c
RegCreateKeyExW((HKEY)0xffffffff80000001,L"Software\\ReverseCourse",0,(LPWSTR)0x0,0,
                0x2001f,(LPSECURITY_ATTRIBUTES)0x0,&local_18,(LPDWORD)0x0);
```

Что за число `0xffffffff80000001` в первом аргументе? А `0x2001f`?
Подсказка: загляни в исходник `behave.c` и в документацию Microsoft.

**15.7.** Какой инструмент выберешь для каждой задачи?
а) узнать, какую DLL программа пытается загрузить и не находит;
б) увидеть, какие файлы программа держит открытыми прямо сейчас;
в) узнать, с какими именами файлов программа вызывает `CreateFileW`;
