# Глава 14. Ghidra

> **Часть V. Инструменты**
> Предыдущая глава: [13. x64dbg](13-x64dbg.md)

В прошлой главе ты смотрел на программу **живьём**: останавливал её,
шагал, менял регистры. Отладчик честно показывает, что происходит, — но
только на той дорожке, по которой программа пошла прямо сейчас.

Сегодня — второй главный инструмент реверсера, **Ghidra** `[гúдра]`. Она
не запускает программу. Она читает файл целиком, находит в нём все функции,
все строки, все связи между ними — и переводит машинный код обратно
в подобие языка C. Это называется **декомпиляция** (decompilation
`[дикомпилéйшен]`).

После главы ты будешь уметь:

- создавать проект в Ghidra и запускать анализ программы;
- ориентироваться в главном окне: список функций, листинг, декомпилятор;
- читать вывод декомпилятора и понимать, где он ошибается;
- находить нужный код по строкам и перекрёстным ссылкам;
- давать имена функциям и переменным и чинить их типы;
- переносить адреса между Ghidra и x64dbg.

Нужны **Ghidra** с **JDK** (ставили в главе 6) и `debugme.exe` из главы 13.

---

## 14.1. Что делает декомпилятор — и чего не делает

Вспомни главу 2. При компиляции теряется многое: имена переменных,
комментарии, типы данных, красивая структура `if` и `for`. От программы
остаются только машинные инструкции и данные.

Декомпилятор пытается проделать путь назад: по инструкциям **угадать**,
какой код на C мог их породить. Результат называют **псевдокодом**
(pseudocode `[сьюдокóуд]`, «ненастоящий код»). Он похож на C, его легко
читать, но это не исходник автора.

Что важно понимать с самого начала:

- **Имена переменных декомпилятор придумывает сам.** Их в файле нет.
  Вместо `result` будет `uVar1`, вместо `x` — `param_1`.
- **Типы он тоже угадывает.** Иногда ошибается, и тогда в коде появляются
  странные преобразования типов.
- **Структура получается похожей, но не той же.** Компилятор мог
  перестроить код, и декомпилятор покажет перестроенный вариант.
- **Декомпилятор может ошибиться.** Поэтому ассемблер из глав 9–12 нужен
  и дальше: когда псевдокод выглядит странно, правду говорят инструкции.

Проще всего думать о декомпиляторе как о **переводчике-помощнике**. Он
быстро даёт общий смысл, а в спорных местах ты проверяешь по оригиналу.

## 14.2. Запуск и проект

Запусти `ghidraRun.bat` из `C:\reverse\tools\ghidra\...` (глава 6). При
первом запуске Ghidra покажет:

- **User Agreement** («Пользовательское соглашение») — нажми **I Agree**
  («Я согласен»);
- **Tip of the Day** («Совет дня») — просто закрой.

Откроется маленькое окно — **Project Manager** («менеджер проектов»).
Ghidra работает не с отдельными файлами, а с **проектами**. Проект — это
папка, где Ghidra хранит результаты анализа: найденные функции, твои
переименования и комментарии. Сам `.exe` при этом никто не трогает.
Та же идея, что у базы x64dbg из главы 13.

Создадим проект один раз на весь курс:

1. **File** («Файл») → **New Project** («Новый проект»), или `Ctrl+N`.
2. Выбери **Non-Shared Project** («Проект без общего доступа») — для
   работы в одиночку. Нажми **Next** («Далее»).
3. **Project Directory** («Папка проекта») — укажи `C:\reverse\ghidra`
   (создай её, если нет). **Project Name** («Имя проекта») — `course`.
4. Нажми **Finish** («Готово»).

## 14.3. Импорт и автоматический анализ

Теперь добавим в проект программу.

1. **File** → **Import File** («Импортировать файл»), клавиша **I**. Или
   просто перетащи `debugme.exe` в окно проекта.
2. Появится окно импорта. Ghidra сама определит формат:

```
Format:    Portable Executable (PE)
Language:  x86:LE:64:default:windows
```

Строку `Language` («язык») стоит уметь читать — в ней всё, что ты знаешь:

| Часть | Что значит | Где было |
|---|---|---|
| `x86` | семейство процессоров | глава 9 |
| `LE` | little-endian, младший байт первым | глава 3 |
| `64` | 64-битный код | глава 8 |
| `windows` | правила Windows, включая соглашение о вызовах | глава 12 |

3. Нажми **OK**. Ghidra покажет отчёт об импорте (**Import Results
   Summary**) — закрой его кнопкой **OK**.

Файл появился в проекте. **Дважды щёлкни** по нему — откроется главное
окно, **CodeBrowser** («обозреватель кода»). И сразу вопрос:

```
debugme.exe has not been analyzed. Would you like to analyze it now?
```

«Файл ещё не проанализирован. Проанализировать сейчас?» Нажми **Yes**
(«Да»). В следующем окне — длинный список видов анализа (**Analysis
Options**). Ничего не меняй, нажми **Analyze** («Анализировать»).

В правом нижнем углу побежит полоска прогресса. Для нашей маленькой
программы — секунды, для больших — минуты и даже часы.

Что Ghidra делает при анализе:

- начиная с точки входа, дизассемблирует код и находит **все функции**;
- находит **строки** и другие данные;
- строит **перекрёстные ссылки** — кто кого вызывает и кто какие данные
  трогает;
- угадывает **типы** и параметры функций;
- подставляет **имена**, если они сохранились в файле.

## 14.4. Главное окно

После анализа CodeBrowser выглядит примерно так:

```
┌──────────────────┬──────────────────────────┬──────────────────────┐
│ Program Trees    │                          │                      │
│ (дерево файла)   │   LISTING                │   DECOMPILE          │
├──────────────────┤   дизассемблер:          │   декомпилятор:      │
│ Symbol Tree      │   адрес, байты,          │   псевдокод на C     │
│ (имена: функции, │   инструкции, метки,     │   для функции,       │
│  импорты, ...)   │   перекрёстные ссылки    │   где стоит курсор   │
├──────────────────┤                          │                      │
│ Data Type Manager│                          │                      │
│ (типы данных)    │                          │                      │
├──────────────────┴──────────────────────────┴──────────────────────┤
│ Console — сообщения Ghidra                                          │
└─────────────────────────────────────────────────────────────────────┘
```

| Окно | Перевод | Зачем |
|---|---|---|
| **Program Trees** | дерево программы | секции файла: `.text`, `.data`, `.rdata`… (глава 8) |
| **Symbol Tree** | дерево символов | все имена: функции, импорты, экспорты, метки |
| **Data Type Manager** | менеджер типов данных | типы: `int`, структуры, типы Windows |
| **Listing** | листинг | дизассемблированный код всего файла |
| **Decompile** | декомпилятор | псевдокод текущей функции |
| **Console** | консоль | служебные сообщения |

Самые важные — **Symbol Tree**, **Listing** и **Decompile**. С ними ты
будешь проводить почти всё время.

Если какое-то окно случайно закрылось — все они открываются заново через
меню **Window** («Окно»). Декомпилятор — ещё и сочетанием `Ctrl+E`.

## 14.5. Первая встреча с декомпилятором

В **Symbol Tree** раскрой папку **Functions** («Функции») и найди `main`.
Щёлкни по ней. Листинг перепрыгнет на начало `main`, а в окне
**Decompile** появится вот что:

```c
int __cdecl main(int _Argc,char **_Argv,char **_Env)

{
  uint uVar1;
  
  __main();
  uVar1 = square_plus(7,5);
  printf("Result: %d\n",(ulonglong)uVar1);
  getchar();
  return 0;
}
```

Это настоящий вывод Ghidra 12.1.4 на нашей программе. Положи рядом
исходник из главы 13:

```c
int main(void)
{
    int a = 7;
    int b = square_plus(a, 5);
    printf("Result: %d\n", b);
    getchar();
    return 0;
}
```

Похоже? Очень. Но различия поучительны, разберём каждое.

**Имена функций на месте.** `main`, `square_plus`, `printf` — Ghidra знает
их. Откуда, если x64dbg в главе 13 имён не показал? Из **таблицы символов**:
gcc по умолчанию оставляет в файле имена функций (глава 2 — помнишь, что
`strip` уменьшил файл в шесть раз?). Ghidra эту таблицу читает, а x64dbg
её, как правило, не использует. В чужих программах таблицы символов
обычно нет — к этому случаю вернёмся в разделе 14.7.

**Переменная `a` исчезла.** Вместо неё — сразу `square_plus(7,5)`.
Декомпилятор заметил, что `a` нигде больше не нужна, и просто подставил
её значение. Код стал короче, но переменной автора ты не увидишь.

**`b` превратилась в `uVar1`.** Имён локальных переменных в файле нет,
и Ghidra придумывает свои. Первая буква подсказывает догадку о типе:
`u` — беззнаковое или просто непонятно какое, `i` — `int`, `b` — байт,
`c` — символ, `p` — указатель. `Var` — «переменная», `1` — номер.

**`(ulonglong)` перед `uVar1`.** Декомпилятор не уверен в типе и вставил
преобразование: «расширить до 8-байтового беззнакового числа». Это
артефакт — в исходнике ничего такого не было. Такие «шумные»
преобразования типов (casts `[кастс]`) — самая частая странность
псевдокода. Научись смотреть сквозь них.

**`main` с тремя параметрами.** `_Argc`, `_Argv`, `_Env` — это
стандартные параметры `main` в Windows: число аргументов командной строки,
сами аргументы и переменные окружения. Ghidra знает, как обычно выглядит
`main`, и подставила полную форму. Наша `main(void)` их просто не
использует.

Теперь щёлкни по `square_plus` в декомпиляторе дважды — Ghidra перейдёт
в неё:

```c
int square_plus(int param_1,int param_2)

{
  return param_2 + param_1 * param_1;
}
```

Три строки вместо пятнадцати инструкций из главы 13. Имя функции есть,
а имена параметров — нет: `param_1` и `param_2`. Имена параметров
в таблице символов не хранятся, только имена функций. А локальная
переменная `r` исчезла так же, как `a`.

**Вот в чём сила декомпилятора.** В главе 13 мы пятнадцать шагов
разбирали, что делает эта функция. Здесь смысл виден за секунду:
«вернуть `param_2 + param_1 * param_1`».

## 14.6. Листинг и декомпилятор в паре

Окна связаны. Щёлкни по строке `uVar1 = square_plus(7,5);`
в декомпиляторе — в листинге подсветятся инструкции, из которых она
получилась. И наоборот: щёлкнешь по инструкции в листинге — подсветится
строка псевдокода. Это лучший способ научиться переводить ассемблер в C
и обратно: смотри, какая строка из каких инструкций родилась.

Листинг Ghidra показывает тот же код, что x64dbg, но в своей манере.
Вот начало `main`:

```
1400014fb  55                     PUSH  RBP
1400014fc  48 89 e5               MOV   RBP,RSP
1400014ff  48 83 ec 30            SUB   RSP,0x30
140001503  e8 18 01 00 00         CALL  __main
140001508  c7 45 fc 07 00 00 00   MOV   dword ptr [RBP + local_c],0x7
14000150f  8b 45 fc               MOV   EAX,dword ptr [RBP + local_c]
140001512  ba 05 00 00 00         MOV   EDX,0x5
140001517  89 c1                  MOV   ECX,EAX
140001519  e8 b6 ff ff ff         CALL  square_plus
```

Сравни с x64dbg:

| | x64dbg | Ghidra |
|---|---|---|
| Адреса | со сдвигом ASLR: `00007FF6C9A214FB` | как в файле: `1400014fb` |
| Числа | hex без `0x`: `30` | hex с `0x`: `0x30` |
| Буквы | маленькие: `push rbp` | большие: `PUSH RBP` |
| Переменные на стеке | `ss:[rbp-4]` | `[RBP + local_c]` |
| Вызовы | по адресу | по имени, если оно известно |

`local_c` — имя, которое Ghidra дала ячейке стека. Число в имени — это
смещение в hex. Считается оно не от `RBP`, а от значения `RSP` в момент
входа в функцию, поэтому `[rbp-4]` превратился в `local_c`, а не
в `local_4`. Не ломай над этим голову: важно, что **одинаковое имя —
одна и та же переменная**. Это удобнее, чем следить за смещениями.

## 14.7. Когда имён нет

С именами всё слишком легко. В настоящих программах таблицы символов
обычно нет: разработчики её удаляют. Сделаем так же. В консоли w64devkit:

```
strip -o debugme_s.exe debugme.exe
```

`strip` («раздеть») — утилита из того же набора, что gcc. Она создаёт
копию файла без таблицы символов. Размер упадёт примерно с 250 до 39 КБ.

Импортируй `debugme_s.exe` в тот же проект и проанализируй. Открой
**Symbol Tree → Functions**. Картина другая: почти сотня функций
с именами вида **`FUN_1400014fb`** (у меня было 87). `FUN_` — «функция»,
дальше её адрес. Имена остались только у тех, чей адрес записан
в служебных таблицах PE:

- `entry` — точка входа, её адрес лежит в заголовке PE;
- `tls_callback_0`, `tls_callback_1` — TLS-колбэки из главы 13, у них
  своя таблица;
- переходники к импортам, например `getchar` (глава 13): имена
  импортов обязаны лежать в файле, иначе загрузчик не найдёт функцию
  (глава 8).

Какая из этих безымянных функций — `main`? Перебирать все — не вариант.
Работает тот же приём, что в главе 13: **идём от строки**.

### Шаг 1. Находим строку

**Search** («Поиск») → **For Strings…** («Строки…»). В окне поиска ничего
не меняй, нажми **Search**. Откроется таблица всех строк программы.
В поле фильтра внизу набери `Result` — останется одна строка. Дважды
щёлкни по ней.

Листинг перепрыгнет в секцию `.rdata`, прямо к строке:

```
s_Result:_%d_140009000        XREF[...]:  FUN_1400014fb:140001526(*), ...
    140009000   ds   "Result: %d\n"
```

`s_Result:_%d_140009000` — имя, которое Ghidra дала строке: `s_` значит
string («строка»), потом начало текста и адрес. `ds` — пометка «здесь
лежит строка». А справа — самое ценное: **`XREF`**.

### Шаг 2. Перекрёстная ссылка ведёт к коду

**XREF** — cross-reference `[кросс рéференс]`, **перекрёстная ссылка**:
«кто ссылается на это место». Ghidra показывает её прямо рядом с меткой,
например `FUN_1400014fb:140001526(*)`. Читается так: «на эту строку
ссылается инструкция по адресу `140001526` внутри функции
`FUN_1400014fb`».

Число в `XREF[...]` — сколько всего ссылок. Не удивляйся, если одна из них
ведёт в заголовок PE: там заголовок секции `.rdata` указывает на начало
секции, а наша строка лежит как раз в начале. Нам нужна ссылка из кода.

Буква в скобках говорит, **как** ссылаются:

| Пометка | Значит |
|---|---|
| `(c)` | call — вызов функции |
| `(j)` | jump — переход |
| `(R)` | read — чтение данных |
| `(W)` | write — запись данных |
| `(*)` | pointer — взяли адрес (например, `lea`) |

Дважды щёлкни по ссылке — и ты в функции `FUN_1400014fb`, на той самой
инструкции `LEA RAX,[s_Result:_%d_140009000]`. Декомпилятор показывает:

```c
undefined8
FUN_1400014fb(undefined8 param_1,undefined8 param_2,undefined8 param_3,undefined8 param_4)

{
  uint uVar1;
  
  FUN_140001620();
  uVar1 = FUN_1400014d4(7,5);
  FUN_140001480((byte *)"Result: %d\n",(ulonglong)uVar1,param_3,param_4);
  getchar();
  return 0;
}
```

Узнаёшь? Это наша `main`, только без имён. Так выглядит почти любая
чужая программа при первом открытии.

Посмотри на строку с `FUN_140001480`: в неё передаются `param_3`
и `param_4`, которых в нашем коде не было. Это **ошибка декомпилятора**.
Он не знает, сколько параметров у `FUN_140001480` (это `printf`, у неё
число параметров переменное). Поэтому он решил, что значения в `R8` и `R9`
(3-й и 4-й аргументы, глава 12) — тоже аргументы. И заодно приписал четыре
параметра самой `main`. Сейчас мы это исправим.

## 14.8. Наводим порядок

Главная работа в Ghidra — не чтение, а **восстановление смысла**:
разобрался, что делает кусок кода, — записал это в программу. Имена,
типы, комментарии. С каждым шагом псевдокод становится понятнее.

### Имена функций

Щёлкни по имени `FUN_1400014fb` в декомпиляторе (или в листинге) и нажми
**L** — это Rename («Переименовать»). Введи `main`, **OK**.

Так же переименуй:

- `FUN_1400014d4` → `square_plus` (дважды щёлкни, зайди в неё — видно,
  что считает `param_2 + param_1 * param_1`);
- `FUN_140001480` → `printf` (принимает строку формата — догадаться
  несложно).

Декомпилятор сразу покажет:

```c
undefined8 main(undefined8 param_1,undefined8 param_2,undefined8 param_3,undefined8 param_4)

{
  uint uVar1;
  
  FUN_140001620();
  uVar1 = square_plus(7,5);
  printf((byte *)"Result: %d\n",(ulonglong)uVar1,param_3,param_4);
  getchar();
  return 0;
}
```

Уже читается. Но лишние параметры остались.

### Сигнатура функции

**Сигнатура** (signature `[сúгнечер]`) — это «паспорт» функции: что она
возвращает, как называется и какие у неё параметры. Например,
`int square_plus(int x, int y)`.

Щёлкни правой кнопкой по имени `main` в декомпиляторе → **Edit Function
Signature** («Изменить сигнатуру функции»). Впиши `int main(void)` и нажми
**OK**. Потом то же самое для `printf`: `int printf(char * format, ...)`.
Многоточие `...` в C значит «дальше — сколько угодно аргументов».

Результат:

```c
int main(void)

{
  uint uVar1;
  
  FUN_140001620();
  uVar1 = square_plus(7,5);
  printf("Result: %d\n",(ulonglong)uVar1);
  getchar();
  return 0;
}
```

Фантомные параметры исчезли. Декомпилятор перестал гадать, потому что
ты сказал ему правду о функциях.

### Имена и типы переменных

Зайди в `square_plus`. Щёлкни по `param_1` и нажми **L** — переименуй
в `x`. `param_2` — в `y`. Ghidra покажет:

```c
int square_plus(int x,int y)

{
  return y + x * x;
}
```

Почти исходник из главы 13.

Вернись в `main`. Щёлкни по `uVar1` и нажми **Ctrl+L** — Retype Variable
(«Изменить тип переменной»). Введи `int`. Потом **L** и имя `result`:

```c
  int result;
  ...
  result = square_plus(7,5);
  printf("Result: %d\n",(ulonglong)(uint)result);
```

Видишь — `(ulonglong)(uint)` осталось. Декомпилятор всё ещё
«перестраховывается» с преобразованиями перед `printf`. Так бывает: не каждый артефакт
уходит. Главное, что смысл читается с первого взгляда.

### Комментарии

Выдели строку в листинге и нажми **`;`** (точка с запятой) — откроется
окно комментария. Пиши туда всё, что понял: «проверка длины пароля»,
«здесь сравнение с ключом». Как и в x64dbg, комментарии хранятся в проекте.

### Всё можно отменить

Переименовал не то? **Ctrl+Z** — Undo («Отменить»). Не бойся
экспериментировать: файл `.exe` не меняется, всё хранится в проекте Ghidra.

## 14.9. Перекрёстные ссылки — главный навигатор

Мы воспользовались XREF один раз, от строки к коду. На самом деле это
основной способ передвигаться по незнакомой программе. Три вопроса,
на которые они отвечают:

- **Кто использует эту строку?** — от сообщения к коду, который его
  выводит (так мы нашли `main`).
- **Кто вызывает эту функцию?** — встал на имя функции, посмотрел XREF:
  список всех мест, откуда её зовут.
- **Кто трогает эту переменную?** — все чтения `(R)` и записи `(W)`
  глобальной переменной.

Полный список ссылок открывается так: правой кнопкой по имени (функции,
строки, метки) → **References** («Ссылки») → **Show References to…**
(«Показать ссылки на…»). Откроется таблица, по любой строке можно
дважды щёлкнуть и перейти.

Особенно полезен второй вопрос в паре с импортами. В **Symbol Tree**
раскрой папку **Imports** («Импорты») — там функции Windows, которые
вызывает программа (глава 7). Нашёл интересную, например `CreateFileW`,
посмотрел её XREF — и сразу видишь все места, где программа работает
с файлами. Это метод из главы 12 («находи вызовы WinAPI»), только теперь
Ghidra делает поиск за тебя.

## 14.10. Оптимизированный код

Все наши программы мы собирали с `-O0` — без оптимизации, чтобы
ассемблер был похож на исходник. Настоящие программы собирают
с оптимизацией. Посмотрим, как это выглядит в декомпиляторе:

```
gcc -O2 -o debugme_o2.exe debugme.c
```

Открой `debugme_o2.exe` в Ghidra, найди `main`:

```c
int __cdecl main(int _Argc,char **_Argv,char **_Env)

{
  undefined8 in_R9;
  
  __main();
  printf_constprop_0("Result: %d\n",0x36,_Env,in_R9);
  getchar();
  return 0;
}
```

Где вызов `square_plus`? **Его нет.** Компилятор ещё при сборке сам
посчитал `7 * 7 + 5` и вписал в программу готовый ответ: `0x36`, то есть
54. Функции `square_plus` просто нечего делать во время работы.

При этом в **Symbol Tree** функция `square_plus` есть. Компилятор оставил
её в файле: вдруг её вызывает какой-то другой файл программы. Посмотри
на её XREF: там всего одна ссылка, из секции `.pdata`, и это не вызов.

`.pdata` мелькала в таблице секций в главе 8 — «данные для обработки
исключений». В 64-битной Windows там лежит таблица с записью почти
о каждой функции: где она начинается и кончается и как её аварийно
прервать при исключении. Поэтому ссылка из `.pdata` есть почти у всех
функций, и её можно не считать. А ссылок-вызовов `(c)` у `square_plus`
нет ни одной — **никто её не вызывает**. Это «мёртвый код».

Отсюда два урока на будущее:

1. **Оптимизированный код не повторяет исходник.** Функции встраиваются
   (inline `[инлáйн]` — компилятор вставляет тело функции прямо в место
   вызова) или исчезают, вычисления выполняются заранее. Декомпилятор
   показывает, что **есть** в файле, а не что было написано.
2. **Прежде чем разбирать функцию — проверь её XREF.** Если её никто не
   вызывает (ссылки из `.pdata` не в счёт), возможно, разбирать её
   незачем.

Ещё две новые странности. `in_R9` — переменная с приставкой `in_`
означает: «регистр использован, но в этой функции ему ничего не
присваивали». Обычно это признак ошибки в угаданной сигнатуре, как
в разделе 14.7. А `printf_constprop_0` — версия `printf`, которую
компилятор специально подготовил для этого вызова (constprop — constant
propagation, «протаскивание констант»). Имя подсказывает, что это
по-прежнему `printf`.

## 14.11. Ghidra и x64dbg работают в паре

Реверсер почти никогда не пользуется одним инструментом. Обычный рабочий
цикл:

1. В **Ghidra** разбираешься, где интересный код, и строишь гипотезу:
   «вот здесь, наверное, сравнивается пароль».
2. В **x64dbg** ставишь точку останова на этом месте и смотришь живые
   значения: что лежит в регистрах, с чем именно сравнивают.
3. Возвращаешься в Ghidra и записываешь понятое: имена, комментарии.

Мешает одно: **адреса разные**. Ghidra показывает адреса как в файле
(`1400014fb`), а x64dbg — со сдвигом ASLR (`00007FF6C9A214FB`). Есть два
способа.

**Способ 1. Пересчитать.** Ты делал это в упражнении 13.6. Вычти из адреса
Ghidra базу образа `140000000` — получишь RVA `14fb`. Прибавь базу, по
которой x64dbg загрузил программу, — получишь адрес в x64dbg. Или совсем
просто: младшие четыре цифры совпадают, значит в x64dbg ищи адрес,
оканчивающийся на `14FB`. Перейти туда — `Ctrl+G` (глава 13).

**Способ 2. Сдвинуть Ghidra.** **Window** → **Memory Map** («Карта памяти»),
в панели инструментов этого окна есть кнопка с домиком — **Set Image Base**
(«Задать базу образа»). Введи базу из x64dbg, например `7FF6C9A20000`, —
и все адреса в Ghidra станут такими же, как в отладчике. Минус: после
перезапуска программы ASLR выберет новую базу.

Для начала хватит первого способа. Он же тренирует понимание RVA
из главы 8.

## 14.12. А как же IDA?

Ты наверняка слышал про **IDA** `[áйда]` от компании Hex-Rays. Это старейший
и самый известный дизассемблер с декомпилятором, стандарт индустрии.
В вакансиях реверсеров его упоминают постоянно.

Честно о вариантах:

- **IDA Pro** — полная версия. Платная, и очень дорогая: счёт идёт на
  тысячи долларов.
- **IDA Free** — бесплатная версия для некоммерческого использования.
  Работает с 64-битными программами Windows, а в свежих версиях умеет
  декомпилировать через облако (нужен интернет).
- По сети ходят **взломанные сборки** IDA Pro. Не бери их: кроме того,
  что это нелегально, такие сборки — известная приманка. В них подсовывают
  трояны, и целятся как раз в начинающих реверсеров.

> Условия IDA Free меняются от версии к версии — проверь актуальность
> на сайте hex-rays.com.

Почему курс построен на Ghidra: она бесплатная, без ограничений, её
декомпилятор работает без интернета, и любой шаг курса воспроизводим
без покупок. **Идеи у всех декомпиляторов одни и те же**: функции,
перекрёстные ссылки, переименование, типы. Освоишь Ghidra — пересядешь
на IDA за вечер. Вот соответствия основных действий:

| Действие | Ghidra | IDA |
|---|---|---|
| Декомпилировать функцию | окно Decompile, `Ctrl+E` | `F5`, переключение `Tab` |
| Переименовать | `L` | `N` |
| Изменить тип | `Ctrl+L` | `Y` |
| Комментарий | `;` | `:` или `;` |
| Перекрёстные ссылки | правой кнопкой → References | `X` |
| Перейти по адресу | `G` | `G` |
| Список строк | Search → For Strings | `Shift+F12` |
| Назад | `Alt+←` | `Esc` |

Клавиши IDA не меняются годами, но на всякий случай сверь со своей
версией.

## 14.13. Заметка про MacBook

Ghidra написана на Java и запускается и на macOS. Но в готовой сборке
нет **декомпилятора для Mac**: его части для этой системы нужно собрать
самостоятельно, это отдельная возня со средствами разработки. Официальная
сборка содержит готовые части только для Windows и Linux.

Совет: не трать на это время. Работай в Ghidra на Windows-машине.
С MacBook удобно читать главы и писать мне.

## 14.14. Что запомнить

1. **Декомпилятор** превращает машинный код в **псевдокод** — похожий
   на C, но не исходник. Имена переменных и часть типов он придумывает сам.
2. Работа в Ghidra идёт в **проекте**: импорт (`I`) → анализ (**Analyze**)
   → CodeBrowser. Файл `.exe` не меняется.
3. Главные окна: **Symbol Tree** (имена), **Listing** (ассемблер),
   **Decompile** (псевдокод). Клик в одном подсвечивает другое.
4. Имена `FUN_адрес`, `DAT_адрес`, `s_текст_адрес` Ghidra даёт сама.
   `param_N` — параметры, `local_XX` — ячейки стека, `uVar1`, `iVar2` —
   переменные в регистрах, `in_` — регистр без значения.
5. Без имён нужный код ищут **от строк и импортов** через **XREF** —
   перекрёстные ссылки.
6. Главная работа — **восстановление смысла**: `L` (имя), `Ctrl+L` (тип),
   **Edit Function Signature**, `;` (комментарий). Каждая правка делает
   псевдокод чище.
7. Неправильная **сигнатура** рождает фантомные параметры и `in_`-переменные.
8. **Оптимизированный код** не повторяет исходник: вычисления делаются
   заранее, функции исчезают или встраиваются.
9. Адреса Ghidra и x64dbg различаются на **сдвиг базы**: пересчитывай
   через RVA или по младшим четырём цифрам.
