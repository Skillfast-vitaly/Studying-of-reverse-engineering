## П7.1. Зачем реверсеру C++

Программу на C ты уже читаешь: функции, переменные, указатели,
структуры. C++ добавляет к этому **классы** — структуры, у которых есть
свои функции. И почти каждая возможность C++ оставляет в машинном коде
узнаваемый след:

| В исходнике C++ | Что видно в листинге |
|---|---|
| метод класса | функция, у которой первый аргумент `RCX` — адрес объекта |
| `new` | вызов `operator new` с размером объекта |
| виртуальная функция | вызов через таблицу: `call qword ptr [rax+…]` |
| имя метода | длинное «искажённое» имя: `?name@Dog@@UEBAPEBDXZ` |
| класс с виртуальными функциями | строка `.?AVDog@@` в данных |
| `throw` | вызов `_CxxThrowException` |

Реверсер C++-программы восстанавливает **классы**: какие функции
принадлежат какому классу, какие поля лежат по каким смещениям, кто
от кого наследует. Это та же работа, что ты делал с задачами, только
единица разбора крупнее: не функция, а класс.

(«командная строка x64 с инструментами»). Имя ярлыка кончается

```
cd C:\reverse\work\cpp
cl /O1 /EHsc zoo.cpp
zoo.exe
```

`cl` — компилятор C и C++ от Microsoft. `/O1` — оптимизация, `/EHsc` —
включить исключения C++ (о них в П7.9). Получится `zoo.exe`.

Зачем два компилятора? Чужие программы чаще собраны Visual Studio — их
приметы и надо знать. А твои учебные — g++. И один и тот же исходник
они превращают в разный машинный код: в П7.5 ты увидишь, что даже
размер объекта у них разный. Реверсер всегда сначала узнаёт
компилятор (глава 7), а потом читает листинг по его правилам.

## П7.3. Класс и скрытый аргумент `this`

Вот программа, на которой построено всё приложение. Создай папку
`C:\reverse\work\cpp` и в ней файл `zoo.cpp`:

```cpp
#include <stdio.h>

class Animal {
public:
    Animal(int legs) : legs_(legs) {}
    virtual ~Animal() {}
    virtual const char *name() const { return "zver"; }
    virtual int speak() const { return puts("..."); }
    int legs() const { return legs_; }
protected:
    int legs_;
};

class Dog : public Animal {
public:
    Dog() : Animal(4), bones_(0) {}
    const char *name() const override { return "sobaka"; }
    int speak() const override { return puts("gav!"); }
    void give_bone() { bones_++; }
private:
    int bones_;
};

class Bird : public Animal {
public:
    Bird() : Animal(2) {}
    const char *name() const override { return "ptica"; }
};

int count_legs(Animal **zoo, int n)
{
    int total = 0;
    for (int i = 0; i < n; i++)
        total += zoo[i]->legs();
    return total;
}

void talk(const Animal *a)
{
    puts(a->name());
    a->speak();
}

void feed(Dog *d)
{
    d->give_bone();
}

int main()
{
    Animal *zoo[2] = { new Dog(), new Bird() };
    for (int i = 0; i < 2; i++)
        talk(zoo[i]);
    feed(static_cast<Dog *>(zoo[0]));
    printf("nog vsego: %d\n", count_legs(zoo, 2));
    delete zoo[0];
    delete zoo[1];
    return 0;
}
```

Вывод:

```
sobaka
gav!
ptica
...
nog vsego: 6
```

Не пугайся, разберём по кусочку. Сначала — первые строки класса
`Animal` («животное»):

- **`class Animal { … };`** — класс. Это структура из главы 5 и П1.4,
  в которой, кроме полей, есть функции. Функции класса называются
  **методами** (method `[мéсод]`);
- **`int legs_;`** — поле, как в структуре. Подчёркивание в конце —
  просто привычка многих программистов помечать поля, языку оно
  безразлично;
- **`public:`** и **`protected:`** — кому можно трогать то, что ниже:
  `public` («открыто») — всем, `protected` («защищено») — только самому
  классу и его наследникам, `private` («закрыто») — только самому
  классу. Это правила для компилятора: в машинном коде их нет;
- **`int legs() const { return legs_; }`** — метод: «вернуть число
  ног». `const` после скобок обещает, что метод не меняет объект.

Главное — как метод узнаёт, **чьи** ноги вернуть? Объектов `Animal`
может быть сколько угодно. Ответ: компилятор тайно передаёт методу
адрес объекта. Этот скрытый аргумент называется **`this`** `[зис]`,
«этот». В Windows x64 он идёт **первым аргументом, в `RCX`** (глава 12).
Запись `legs_` внутри метода значит `this->legs_`.

То есть метод — это обычная функция C из П1, которой передали
указатель на структуру:

```c
/* как метод выглядит «изнутри», на языке C */
int Animal_legs(const struct Animal *this) { return this->legs_; }
```

Посмотрим на настоящий машинный код. Метод `give_bone` («дать кость»)
у собаки увеличивает поле `bones_`. В отладочной сборке, где компилятор
ничего не встраивает (у Visual Studio это сборка Debug), он выглядит так:

```
Dog::give_bone:
    push    rax
    mov     [rsp], rcx              ; сохранить this
    mov     rax, [rsp]              ; rax = this
    mov     ecx, [rax+10h]          ; ecx = this->bones_
    add     ecx, 1
    mov     [rax+10h], ecx          ; this->bones_ = ecx
    pop     rax
    retn
```

Ни одного явного аргумента у метода нет, а `RCX` используется — это
и есть `this`. Поле `bones_` лежит по смещению `10h` от начала объекта.
Почему именно там — в П7.5.

А в сборке с оптимизацией (`-O1`, у Visual Studio — Release) компилятор
**встроил** метод прямо в функцию `feed`:

```
feed:
    inc     dword ptr [rcx+10h]     ; d->bones_++
    retn
```

Одна инструкция. Узнать в ней вызов метода по листингу нельзя — видно
только «увеличить поле по смещению `10h` у объекта из `RCX`». Так
и восстанавливают классы: по смещениям от `this` собирают, какие поля
у объекта есть.

> Листинги в этом приложении — в манере IDA (П5.6), но адреса я убрал,
> а имена функций расшифровал: в настоящем файле они будут длинными
> искажёнными (П7.7). Комментарии после `;` — мои.

## П7.4. Конструктор, деструктор, `new` и `delete`

### Конструктор и деструктор

```cpp
Dog() : Animal(4), bones_(0) {}
```

**Конструктор** (constructor `[констрáктор]`) — метод с именем класса,
который готовит новый объект: заполняет поля. После двоеточия —
список того, что сделать первым: `Animal(4)` — сначала построить
«животную» часть объекта с четырьмя ногами, `bones_(0)` — потом
обнулить кости.

**Деструктор** (destructor `[дистрáктор]`) — метод с тильдой: `~Animal()`.
Его вызывают, когда объект уничтожают, — убрать за собой. У нас он
пустой, но слово `virtual` перед ним важно — о нём в П7.6.

### `new` и `delete`

```cpp
Animal *zoo[2] = { new Dog(), new Bird() };
…
delete zoo[0];
```

`new Dog()` делает две вещи: выделяет память под объект — как `malloc`
из главы 5 — и вызывает для неё конструктор. `delete` — наоборот:
сначала деструктор, потом освободить память, как `free`. Выделяет
и освобождает память особая функция `operator new` и пара к ней
`operator delete` («оператор new», «оператор delete»).

### Конструктор в листинге

Отладочная сборка (Debug), где ничего не встроено. Конструктор `Dog`:

```
Dog::Dog:
    sub     rsp, 38h
    mov     [rsp+30h], rcx
    mov     rcx, [rsp+30h]
    mov     [rsp+28h], rcx             ; запомнить this
    mov     edx, 4                     ; второй аргумент: 4 ноги
    call    Animal::Animal             ; первый — this, он уже в RCX
    mov     rax, [rsp+28h]             ; rax = this
    lea     rcx, Dog::`vftable'
    mov     [rax], rcx                 ; this+0 = адрес таблицы Dog
    mov     dword ptr [rax+10h], 0     ; this->bones_ = 0
    add     rsp, 38h
    retn
```

И конструктор `Animal`, который он зовёт:

```
Animal::Animal:
    sub     rsp, 10h
    mov     [rsp+0Ch], edx             ; legs
    mov     [rsp], rcx                 ; this
    mov     rax, [rsp]
    lea     rcx, Animal::`vftable'
    mov     [rax], rcx                 ; this+0 = адрес таблицы Animal
    mov     ecx, [rsp+0Ch]
    mov     [rax+8], ecx               ; this->legs_ = legs
    add     rsp, 10h
    retn
```

Видишь порядок? Сначала конструктор `Animal` пишет в первые 8 байт
объекта адрес таблицы `Animal` и ставит ноги по смещению `8`. Потом
конструктор `Dog` **перезаписывает** первые 8 байт адресом своей
таблицы и обнуляет кости по смещению `10h`. Что за таблица и зачем её
адрес лежит в самом начале объекта — тема П7.6. Пока запомни примету:
**в начале конструктора класса с виртуальными функциями в `[this]`
записывается адрес из `.rdata`**. По этой строке конструкторы и находят.

### `new` в листинге

Теперь сборка с оптимизацией. Начало `main`, где создаются два объекта:

```
main:
    …
    mov     ecx, 18h                   ; размер Dog — 24 байта
    call    operator new(unsigned __int64)
    mov     rsi, rax                   ; rsi = новый объект
    mov     dword ptr [rax+8], 4       ; legs_ = 4
    lea     rax, Dog::`vftable'
    mov     [rsi], rax                 ; таблица Dog
    mov     dword ptr [rsi+10h], 0     ; bones_ = 0
    mov     [rsp+20h], rsi             ; zoo[0]
    mov     ecx, 10h                   ; размер Bird — 16 байт
    call    operator new(unsigned __int64)
    mov     rdi, rax
    mov     dword ptr [rax+8], 2       ; legs_ = 2
    lea     rax, Bird::`vftable'
    mov     [rdi], rax                 ; таблица Bird
    mov     [rsp+28h], rdi             ; zoo[1]
```

Конструкторы встроились: вызовов `Dog::Dog` больше нет, остались их
три записи. Зато `operator new` всегда остаётся вызовом, и его
единственный аргумент в `ECX` — **размер объекта**. Это подарок
реверсеру: увидел `mov ecx, 18h` перед `operator new` — знаешь, что
объект этого класса занимает 24 байта, и можешь заводить структуру
под него.

### `delete` в листинге

Конец `main`:

```
    mov     rax, [rsi]                 ; таблица объекта zoo[0]
    mov     rcx, rsi                   ; this
    mov     edx, 1                     ; «и освободи память»
    call    qword ptr [rax]            ; первая ячейка таблицы
```

`delete` вызвал **первую функцию из таблицы объекта**. Visual Studio
кладёт туда особую функцию — **scalar deleting destructor**
`[скéйлер дилúтинг дистрáктор]`, «удаляющий деструктор». Она вызывает
деструктор, а если во втором аргументе 1 — ещё и освобождает память:

```
Dog::`scalar deleting dtor':
    push    rsi
    sub     rsp, 20h
    mov     rsi, rcx                   ; this
    test    edx, edx                   ; освобождать?
    jz      short skip
    mov     edx, 18h                   ; размер — опять 24 байта
    mov     rcx, rsi
    call    operator delete(void *, unsigned __int64)
skip:
    mov     rax, rsi
    add     rsp, 20h
    pop     rsi
    retn
```

Деструктор у нас пустой, и компилятор его выбросил: осталось только
освобождение. Обрати внимание на `mov edx, 18h`: Visual Studio
по умолчанию передаёт в `operator delete` и размер объекта (так написано
в документации Microsoft про ключ `/Zc:sizedDealloc`). Размер класса
виден дважды — у `new` и у `delete`.

## П7.5. Наследование и раскладка объекта

```cpp
class Dog : public Animal { … };
```

Запись `: public Animal` значит: `Dog` **наследует** (inherit
`[инхéрит]` — «наследовать») `Animal`. У каждой собаки есть всё, что есть у животного:
поле `legs_`, методы `legs()`, `name()`, `speak()`. `Animal` — **базовый
класс** (base class), `Dog` — **производный** (derived class, «наследник»).
В памяти объект `Dog` — это объект `Animal`, к хвосту которого
приписаны поля собаки.

Соберём, что мы узнали о смещениях из листингов П7.3 и П7.4:

```
Dog у Visual Studio, 24 байта (new 18h):
+00  адрес таблицы класса       8 байт   ┐
+08  legs_                      4 байта  │ часть Animal, 16 байт
+0C  (пусто)                    4 байта  ┘ выравнивание (П1.4)
+10  bones_                     4 байта    своё поле Dog
+14  (пусто)                    4 байта    выравнивание до 8
```

А теперь та же программа, собранная **g++** из w64devkit. Метод `feed`:

```
feed:
    add     dword ptr [rcx+0Ch], 1     ; bones_ по смещению 0Ch!
    retn
```

И `new Dog()`:

```
    mov     ecx, 10h                   ; 16 байт, а не 24
    call    operator new(unsigned long long)
```

```
Dog у g++, 16 байт (new 10h):
+00  адрес таблицы класса       8 байт   ┐ часть Animal
+08  legs_                      4 байта  ┘
+0C  bones_                     4 байта    своё поле Dog — в «пустоте» Animal
```

Один исходник — два разных объекта! g++ разрешает себе положить поле
наследника в пустые байты выравнивания базового класса. Visual Studio
так не делает: часть `Animal` у неё всегда занимает полные 16 байт.
Обе правы: каждый компилятор следует своим правилам раскладки, и в
пределах своей программы они соблюдаются строго.

Отсюда правило реверсера: **смещения полей бери из листинга, а не
высчитывай в уме**. И сначала узнай компилятор — Detect It Easy,
глава 7.

## П7.6. Виртуальные функции и их таблица

Второй заход начался с П7.5. Теперь — самое важное в C++ для реверсера.

### Одна функция — разные ответы

Посмотри на `talk`:

```cpp
void talk(const Animal *a)
{
    puts(a->name());
    a->speak();
}
```

`talk` получает просто «какое-то животное». Но для собаки печатается
`sobaka` и `gav!`, а для птицы — `ptica` и `...`. Как одна и та же
строка `a->name()` вызывает разные функции?

Всё дело в слове **`virtual`** («виртуальный») перед методом в классе
`Animal`. Оно говорит: «какую функцию вызвать, решай **во время
работы** по настоящему классу объекта, а не по типу указателя».
Наследник может заменить такой метод своим — для этого слово
`override` («заменить»). `Dog` заменил и `name`, и `speak`, а `Bird`
только `name`: птица говорит по-звериному, `...`.

### Таблица виртуальных функций

Как процессор узнает класс объекта? Никак — у процессора нет классов.
Поэтому компилятор делает вот что:

1. Для каждого класса с виртуальными функциями кладёт в `.rdata`
   **таблицу виртуальных функций** — vtable `[ви-тэйбл]`, у Visual
   Studio она называется vftable. Это просто массив адресов функций,
   по 8 байт.
2. В **первые 8 байт каждого объекта** конструктор записывает адрес
   таблицы его класса. Вот что за строку ты видел в П7.4:
   `mov [rax], rcx` с адресом `Dog::'vftable'`.

Таблицы нашей программы у Visual Studio:

```
               Animal::`vftable'      Dog::`vftable'       Bird::`vftable'
ячейка 0, +00  Animal::scalar del.    Dog::scalar del.     Bird::scalar del.
ячейка 1, +08  Animal::name           Dog::name            Bird::name
ячейка 2, +10  Animal::speak          Dog::speak           Animal::speak
```

Ячейка 0 — удаляющий деструктор из П7.4: деструктор у нас виртуальный,
поэтому он тоже в таблице. Порядок остальных — порядок объявления
в `Animal`: `name`, потом `speak`. Наследник сохраняет порядок
и подставляет в ячейки свои функции. У `Bird` своей `speak` нет —
в её таблице стоит адрес `Animal::speak`.

### Виртуальный вызов в листинге

Функция `talk` в сборке с оптимизацией:

```
talk:
    push    rsi
    sub     rsp, 20h
    mov     rsi, rcx                   ; rsi = a
    mov     rax, [rcx]                 ; rax = адрес таблицы из объекта
    call    qword ptr [rax+8]          ; ячейка 1 — name()
    mov     rcx, rax
    call    puts
    mov     rax, [rsi]                 ; снова таблица
    mov     rcx, rsi                   ; this = a
    add     rsp, 20h
    pop     rsi
    jmp     qword ptr [rax+10h]        ; ячейка 2 — speak()
```

Вот она, главная примета C++ в листинге:

```
mov     rax, [rcx]             ; взять таблицу из начала объекта
call    qword ptr [rax+8]      ; вызвать функцию из ячейки
```

Номер ячейки — смещение, делённое на 8: `+8` — ячейка 1, `+10h` —
ячейка 2. Последний вызов стал `jmp` вместо `call`: `speak` — последнее
действие `talk`, и компилятор передал ей управление прыжком. Её `ret`
вернётся сразу туда, откуда звали `talk`.

**Как реверсер узнаёт, что вызвалось.** Прямо из листинга — никак:
адрес в `RAX` появится только во время работы. Поэтому идут обходным
путём: выясняют, объект **какого класса** приходит в `RCX`, находят
таблицу этого класса и смотрят в нужную ячейку. В x64dbg проще:
поставь точку останова на `call qword ptr [rax+8]` и посмотри, куда
пойдёт процессор — глава 13.

### У g++ таблица устроена иначе

```
talk у g++:
    mov     rax, [rcx]
    call    qword ptr [rax+10h]        ; name — ячейка 2, а не 1
    …
    call    qword ptr [rax+18h]        ; speak — ячейка 3
```

У g++ в таблице два деструктора: один только разрушает объект, другой
ещё и освобождает память. Они занимают ячейки 0 и 1, поэтому `name`
сдвинулась на `+10h`. А перед ячейкой 0 лежат ещё две служебные
(о них — в упражнении П7.4). Мысль та же, номера другие — снова
«сначала узнай компилятор».

Заметь ещё: таблица виртуальных функций — это массив указателей на
функции, который ты сам строил в П1.7 для обработчиков. Только здесь
его строит компилятор. Ничего нового: взять адрес из таблицы по номеру
и вызвать по нему — как `table[reason](value)` в П1.7.

## П7.7. Искажённые имена

### Зачем искажать

В C имя функции в файле — просто её имя: `count_legs`. В C++ так нельзя.
У нас три функции `name` — у `Animal`, `Dog` и `Bird`. А ещё C++
разрешает несколько функций с одним именем, но разными аргументами.
Компоновщику (глава 2) же нужно, чтобы каждое имя было единственным.
Поэтому компилятор зашивает в имя класс, аргументы и прочее. Это
называется **name mangling** `[нэйм мэ́нглинг]` — «искажение имён».
Microsoft в своей документации зовёт такие имена **decorated names** —
«украшенные имена».

Имена нашей программы у Visual Studio:

| Искажённое имя | Что это |
|---|---|
| `?name@Dog@@UEBAPEBDXZ` | `public: virtual char const * Dog::name(void) const` |
| `?legs@Animal@@QEBAHXZ` | `public: int Animal::legs(void) const` |
| `?give_bone@Dog@@QEAAXXZ` | `public: void Dog::give_bone(void)` |
| `?count_legs@@YAHPEAPEAVAnimal@@H@Z` | `int count_legs(class Animal **, int)` |
| `??0Dog@@QEAA@XZ` | `public: Dog::Dog(void)` — конструктор |
| `??_GDog@@UEAAPEAXI@Z` | `public: virtual void * Dog::'scalar deleting dtor'(unsigned int)` — удаляющий деструктор |
| `??_7Dog@@6B@` | `const Dog::'vftable'` — таблица |
| `??2@YAPEAX_K@Z` | `void * operator new(unsigned __int64)` |
| `??3@YAXPEAX_K@Z` | `void operator delete(void *, unsigned __int64)` |

Расшифровка — настоящий вывод расшифровщика, слово `__cdecl` я убрал,
а пояснения после тире добавил сам.

### Как читать на глаз

Целиком учить схему не нужно — её расшифровывают программы. Но
несколько примет стоит знать:

- `?` в начале — имя C++. Дальше имена **задом наперёд** до `@@`:
  `name@Dog@@` — это `Dog::name`;
- `??0` — конструктор, `??1` — деструктор, `??_G` — удаляющий
  деструктор, `??_7` — таблица виртуальных функций, `??2` и `??3` —
  `operator new` и `operator delete`;
- после `@@`: `Q` — обычный открытый метод, `U` — открытый
  **виртуальный** метод, `Y` — функция вне класса;
- `QEAA` — метод может менять объект, `QEBA` — не может (`const`);
- типы: `H` — `int`, `X` — `void` (или «нет аргументов»), `D` — `char`,
  `PEA…` — указатель, `V…@@` — класс. `Z` — конец.

Так `?legs@Animal@@QEBAHXZ` читается: метод `legs` класса `Animal`,
открытый (`Q`), не меняет объект (`EBA`), возвращает `int` (`H`),
аргументов нет (`X`), конец (`Z`).

### Кто расшифровывает

- **IDA** и **Ghidra** — сами: в листинге будут человеческие имена;
- в консоли Visual Studio из П7.2 есть программа **undname**
  («разукрашиватель»):

  ```
  undname ?name@Dog@@UEBAPEBDXZ
  ```

  Она ответит строкой вида
  `is :- "public: virtual char const * __cdecl Dog::name(void) const"`
  (так описано в документации Microsoft; точный вид у тебя может чуть
  отличаться).

У **g++** схема другая, её называют Itanium `[айтéйниум]` — по
процессору, для которого её придумали:

| Имя у g++ | Что это |
|---|---|
| `_ZNK3Dog4nameEv` | `Dog::name() const` |
| `_Z4feedP3Dog` | `feed(Dog*)` |
| `_ZN3DogD0Ev` | `Dog::~Dog()` — деструктор, который ещё и освобождает память |
| `_ZTV3Dog` | `vtable for Dog` — таблица |
| `_ZTS3Dog` | `typeinfo name for Dog` — строка `3Dog` |

Начало `_Z` и длины перед именами: `3Dog` — три буквы, `4name` —
четыре. IDA расшифровывает и эту схему.

### Где эти имена встретятся на деле

Честно: в чужом `.exe` из Visual Studio **таблицы символов нет**. Имена
методов живут только в отдельном файле символов `.pdb`, а его обычно
не выдают. Поэтому в чужой программе вместо `Dog::name` будет
`sub_140001230`. Искажённые имена ты встретишь:

- в **экспорте** DLL, написанных на C++: методы классов, которые DLL
  отдаёт наружу, видны в таблице экспорта под своими искажёнными
  именами;
- в **символах Microsoft** для файлов Windows — тех самых, что WinDbg
  качает с сервера (глава 30). IDA тоже умеет их подтянуть;
- в **своих сборках**: g++ оставляет таблицу символов (поэтому IDA
  в П5 знала `main`), а Visual Studio кладёт рядом `.pdb`, если
  собирать с ключом `/Zi`.

А в чужой программе без имён классы всё равно можно опознать —
следующий раздел.

## П7.8. Имена классов в самом файле

У Visual Studio по умолчанию включён ключ `/GR` — **RTTI** `[ар-ти-ти-áй]`,
Run-Time Type Information, «сведения о типах во время работы» (по
документации Microsoft он включён по умолчанию). Это данные, по которым
программа может во время работы узнать класс объекта. Нужны они редко,
а для реверсера это подарок: **имена всех классов с виртуальными
функциями лежат в файле строками**.

В нашей программе, собранной с RTTI, в секции данных нашлись три
строки:

```
.?AVDog@@
.?AVAnimal@@
.?AVBird@@
```

`.?AV` — «класс» (V от class), дальше имя и `@@`. Для структур будет
`.?AU` (U от struct). Поиск строк по `.?AV` — своим `strings.py`
из П6.9 или окном Strings в IDA — выдаёт **список классов программы**.
Даже без единого имени функции.

А как найти таблицу класса? Visual Studio кладёт **прямо перед таблицей**
ещё 8 байт — адрес служебной записи RTTI, а та ведёт к строке с именем.
То есть цепочка такая: строка `.?AVDog@@` ← записи RTTI ← 8 байт перед
таблицей ← сама таблица `Dog` ← конструктор `Dog`, который её
записывает в объект. По перекрёстным ссылкам (клавиша X в IDA, П5.5)
от строки до конструктора — несколько шагов.

Инструменты умеют проходить эту цепочку сами. В Ghidra этим занимается
анализатор **Windows x86 PE RTTI Analyzer** при автоанализе, а скрипт
**RecoverClassesFromRTTIScript** (папка `C++` в Script Manager)
восстанавливает классы целиком (оба названия — из исходников Ghidra
12.1.4). Для IDA тоже есть такие средства. Что IDA 9.2 подпишет
сама, без помощи, я проверить не могу — посмотри в упражнении П7.5
и расскажи мне.

## П7.9. Исключения: `throw` и `catch`

Третий заход. В C ошибку обычно возвращают числом: `return -1`. В C++
есть ещё один способ — **исключение** (exception, глава 27 — то же
слово, но здесь это механизм языка, а не процессора). Функция
**бросает** (throw `[сроу]`) объект-ошибку, и он летит вверх по цепочке
вызовов, пока его не **поймает** (catch `[кэч]`) блок `try` («попробуй»)
где-то выше.

Файл `exc.cpp`:

```cpp
#include <stdio.h>

struct BadInput {
    int code;
};

int parse(int x)
{
    if (x < 0)
        throw BadInput{ x };
    return x * 2;
}

int safe(int x)
{
    try {
        return parse(x);
    } catch (const BadInput &e) {
        printf("oshibka %d\n", e.code);
        return -1;
    }
}
```

`struct` в C++ — тот же класс, только всё в нём по умолчанию
`public`. `parse(5)` вернёт 10, а `parse(-3)` бросит `BadInput`
с кодом −3, его поймает `safe`, напечатает `oshibka -3` и вернёт −1.

### `throw` в листинге

`parse` у Visual Studio (с оптимизацией):

```
parse:
    sub     rsp, 28h
    test    ecx, ecx
    js      short throw_it             ; x < 0? (знак — глава 9)
    add     ecx, ecx                   ; x * 2
    mov     eax, ecx
    add     rsp, 28h
    retn
throw_it:
    mov     [rsp+24h], ecx             ; объект BadInput{x} на стеке
    lea     rdx, _TI1?AUBadInput@@     ; «паспорт» типа исключения
    lea     rcx, [rsp+24h]             ; адрес объекта
    call    _CxxThrowException
    int     3                          ; сюда управление не вернётся
```

Вот примета: **`throw` — это вызов `_CxxThrowException`**. Первый
аргумент — адрес объекта-ошибки, второй — описание его типа, имя
которого начинается с `_TI` (от throw info, «сведения о броске»).
`_CxxThrowException` не возвращается никогда, поэтому компилятор
ставит после него `int 3` — точку останова из главы 13, просто как
заглушку «сюда не попадаем».

В имени описания снова видно имя типа: `?AUBadInput@@`. И строка
`.?AUBadInput@@` лежит в данных, даже если RTTI выключен ключом `/GR-`:
исключениям она нужна всегда (проверено компилятором). Так поиск
строк `.?AU` и `.?AV` выдаёт и типы ошибок программы.

### `catch` в листинге

Тело `catch` компилятор выносит в **отдельную маленькую функцию**,
а рядом кладёт таблицы: какой кусок кода к какому `try` относится
и где искать обработчик. Читает эти таблицы особая функция библиотеки
C++ — **обработчик кадра** (frame handler). В программах из Visual
Studio 2019 и новее это `__CxxFrameHandler4` из файла
`VCRUNTIME140_1.dll` (так в блоге команды C++ Microsoft: новый формат
таблиц стал примерно на 60% меньше). У clang в облаке —
`__CxxFrameHandler3`, старый формат.

Для реверсера отсюда простое правило. Видишь в импортах
`_CxxThrowException` и `__CxxFrameHandler4` — программа на C++
из Visual Studio, и в ней есть исключения. Разбирать таблицы
руками почти никогда не нужно; как твоя IDA покажет блок `catch`, —
посмотри сам на этом примере (упражнение П7.7).

## П7.10. `std::string` и `std::vector` в памяти

В C++ есть **стандартная библиотека** (standard library) — готовые
классы. Два главных, которые встретятся в любой программе:

```cpp
#include <string>
#include <vector>

std::string s = "sobaka";             // строка, которая сама знает длину
std::vector<int> v = { 1, 2, 3 };     // массив, который растёт сам
```

`std::` — «из стандартной библиотеки» (std — standard). В IDA таких
объектов в программах из Visual Studio будет полно, и выглядят они
просто как куски памяти по 32 и 24 байта. Устройство я взял прямо
из исходников библиотеки Microsoft (`microsoft/STL`, файлы `xstring`,
`vector`, `xmemory`, октябрь 2026). Числа — для сборки Release.

### `std::string` — 32 байта

```
+00  16 байт: либо сам текст (если он не длиннее 15 букв),
              либо адрес текста в куче (если длиннее)
+10  размер — сколько букв сейчас (8 байт)
+18  вместимость — сколько поместится без нового выделения (8 байт)
```

Короткий текст живёт **прямо в объекте**: это экономит обращение
к куче для большинства строк. Такой приём называют **SSO**
`[эс-эс-óу]` — Small String Optimization, «оптимизация коротких
строк». Как понять, что лежит в первых 16 байтах? Смотри на
вместимость: **если она больше 15 — там адрес**, иначе — сам текст.

`std::string s = "sobaka";` в памяти (по исходнику):

```
+00  73 6F 62 61 6B 61 00 00 00 00 00 00 00 00 00 00   "sobaka" и нули
+10  06 00 00 00 00 00 00 00                           размер 6
+18  0F 00 00 00 00 00 00 00                           вместимость 15
```

А строка из 30 букв уже не влезет: первые 8 байт станут адресом
в куче, размер — `1E` (30), вместимость — `1F` (31). Почему 31, а не
30? Библиотека округляет вместимость вверх так, чтобы младшие четыре
бита были единицами: `30 | 15 = 31` (функция `_Calculate_growth`
в `xstring`).

### `std::vector` — 24 байта

```
+00  адрес первого элемента
+08  адрес сразу за последним элементом
+10  адрес конца выделенной памяти
```

Три указателя, и всё. Размер вектора нигде не записан — его
вычисляют: `(второй − первый) / размер элемента`. Для
`std::vector<int> v = {1, 2, 3}` разница первых двух адресов — 12 байт,
`12 / 4 = 3` элемента. В листинге это узнаётся по вычитанию двух
указателей и сдвигу вправо: `sar rax, 2` — деление на 4 (глава 10).

### В отладочной сборке — на 8 байт больше

В сборке Debug у Visual Studio перед полями появляется ещё один
служебный указатель — для проверок ошибок при работе со строками
и массивами (в `xmemory` это `_Container_base12` и его `_Myproxy`).
Тогда строка занимает 40 байт, вектор — 32, и все смещения сдвигаются
на 8. Ещё одна причина сначала понять, что перед тобой: Debug
или Release.

### У g++ строка устроена иначе

Библиотека g++ (libstdc++) тоже кладёт короткие строки в объект, но
порядок полей другой: сначала **всегда** указатель на текст (для
короткой строки он указывает внутрь самого объекта), потом длина, потом
16 байт буфера. Тоже 32 байта, но читать их надо по-другому. Снова
правило: сначала узнай компилятор.

## П7.11. Практика: классы в IDA

Теперь всё вместе, руками. Нужны две сборки `zoo.cpp`: g++ (из П7.2)
и, если поставил Visual Studio, `cl /O1 /EHsc zoo.cpp`.

### Сборка g++: имена есть

g++ оставляет в файле таблицу символов, и IDA их прочитает (как `main`
в П5). Открой `zoo.exe` от g++ и дождись `AU: idle`:

1. Окно **Functions** (Shift+F3): найди `Dog::name(void)`,
   `Dog::speak(void)`, `talk(Animal const*)` — имена уже расшифрованы.
2. Окно **Names** (Shift+F4): найди `vtable for Dog`. Двойной щелчок —
   и ты в `.rdata`, где стоят строки `dq offset …`: это ячейки таблицы.
   Сколько их и что в первых двух — упражнение П7.4.
3. Встань на `talk` и найди обе строки `call qword ptr [rax+…]`. По
   смещениям определи, какие это методы (П7.6).

### Сборка Visual Studio: имён нет

Так выглядят настоящие чужие программы. Открой `zoo.exe` из Visual
Studio:

1. Функции почти все `sub_…` — `.pdb` мы не делали (П7.7). Зато IDA
   узнает функции библиотеки C++ по их коду и назовёт, например,
   `operator new` — проверь, так ли у тебя.
2. Окно **Strings** (Shift+F12), найди `.?AV`. Строки с именами
   классов — твоя первая зацепка.
3. От строки `.?AVDog@@` иди по перекрёстным ссылкам (X, П5.5):
   строка ← записи RTTI ← 8 байт перед таблицей ← таблица `Dog` ←
   место, где её адрес пишут в объект. Это и есть встроенный
   конструктор в `main`, рядом с `mov ecx, 18h` и вызовом
   `operator new`.
4. Переименуй найденное (N, П5.7): таблицу — `Dog_vftable`, функции из
   её ячеек — `Dog_name`, `Dog_speak`. Теперь в `talk` будет понятно,
   что вызывается.

Этот путь — от строки RTTI к таблице, от таблицы к конструктору,
от конструктора к размеру объекта — и есть начало восстановления
классов в любой C++-программе. Дальше реверсеры заводят в IDA
структуру с полями по найденным смещениям, но это уже следующий шаг.

## П7.12. C++ на дороге к гипервизору

Свой гипервизор ты будешь писать на C и ассемблере (П1, П2). Почему
не на C++? Ответ в документации Microsoft о ключе компилятора
`/kernel`, которым собирают код для ядра. В таком коде **выключены
исключения C++** (`throw` и `try` — ошибка компиляции), **выключен
RTTI**, а `new` и `delete` надо написать самому — у ядра их нет.
Классы и виртуальные функции остаются, но половина удобств C++
пропадает. Поэтому драйверы и гипервизоры часто пишут на C.

Зачем тогда П7 на пути к гипервизору? Три причины:

- **Таблицы функций.** Виртуальный вызов — это таблица указателей
  на функции, как твоя таблица обработчиков в П1.7. Ты научился
  узнавать такую таблицу в чужом листинге, а в своём гипервизоре
  построишь её сам.
- **Чужой код вокруг.** Многие компоненты Windows и почти все программы,
  которые ты будешь исследовать рядом с ядром, написаны на C++.
  В символах Microsoft (глава 30) ты встретишь их имена — теперь
  ты знаешь, как их читать.
- **Привычка «сначала узнай компилятор».** Раскладка объекта, таблица,
  `std::string` — всё у Visual Studio и g++ разное. Та же привычка
  нужна везде, где ты читаешь чужой машинный код.

## П7.13. Что запомнить

1. **Метод — функция с `this` в `RCX`.** Поля — смещения от `this`:
   `[rcx+10h]`.
2. **`new` — вызов `operator new` с размером объекта в `ECX`**
   (`mov ecx, 18h`). Visual Studio передаёт размер и в `operator delete`.
3. **Конструктор пишет в `[this]` адрес таблицы класса** — `lea` адреса
   из `.rdata`, потом `mov [rax], rcx`. По этому конструкторы и находят.
4. **Виртуальный вызов:** `mov rax, [rcx]` → `call qword ptr [rax+N]`.
   Ячейка = N / 8. У Visual Studio ячейка 0 — удаляющий деструктор,
   у g++ ячейки 0 и 1 — два деструктора, а перед таблицей ещё две
   служебные ячейки.
5. **Раскладка у компиляторов разная:** `Dog` — 24 байта у Visual
   Studio и 16 у g++. Смещения бери из листинга.
6. **Искажённые имена:** `?метод@Класс@@…` у Visual Studio,
   `_ZN…` у g++. `??0` — конструктор, `??_7` — таблица. Расшифровывают
   IDA, Ghidra, `undname`.
7. **В чужом `.exe` имён методов нет**, но есть строки RTTI
   `.?AV…@@` — имена классов (и `.?AU…@@` у структур). От них по
   ссылкам — к таблицам и конструкторам.
8. **`throw` — `_CxxThrowException`** (у g++ — `__cxa_throw`). Тело
   `catch` — отдельная маленькая функция.
9. **`std::string` у Visual Studio** — 32 байта: текст до 15 букв внутри,
   длиннее — адрес; размер на `+10h`, вместимость на `+18h`.
   **`std::vector`** — три указателя, размер = разность / размер
   элемента. В Debug всё на 8 байт длиннее.
10. **В ядре C++ урезан:** без исключений, RTTI и стандартного `new`.
