# Ответы к упражнениям

Сначала реши сам. Серьёзно: подсмотренный ответ выглядит очевидным и создаёт
ложное чувство понимания. Полчаса своих мучений стоят больше, чем прочитанное
решение.

Если ответ не сходится с твоим — не спеши считать себя неправым. Иногда
формулировка вопроса допускает несколько толкований. Приходи с вопросом.

## Глава 1. Как устроен компьютер

### 1.1. Сколько значений помещается в 4 бита? В 12 битов?

Работает правило «n битов → 2ⁿ значений».

- 4 бита → 2⁴ = **16** значений (от 0 до 15)
- 12 битов → 2¹² = **4096** значений (от 0 до 4095)

Запомни 16 — это ровно одна шестнадцатеричная цифра. В следующей главе
станет ясно, почему это удобно.

### 1.2. Почему 300 не помещается в байт? Сколько байтов нужно?

Байт — это 8 битов, то есть 2⁸ = 256 разных значений: от 0 до 255.
300 больше 255, места не хватает.

Нужно **2 байта** (16 битов): они вмещают числа от 0 до 65 535.

Практическое следствие: если программа хранит счётчик в одном байте, а он
дорастает до 256, происходит **переполнение** — значение сбрасывается в 0.
Это источник огромного числа ошибок и уязвимостей, и в реверсе такие места
ищут специально.

### 1.3. Байты 82, 101, 118, 101, 114 — какое слово?

`A` = 65, и дальше по алфавиту. `a` = 97.

- 82 → 65 + 17 → восемнадцатая заглавная буква → `R`
- 101 → 97 + 4 → пятая строчная → `e`
- 118 → 97 + 21 → `v`
- 101 → `e`
- 114 → `r`

Получается **`Rever`** — начало слова `Reverse`.

### 1.4. Почему байт нельзя однозначно назвать кодом или данными?

Потому что в самом байте это не записано. Смысл задаёт только то, **как
к байту обратились**: если процессор передал на него управление — это код,
если прочитал как значение — данные.

Пример, где программа читает собственный код как данные: **проверка
целостности**. Программа считает контрольную сумму собственных инструкций и
сравнивает с эталоном. Если кто-то изменил хоть байт — сумма не сойдётся, и
программа поймёт, что её пропатчили. Такие проверки — частая защита, и
обходят их, патча саму проверку.

Обратный случай: программа **создаёт код в памяти и исполняет его**. Так
работают упаковщики: в файле лежат сжатые данные, при запуске они
распаковываются в память и становятся кодом.

### 1.5. Что будет, если в RIP попадёт адрес текстовой строки?

Процессор начнёт честно исполнять байты строки как инструкции. Он не умеет
отличать одно от другого — просто берёт байт и делает то, что тот означает.

Дальше один из вариантов:
- байты случайно окажутся допустимыми инструкциями, и программа натворит
  что-то бессмысленное;
- попадётся недопустимая последовательность → аварийное завершение;
- современная Windows чаще всего прервёт программу сразу: у области с
  данными нет права на исполнение (защита **DEP**, Data Execution Prevention),
  и попытка исполнить оттуда вызовет ошибку.

Именно DEP появилась потому, что раньше атака «подсунуть свои байты в
буфер данных и прыгнуть на них» работала повсеместно.

## Глава 2. Что такое программа

### 2.1. Почему комментарии невозможно восстановить?

Потому что они **не попадают в файл вообще**. Препроцессор выбрасывает их
на первом шаге конвейера, ещё до перевода в ассемблер. В `.exe` их нет
физически — восстанавливать нечего.

С именами переменных разница принципиальная: имена **влияют на компиляцию**
(компилятор по ним различает переменные) и могут сохраниться в отладочной
информации или таблице символов. То есть имя иногда восстановимо, потому что
оно где-то записано. Комментарий не записан нигде.

Аналогия: комментарий — это заметка карандашом на полях рукописи, которую
не стали набирать в типографии. Имя переменной — это имя персонажа: в
переводе оно может поменяться, но след остаётся.

### 2.2. Версия в 4 байта работает в 8 раз быстрее?

**Нет.** Размер кода и скорость — разные вещи.

Скорость правильнее оценивать по числу выполненных инструкций и по тому,
сколько раз программа лезет в память. Версия без оптимизации выполняет
13 инструкций и несколько раз обращается к памяти; оптимизированная — две
инструкции и ни одного обращения. Разница в скорости есть, и она большая,
но она не выводится из соотношения 33/4.

Бывает и наоборот: оптимизирующий компилятор иногда **увеличивает** код ради
скорости — например, разворачивает цикл в десять копий тела, чтобы не тратить
время на проверку условия. Код толще, работает быстрее.

### 2.3. Импорты `CreateFileW`, `WriteFile`, `InternetOpenUrlW`

Скорее всего, программа **скачивает что-то из интернета и сохраняет в файл**.
Загрузчик, обновлятор — или вредонос, который тянет вторую ступень.

Утверждать наверняка **нельзя**, по двум причинам:

1. Наличие импорта означает лишь, что функция **доступна**, а не что она
   вызывается. Код мог остаться от удалённой возможности.
2. Настоящая функциональность может быть спрятана. Программа умеет получить
   адрес любой функции во время работы (`GetProcAddress`), и в таблице
   импортов этого не будет видно. Так поступают почти все вредоносы.

Правильная формулировка: «импорты показывают, что программа **может**
делать». Проверяется динамическим анализом.

### 2.4. `.exe` на 8 килобайт с окном — статика или динамика?

**Динамическая** линковка.

Рассуждение: код отрисовки окна — это тысячи строк работы с графикой. При
статической линковке он попал бы внутрь файла, и 8 килобайтами дело бы не
кончилось — счёт пошёл бы на сотни килобайт.

Значит, программа не содержит этот код, а **зовёт** его из системных
библиотек Windows (`user32.dll`, `gdi32.dll`). Внутри файла лежит только
список имён нужных функций — он занимает копейки.

Для сравнения: `hello.exe` из главы со статически влинкованной библиотекой C
весит 250 килобайт, и это всего лишь вывод строки в консоль.

### 2.5. Что даёт файл `.pdb`?

Настоящие **имена** функций и переменных, **номера строк** исходного файла и
информацию о **структурах данных**.

На практике это означает, что вместо `sub_401A20` ты видишь
`CheckLicenseKey`, а вместо `[rbp-0x24]` — переменную `attemptsLeft`. Отладчик
может показывать, какой строке исходника соответствует текущая инструкция.

Разница по трудозатратам — порядок величины. Файл `.pdb` рядом с программой
превращает многодневный анализ в многочасовой.

### 2.6. Python бессмысленно, C# осмысленно, но легко — почему?

**Python** не компилируется в машинный код: программа поставляется исходником
или почти-исходником, интерпретатор читает его на ходу. Реверсить нечего —
открой в блокноте и читай. (Нюанс: `.pyc` — это байт-код, но он
восстанавливается обратно в исходник почти дословно.)

**C#** компилируется в байт-код промежуточного языка (IL). Байт-код исполняет
виртуальная машина .NET, и чтобы она могла работать, в файле **обязаны**
сохраниться имена классов, методов и типов. То есть информация, которая в C
теряется навсегда, здесь остаётся по необходимости. Инструмент dnSpy
показывает почти оригинальный код.

**C и C++** компилируются в машинный код, где не остаётся ни имён, ни типов.
Отсюда и разница в сложности: в первых двух случаях восстанавливать нечего
или почти нечего, в третьем — всё.

## Глава 3. Числа, которыми говорит машина

### Задание 3.А — переводы

1. `0x2A` = 2×16 + 10 = **42**
2. `0xFF` = 15×16 + 15 = **255**
3. `100` = 6×16 + 4 → **`0x64`**
4. `255` → **`11111111`** (все восемь битов подняты — это и есть максимум байта)
5. `0x1000` = 1×4096 = **4096**

### Задание 3.Б — байты `04 01 00 00`

Порядок little-endian, значит байты перевёрнуты. Переворачиваем:

```
в памяти:  04 01 00 00
переворот: 00 00 01 04
число:     0x00000104 = 260
```

Ответ: **260**.

Типичная ошибка — прочитать как `0x04010000` (это 67 174 400). Признак, что
что-то не так: нули в памяти стоят **справа**, а у большого числа они стояли
бы слева. Нули справа в памяти почти всегда означают маленькое число.

### Задание 3.В — байты `52 65 76 65 72 73 65 00`

По таблице ASCII:

```
52 → R      72 → r
65 → e      73 → s
76 → v      65 → e
65 → e      00 → ?
```

Получается **`Reverse`**.

Последний байт `00` — это не символ. Это **признак конца строки** в языке C,
его называют нуль-терминатор (null terminator). Язык C не хранит длину строки
отдельно: чтобы узнать, где строка кончается, программа читает байты подряд,
пока не встретит ноль.

Отсюда растёт целый класс уязвимостей: если нуля не окажется, программа будет
читать дальше и выйдет за пределы строки — в чужие данные.

### Задание 3.Г — `0xFFFFFFFF` и знаковость

**Знаковый `int`:** `0xFFFFFFFF` — это `-1`. Условие `result > 0` **не
сработает**. Так и задумано: функция вернула ошибку, программа её заметила.

**Беззнаковый `unsigned int`:** `0xFFFFFFFF` — это 4 294 967 295. Условие
`result > 0` **сработает**. Программа решит, что всё прошло успешно, и пойдёт
работать с несуществующим результатом.

Чем опасно: многие функции Windows возвращают `-1` как признак ошибки.
Например, `INVALID_HANDLE_VALUE` — это ровно `0xFFFFFFFFFFFFFFFF`. Если
программист сохранил результат в беззнаковую переменную, проверка ошибки
молча перестаёт работать.

Это не выдуманный пример, а одна из самых частых реальных ошибок. В реверсе
такие места ищут специально: они означают, что программу можно завести
в состояние, которого её автор не предусмотрел.

### 3.1. Почему одна hex-цифра — ровно 4 бита?

Потому что 16 = 2⁴. Шестнадцатеричная цифра принимает 16 значений, и ровно
столько же комбинаций даёт группа из 4 битов. Соответствие получается
один к одному, без остатка.

С тремя битами вышло бы 8 значений — это восьмеричная система, её тоже
использовали (в старом Unix), но она неудобна: байт из 8 битов на тройки
не делится нацело.

С пятью битами получилось бы 32 значения, и понадобилось бы 32 разных цифры.
Придумать их можно, но 8 на 5 тоже не делится — байт снова не ляжет ровно.

Шестнадцать выигрывает именно потому, что **8 делится на 4 нацело**: байт —
это всегда ровно две hex-цифры, без исключений.

### 3.2. Байт содержит `0x80`

Это либо **128** (если число беззнаковое), либо **−128** (если знаковое).

От чего зависит — **не от байта**. В байте этого не записано. Зависит от того,
какие инструкции с ним работают: у процессора разные команды для знакового и
беззнакового сравнения, разные переходы, разные инструкции расширения.

Определить знаковость можно только по коду вокруг. Это одна из постоянных
задач реверсера, и ошибиться здесь легко.

### 3.3. В памяти `00 10 00 00`

Переворачиваем: `00 00 10 00` → `0x00001000` = **4096**.

Про «нули слева в записи, но справа в памяти»: противоречия нет, это одно и
то же, просто увиденное с разных сторон. В записи `0x00001000` старшие байты
идут первыми (слева). В памяти little-endian первым лежит **младший** байт,
поэтому старшие нули оказываются в конце.

Иначе говоря, память хранит число в обратном порядке относительно того, как
мы его пишем.

### 3.4. Строки слева направо, числа справа налево — противоречие?

Нет, и вот почему.

**Число** — это одна величина, которую пришлось разложить по нескольким
байтам. Порядок раскладки — внутреннее дело процессора, договорённость.
x86 решил класть младший байт первым.

**Строка** — это не одна величина, а последовательность **самостоятельных**
байтов. Каждый символ — отдельное значение, помещающееся в один байт.
Раскладывать нечего, переворачивать тоже.

Проверка понимания: а если строка в UTF-16, где каждый символ занимает два
байта? Тогда переворачивается **каждый символ по отдельности**, но порядок
символов остаётся прямым. Поэтому `Hello` в UTF-16 выглядит как
`48 00 65 00 6C 00 6C 00 6F 00` — буквы по порядку, но у каждой свой нулевой
довесок после.

### 3.5. Инструкция `sub al, 0x30`

`0x30` — это код символа `0` в ASCII. Вычитание `0x30` из кода символа
превращает **символ цифры в само число**:

```
символ '7' = 0x37
0x37 - 0x30 = 0x07 = число 7
```

Значит, программа **разбирает число из текста**. Скорее всего, рядом будет
цикл: взять символ, вычесть `0x30`, умножить накопленное на 10, прибавить.

Где встречается: проверка серийного номера, разбор введённых данных, чтение
чисел из файла. Увидел `sub al, 0x30` или `sub eax, 0x30` — ищи рядом разбор
числа.

Родственный приём: `cmp al, 0x30` / `cmp al, 0x39` подряд — это проверка
«а цифра ли это вообще».

### 3.6. Почему `0x1000` встречается постоянно?

`0x1000` = 4096 — это **размер страницы памяти** (page size) в x86.

Операционная система управляет памятью не байтами, а страницами по 4 КБ.
Из этого следует, что по 4096 выровнено почти всё: секции внутри `.exe`,
адреса загрузки модулей, выделяемые блоки памяти.

Поэтому адреса вида `0x00401000`, `0x7FF6A2B10000` — с нулями на конце —
это не совпадение, а следствие выравнивания. Увидев такой адрес, можно сразу
предполагать начало какой-то области, а не середину данных.

Права доступа (читать, писать, исполнять) тоже назначаются страницами
целиком. Отсюда следует полезное для реверса: нельзя сделать исполняемыми
три байта — только страницу целиком, вместе со всем, что на ней лежит.

## Глава 4. Память, адреса, указатели

### 4.1. `printf("%d", p)` и `printf("%d", *p)`

- `p` — это сам указатель, в нём лежит адрес `0x1000`. Напечатается **4096**.
- `*p` — разыменование: «сходи по адресу и возьми, что там». Напечатается **25**.

Звёздочка в коде означает «значение по адресу». Без звёздочки — сам адрес.
Путаница между этими двумя вещами — самая частая ошибка у начинающих в C,
и разбирая чужой код, ты будешь постоянно отвечать себе на вопрос: тут
работают с адресом или со значением?

### 4.2. Адрес `values[6]`

```
адрес = начало + индекс × размер
      = 0x2000 + 6 × 2
      = 0x2000 + 12
      = 0x2000 + 0xC
      = 0x200C
```

Ответ: **`0x200C`**.

Не забудь, что 12 в десятичной — это `0xC` в шестнадцатеричной. Складывать
десятичное смещение с шестнадцатеричным адресом напрямую нельзя.

### 4.3. `mov eax, [rbx + rcx*8]`

Множитель `8` означает, что элементы массива занимают **по 8 байт**.

Что обычно занимает 8 байт на x86-64:

- **указатели** — самый частый случай, это массив адресов;
- `long long` — 64-битные целые;
- `double` — вещественные числа двойной точности.

Массив указателей встречается чаще всего: так устроены таблицы строк,
таблицы функций, массивы объектов.

Множитель — бесплатная подсказка о типе данных, и читать его стоит всегда:
`*1` — байты или строки, `*2` — `short` или UTF-16, `*4` — `int`,
`*8` — указатели.

Тонкость: приёмник `eax` — 32-битный регистр, хотя элемент 8-байтовый.
Значит, берётся только младшая половина. Возможно, это структура, а не
простой массив.

### 4.4. Почему адрес `0x00000000` роняет программу

Потому что Windows **намеренно оставляет первую страницу памяти
неотображённой**. Обращение по адресу, которому не сопоставлена физическая
память, вызывает аппаратное исключение, и система завершает процесс.

Сделано это специально. `NULL` в C равен нулю и означает «указатель никуда
не ведёт». Если бы адрес 0 был рабочим, ошибка «забыли проверить результат
функции» приводила бы к тихой порче данных вместо честного падения.

Практический вывод для отладки: увидел попытку обращения по адресу вроде
`0x00000000` или `0x00000008` — ищи не экзотику, а обычную непроверенную
функцию, вернувшую `NULL`. Смещение (`+8`, `+24`) подскажет, к какому полю
структуры пытались обратиться.

### 4.5. Строка `41 42 43 44 45` без нулевого байта

Функция печати не знает длину — она читает байты, пока не встретит `0x00`.
Нуля здесь нет, поэтому она **выйдет за пределы строки** и продолжит читать
чужие данные.

На экране появится `ABCDE`, а следом — мусор: куски соседних переменных,
обрывки других строк. Печать остановится на первом нулевом байте, который
случайно попадётся дальше.

Возможен и худший исход: если нулевой байт не встретится до конца доступной
области памяти, программа упадёт.

Это не теория, а механизм утечки **Heartbleed** (2014): программу удавалось
попросить прочитать больше, чем есть, и она отдавала содержимое чужой
памяти — включая пароли и ключи.

### 4.6. Миллион `malloc` без `free`

Это **утечка памяти** (memory leak). Программа просит память и не возвращает.

Что произойдёт по шагам:

1. Потребление памяти процессом растёт.
2. Windows начинает вытеснять память на диск — всё замедляется.
3. Когда исчерпается и это, очередной `malloc` вернёт `NULL`.
4. Если результат не проверяют (а обычно не проверяют) — обращение по
   нулевому указателю и падение.

Утечка сама по себе не уязвимость, но ведёт к отказу в обслуживании: если
утечку вызывает действие пользователя, достаточно повторить его много раз.

### 4.7. Как отладчик ставит точки останова в `.text`

Хороший вопрос — противоречие настоящее. Два механизма.

**1. Программные точки останова.** Отладчик временно снимает защиту с нужной
страницы вызовом `VirtualProtect`, заменяет один байт кода на `0xCC`
(инструкция `int 3` — «прервись и позови отладчик»), возвращает защиту.
Оригинальный байт он запоминает и подставляет обратно, когда ты смотришь
на код, — поэтому подмены не видно.

Отсюда способ обнаружить отладку: программа может **сама прочитать свой код**
и поискать байты `0xCC`. Приём известный, встретится в главе 23.

**2. Аппаратные точки останова.** У процессора есть четыре специальных
регистра (`DR0`–`DR3`): в них записывают адрес, и процессор останавливается
сам, ничего не меняя в памяти. Их всего четыре, зато код остаётся
нетронутым и проверкой целостности они не ловятся.

Именно поэтому в x64dbg есть два вида точек останова. Теперь понятно, зачем.

## Глава 5. Язык C за один вечер

### 5.1. Что не так с `if (x = 5)`

Один знак равенства вместо двух. `=` — это **присваивание**, а не сравнение.

`if (x = 5)` не проверяет, равен ли `x` пяти. Она **кладёт** 5 в `x`, а
потом проверяет получившееся значение. Пятёрка не ноль → условие всегда
истинно, при любом исходном `x`. И вдобавок исходное значение `x` затирается.

Правильно — `if (x == 5)`. Ошибка коварна тем, что код компилируется без
ошибки и внешне выглядит нормально. Это классический баг, и в реверсе такие
места видны: сравнение, которое всегда срабатывает одинаково.

### 5.2. Что лежит в `char c = 'Z'`

Число **90** (в шестнадцатеричной `0x5A`). По таблице ASCII из главы 3
`'Z'` = 90. Апострофы — просто удобная запись: компилятор подставит 90, и
в ассемблере ты увидишь именно `0x5A`, а не букву.

### 5.3. `cmp eax, 0x1A0A`

Переводим `0x1A0A` в десятичную:

```
1×4096 + 10×256 + 0×16 + 10 = 4096 + 2560 + 0 + 10 = 6666
```

Значит, программа сравнивает что-то с числом **6666**. Раз это `cmp` перед
условным переходом — это проверка (`if`). Число 6666 «зашито» в код открыто:
если это, скажем, ожидаемый серийник или магическое значение — ты его уже
нашёл, просто прочитав ассемблер. Именно так и ловятся простые проверки.

### 5.4. `jne` на адрес выше

Это **цикл**. Переход назад (на инструкцию выше текущей) означает «вернись и
повтори». `jne` — «прыгни, если не равно»: цикл крутится, пока условие
выхода не выполнится.

Общее правило из главы 5: переход вперёд — это обычно `if` (перепрыгнуть блок),
переход назад — это цикл (повторить блок).

### 5.5. В регистр кладут адрес переменной перед вызовом

Функция собирается **записать** что-то в эту переменную (или изменить её).

Логика: если бы функции нужно было только прочитать значение, ей передали бы
само значение. Раз передают адрес — значит, функция пойдёт по этому адресу и
что-то туда положит. Классика — `scanf("%d", &x)`: читает ввод и кладёт в `x`.

Это полезный приём анализа: по тому, что передают — значение или адрес, —
часто можно понять, читает функция данные или пишет.

### 5.6. `mov eax, [rcx+8]` при `rcx` = адрес структуры

Читают **поле структуры, лежащее на смещении 8** от её начала.

Квадратные скобки — обращение по адресу (глава 5.9, это разыменование).
`rcx` — база (начало структуры), `+8` — смещение до нужного поля. Если,
например, структура начинается с двух полей по 4 байта, то на смещении 8
лежит третье поле — его и читают в `eax`.

Смещение подсказывает, какое это поле; размер приёмника (`eax` — 4 байта)
подсказывает размер поля.

### 5.7. Эксперимент на godbolt

Что ты должен был увидеть:

- **При `-O0`** твоё число лежит в коде как `cmp` с этой константой,
  открытым текстом. Найти его глазами — секунда.
- **При `-O2`** код может стать короче (компилятор иногда сворачивает
  функцию в пару инструкций, как мы видели в главе 2), но **константа
  почти всегда остаётся видна** — сравнивать-то с чем-то надо. Убрать само
  число компилятор не может: оно часть логики.

Вывод, важный для реверса: оптимизация меняет **форму** кода, но константы
сравнения — пароли, магические числа, размеры — обычно переживают её и
остаются на виду. Прятать их — отдельная работа (обфускация, часть VII),
и по умолчанию компилятор её не делает.

## Глава 6. Ставим инструменты

### 6.1. UPX и энтропия 7.9 — открывать ли в Ghidra?

**Не сразу.** UPX — это упаковщик (глава 2): настоящий код сжат, а в файле
лежит распаковщик, который развернёт его в памяти при запуске. Энтропия 7.9
(почти максимум 8.0) это подтверждает — данные сжаты/зашифрованы.

Если открыть такой файл в Ghidra как есть, увидишь только код распаковщика —
крохотный кусок, который разворачивает основную программу. Самой логики там
нет, она появится лишь в памяти во время работы.

Правильный порядок: сначала **распаковать** (для UPX часто хватает
`upx -d`, но не всегда — бывают модифицированные упаковщики), и только потом
анализировать. Распаковку разберём в главе 24. Пока запомни: DIE показал
упаковщик → сначала распаковка, потом всё остальное.

### 6.2. Зачем папка и заметки

Потому что анализ программы — это **сотни мелких фактов**, которые физически
не помещаются в голову: какая функция что делает, где сравнивается пароль,
куда приходит ввод, какой адрес что значит. Через час работы ты забудешь то,
что понял в начале, и будешь разбираться заново.

Заметки превращают разрозненные открытия в **карту программы**, которая
растёт и остаётся между сессиями. Отдельная папка под каждый файл — чтобы
дампы, патченные копии и заметки не смешивались. Это не бюрократия, а
внешняя память: опытные реверсеры ведут заметки всегда, именно потому что
знают предел собственной.

### 6.3. Почему Defender удаляет x64dbg

Потому что инструменты реверса — **двойного назначения**. Отладчик умеет
внедряться в чужой процесс, менять его память, перехватывать выполнение —
ровно то, что делает и вредонос. Антивирус не может по коду понять намерение,
поэтому перестраховывается.

Как отличить ложное срабатывание от настоящего:

1. **Источник.** Скачал с официального GitHub проекта → почти наверняка
   ложное срабатывание. Скачал с левого сайта → могли подсунуть заражённое.
2. **Контрольная сумма.** У серьёзных проектов на странице релиза бывают
   хеши (SHA-256) — сверь с тем, что скачал (тот же HxD умеет считать).
3. **Репутация.** Можно проверить файл на VirusTotal: если ругается 1–2
   антивируса из семидесяти и это известный инструмент — ложное срабатывание;
   если половина — выброси.

Практика: держи инструменты в отдельной папке и добавь её в исключения
Defender — но только инструменты из проверенных источников.

### 6.4. В начале файла нет `4D 5A`

Значит, это **не обычный исполняемый файл Windows**. Подпись `MZ` (`4D 5A`)
стоит в начале любого `.exe` и `.dll`. Нет её — варианты:

- это вообще не PE-файл (картинка, документ, архив — у каждого своя подпись);
- файл повреждён;
- файл зашифрован или упакован нестандартно;
- расширение `.exe` подделано, а внутри другое.

Первый байт-другой файла называют «магической подписью» — по ней определяют
тип. `4D 5A` → PE, `7F 45 4C 46` → ELF (Linux), `50 4B` → ZIP/архив,
`89 50 4E 47` → PNG. DIE и опознаёт файлы в основном по таким подписям.

### 6.5. Какой компилятор покажет DIE

Для твоего `hello.exe`, собранного gcc, — **GCC** (точнее, DIE покажет
что-то вроде «MinGW» / «GCC», потому что w64devkit это сборка gcc под
Windows).

Если бы ту же программу ты собрал в **Visual Studio**, DIE показал бы
**Microsoft Visual C++ (MSVC)**. Это разные компиляторы, и код они
порождают заметно разный: пролог функций, порядок инструкций, служебные
вставки отличаются. Опытный реверсер по стилю ассемблера часто угадывает
компилятор, ещё не заглянув в DIE, — потому что MSVC и GCC «пишут» по-разному.

Это практически важно: зная компилятор, ты знаешь его типовые шаблоны и
быстрее отделяешь служебный код от логики программы.

## Глава 7. Первое вскрытие

### 7.1. Энтропия 7.86, четыре импорта, VirtualAlloc и LoadLibraryA

Это **упакованный файл**. Три улики сходятся:

- энтропия почти максимальная — данные выглядят случайным шумом, значит
  сжаты или зашифрованы;
- импортов всего четыре — настоящая программа столькими не обходится;
- `VirtualAlloc` (выделить память) и `LoadLibraryA` (подгрузить библиотеку) —
  ровно то, что нужно распаковщику: выделить место, развернуть туда
  настоящий код, подтянуть нужные библиотеки.

**Строки искать бессмысленно.** В файле их нет — они появятся в памяти
только после распаковки при запуске. Сначала распаковка (глава 24), потом
всё остальное.

### 7.2. `http://update.example.com/patch.bin` и `C:\ProgramData\svc\cache.dat`

Гипотеза: программа **скачивает файл из интернета и сохраняет его на диск**.
Похоже на загрузчик обновлений — или на загрузчик вредоносной «второй
ступени», который тянет основное тело.

Что настораживает: путь в `C:\ProgramData\` — это общая папка, доступная
всем пользователям, и туда часто прячут файлы, потому что она не на виду.
Имя `svc` намекает на маскировку под системную службу.

Проверять гипотезу надо импортами (есть ли сетевые функции и работа с
файлами) и дальше — динамическим анализом.

### 7.3. `IsDebuggerPresent` в импортах

Программа **умеет замечать отладчик**. Это меняет план:

1. Под отладчиком она может вести себя иначе — вплоть до того, что
   правильный пароль перестанет подходить (ровно как наш crackme 04).
2. Значит, **нельзя доверять результатам динамического анализа**, пока
   защита не обойдена.
3. Приоритет смещается к статическому анализу: найти сам вызов
   `IsDebuggerPresent` и посмотреть, что происходит с его результатом.

Тонкость: отсутствие этого импорта **не** означает отсутствие защиты.
Проверку можно сделать вручную, читая структуру процесса напрямую, — тогда
в импортах не будет ничего подозрительного.

### 7.4. Пароль сравнивается, но в строках его нет

Минимум четыре причины:

1. **Строка зашифрована** и расшифровывается в памяти перед сравнением
   (наш crackme 02).
2. **Пароль вычисляется**, а не хранится: программа считает что-то из ввода
   и сравнивает с числом (наш crackme 03).
3. **Сравнивается не пароль, а его хеш.** В файле лежит результат
   математического преобразования, по которому исходный пароль не
   восстанавливается напрямую — только перебором.
4. **Ищешь не в той кодировке:** строка в UTF-16, а поиск идёт по ASCII.

Первое, что стоит проверить, — четвёртый пункт, он самый дешёвый.

### 7.5. Почему `GetProcAddress` обесценивает таблицу импортов

`GetProcAddress` получает адрес **любой** функции по её имени во время
работы программы. То есть программа может вызвать что угодно, ничего не
объявляя заранее.

Схема простая: в импортах честно лежат только `LoadLibraryA` и
`GetProcAddress`, а имена настоящих функций хранятся как обычные строки
(часто зашифрованные) и подтягиваются по ходу дела.

Вывод: таблица импортов показывает **нижнюю границу** возможностей
программы. Она говорит «умеет как минимум это», но никогда — «умеет только
это». Так работают почти все вредоносы: скромный список импортов при полном
наборе возможностей.

### 7.6. Программа печатает слово, но поиск его не находит

Почти наверняка дело в **кодировке**. Windows хранит текст в UTF-16 — по два
байта на символ. Если инструмент ищет строки в ASCII, он пройдёт мимо: для
него `Пароль` в UTF-16 выглядит как набор символов, разделённых нулевыми
байтами.

Решение: переключить поиск на Unicode / UTF-16 (в Detect It Easy и HxD это
отдельная опция).

Вторая возможная причина: строка собирается из кусков во время работы или
приходит из ресурсов программы, а не из секции данных.

### 7.7. Практическое: вскрой `01_strings.exe`

Разбор не привожу — это твоя задача, и она решается ровно тем методом, что
описан в главе: опознай файл, вытащи строки, найди среди них ту, которая
не похожа на сообщение пользователю.

Подсказка, если застрял: сообщения программы написаны русскими словами
латинскими буквами (`Vvedite parol`), а искомая строка на сообщение
не похожа. Она короткая, из латинских букв, цифр и подчёркиваний, и стоит
в списке рядом с этими сообщениями.

Получилось — поздравляю, это твой первый самостоятельно вскрытый бинарник.
Подробный разбор с другими методами — в главе 16.

## Глава 8. Формат PE

### 8.1. Зачем `.exe` заголовок от мёртвой MS-DOS

Две причины, и вторая важнее первой.

**Историческая совместимость.** Изначально — чтобы старая система могла
хотя бы вежливо отказаться запускать новую программу, а не рухнуть.

**Практическая, живая до сих пор:** в DOS-заголовке лежит поле по смещению
`0x3C`, которое указывает, где начинается настоящий PE-заголовок. Загрузчик
Windows читает именно его. То есть DOS-заголовок стал **указателем на
современный формат**.

Если его убрать, файл перестанет запускаться: Windows не найдёт подпись `MZ`
и не узнает, где искать `PE\0\0`. Формально можно оставить огрызок из
подписи и поля `0x3C` — некоторые упаковщики так и делают, чтобы уменьшить
файл, и это само по себе признак ненормальной сборки.

### 8.2. По `0x3C` лежит `F8 00 00 00`

Порядок little-endian, переворачиваем: `00 00 00 F8` → `0x000000F8`.

`0xF8` = 15×16 + 8 = **248**.

Подпись `PE\0\0` искать по смещению **248**.

### 8.3. Точка входа при `AddressOfEntryPoint = 0x2340`

```
VA = ImageBase + AddressOfEntryPoint
   = 0x140000000 + 0x2340
   = 0x140002340
```

Выполнение начнётся с адреса **`0x140002340`**.

**При следующем запуске адрес почти наверняка будет другим.** Виновата
**ASLR** (глава 4): Windows сдвигает базу образа на случайную величину
при каждом запуске, чтобы атакующий не мог заранее знать адреса.

Что при этом не меняется — **RVA**. Смещение `0x2340` от начала образа
остаётся верным всегда, потому и записано в файле именно оно.

Практическое следствие: адреса из файла нельзя запоминать как абсолютные.
В отладчике ориентируйся на смещения от базы модуля.

### 8.4. `SectionAlignment` против `FileAlignment`

Это выравнивание одних и тех же секций в двух разных местах.

| | `SectionAlignment` | `FileAlignment` |
|---|---|---|
| Где действует | в памяти | в файле на диске |
| Типичное значение | `0x1000` (4096) | `0x200` (512) |
| Почему такое | размер **страницы** памяти | размер сектора диска |

Разные они потому, что у памяти и диска разные единицы работы.

В памяти права доступа (читать, писать, исполнять) назначаются **страницами
по 4096 байт** — нельзя сделать исполняемыми 100 байт, только страницу
целиком. Поэтому каждая секция обязана начинаться с новой страницы, иначе
права соседних секций перемешались бы.

На диске такой необходимости нет, а выравнивать по 4096 было бы расточительно:
секция в 50 байт заняла бы 4096. Поэтому в файле шаг мельче.

Отсюда и главное следствие: **расположение данных в файле и в памяти не
совпадает**, и одно приходится пересчитывать в другое.

### 8.5. У `.text` права «чтение + запись + исполнение»

Подозрительно, потому что **нормальной программе это не нужно**. Код пишется
один раз компилятором и во время работы не меняется — ему хватает прав
«чтение + исполнение».

Право записи на исполняемой секции означает: **код собирается меняться сам
во время работы**. Типичные причины:

- **упаковщик** — распаковывает настоящий код поверх себя;
- **самомодифицирующийся код** — приём обфускации, чтобы дизассемблер
  видел не то, что реально выполнится;
- **вредонос** — расшифровывает полезную нагрузку в памяти.

Ни один из вариантов не характерен для обычной программы. Вывод: статический
анализ такого файла покажет не то, что выполнится. Сначала надо получить
распакованное состояние (глава 24).

Для сравнения: сочетание «запись + исполнение» настолько опасно, что
современные системы защищаются от него на уровне процессора — это **DEP**
из ответа 1.5.

### 8.6. Секция: 0 байт в файле, 200 килобайт в памяти

Два принципиально разных объяснения, и различать их надо по имени секции.

**Вариант нормальный — это `.bss`.** Там лежат глобальные переменные,
которые в C по стандарту начинаются с нуля. Хранить в файле 200 килобайт
нулей бессмысленно — достаточно записать «выдели столько-то и заполни
нулями». Это штатное поведение любого компилятора, тревоги нет.

**Вариант тревожный — если так выглядит секция с кодом** (`.text`) или
секция со странным именем (`UPX1`, `.vmp0`). Тогда это упаковщик: в файле
пусто, содержимое появится в памяти при запуске, когда распаковщик его
туда развернёт.

Как отличить на практике: посмотри имя секции и её права. `.bss` с правами
«чтение + запись» и без исполнения — норма. Секция с правом исполнения и
нулевым размером в файле — почти наверняка упаковка.

### 8.7. Почему нельзя перейти в HxD к смещению `0x140001500`

Потому что это **виртуальный адрес** — адрес в памяти запущенного процесса.
А HxD работает с **файлом на диске**, где та же информация лежит совсем по
другому смещению.

Три числа из раздела 8.7 главы:

```
VA   = 0x140001500   адрес в памяти (его показал отладчик)
RVA  = VA - ImageBase = 0x140001500 - 0x140000000 = 0x1500
Raw  = ?             смещение в файле — считается по таблице секций
```

Пересчёт RVA в файловое смещение делается так: найти секцию, в которую
попадает этот RVA, и применить разницу между её виртуальным и файловым
началом. Из-за разных выравниваний (ответ 8.4) эта разница не нулевая.

На практике вручную это не считают — **PE-bear пересчитывает сам** (колонки
`Raw Addr.` и `Virtual Addr.`). Но понимать, что числа разные, обязательно:
попытка править файл по виртуальному адресу испортит совсем другое место.

Этим займёмся вплотную в главе 21, когда будем патчить программу.

### 8.8. Практическое

Проверь себя так: значение, которое ты прочитал руками по смещению `0x3C`,
должно привести ровно к подписи `PE\0\0`, а число секций из заголовка —
совпасть с тем, что показывают Detect It Easy и PE-bear.

Если сошлось — ты научился читать заголовок PE без инструментов. Адрес
точки входа, который ты посчитал, сохрани: в главе 13 поставишь по нему
первую точку останова.

## Глава 9. Процессор x86-64

### 9.1. Меняет ли `mov al, 5` значение `RAX`?

**Да.** `AL` — это младший байт `RAX`, не отдельная ячейка. Записал в `AL` —
изменился и `RAX`.

Но здесь прячется тонкость x86-64, на которой спотыкаются даже опытные:

| Куда пишем | Что происходит со старшими битами |
|---|---|
| `AL` (8 бит) | **сохраняются** |
| `AX` (16 бит) | **сохраняются** |
| `EAX` (32 бита) | **обнуляются!** |
| `RAX` (64 бита) | перезаписывается весь |

Пример. Пусть в `RAX` лежит `0x1122334455667788`:

```
mov al,  0x99   →  RAX = 0x1122334455667799   (тронут один байт)
mov ax,  0x9999 →  RAX = 0x1122334455669999   (тронуты два байта)
mov eax, 0x99   →  RAX = 0x0000000000000099   (верх обнулён!)
```

Почему так: правило «запись в 32-битный регистр обнуляет верхнюю половину»
ввели специально при переходе на 64 бита — оно делает код короче и убирает
зависимость от прежнего значения.

Для реверса это важно: увидев `mov eax, 5`, знай, что весь `RAX` стал равен
5, а не только его младшая часть.

### 9.2. `mov BYTE PTR [rbx], al` внутри цикла

Программа **пишет отдельные байты по адресу** и делает это многократно.

`BYTE PTR` и `AL` означают размер в один байт. Один байт за раз, в цикле,
по адресу из регистра — это почти наверняка **работа со строкой**:
копирование, шифрование (вспомни XOR из crackme 02), перевод регистра,
посимвольная проверка пароля.

Признак, по которому это узнают: цикл + однобайтовые операции + указатель,
который увеличивается. Рядом обычно есть проверка на нулевой байт — конец
строки (глава 4).

### 9.3. Что делает `cmp eax, eax`

`cmp` вычитает второй операнд из первого. Здесь оба операнда — один и тот же
регистр, поэтому результат **всегда ноль**, независимо от содержимого.

Значит, `ZF` (флаг нуля) гарантированно становится **1**, а `SF` и `CF` — 0.

Зачем такое пишут: чтобы принудительно установить флаги в известное
состояние. Например, чтобы следующий `je` сработал **всегда** — получается
безусловный переход, замаскированный под условный. Это приём обфускации:
дизассемблер покажет ветвление, хотя ветки на самом деле нет.

Увидел `cmp регистр, тот же регистр` — присмотрись, скорее всего тебя
пытаются запутать.

### 9.4. Почему переход стоит сразу за `cmp`

Потому что **флаги перезаписываются почти каждой арифметической
инструкцией**. `add`, `sub`, `and`, `or`, `inc` — все они выставляют флаги
по своему результату.

Если между `cmp` и переходом вклинится такая инструкция, переход посмотрит
уже на **её** флаги, а не на результат сравнения. Логика сломается.

Поэтому компилятор держит их вплотную. Практическое следствие для реверса:
увидев условный переход, ищи сравнение **непосредственно перед ним** — это
и есть проверяемое условие.

Исключение, о котором стоит знать: `mov` и `lea` флаги **не меняют**. Их
компилятор иногда вставляет между `cmp` и переходом, и это не ошибка.

### 9.5. `cmp ecx, 100` и следом `ja`

`ja` — **j**ump if **a**bove, переход для **беззнаковых** чисел.

Значит, программа трактует содержимое `ECX` как **беззнаковое** — только
положительное, от 0 до 4 294 967 295.

Для знакового сравнения компилятор выбрал бы `jg` (**g**reater).

Это ровно тот ответ на вопрос из главы 3, который мы тогда отложили: в самом
байте знаковость не записана, но её **видно по инструкции перехода**.

Практическая ценность: если данные приходят от пользователя и сравниваются
беззнаково, отрицательное значение превратится в огромное положительное —
и проверка «не больше 100» пройдёт совсем не так, как задумано.

### 9.6. Почему нельзя `mov rip, 0x401000`

Процессор просто не поддерживает такую инструкцию — `RIP` недоступен как
приёмник для `mov`.

Это сделано намеренно. `RIP` определяет, что выполняется следующим; если бы
в него можно было писать как в обычный регистр, любая ошибка в вычислениях
уводила бы программу в случайное место памяти.

Менять `RIP` можно только специальными инструкциями передачи управления:

| Инструкция | Что делает с `RIP` |
|---|---|
| `jmp адрес` | записывает новый адрес |
| `call адрес` | сохраняет текущий на стеке, записывает новый |
| `ret` | снимает сохранённый со стека и записывает |
| `je`, `jne`, `jg`… | записывает новый, если флаги сошлись |

Тонкость: `jmp` и `call` умеют брать адрес из регистра или памяти
(`jmp rax`, `call qword ptr [rbx]`). Так что косвенно управление всё же
передаётся вычисленному значению — и на этом строятся как таблицы
переходов, так и атаки.

### 9.7. `[rbp-8]` и `[rbp+24]`

- **`[rbp-8]`** — **локальная переменная**. Отрицательное смещение от `RBP`.
- **`[rbp+24]`** — **аргумент** функции. Положительное смещение.

Причина в устройстве стекового кадра. `RBP` ставится как опора при входе в
функцию; **ниже** него (меньшие адреса) функция выделяет место под свои
локальные переменные, а **выше** (большие адреса) лежит то, что было до
вызова: сохранённый `RBP`, адрес возврата и аргументы.

Правило для чтения кода:

```
[rbp - число]  →  своё, локальное
[rbp + число]  →  пришедшее снаружи
```

Подробно разберём в главе 11.

### 9.8. Проверка длины через `jl`, копирование беззнаковое

Пользователь может ввести **отрицательную длину**, например −1.

Что произойдёт:

1. Проверка `jl` — знаковая. −1 действительно меньше максимума, проверка
   пройдена.
2. Функция копирования трактует размер как беззнаковый. Для неё −1 — это
   `0xFFFFFFFF`, то есть 4 294 967 295.
3. Программа пытается скопировать четыре гигабайта в маленький буфер.

Результат — переполнение буфера (глава 4) со всеми последствиями вплоть до
перехвата управления.

Это не выдуманный, а один из самых частых классов уязвимостей. В ассемблере
он виден как **несогласованность**: проверка знаковая (`jl`, `jg`),
а использование беззнаковое. Такие места ищут прицельно.

## Глава 10. Ассемблер: основные инструкции

### 10.1. `mov rax, rbx` против `mov rax, [rbx]`

- **`mov rax, rbx`** — скопировать **само значение** из `rbx`. К памяти
  обращения нет.
- **`mov rax, [rbx]`** — взять значение из `rbx` как **адрес**, сходить по
  нему в память и загрузить то, что там лежит.

В терминах C (глава 5):

```c
rax = rbx;      // mov rax, rbx
rax = *rbx;     // mov rax, [rbx]
```

Скобки в ассемблере — это звёздочка в C. Путать их нельзя: в первом случае
ты работаешь с адресом, во втором — с данными по нему.

### 10.2. `lea rax, [rbx+rbx*4]`

Вычисляет `rbx + rbx×4 = rbx×5` и кладёт результат в `rax`.

**К памяти не обращается.** В этом вся суть `lea`: она использует запись
с квадратными скобками, но только считает выражение, а не идёт по адресу.

Здесь налицо тот самый трюк из раздела 10.4: компилятор заменил умножение
на 5 одной быстрой инструкцией. Признак того, что это арифметика, а не
адрес, — множитель внутри скобок и отсутствие осмысленного смещения.

### 10.3. `shl eax, 4`

Сдвиг влево на 4 бита = **умножение на 2⁴ = 16**.

Общее правило: `shl a, n` — умножение на 2ⁿ, `shr a, n` — деление на 2ⁿ
(для беззнаковых).

Компилятор так делает, потому что сдвиг выполняется за один такт, а
умножение — за несколько. Увидев сдвиг, сразу переводи его в умножение или
деление — читать станет понятнее.

### 10.4. Зачем `xor eax, eax` вместо `mov eax, 0`

Результат одинаковый, но **машинный код короче**:

```
xor eax, eax   →  31 C0           (2 байта)
mov eax, 0     →  B8 00 00 00 00  (5 байт)
```

Экономия три байта на каждом обнулении. В большой программе это заметно,
а обнуление — операция очень частая.

Есть и вторая причина, техническая: процессоры распознают `xor` регистра
с самим собой как «обнуление» и выполняют его особенно эффективно, не
создавая зависимости от прежнего значения.

Для реверса важно одно: **это не шифрование**. Увидел `xor` регистра с самим
собой — читай как «обнулить».

### 10.5. `test rcx, rcx` + `je метка`

Это **проверка указателя на `NULL`**:

```c
if (p == NULL) { ... }
```

`test` делает побитовое И и выставляет флаги. `rcx & rcx` равно нулю только
если сам `rcx` равен нулю. Значит, `je` сработает ровно тогда, когда
указатель нулевой.

Тот же шаблон используется для любой проверки «равно ли нулю»: код возврата
функции, конец строки, признак ошибки. Понять, что именно проверяется,
помогает контекст — что лежало в регистре до этого.

### 10.6. `mov eax, DWORD PTR [rsi+rdi*8]`

Множитель `8` означает, что **элементы массива занимают по 8 байт**.

Что обычно бывает восьмибайтовым на x86-64:

- **указатели** — самый частый случай (массив строк, таблица функций);
- `long long` — большие целые;
- `double` — вещественные числа.

Здесь есть любопытная деталь: приёмник — `eax`, то есть **32 бита**, хотя
элемент восьмибайтовый. Значит, берут только младшую половину элемента.
Скорее всего, это не простой массив, а **массив структур**, и читают его
четырёхбайтовое поле.

### 10.7. `cmp al, 57` и `cmp al, 48`

По таблице ASCII (глава 3):

- `48` = `0x30` = символ **`'0'`**
- `57` = `0x39` = символ **`'9'`**

Два таких сравнения подряд — это **проверка, является ли символ цифрой**:

```c
if (c >= '0' && c <= '9')
```

Программа разбирает текст: читает число из введённой строки, проверяет
формат серийного номера, парсит данные из файла. Рядом почти наверняка
будет `sub al, 48` — превращение символа цифры в само число (ответ 3.5).

Это один из самых узнаваемых шаблонов, и встретится он тебе в crackme 03.

### 10.8. Почему `push` и `pop` должны быть сбалансированы

Потому что **адрес возврата лежит на том же стеке**.

Когда выполняется `call`, процессор кладёт на стек адрес следующей
инструкции. Инструкция `ret` снимает со стека **то, что лежит на вершине**,
и прыгает туда — она не проверяет, действительно ли это адрес возврата.

Если сделать лишний `push` перед `ret`, на вершине окажется не адрес
возврата, а положенное значение. `ret` прыгнет по нему — и программа почти
наверняка рухнет, потому что там не код.

Это ровно тот механизм, на котором работает переполнение буфера (глава 4):
атакующему не нужен лишний `push`, ему достаточно перезаписать адрес
возврата данными.

### 10.9. Разбор функции

```asm
func:
    xor   eax, eax            ; счётчик = 0
.L1:
    cmp   BYTE PTR [rcx], 0   ; байт по адресу rcx равен нулю?
    je    .L2                 ; да — выйти
    add   eax, 1              ; счётчик++
    add   rcx, 1              ; перейти к следующему байту
    jmp   .L1                 ; повторить
.L2:
    ret                       ; вернуть счётчик (он в eax)
```

Разбираем по методу из главы:

1. Пролога нет — функция простая, стек не трогает.
2. `rcx` — первый аргумент (глава 9), и с ним работают через `BYTE PTR`,
   то есть это **указатель на строку**.
3. `jmp .L1` — переход назад, **цикл**.
4. Условие выхода — нулевой байт, то есть **конец строки** (глава 4).
5. `eax` растёт на каждом шаге и возвращается — это **счётчик**.

**Функция считает количество байтов в строке до нулевого — то есть её
длину.**

В стандартной библиотеке C её аналог называется **`strlen`**.

Узнавать этот шаблон полезно: цикл по байтам с выходом по нулю встречается
в любой работе со строками — копировании, сравнении, поиске, шифровании.

## Глава 11. Стек и функции

### 11.1. Что кладёт на стек `call`

**Адрес следующей инструкции** — той, что идёт сразу за самим `call`.
Это адрес возврата.

Нужен он затем, что функция обязана вернуть управление туда, откуда её
позвали. Инструкция `ret` в конце снимает это значение со стека и
записывает в `RIP`.

То есть `call` — это два действия в одном: `push` адреса возврата и `jmp`
на функцию. А `ret` — обратное: `pop` в `RIP`.

Ключевое для реверса: **`ret` не проверяет, что снимает**. Ему всё равно,
лежит там настоящий адрес возврата или подсунутое значение.

### 11.2. Зачем сохранять `RBP`, если есть `RSP`

Потому что **`RSP` постоянно двигается**, а `RBP` — нет.

Каждый `push`, `pop` и вызов функции меняет `RSP`. Если адресовать
переменные от него, смещения пришлось бы пересчитывать после каждой такой
операции: сегодня переменная в `[rsp+8]`, а через две инструкции — уже
в `[rsp+24]`.

`RBP` ставится один раз в прологе и до эпилога стоит неподвижно. От него
все смещения постоянны на протяжении всей функции — и код проще, и читать
его человеку легче.

Сохранять его обязательно, потому что он принадлежит вызывающей функции:
испортим — та потеряет доступ к своим переменным.

Цена — две инструкции. Поэтому оптимизирующий компилятор от кадра часто
отказывается (раздел 11.10).

### 11.3. `mov eax, DWORD PTR [rbp+24]`

Это **аргумент функции, второй по счёту**.

Разбор по карте кадра:

```
[rbp+8]   адрес возврата
[rbp+16]  1-й аргумент  (пришёл в RCX)
[rbp+24]  2-й аргумент  (пришёл в RDX)   ← наш случай
[rbp+32]  3-й аргумент  (R8)
[rbp+40]  4-й аргумент  (R9)
```

Размер `DWORD` — четыре байта, значит это `int` или другое 32-битное
значение.

Правило, которое стоит довести до автоматизма: **положительное смещение
от `RBP` — данные снаружи, отрицательное — свои**.

### 11.4. Почему `add rsp, 16` не стирает переменные

Потому что эта инструкция меняет **только значение регистра `RSP`** —
она сдвигает указатель вершины стека. К самой памяти она не обращается
и ничего туда не пишет.

Байты остаются лежать там же. Просто область перестаёт считаться занятой,
и следующий вызов функции получит её под свои нужды — и перезапишет, когда
и если дойдёт.

Два практических последствия:

**Мусор в неинициализированных переменных.** Объявил `int x;` и не присвоил
значение — в `x` окажется то, что оставил предыдущий вызов. Программа будет
вести себя непредсказуемо, а иногда этот мусор утекает наружу вместе
с выводом.

**Секреты остаются в памяти.** Пароль, ключ или токен, с которым работала
завершившаяся функция, продолжает лежать в памяти процесса. Дамп памяти
покажет его. Поэтому аккуратные программы **явно затирают** такие буферы
перед выходом.

### 11.5. `push rbx` без парного `pop rbx`

Стек окажется **несбалансирован на 8 байт**, и функция вернётся не туда.

По шагам: `push rbx` опустил `RSP` на 8. К моменту `ret` вершина указывает
не на адрес возврата, а на сохранённое значение `RBX`. `ret` снимает его
и прыгает по нему как по адресу.

Результат — почти наверняка аварийное завершение: в `RBX` лежало какое-то
данное, а не адрес исполняемого кода. В худшем случае там окажется
что-то, похожее на адрес, и программа выполнит случайный кусок памяти.

Именно поэтому баланс `push` и `pop` — жёсткое правило (упражнение 10.8),
а компилятор его никогда не нарушает. Нарушения бывают в написанном
вручную ассемблере и в намеренно запутанном коде.

### 11.6. Где канарейка поймала атаку

На шаге **проверки перед эпилогом**, в этих двух инструкциях:

```asm
    mov  rax, QWORD PTR 56[rsp]   ; прочитать канарейку со стека
    sub  rax, QWORD PTR [rbx]     ; сравнить с эталонным значением
    jne  .L3                      ; не совпало → __stack_chk_fail
```

Почему это сработало: канарейка лежит **между буфером и адресом возврата**.
Переполнение пишет последовательно, снизу вверх — чтобы добраться до адреса
возврата, оно обязано пройти через канарейку и затереть её.

Программа обнаружила подмену **до** выполнения `ret`, то есть до того, как
управление было бы передано атакующему, и завершилась сама.

Тонкость: защита ловит именно **последовательную** запись насквозь. Если
уязвимость позволяет писать по произвольному смещению, канарейку можно
перешагнуть, не тронув.

### 11.7. Функция без `push rbp`

Это **функция без стекового кадра** — результат оптимизации. Компилятор
решил, что `RBP` как опора не нужен, и адресуется прямо от `RSP`,
экономя две инструкции. Освободившийся `RBP` он использует как обычный
регистр.

Чем усложняет анализ: **`RSP` двигается по ходу функции** — при каждом
`push` и при подготовке вызовов. Поэтому одно и то же смещение `[rsp+32]`
в разных местах функции может указывать на разные данные.

Приходится следить за значением `RSP` от начала функции, чтобы понимать,
на что ссылается очередное смещение. Инструменты вроде Ghidra делают это
автоматически и показывают нормальные имена переменных — это одна из причин
пользоваться декомпилятором.

### 11.8. Пароль остаётся в памяти

Причина — та же, что в ответе 11.4: **освобождение стека не стирает данные**.
Функция завершилась, `RSP` поднялся, но байты пароля продолжают лежать
в памяти процесса, пока их случайно не перезапишет другой вызов.

Чем опасно: пароль можно вытащить из дампа памяти, из файла аварийного
завершения, а иногда и через уязвимость чтения чужой памяти.

Что должен сделать аккуратный программист: **явно затереть буфер** перед
выходом из функции — записать туда нули.

Тонкость, которую знают не все: простое обнуление компилятор имеет право
**выбросить** при оптимизации, рассудив, что результат всё равно никто не
читает. Поэтому для такого затирания существуют специальные функции,
которые компилятору запрещено удалять (в Windows это `SecureZeroMemory`).

Для реверсера отсюда практический приём: **искать секреты в памяти
процесса** имеет смысл даже после того, как работавшая с ними функция
завершилась.

### 11.9. Разбор кадра

```asm
push  rbp
mov   rbp, rsp
sub   rsp, 48
mov   QWORD PTR 16[rbp], rcx     ; 1-й аргумент, 8 байт
mov   DWORD PTR 24[rbp], edx     ; 2-й аргумент, 4 байта
```

**Аргументов — два** (сохраняются только они):

| Смещение | Регистр | Размер | Скорее всего |
|---|---|---|---|
| `[rbp+16]` | `RCX` | `QWORD`, 8 байт | **указатель** (строка или структура) |
| `[rbp+24]` | `EDX` | `DWORD`, 4 байта | **`int`** |

Похоже на сигнатуру вида `функция(указатель, число)` — например, «обработать
строку с заданной длиной» или «прочитать N байт из буфера».

**Под локальные данные отведено 48 байт** (`sub rsp, 48`).

Но осторожно с трактовкой: эти 48 байт не обязательно все заняты
переменными. В них может входить выравнивание стека и теневое пространство
под собственные вызовы функции (раздел 11.5). Сколько именно ушло на
переменные, видно только по тому, какие смещения реально используются
дальше в коде.

## Глава 12. Соглашение о вызовах и WinAPI

### 12.1. Зачем нужны соглашения

Чтобы код, написанный разными людьми и собранный разными компиляторами,
мог работать вместе.

Функция `A` кладёт аргумент в `RCX` и вызывает `B`. Если `B` ожидает
аргумент в `RDX`, она возьмёт мусор. Программа не упадёт честно — она
поведёт себя непредсказуемо, и найти причину будет крайне тяжело.

Без общих правил было бы невозможно:

- вызывать функции из чужих библиотек;
- обращаться к системе (WinAPI — это тоже чужие функции);
- собирать программу из модулей, скомпилированных разными компиляторами.

Для реверсера соглашение — **бесплатный источник информации**: раз правила
обязательны для всех, любой вызов читается однозначно.

### 12.2. Доверять ли `RBX` и `RCX` после вызова

- **`RBX` — non-volatile.** Вызванная функция обязана вернуть его в исходном
  состоянии. Значению **можно доверять**.
- **`RCX` — volatile.** Функция имеет право испортить его как угодно.
  Доверять **нельзя**.

Отсюда практическое следствие для чтения кода: если компилятор держит
значение в `RBX`, `RSI`, `RDI` или `R12`–`R15`, значит оно должно
**пережить вызовы** — то есть это что-то долгоживущее: счётчик длинного
цикла, указатель на структуру, с которой работает вся функция.

А значение в `RAX`, `RCX`, `RDX` живёт от силы до ближайшего `call`.

### 12.3. `sub rsp, 56` в функции без локальных переменных

Минимум **32 байта** — обязательное теневое пространство под будущие вызовы
(глава 11). Раз функция его резервирует, значит она **сама кого-то вызывает**.

Остальные 24 байта уходят на:

- **выравнивание стека до 16 байт** — требование перед `call`;
- место под временные значения, которым не хватило регистров;
- возможно, под аргументы с пятого и дальше, если функция вызывает
  что-то многоаргументное.

Проверка арифметикой: `call` уже положил на стек 8 байт адреса возврата,
поэтому при входе `RSP` кратен 16 с остатком 8. Чтобы перед следующим
`call` он снова стал кратен 16, вычесть надо число, дающее остаток 8:
`40`, `56`, `72`. Все «странные» значения из реального кода именно такие —
теперь понятно почему.

### 12.4. Регистры плюс `[rsp+32]` и `[rsp+40]`

**Шесть аргументов.**

Разбор по правилу:

| Где | Какой аргумент |
|---|---|
| `RCX` | 1-й |
| `RDX` | 2-й |
| `R8` | 3-й |
| `R9` | 4-й |
| `[rsp+32]` | 5-й |
| `[rsp+40]` | 6-й |

Смещения начинаются с 32, потому что первые 32 байта стека занимает теневое
пространство под четыре регистровых аргумента. Пятый аргумент кладётся
сразу за ним.

### 12.5. `CreateFileA` против `CreateFileW`

- **`A`** — ANSI, однобайтовая кодировка. Устаревший вариант, оставлен
  для совместимости со старыми программами.
- **`W`** — Wide, UTF-16, по два байта на символ. Основной вариант:
  современная Windows внутри работает именно так.

В современной программе ожидаешь **`W`**. Версии с `A` обычно просто
переводят строку в UTF-16 и вызывают `W`-версию.

**Почему это важно при поиске имени файла в памяти:** строка для `W`-функции
лежит в UTF-16, то есть с нулевым байтом после каждой буквы:

```
43 00 3A 00 5C 00 ...     →  "C:\..."
```

Если искать её в hex-редакторе как обычный текст, **не найдёшь**. Нужно
переключить поиск на Unicode (глава 7, ответ 7.6).

### 12.6. Что такое дескриптор и зачем номер вместо адреса

**Дескриптор** (handle) — это номер записи в системной таблице объектов,
которую ведёт Windows для каждого процесса. Открыв файл, программа получает
не адрес структуры файла, а её номер.

Причины, по которым сделано именно так:

**Безопасность.** Программа не может испортить системные структуры, потому
что не имеет к ним прямого доступа. Максимум — передать неверный номер,
и система корректно ответит ошибкой.

**Изоляция.** Windows вольна перемещать и перестраивать свои структуры —
номер остаётся прежним.

**Контроль прав.** При каждом обращении система проверяет по таблице, что
именно этому процессу позволено делать с этим объектом.

Для анализа полезно: дескриптор — это ниточка, за которую тянется вся
операция. Нашёл, где его получили, — проследи, куда передают дальше, и
увидишь всю работу с объектом.

### 12.7. Почему WinAPI вызывается через квадратные скобки

Потому что **адрес системной функции заранее неизвестен**.

Своя функция лежит внутри того же файла, её адрес известен на этапе сборки —
компоновщик подставляет его прямо в инструкцию:

```asm
call 0x140001234        ; адрес известен
```

Функция Windows живёт в отдельной библиотеке, которая при каждом запуске
может оказаться по разному адресу (ASLR, глава 4). Поэтому в файле
резервируется ячейка в **таблице импортов**, а загрузчик Windows заполняет
её настоящим адресом при запуске (глава 8).

Программа обращается к ячейке:

```asm
call QWORD PTR [rip+0x6df8]     ; взять адрес из ячейки и прыгнуть
```

Отсюда правило чтения: **`call` со скобками — почти всегда вызов чужой
функции через таблицу импортов**.

### 12.8. Разбор вызова `MessageBoxW`

```asm
    mov   r9d, 64              ; 4-й аргумент
    xor   r8d, r8d             ; 3-й аргумент = 0
    lea   rdx, [сообщение]     ; 2-й аргумент
    mov   rcx, [rbp-16]        ; 1-й аргумент
    call  [QWORD PTR __imp_MessageBoxW[rip]]
```

**Четыре аргумента.** По сигнатуре `MessageBoxW(hWnd, lpText, lpCaption, uType)`:

| Регистр | Параметр | Значение |
|---|---|---|
| `RCX` | `hWnd` | дескриптор окна, взят из локальной переменной `[rbp-16]` |
| `RDX` | `lpText` | адрес текста сообщения |
| `R8` | `lpCaption` | **0** — заголовка нет, будет стандартный |
| `R9D` | `uType` | **64** = `0x40` = `MB_ICONINFORMATION`, значок «информация» |

**`xor r8d, r8d`** — это идиома обнуления из главы 10. Не шифрование:
регистр, сложенный «исключающим ИЛИ» сам с собой, всегда даёт ноль.
Компилятор пишет так, потому что короче, чем `mov r8d, 0`.

Итог: программа показывает информационное окно с текстом, без своего
заголовка, привязанное к окну, дескриптор которого хранится в локальной
переменной.

### 12.9. `VirtualProtect` и `GetProcAddress` в импортах

Две гипотезы, и обе неприятные.

**1. Программа меняет права памяти** (`VirtualProtect`). Нормальной программе
это почти никогда не нужно: код исполняется, данные пишутся, границы
установлены при загрузке. Смена прав нужна тому, кто собирается **писать
в область кода или исполнять данные**. Типично для:

- упаковщиков — распаковывают настоящий код в память и делают его
  исполняемым;
- самомодифицирующегося кода;
- внедрения кода в чужой процесс.

**2. Программа скрывает свои импорты** (`GetProcAddress`). Она получает
адреса функций во время работы, по именам, которые хранит как строки — часто
зашифрованные. В таблице импортов этих функций не видно (глава 7).

Вместе эти две функции — **классический набор упаковщика или вредоноса**.
Не доказательство: их используют и легальные протекторы, и системные
утилиты. Но повод не доверять статическому анализу и переходить
к динамическому.

## Глава 13. x64dbg

### 13.1. Почему первая остановка в `ntdll`

Потому что наш код начинает работать далеко не сразу. Прежде чем
программа выполнит хоть одну свою инструкцию, **загрузчик Windows**
(он живёт в `ntdll.dll`) размещает файл в памяти, загружает библиотеки
и заполняет таблицу импортов (глава 8). x64dbg останавливает процесс
на самом раннем этапе — внутри загрузчика. Это **системная точка
останова** (`System breakpoint reached!`).

Дальше при нажатии F9:

1. **`TLS Callback 1`, `TLS Callback 2`** — служебные функции, которые gcc
   вставляет в программу. Windows вызывает их раньше точки входа.
2. **`entry breakpoint`** — точка входа, адрес из заголовка PE. Но это
   **стартовый код** библиотеки C, а не `main` (глава 8).
3. И только потом, если не поставить свою точку останова, программа
   добежит до `main` и выполнится до конца.

Зачем x64dbg останавливается так рано: чтобы ты мог вмешаться в работу
программы до того, как она успеет что-то сделать. Для учебной программы
это лишнее, а для программы, которая сопротивляется анализу (глава 23),
это бывает очень важно.

### 13.2. Что происходит при F2

x64dbg **записывает в память процесса байт `CC`** вместо первого байта
инструкции. `CC` — это инструкция `int3`: когда процессор до неё дойдёт,
возникнет исключение, Windows заморозит программу и сообщит отладчику.

Программа может это заметить, потому что **её код — это её же память**.
Ничто не мешает программе прочитать байты своих функций и проверить,
нет ли среди них чужого `CC`. Или посчитать контрольную сумму своего
кода: подменённый байт её изменит. Это классические приёмы анти-отладки,
разберём их в главе 23.

Аппаратная точка останова лучше, когда:

- нужно, чтобы код остался **нетронутым** (программа проверяет свои байты);
- нужно поймать **обращение к данным** — «кто записал в эту переменную?».
  Программная точка так не умеет: она ловит только выполнение.

Ограничение аппаратных точек — их всего **четыре** (регистры `DR0`–`DR3`).

### 13.3. F7 и F8 на `call <JMP.&getchar>`

**F7** (шаг с заходом) — зайдёт внутрь. Первым делом ты окажешься на
переходнике, на одной инструкции `jmp qword ptr ds:[<&getchar>]`. Ещё одно
нажатие F7 — и ты внутри настоящей `getchar` в библиотеке `msvcrt.dll`.
Смотреть там нечего, это чужой системный код. Выбраться: Ctrl+F9, потом F8.

**F8** (шаг с обходом) — выполнит `getchar` целиком и остановится на
следующей строке. Но `getchar` **ждёт, пока пользователь нажмёт Enter**.
Пока ты не нажмёшь Enter в окне консоли программы, функция не вернётся.
Отладчик в это время показывает `Running` и выглядит зависшим — хотя на
самом деле программа просто ждёт тебя. Окно консоли обычно прячется за
x64dbg: найди его на панели задач.

Общее правило: в функции Windows и библиотек заходить незачем, через
них шагают с помощью F8.

### 13.4. Числа из листинга x64dbg

x64dbg пишет всё в hex без приставки `0x`:

| Запись | Hex | Десятичное |
|---|---|---|
| `sub rsp,28` | `0x28` | 2 × 16 + 8 = **40** |
| `mov ecx,10` | `0x10` | **16** |
| `add eax,FF` | `0xFF` | 15 × 16 + 15 = **255** |

40 байт у функции без локальных переменных — это знакомая картина из
главы 12: **32 байта теневого пространства** для вызываемых функций
плюс **8 байт на выравнивание**. Выравнивание нужно, потому что `call`
положил на стек 8-байтовый адрес возврата, и без добавки `RSP` перестал
бы быть кратным 16.

Главный урок упражнения: увидел в x64dbg `10` — это **шестнадцать**.
Эта ловушка ловит всех новичков, и не по одному разу.

### 13.5. `RDX = 10` перед вызовом

Сначала на бумаге. Ты ввёл `10`, а x64dbg считает ввод шестнадцатеричным.
Значит, `RDX = 0x10` = **16**. `RDX` — второй аргумент, то есть `y`.

```
x * x + y = 7 * 7 + 16 = 49 + 16 = 65
```

Программа напечатает **`Result: 65`**.

Если ты ожидал `59` (49 + 10) — ты попался в ловушку из раздела 13.7.
Чтобы получить именно десять, нужно было ввести `A` или `.10` (с точкой,
это десятичная запись в x64dbg).

Заметь, что мы поменяли аргумент **до** входа в функцию, а функция об этом
не узнала: она честно взяла то, что лежало в `RDX`. Функция не может
отличить «настоящий» аргумент от подложенного отладчиком.

### 13.6. База загрузки по адресу `main`

Адрес в памяти = база + RVA (глава 8). Отсюда:

```
база = 00007FF7A1B514FB − 14FB = 00007FF7A1B50000
```

Проверка: база кончается на четыре нуля, то есть кратна `0x10000`. Так и
должно быть: ASLR всегда выбирает базу, кратную `0x10000`.

Секция `.rdata`:

```
00007FF7A1B50000 + 9000 = 00007FF7A1B59000
```

Метод пригодится постоянно. В PE-bear или Ghidra адреса одни, в
x64dbg — другие, но разница между ними — всегда одно и то же число,
сдвиг базы. Нашёл интересное место в одном инструменте — пересчитай
адрес и найди его в другом.

### 13.7. `Result: 14` через память

Нужно, чтобы функция получила `x = 3`: 3 × 3 + 5 = 14. Значит, менять
надо переменную `a`, которая лежит в `[rbp-4]`, — и менять **после** того,
как программа записала туда 7, но **до** того, как прочитала.

Смотрим на код `main`:

```
mov dword ptr ss:[rbp-4],7      ← запись 7
mov eax,dword ptr ss:[rbp-4]    ← чтение: вот перед этим и нужно успеть
mov edx,5
mov ecx,eax
call square_plus
```

Порядок действий:

1. Поставь точку останова (F2) на `mov eax,dword ptr ss:[rbp-4]`.
   Точка останова срабатывает **до** выполнения инструкции, так что
   запись семёрки уже прошла, а чтение ещё нет.
2. F9 — программа остановится на этой строке.
3. Правой кнопкой по строке → **Follow in Dump** → **Address: RBP-4**.
   В дампе увидишь `07 00 00 00`.
4. Выдели байт `07`, нажми **Ctrl+E**, введи `03`, **OK**.
5. F9. Программа напечатает **`Result: 14`**.

Если бы ты поменял байт раньше — до записи семёрки, — программа сама
перезаписала бы его. Если позже — после `mov eax,...`, — значение уже
ушло бы в регистр, и изменение памяти ничего бы не дало. **Время — такой
же важный параметр вмешательства, как место.** Это главная мысль
упражнения, и она будет встречаться в каждой задаче части VI.

## Глава 14. Ghidra

### 14.1. Псевдокод против исходника

Исходник — то, что написал автор. Псевдокод — **догадка** декомпилятора
о том, какой код на C мог дать такие инструкции. Он похож на исходник,
но это реконструкция.

Декомпилятору неоткуда взять:

1. **Имена локальных переменных и параметров.** В файле их нет (без
   отладочной информации), поэтому появляются `uVar1`, `param_1`, `local_c`.
2. **Комментарии.** Компилятор выбрасывает их первыми, ещё до генерации
   кода.
3. **Точные типы.** В машинном коде есть только размеры (1, 2, 4, 8 байт)
   и способ работы с числом. Был ли это `int` или `unsigned`, структура или
   массив — декомпилятор угадывает. Отсюда лишние преобразования типов.

Можно добавить и четвёртое: **исходную структуру кода**. Компилятор мог
выкинуть переменную, встроить функцию или посчитать выражение заранее.

### 14.2. Куда делась `a`

Декомпилятор увидел, что в ячейку `[rbp-4]` записали 7 и тут же прочитали
обратно, и больше она нигде не нужна. Поэтому он **подставил значение**
прямо в вызов: `square_plus(7,5)`. Для читателя так проще.

По псевдокоду понять, была ли переменная, **нельзя**. Автор мог написать
`square_plus(7, 5)` сразу — псевдокод был бы тем же. Но это можно увидеть
в **листинге**: там остались инструкции
`MOV dword ptr [RBP + local_c],0x7` и `MOV EAX,dword ptr [RBP + local_c]`.
При `-O0` компилятор честно заводит ячейку под каждую переменную. Вот
пример, когда ассемблер говорит больше псевдокода.

### 14.3. Два пути к `main` без имён

**Путь 1 — от строки.** Search → For Strings → фильтр `Result` → двойной
щелчок → XREF из функции `FUN_1400014fb` → это `main`.

**Путь 2 — от импорта.** `getchar` — функция из `msvcrt.dll`, её имя
сохранилось даже после `strip` (без имён импортов загрузчик не смог бы
найти функции). В **Symbol Tree → Imports** найди `getchar`, посмотри
её XREF. Вызов идёт из `FUN_1400014fb` — снова `main`.

Есть и третий путь, для любознательных: от `entry`. Точка входа вызывает
стартовый код, а он в конце вызывает `main`. У нашей программы это
вызов по адресу `140001302` внутри стартовой функции `FUN_140001190`.
Путь длиннее, но работает, даже если в программе нет ни строк, ни
понятных импортов.

Общий принцип: **ищи то, что имена сохраняет**. Строки и импорты
переживают `strip`, и от них по XREF добираешься до безымянного кода.

### 14.4. Расшифровка имён Ghidra

| Имя | Что значит |
|---|---|
| `FUN_140001620` | функция по адресу `140001620`, настоящего имени нет. Это служебная `__main` |
| `DAT_140008000` | данные (data) по адресу `140008000`, тип неизвестен |
| `s_Result:_%d_140009000` | строка (`s_`) с текстом `Result: %d` по адресу `140009000` |
| `param_2` | второй параметр функции |
| `local_10` | ячейка стека со смещением `0x10` от значения `RSP` при входе в функцию |
| `uVar1` | переменная в регистре, тип неясен или беззнаковый (`u`), номер 1 |
| `in_R9` | регистр `R9` используется, но в функции ему ничего не присваивали. Признак неверной сигнатуры |

`local_10` в нашей `main` — это переменная `b`: `[rbp-8]` = вход − 8 − 8.
Так же, как `local_c` — это `a`.

### 14.5. Адрес для x64dbg

```
RVA = 1400014d4 − 140000000 = 14d4
адрес в x64dbg = 00007FF6C9A20000 + 14D4 = 00007FF6C9A214D4
```

Быстрая проверка: младшие четыре цифры совпадают (`14D4`), старшие —
от базы x64dbg. Перейти: в x64dbg `Ctrl+G`, ввести `7FF6C9A214D4`, Enter.
Потом F2 — точка останова.

### 14.6. Почему `square_plus` не выкинули

Компилятор обрабатывает **один файл `.c` за раз**. `square_plus` объявлена
без `static`, то есть видна снаружи. Компилятор не знает, не вызовет ли
её какой-нибудь другой `.c` той же программы, и обязан оставить функцию.
В нашем случае её никто не вызывает, но выяснить это мог бы только
компоновщик, а gcc по умолчанию такие функции не выбрасывает.

Ошибка реверсера — **потратить время на мёртвый код**. Функция выглядит
осмысленной: считает что-то с параметрами, её хочется понять. Но она
ни на что не влияет. В больших программах таких функций бывают сотни
(остатки старых версий, неиспользуемые части библиотек). Проверка XREF
занимает секунду: нет вызовов `(c)` — откладываем. Ссылку из `.pdata`
при этом не считаем: она есть почти у каждой функции.

### 14.7. Сигнатура `printf`

Правильная сигнатура: `int printf(char * format, ...)`. Многоточие
говорит: «после строки формата — переменное число аргументов».

Если дать сигнатуру **без многоточия**, например `int printf(char * format)`,
Ghidra поверит тебе и решит, что аргумент один. Вот что она покажет
(проверено на Ghidra 12.1.4):

```c
  square_plus(7,5);
  printf("Result: %d\n");
```

Результат `square_plus` **пропал**. Декомпилятор решил, что значение
в `EDX` никому не передаётся, и значит, возвращаемое значение
`square_plus` не используется. Псевдокод стал выглядеть чище — и при
этом **врёт**: будто программа печатает строку без числа.

Урок: неверная сигнатура опаснее, чем её отсутствие. Когда не уверен —
лучше оставить догадку Ghidra и проверить по листингу, какие регистры
заполняются перед вызовом (метод главы 12).

## Глава 15. Наблюдение за поведением

### 15.1. Почему в виртуальной машине

Procmon только **наблюдает**, он ничего не запускает сам. Но чтобы было
за чем наблюдать, программу приходится **запустить**. А запущенная
программа делает всё, на что способна: если она вредоносная, она
заразит систему, пока ты смотришь на красивые строки в Procmon.

Виртуальная машина — изолированная Windows внутри твоей Windows. Всё, что
программа испортит, останется внутри. А перед запуском можно сделать
**снимок** состояния машины и после анализа откатиться к нему за секунду.

Своя учебная программа — другое дело: ты знаешь её исходник и знаешь,
что она не делает ничего плохого.

### 15.2. Разбор журнала незнакомой программы

Читаем по строкам:

1. Программа ищет `settings.json` в своей папке в `AppData\Roaming` —
   **не находит**.
2. Ищет свой раздел в реестре — **тоже нет**.
3. Создаёт `settings.json` (`CreateFile` с `SUCCESS`) и записывает в него.

Вывод: это, скорее всего, **первый запуск**. Программа хранит настройки
в `%APPDATA%\Tool\settings.json`. Не найдя их, она создала файл
с настройками по умолчанию. Реестр она проверяет, но, похоже, не
использует (или использует только для чтения старых настроек).

При втором запуске первая строка будет уже `SUCCESS`: файл есть, и
программа прочитает его (`ReadFile`), а не будет создавать заново.

Практический вывод: теперь ты знаешь, где лежат настройки, и можешь их
почитать или поменять, чтобы проверить, как программа на это реагирует.
Всё это — не прочитав ни одной инструкции.

### 15.3. `BUFFER OVERFLOW` в Procmon

Никто никого не атакует. Это **код ответа** Windows, а не событие
безопасности. Имя совпадает с атакой из главы 11 случайно: там
«переполнение буфера» — запись за его границу, а здесь — сообщение
«твой буфер слишком мал для ответа».

Типичная переписка программы с Windows выглядит так:

1. Программа спрашивает значение реестра и даёт буфер наугад, например
   на 4 байта.
2. Windows отвечает `BUFFER OVERFLOW` («не влезает») и сообщает, сколько
   байт нужно на самом деле.
3. Программа выделяет буфер нужного размера и спрашивает снова.

Поэтому в следующей строке ты, скорее всего, увидишь ту же операцию
с тем же путём и результатом `SUCCESS`.

### 15.4. `behave.exe + 0x1632` в Ghidra

`0x1632` — это **RVA**. Адрес в Ghidra:
`140000000 + 1632 = 140001632`. Перейди туда клавишей **G**.

По этому адресу стоит **не вызов**, а следующая за ним инструкция:

```
140001629  MOV   RAX,qword ptr [__imp_RegSetValueExW]
140001630  CALL  RAX
140001632  MOV   RAX,qword ptr [RBP + local_18]     ← сюда указывает стек
```

Почему так: стек вызовов состоит из **адресов возврата** (глава 11).
Когда `call` выполняется, он кладёт на стек адрес следующей инструкции —
именно его и показывает Procmon. Сам вызов — на одну инструкцию выше,
`CALL RAX` по адресу `140001630`.

Чтобы убедиться, что это `RegSetValueExW`, смотри, откуда взялся `RAX`:
строкой выше в него загрузили адрес из ячейки `__imp_RegSetValueExW`
таблицы импортов. Для верности можно посмотреть и аргументы по
соглашению о вызовах: в `RDX` положили адрес строки `u_Runs_...` (имя
значения `Runs`), в `R9D` — `4` (тип `REG_DWORD`). Всё сходится
с исходником.

### 15.5. Запись вызовов `RegSetValueExW`

Сигнатура из документации Microsoft:

```c
LSTATUS RegSetValueExW(HKEY hKey, LPCWSTR lpValueName, DWORD Reserved,
                       DWORD dwType, const BYTE *lpData, DWORD cbData);
```

Имя значения — **второй** параметр, значит, по главе 12 оно в **`RDX`**.
Суффикс `W` — строка в UTF-16. Команды для x64dbg (на системной точке
останова, когда `advapi32.dll` уже загружена):

```
bp advapi32:RegSetValueExW
bpcond advapi32:RegSetValueExW, 0
bplog advapi32:RegSetValueExW, "RegSetValueExW: {utf16@rdx}"
```

После F9 в журнале будет `RegSetValueExW: Runs`.

**Для любознательных — пятый аргумент.** Первые четыре аргумента
в регистрах, пятый и дальше — на стеке (глава 12). В момент входа
в функцию:

- `[rsp]` — адрес возврата (его только что положил `call`);
- `[rsp+8]` … `[rsp+27]` — 32 байта теневого пространства;
- `[rsp+28]` — **пятый аргумент**, `lpData`.

Помни, что x64dbg считает числа шестнадцатеричными: `28` — это `0x28` = 40
байт = 8 (адрес возврата) + 32 (теневое пространство).

Напечатать 4 байта по этому указателю:

```
bplog advapi32:RegSetValueExW, "{utf16@rdx} = {mem;4@[rsp+28]}"
```

`[rsp+28]` — прочитать указатель со стека, `mem;4@...` — вывести 4 байта
по этому адресу в hex. При втором запуске будет что-то вроде
`Runs = 02000000`. Число 2, записанное **младшим байтом вперёд** —
little-endian из главы 3.

### 15.6. Странные числа в `RegCreateKeyExW`

**`0xffffffff80000001`** — это `HKEY_CURRENT_USER`. В заголовках Windows
предопределённые разделы реестра — это особые значения-дескрипторы:
`HKEY_CLASSES_ROOT` = `0x80000000`, `HKEY_CURRENT_USER` = `0x80000001`,
`HKEY_LOCAL_MACHINE` = `0x80000002` и так далее. Они объявлены как
**знаковые** 32-битные числа, поэтому при расширении до 64 бит старший
бит размножился на весь старший регистр: `0x80000001` превратилось
в `0xffffffff80000001`. Это знаковое расширение — то, что делает
`movsx` из главы 10 (а почему старший бит означает знак — глава 3).

**`0x2001f`** — желаемые права доступа, `KEY_READ | KEY_WRITE` из
исходника. `KEY_READ` = `0x20019`, `KEY_WRITE` = `0x20006`, их побитовое
ИЛИ (глава 10) даёт `0x2001f`.

Урок: декомпилятор показывает **числа**, а не имена констант. Имена
возвращаешь ты сам — по документации функции. Со временем самые частые
(`0x80000001`, `GENERIC_READ = 0x80000000`) начнёшь узнавать в лицо.

### 15.7. Выбор инструмента

- **а)** **Process Monitor** с фильтром `Result is NAME NOT FOUND` и,
  например, `Path ends with .dll`. Попытки загрузить отсутствующую
  библиотеку будут видны сразу.
- **б)** **Process Explorer**, нижняя панель в режиме **Handles** (`Ctrl+H`),
  строки с типом `File`.
- **в)** **x64dbg**: точка останова на `kernel32:CreateFileW` с условием `0`
  и журналом `{utf16@rcx}`.
- **г)** **Process Monitor** → найти событие `RegSetValue` с нужным путём →
  вкладка **Stack** → RVA → **Ghidra**. Цепочка из раздела 15.6.

## Глава 16. Разбор задачи 1: пароль открытым текстом

### 16.1. Смещение `0x763F` → RVA

Метод из главы 8: найти секцию, в которую попадает смещение, и сдвинуть.

1. Секция: `.rdata` начинается в файле с `0x7600`, следующая за ней
   в файле лежит дальше. `0x763F` больше `0x7600` — значит, `.rdata`.
2. Смещение внутри секции: `0x763F − 0x7600 = 0x3F`.
3. RVA: `0x9000 + 0x3F = 0x903F`.
4. Адрес в Ghidra: `0x140000000 + 0x903F = 0x14000903F`.

В листинге раздела 16.3 это инструкция
`14000157c lea rax, [rip+0x7abc] ; 14000903f → "[-] Neverno."` —
она берёт адрес строки отказа перед `puts`.

### 16.2. Восемь байтов в `.data`

Разворачиваем little-endian (глава 3):

```
в памяти:   30 7C 00 40 01 00 00 00
число:      0x0000000140007C30
```

RVA: `0x140007C30 − 0x140000000 = 0x7C30`. Смотрим таблицу секций:
`.text` начинается с RVA `0x1000`, `.data` — с `0x8000`. `0x7C30` лежит
между ними, значит, в `.text`, то есть **в коде**.

Вывод: это указатель не на строку, а на **функцию** — адрес кода.
Такие указатели хранят, например, чтобы вызвать функцию позже
(обработчики, таблицы функций). Узнать, какая именно, можно в Ghidra:
**G** → `140007c30`.

Главный навык здесь — не число, а привычка: увидел в данных 8 байтов
вида `xx xx xx 40 01 00 00 00` — это почти наверняка адрес внутри
программы (база `0x140000000`), его стоит проверить.

### 16.3. Массив вместо указателя

**Предсказание:**

- адрес пароля в `RDX` положит **`lea`** — как адреса всех остальных
  строк: `lea rdx, [rip+…]`;
- XREF от строки поведёт **прямо в `main`**, без промежуточной ячейки;
- 8 байтов указателя в начале `.data` **исчезнут**.

**Почему.** `const char *SECRET = "…"` — это **две** вещи: строка
в `.rdata` и отдельная переменная-указатель в `.data`, где лежит адрес
строки. Код должен сначала **прочитать** переменную (`mov` со скобками).
`const char SECRET[] = "…"` — это **одна** вещь: сам массив байтов,
и имя `SECRET` означает его адрес. Адрес известен заранее, его остаётся
только **вычислить** (`lea`).

В моей сборке так и вышло:

```
lea   rdx, [rip+0x7aa6]    ; 140009000 <SECRET>
call  strcmp
```

а `.data` начинается уже с других байтов. Пароль в `.rdata` остался
на месте — первой строкой.

### 16.4. Пароль с лишним `!`

В дампе по `RCX` будет `rev_is_fun_2024!` и ноль, по `RDX` — эталон
`rev_is_fun_2024` и ноль.

`strcmp` вернёт **не ноль**. Она сравнивает строки байт за байтом:
первые 15 совпадают, а 16-й у ввода — `!` (`0x21`), у эталона — конец
строки, нулевой байт. Разные байты — строки разные, и программа скажет
«Neverno».

Урок: `strcmp` требует **точного** совпадения, до завершающего нуля.
Лишний символ, пробел в конце, другая буква в регистре — и всё.
Поэтому программа и отрезает `\n`, который `fgets` оставляет в конце
ввода: иначе даже правильный пароль не прошёл бы.

### 16.5. Число `0x657265685f746f6e`

Раскладываем по байтам и разворачиваем:

```
число:      65 72 65 68 5f 74 6f 6e
в памяти:   6e 6f 74 5f 68 65 72 65
ASCII:      n  o  t  _  h  e  r  e
```

Спрятано `not_here` — «здесь нет». Опоры из главы 3: `a` = `0x61`,
поэтому `0x6e` = `n` (a + 13), `0x6f` = `o`, `0x74` = `t`;
`0x5f` — подчёркивание, `0x68` = `h`, `0x65` = `e`, `0x72` = `r`.

Навык на будущее: длинное число из `mov`, у которого все байты
в диапазоне `0x20`–`0x7e`, — почти наверняка текст. Проверяй всегда.

### 16.6. `strncmp` на 3 символа

Программа примет **любой** ввод, который начинается на `rev`: `rev`,
`revolver`, `rev_is_boring` — все пройдут. Сравниваются только первые
три символа, остальное не проверяется.

Как заметить в листинге: у `strncmp` **три** аргумента, а у `strcmp` —
два. Перед вызовом появится третья загрузка — в `R8` (глава 12):

```
mov   r8d, 3          ; сколько символов сравнивать
mov   rdx, …          ; эталон
mov   rcx, …          ; ввод
call  strncmp
```

Маленькое число в `R8` рядом с вызовом сравнения — сигнал внимательно
посмотреть, **сколько** на самом деле проверяется. Такие ошибки
встречаются и в настоящих программах: проверка есть, но проверяет
не всё.

проверить самому перед отправкой:

  (флаг `-s`), `main` придётся искать через строки.

## Глава 17. Разбор задачи 2: пароль под XOR

### 17.1. XOR по битам

**а)** `0x3D XOR 0x5A`:

```
  0x3D   0011 1101
^ 0x5A   0101 1010
  ----   ---------
  0x67   0110 0111     → 'g'
```

`g` — последняя буква пароля `xor_hides_nothing`, и `0x3D` — последний
из 17 зашифрованных байтов. Сходится.

**б)**

```
0x41 ('A')  0100 0001  XOR 0010 0000  =  0110 0001  0x61 ('a')
0x61 ('a')  0110 0001  XOR 0010 0000  =  0100 0001  0x41 ('A')
```

XOR с `0x20` **меняет регистр** латинской буквы: большая становится
маленькой и наоборот. Почему: в таблице ASCII коды больших и маленьких
букв отличаются ровно на `0x20` (глава 3), то есть одним битом — пятым.
XOR с `0x20` этот бит переворачивает. Встретишь в коде `xor al, 0x20`
рядом с буквами — почти наверняка смена регистра, а не шифрование.

### 17.2. Ключ по известной букве

Второе свойство XOR: `текст XOR шифр = ключ`.

```
0x68 ('h') XOR 0x2C = 0x44   → ключ
```

Вторая буква: `0x30 XOR 0x44 = 0x74` → `t`.

Строка начинается на `ht…` — очень похоже на `http`. Так часто и
бывает: адреса в зашифрованных строках — самый частый «известный
текст».

### 17.3. Шифровальщик на C

Раз для XOR шифрование и расшифровка — одна операция, достаточно
поменять данные. Например:

```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    const char *text = "ivan";           /* своё имя латиницей */
    size_t i;

    for (i = 0; i < strlen(text); i++)
        printf("%02X ", (unsigned char)(text[i] ^ 0x5A));
    printf("\n");
    return 0;
}
```

Для `ivan` получится `33 2C 3B 34`. Вставь эти байты в массив `enc`
программы `decode.c` вместо пароля задачи — она напечатает `ivan`.
Круг замкнулся: ты сам зашифровал и сам расшифровал, одной и той же
операцией с одним ключом.

`%02X` в `printf` значит: число в hex, большими буквами, минимум две
цифры с ведущим нулём (`05`, а не `5`). Приведение `(unsigned char)`
нужно, чтобы байты больше `0x7F` не печатались как отрицательные
(знаковые числа, глава 3).

### 17.4. Пароль сразу после расшифровки

После `call` функции расшифровки в `main` стоит
`lea rdx, [rbp-0x60]` — это адрес буфера, куда функция только что
записала расшифрованный пароль. Смотреть надо **`RBP − 0x60`**.

Два способа попасть туда в дампе x64dbg:

1. Нажать **F7** один раз — выполнится `lea`, и в `RDX` окажется нужный
   адрес. Дальше **Follow in Dump** по `RDX`.
2. В окне дампа нажать **Ctrl+G** и ввести выражение `rbp-60` — x64dbg
   умеет считать выражения с регистрами (глава 13). Помни: числа
   в x64dbg — hex, так что `60` здесь и есть `0x60`.

В дампе будет `xor_hides_nothing` и ноль. Урок: пароль доступен
**сразу**, как только его расшифровали, — не нужно ждать сравнения.
Точка сразу после функции расшифровки — стандартный приём, когда
функцию сравнения найти трудно.

### 17.5. Почему в тяжёлой версии нет мусора

Компилятор с `-O2` расположил данные в `.rdata` в другом порядке:
зашифрованные 17 байтов оказались не в начале секции, перед
приглашением, а **после** всех сообщений (по `140009040`). Теперь
за ними идут нулевые байты, и прилипнуть не к чему.

Вывод: подсказка «мусор перед строкой» — случайность раскладки,
на неё нельзя рассчитывать. Надёжный путь — код: цикл расшифровки
указывает на данные (`lea r8, [rip+…]`) при любой раскладке.

### 17.6. XOR с номером байта

Здесь `xor edx, eax`, а в `rax` лежит счётчик `i`. Значит, **ключ меняется
от байта к байту**: первый байт XOR-ится с `0`, второй — с `1`, третий —
с `2` и так далее. Точнее, с младшим байтом `i`: в `DL` попадают только
младшие 8 битов результата.

`decode.c` меняется в одном месте:

```c
putchar(enc[i] ^ i);        /* ключ — номер байта */
```

Такой «ключ» уже не найти одним известным символом: у каждого байта свой.
Но он по-прежнему **целиком виден в коде**, так что для реверсера
разница невелика: прочитай цикл — и повтори его.

### 17.7. Отчёт по `02_xor.hard.exe`

Эталона нет — пришли свой отчёт. Проверь перед отправкой:

- **Опознание:** имён нет (`-s`), `decrypt` встроена в `main` —
  отдельной функции не будет.
- **Находка:** `xor_hides_nothing`.
- **Статика:** RVA цикла; таблица шифра — RVA `0x9040` (в моей сборке),
  длина `0x11` = 17 — прямо в `cmp`, ключ `0x5A` — прямо в `xor`.
  Результат расшифровки — программа `decode.c`.
- **Динамика:** точка на `msvcrt!strcmp`, в `RDX` — адрес на стеке,
  там открытый пароль.
- **Контроль:** запуск с паролем печатает `[+] Verno`.
- **Наблюдение:** в тяжёлой версии зашифрованные байты не прилипают
  к строкам — поиск строк не даёт даже намёка.

## Глава 18. Разбор задачи 3: серийный номер

### 18.1. Почему отсеиваются `':'` и пробел

**`':'` = `0x3A`.** `0x3A − 0x30 = 0x0A` = 10. `cmp 10, 9` → 10 больше 9,
`jbe` не прыгает — отказ. Двоеточие стоит в таблице ASCII сразу **после**
цифр, поэтому даёт 10.

**Пробел = `0x20`.** `0x20 − 0x30` = −16. В 32 битах это
`0xFFFFFFF0` (дополнительный код, глава 3). `jbe` сравнивает
**беззнаково**, а беззнаково `0xFFFFFFF0` — это 4 294 967 280, намного
больше 9. Отказ.

Вывод: одно беззнаковое сравнение «≤ 9» ловит и символы **выше** цифр
(как `:`), и символы **ниже** (как пробел). Если бы компилятор
сравнивал знаково (`jle`), пробел дал бы −16 ≤ 9 и прошёл бы как цифра —
понадобилась бы вторая проверка «≥ 0». Беззнаковый приём экономит её.

### 18.2. Цикл по шагам

`RE-0042000-?`: цифры `0 0 4 2 0 0 0`.

```
n = 0
0: 0 × 10 + 0 = 0
0: 0 × 10 + 0 = 0
4: 0 × 10 + 4 = 4
2: 4 × 10 + 2 = 42
0: 42 × 10 + 0 = 420
0: 420 × 10 + 0 = 4200
0: 4200 × 10 + 0 = 42000
```

`n = 42000`. Нули впереди ничего не добавляют — как и в обычной записи
чисел.

`RE-1000000-?`: `1`, потом шесть раз «× 10 + 0» → `n = 1 000 000`.

### 18.3. Сколько всего верных номеров

Верный номер — это `q × 1337` в семи цифрах, то есть
`q × 1337 ≤ 9 999 999`:

```
q ≤ 9 999 999 / 1337 = 7479,4…   →   q от 0 до 7479
```

Всего **7480** номеров (не забудь `q = 0`!). Последний:

```
n = 7479 × 1337 = 9 999 423
буква = 'A' + 7479 % 26 = 'A' + 17 = 'R'      (7479 = 26 × 287 + 17)
номер: RE-9999423-R
```

Изменённая `valid.c`:

```c
#include <stdio.h>

int main(void)
{
    int q, count = 0, last = 0;

    for (q = 0; q * 1337 <= 9999999; q++) {
        count++;
        last = q;
    }
    printf("vsego: %d\n", count);
    printf("posledniy: RE-%07d-%c\n", last * 1337, 'A' + last % 26);
    return 0;
}
```

Выведет `vsego: 7480` и `posledniy: RE-9999423-R`.

Частая ошибка — ответить 7479: забыть, что счёт начинается с нуля.
Та же ловушка, что с байтом из главы 1: значения от 0 до 255 — это
256 штук.

### 18.4. `RE-1234567-X`

Формат в порядке: 12 символов, `RE-`, дефис на позиции 10, семь цифр.
Цикл соберёт `n = 1 234 567`.

**Условие 1** — делится ли на 1337? `1 234 567 / 1337 = 923,4…`, не
целое. Остаток: `1 234 567 − 923 × 1337 = 1 234 567 − 1 234 051 = 516`.
Не ноль — отказ.

До буквы дело не дойдёт: функция вернёт 0 на первом же условии.
Подобрать букву к такому номеру невозможно — сначала надо, чтобы число
делилось на 1337.

### 18.5. Деление на что?

```
2^35 = 34 359 738 368
0xCCCCCCCD = 3 435 973 837
34 359 738 368 / 3 435 973 837 ≈ 9,9999999994
```

Делитель — **10**. Магия чуть округлена вверх, поэтому получилось
не ровно 10, а «почти 10» — так и должно быть.

Проверка: функция

```c
unsigned d10(unsigned x) { return x / 10; }
```

собранная с `-O2` моим gcc, даёт ровно такой код:

```
mov   edx, 0xcccccccd
mov   eax, ecx
imul  rax, rdx
shr   rax, 0x23
```

Число `0xCCCCCCCD` стоит запомнить: это **деление на 10**, одно из самых
частых в программах (перевод чисел в текст, работа с десятичными
цифрами). Увидишь — узнаешь сразу. Для знакового деления на 10
компилятор использует другое число, `0x66666667`, — его мы упоминали
в главе 10.

### 18.6. Буква для `RE-2674000-?`

```
n = 2 674 000
n % 1337 = 0              (2 674 000 = 2000 × 1337) — условие 1 выполнено
q = n / 1337 = 2000
q % 26 = 2000 − 26 × 76 = 2000 − 1976 = 24
буква = 'A' + 24 = 'Y'    (A=0, B=1, …, Y=24, Z=25)
```

Номер `RE-2674000-Y`. Я проверил его на задаче — принимается.

### 18.7. Отчёт по `03_serial.hard.exe`

Эталона нет — пришли свой. Проверь перед отправкой:

- **Опознание:** имён нет, проверка встроена в `main`; строк-подсказок
  нет, `strcmp` в импортах нет — только код.
- **Находка — правило словами:** `RE-NNNNNNN-C`, `N` кратно 1337,
  `C = 'A' + (N / 1337) % 26`. Три номера, например `RE-0001337-B`,
  `RE-0002674-C`, `RE-6685000-I`.
- **Доказательства:** RVA проверки длины (`cmp rax, 0xc`), постоянных
  символов, цикла, двух `div` (1337 и 26) и сравнения буквы.
- **Проверка:** номера приняты тяжёлой версией; буква сверена
  в отладчике на `cmp` после `add edx, 0x41`.
- **Наблюдение:** в обычной сборке деление записано умножением
  на магические числа, в тяжёлой — инструкцией `div`. Логика та же.
- **Открытый вопрос (честный):** номер `RE-0000000-A` принимается —
  намеренно ли это автор? По коду — да, правило его пропускает.

## Глава 26. Процессы, потоки, память глазами системы

### 26.1. Два Блокнота

**Процессов — два.** Файл `notepad.exe` один, но каждый запуск создаёт
свой процесс со своим PID.

**Потоков в каждом — минимум один**, главный. На деле у Блокнота их
больше: окну нужны служебные потоки, да и пул потоков Windows (раздел 26.5)
добавит своих. Но меньше одного не бывает: процесс завершается, когда
завершается его **последний** поток (раздел 26.13). Процесс без потоков —
это уже умерший процесс.

**Один и тот же адрес — не проблема**, потому что адреса виртуальные
(глава 4, раздел 26.6). У каждого процесса своё адресное пространство
и своя таблица перевода адресов. Адрес `00007FF6A1B20000` в первом
Блокноте и такой же адрес во втором — это два разных «номера квартиры»
в двух разных домах.

Любопытная деталь из раздела 26.8: если по этому адресу лежит код
`notepad.exe` (память типа `IMAGE`), Windows может показать обоим
процессам **одни и те же** физические страницы — код ведь никто не
меняет. А как только один процесс запишет в такую страницу, он получит
собственную копию (копирование при записи, глава 13). Так что
помешать друг другу они не могут и в этом случае.

### 26.2. Своё и общее

Правило из раздела 26.2: у потока своё — **регистры и стек**, всё
остальное — общее.

- **а) `shared` — общая.** Глобальная переменная в `.data`, одна на
  процесс. Все потоки печатали один и тот же её адрес.
- **б) `local` в `worker` — своя.** Лежит на стеке, а стек у каждого
  потока свой. В исходнике переменная одна, в памяти — по одной на поток.
- **в) `ids` — общий.** Это глобальный массив. То, что каждый поток
  получил указатель на **свой элемент**, ничего не меняет: оба элемента
  лежат в общей памяти, и поток 1 при желании мог бы прочитать `ids[1]`.
- **г) `RIP` — свой.** Это регистр, а регистры у каждого потока свои.
  Ты сам видел в x64dbg: переключаешь поток — меняется `RIP`.
- **д) 100 байт из `malloc` — общие.** Куча принадлежит процессу. Если
  адрес буфера передан обоим потокам, они работают с **одними и теми же**
  байтами. Отсюда главная беда многопоточных программ: два потока пишут
  в одно место одновременно, и результат зависит от того, кто успел
  первым (помнишь — порядок не гарантирован).
- **е) дескриптор `t1` — общий.** Тонкое место. Сама переменная `t1` —
  локальная в `main`, лежит на стеке главного потока. Но **число** в ней —
  номер в таблице дескрипторов, а таблица одна на **процесс** (раздел 26.1).
  Если передать это число другому потоку, оно будет работать и там.

### 26.3. Права страницы без записи

Предсказание: строка `global` покажет **`prot 8`** — `PAGE_WRITECOPY`,
в x64dbg это `-RWC-`.

Рассуждение. Секция `.data` приходит из файла `.exe`, это память типа
`IMAGE`. Пока в страницу никто не писал, Windows не тратит на неё
отдельную копию: страница остаётся общей с образом файла и помечена
«копировать при записи» (глава 13). В исходной программе строка
`counter++` делала запись — процесс получал свою копию страницы, и права
становились обычными `0x04`. Убрали запись — копии нет, права `0x08`.

Если у тебя всё равно вышло `4` — это тоже объяснимо и полезно понять
почему. Права назначаются **страницей целиком**, а в `.data` лежит не
только `counter`: там же переменные стартового кода библиотеки C (у gcc
`.data` в нашей программе — `0xd0` байт, и `counter` — лишь первые 4 из
них). Если стартовый код до `main` что-то записал в ту же страницу, копия
уже сделана — и права `0x04`, хотя **ты** в неё не писал.

Урок: права говорят о **странице**, а не о переменной.

### 26.4. Запись в невыделенную страницу

Страница 1 нашего мегабайта **зарезервирована, но не выделена**. По
таблице из раздела 26.7 обращение к ней — исключение. Программа
напечатает строки про память и **упадёт** на `big[4096] = 'B'`, так и
не дойдя до `Press Enter`.

Под x64dbg программа остановится, а в журнале (**Log**) будет строка
вида:

```
First chance exception on 00007FF7B2C4176A (C0000005, EXCEPTION_ACCESS_VIOLATION)!
```

Разбор:

- **`C0000005`** — код исключения, **`EXCEPTION_ACCESS_VIOLATION`** —
  «нарушение доступа». Самое частое исключение в Windows: так же падает
  программа при чтении нулевого указателя (глава 4). Запомни это число
  в лицо.
- **Адрес в сообщении — это адрес инструкции**, которая попыталась
  записать, а не адрес памяти, куда она писала. У нас RVA этой
  инструкции `0x176a`:

  ```
  140001760   mov   rax, qword ptr [rbp-0x10]   ; rax = big
  140001764   add   rax, 0x1000                 ; rax = big + 4096
  14000176a   mov   byte ptr [rax], 0x42        ; записать 'B' — здесь падение
  ```

  Куда она писала, видно по регистру `RAX`: там `big + 0x1000`, начало
  зарезервированной страницы. (`0x42` — код буквы `B` в ASCII, глава 3.
  Твои адреса и RVA будут другими.)
- **First chance** — «первый шанс»: отладчик узнал об исключении раньше
  программы. Без отладчика Windows поискала бы в программе обработчик
  исключений, не нашла бы его (у нас его нет) и завершила бы процесс.

**Как исправить:** выделить обе страницы. Проще всего изменить второй
вызов:

```c
VirtualAlloc(big, 8192, MEM_COMMIT, PAGE_READWRITE);   /* две страницы */
```

Кстати, сработало бы и `4097`: `VirtualAlloc` округляет размер до целых
страниц, и 4097 байт займут две страницы.

### 26.5. Незнакомый `VirtualAlloc`

Раскладываем по регистрам (глава 12):

| Регистр | Значение | Смысл |
|---|---|---|
| `RCX` | `0` (`xor ecx, ecx` — обнуление, глава 10) | адрес выберет Windows |
| `RDX` | `0x5000` | 20 480 байт = 20 КБ = 5 страниц |
| `R8` | `0x3000` | `MEM_COMMIT \| MEM_RESERVE` — зарезервировать и сразу выделить |
| `R9` | `0x40` | `PAGE_EXECUTE_READWRITE` — чтение, запись **и выполнение** |

По-человечески: **«дай мне 20 КБ памяти, в которую можно и писать, и
откуда можно выполнять код»**.

**Сколько памяти:** 5 страниц, выделенных сразу. Адресов же область
займёт больше: начинаться она будет с границы 64 КБ, и оставшиеся
в этом «слоте» 44 КБ никому не достанутся — VMMap покажет их как
`Unusable` (раздел 26.10).

**Младшие цифры адреса:** из-за гранулярности (раздел 26.7) адрес в `RAX`
после вызова будет кратен `0x10000`, то есть кончится минимум на
**четыре нуля**.

**Что настораживает:** права `0x40`. Нормальной программе память, где
одновременно пишут и исполняют, почти не нужна. Такой вызов значит:
программа собирается **записать туда код и передать ему управление**.
Так делают упаковщики (глава 24), движки JIT (JavaScript в браузере) — и
вредоносные программы, которые прячут основной код. Рабочий план
реверсера: поставить точку останова сразу после вызова, записать адрес
из `RAX` и посмотреть, **что туда пишут** и **когда туда прыгают**.

### 26.6. Стек события из рабочего потока

Снизу вверх:

```
U  ntdll.dll       RtlUserThreadStart
U  KERNEL32.DLL    BaseThreadInitThunk
U  threads.exe     threads.exe + 0x....     (внутри worker, после call CreateFileW)
U  KERNELBASE.dll  CreateFileW
U  ntdll.dll       NtCreateFile
```

а выше — строки `K`, ядро.

**`main` здесь не будет.** Это главный вывод. Стек вызовов — это цепочка
кадров на стеке **того потока**, который сделал операцию (глава 11).
Рабочий поток начал жизнь не из `main`, а прямо с `worker`: система
вызвала `RtlUserThreadStart`, та — `BaseThreadInitThunk`, та — функцию,
которую мы передали в `CreateThread` (раздел 26.13). А `main` крутится
в другом потоке, на другом стеке.

Нет тут и стартового кода библиотеки C (`mainCRTStartup` и компании):
он работает только в главном потоке.

Практическая польза: увидев в Procmon стек, который начинается не
с точки входа `.exe`, а с какой-то внутренней функции, ты сразу знаешь —
это отдельный поток, и эта функция — его стартовая.

### 26.7. Поток, который не успел

`main` создаёт поток и **сразу** делает `return`. Как мы выяснили
в разделе 26.13, после `return` из `main` стартовый код библиотеки C
вызывает `ExitProcess`, а он завершает **все** потоки процесса. Рабочий
поток убивают, едва он родился. Успеет ли он напечатать строку-другую,
зависит от планировщика: если его поставили на соседнее ядро сразу, пару
строк он выдаст. Если нет — ничего.

**Как исправить:** `main` должен дождаться потока. Для этого есть
функция `WaitForSingleObject` («ждать один объект»):

```c
int main(void)
{
    HANDLE h = CreateThread(NULL, 0, worker, NULL, 0, NULL);
    WaitForSingleObject(h, INFINITE);   /* ждать, пока поток не завершится */
    CloseHandle(h);
    return 0;
}
```

Объект «поток» считается «сработавшим», когда поток завершается. Наш
`worker` бесконечный, значит, `main` будет ждать вечно — именно этого
друг и хотел.

**Для любознательных.** Есть и другой способ, прямо из правила
«процесс живёт, пока жив последний поток»: вместо `return 0` вызвать
в `main` функцию `ExitThread(0)` («завершить поток»). Главный поток
закончится, но `ExitProcess` никто не вызовет — и процесс будет жить,
пока жив `worker`. Для учебного опыта интересно, в настоящей программе
лучше явно ждать, как выше.

## Глава 27. Kernel mode и user mode

### 27.1. Номер кольца по `CS`

Метод один на все три случая: перевести число в двоичную систему
(глава 3) и посмотреть на **два младших бита** (раздел 27.3).

- **а) `0x33` = `0011 0011`.** Младшие биты `11` = 3. **Кольцо 3**, режим
  пользователя. Так выглядит `CS` у любой 64-битной программы.
- **б) `0x10` = `0001 0000`.** Младшие биты `00` = 0. **Кольцо 0**, режим
  ядра. Такой `CS` ты увидишь в WinDbg в главе 30.
- **в) `0x23` = `0010 0011`.** Младшие биты `11` = 3. **Кольцо 3.**

Случай «в» — ловушка для тех, кто запомнил «`0x33` значит кольцо 3»
вместо правила. Число другое, а кольцо то же. Остальные биты `CS`
говорят процессору, **какой это код**: 64-битный или 32-битный.
32-битной программе нужен 32-битный режим, поэтому Windows даёт ей
другое значение `CS`. Но права у неё ровно те же — кольцо 3. Как
устроены остальные биты, разберём в главе 33.

**Почему нельзя просто записать `0x10` в `CS`.** Потому что процессор
это не пропустит. Во-первых, обычной инструкции `mov cs, …` не
существует: `CS` меняется только при особых переходах, и на каждом
таком переходе процессор проверяет права. Попытка из кольца 3 перейти
в код кольца 0 любым путём, кроме трёх дверей из раздела 27.6,
закончится исключением. Во-вторых — и это главное — если бы так было
можно, вся защита не стоила бы ничего: любая программа объявила бы
себя ядром. Правило раздела 27.6: программа может постучать, но
не может выбрать. Номер кольца снижается **только** через двери,
адреса за которыми заранее записало ядро.

### 27.2. Какие инструкции разрешены в кольце 3

- **а) `add rax, rbx` — выполнится.** Обычная арифметика, разрешена
  в любом кольце.
- **б) `cpuid` — выполнится.** Узнать модель процессора — законная
  нужда любой программы (раздел 27.4). Но помни: под гипервизором на
  Intel она всегда вызывает VM exit — только программа этого не
  заметит.
- **в) `wrmsr` — `C0000096`.** Записать особый регистр настроек
  процессора — это переделать сам процессор. Только кольцо 0.
- **г) `syscall` — выполнится.** Это не нарушение, а **законная дверь**
  в ядро. Процессор переходит в кольцо 0, но не туда, куда хочет
  программа, а туда, куда заранее указало ядро. Ядро сделает работу
  и вернёт поток обратно.
- **д) `mov cr0, rax` — `C0000096`.** Управляющие регистры задают
  главные режимы процессора (в `CR0`, например, есть бит, который
  включает страничную память целиком). Только кольцо 0.
- **е) `rdtsc` — выполнится.** Счётчик тактов нужен программам для
  точных замеров. Процессор умеет запретить его в кольце 3, но Windows
  этого не делает.
- **ж) `int3` — «выполнится», но вызовет исключение.** Это та «особая
  нормальная», про которую был вопрос. `int3` разрешена в кольце 3 —
  но её **единственная работа** и есть вызвать исключение (глава 13).
  Исключение будет **другое**: не «привилегированная инструкция»,
  а «точка останова», `EXCEPTION_BREAKPOINT`, код `80000003`. Причина
  тоже другая: не нарушение прав, а так задумано. Именно поэтому
  отладчики и ставят `CC` в чужой код.

**Для любознательных.** Сам процессор при нарушении прав выдаёт одно
и то же исключение «общей защиты» — и для `hlt`, и для многих других
нарушений. Ядро Windows, получив его из кольца 3, **смотрит на байты
инструкции** по адресу `RIP`: если там `F4` (`hlt`), `FA` (`cli`),
`0F 30` (`wrmsr`), `0F 22` (`mov cr…, …`) и тому подобное, ядро
сообщает программе `C0000096`, иначе — `C0000005`. Так поступает,
например, ReactOS — открытая система, повторяющая устройство Windows.
Реверсер, который видит в коде ядра сравнение байтов с `F4` и `FA`,
теперь поймёт, что происходит.

### 27.3. Ветка `cli`

Добавить в `rings.c` перед последним `return 0;`:

```c
    if (strcmp(argv[1], "cli") == 0) {
        printf("Trying cli...\n");
        __asm__ volatile ("cli");        /* запретить прерывания */
        printf("cli worked?!\n");
    }
```

**Предсказание** (примерно так, адрес у тебя другой):

```
CS = 0033, ring 3
Trying cli...
Exception c0000096 at 00007FF7A3B81685
```

Рассуждение. `cli` запрещает аппаратные прерывания. Если бы программе
это разрешили, таймер перестал бы стучать в ядро, и планировщик не смог
бы отнять у программы процессор (раздел 27.6) — одна программа
захватила бы ядро процессора навсегда. Поэтому `cli` в кольце 3 под
Windows запрещена, и ответ тот же, что у `hlt`: `C0000096`,
«привилегированная инструкция». Строки `cli worked?!` не будет.

В моей сборке `cli` — один байт `FA` по RVA `0x1685`. Проверь по своему
адресу: четыре последние цифры — RVA, в Ghidra это `140000000` плюс
они (раздел 27.5).

Если строка всё же напечаталась — проверь, что ты запускаешь **новую**
сборку (`gcc` ещё раз) и передаёшь аргумент именно `cli`: при другом
слове ни одна ветка не сработает, и программа просто завершится после
первой строки.

### 27.4. `GetCurrentThreadId` вместо `ResetEvent`

**Ответ:** на втором этапе `kernel` почти **не вырастет**, вырастет
немного `user`.

Рассуждение. В разделе 26.12 главы 26 мы выяснили: `GetCurrentThreadId`
**не обращается к ядру**. Номер потока уже лежит в TEB — «паспорте»
потока в памяти самого процесса, — и функция просто читает его оттуда.
Никакого `syscall`, никакой двери: чистое кольцо 3. Значит, два
миллиона вызовов — это два миллиона коротких функций кольца 3, и всё их
время запишется в `user`.

Сравни с `ResetEvent`: событие живёт **в ядре**, и опустить его флажок
может только ядро. Поэтому каждый `ResetEvent` — поход через `syscall`.

Вывод, полезный для реверса: **по имени функции не видно, ходит ли она
в ядро**. `GetCurrentThreadId` звучит «системно», а работает в кольце 3.
`ResetEvent` звучит безобидно, а каждый раз уходит в кольцо 0. Узнать
наверняка можно, пройдя функцию в x64dbg по **F7** до конца: встретишь
`syscall` — значит, ходит. Как выглядит этот путь, увидим в главе 28.

### 27.5. Через какую дверь

- **а) `CreateFileW` — системный вызов.** Открыть файл — это работа
  с диском, её делает ядро. Программа сама и нарочно просит его через
  `syscall`.
- **б) Нажатие клавиши — аппаратное прерывание.** Клавиатура — устройство,
  она стучит в процессор в любой момент, что бы ни делала программа.
- **в) Первая запись в новую страницу — исключение**, страничный сбой.
  Физической памяти под страницей ещё нет (глава 26, раздел 26.7),
  процессор не может выполнить запись и зовёт ядро.
- **г) Точка останова — исключение.** `int3` (байт `CC`) вызывает
  исключение «точка останова», ядро передаёт его отладчику (глава 13,
  раздел 27.5).
- **д) Кончился квант — аппаратное прерывание** от таймера. Поток
  в бесконечном цикле ничего у ядра не просит, поэтому только таймер
  может вернуть процессор ядру (раздел 27.6).
- **е) Деление на ноль — исключение.** Процессор не может выполнить
  инструкцию деления и зовёт ядро.

**Программа никак не узнает о походе в ядро** в случаях **б**, **в** и **д**.
Прерывания (б, д) приходят «между инструкциями», ядро делает своё дело
и возвращает поток ровно туда же, со всеми регистрами (контекст, глава
26). Страничный сбой (в) ядро обрабатывает молча: подставляет физическую
страницу и повторяет ту же инструкцию. В случаях **а**, **г**, **е**
программа узнаёт: в «а» она сама попросила и получила результат, в «г»
и «е» ей (или отладчику) сообщили об исключении.

Строго говоря, одно косвенное свидетельство у программы всё-таки есть:
**время**. Поход в ядро занимает время, и точный замер (например,
`rdtsc` до и после) покажет «провал». Запомни эту мысль — в главе 39 ты
увидишь, что так пытаются заметить и гипервизор.

### 27.6. «Код одинаковый — пусть и падает одинаково»

Друг прав в одном: инструкции действительно те же, x86-64. Но падение —
это не свойство **инструкции**, а свойство того, **кто её подхватит**.

1. **Кто ловит.** Когда падает программа (кольцо 3), исключение
   уходит в ядро (раздел 27.5). Ядро стоит **выше** программы, цело и
   невредимо, и может аккуратно закрыть процесс: освободить его память,
   закрыть дескрипторы (глава 26). Когда падает драйвер (кольцо 0),
   ловить **некому**: выше ядра никого нет, а драйвер — это и есть
   часть ядра.
2. **Что задето.** Программа живёт в своём адресном пространстве
   (глава 26) — её ошибка портит только её память. Драйвер живёт
   в **общей** верхней половине вместе с ядром и всеми другими
   драйверами. Документация Microsoft говорит прямо: драйвер ядра не
   изолирован, и неверная запись может испортить данные системы или
   чужого драйвера. После такой ошибки нельзя быть уверенным, что
   ядро ещё цело.
3. **Что безопаснее.** Раз ядро могло быть испорчено, продолжать опасно:
   следующий шаг может записать мусор на диск. Поэтому Windows
   останавливает всё — bug check (раздел 27.9). Это не жестокость,
   а меньшее из зол.

Итог для друга: «закрыть только драйвер» можно было бы, если бы над
драйвером был кто-то, кто за ним следит и может его отделить. Для
программ такой «кто-то» есть — ядро. Для кода ядра его нет. (Точнее,
**может** быть — гипервизор. Но это уже часть XI.)

### 27.7. `msinfo32` на твоём компьютере

Ответ зависит от твоего компьютера, поэтому разберу оба варианта.

**Если написано «Выполняется» (Running) и есть строка «обнаружен
гипервизор».** Под твоей Windows уже работает Hyper-V, а сама Windows —
его гость (раздел 27.10). Место «ниже нуля» занято. Запустить свой
гипервизор прямо на этой системе не получится. Путь — вложенная
виртуализация: виртуальная машина, внутри которой процессор разрешает
пользоваться VT-x или AMD-V. Второй путь — отключить VBS на время
опытов, но это ослабляет защиту основной системы, и решать это будем
не сейчас, а в части XI, с полным пониманием последствий.

**Если написано «Не включено» (Not enabled) или «Включено, но
не выполняется» (Enabled but not running).** Гипервизора Microsoft
сейчас нет, место «ниже нуля» свободно. Но это не повод ставить опыты
на основной системе: ошибка в гипервизоре роняет компьютер так же, как
ошибка в драйвере (раздел 27.9), только хуже. Разработка всё равно
пойдёт в виртуальной машине.

В обоих случаях запиши в `PROGRESS.md` точную строку и процессор,
на котором смотрел (у тебя их два: на Intel и на AMD ответ может
отличаться). Это пригодится, когда будем выбирать, на каком из двух ПК
собирать стенд для гипервизора.

## Глава 28. Системные вызовы

### 28.1. Байты заглушки

Метод: разрезать байты на инструкции по таблице из раздела 28.3.

```
4C 8B D1                   mov  r10, rcx
B8 0F 00 00 00             mov  eax, 0x0F
F6 04 25 08 03 FE 7F 01    test byte ptr [0x7FFE0308], 1
75 03                      jne  +15
0F 05                      syscall
C3                         ret
CD 2E                      int  0x2E
C3                         ret
```

- **а)** Заглушка системного вызова из `ntdll.dll`. Узнаётся по трём
  приметам: `mov r10, rcx` в начале, `mov eax, число`, `0F 05`.
- **б)** Номер — **`0x0F`**. После опкода `B8` идут четыре байта числа
  в порядке little-endian (глава 3): `0F 00 00 00` → `0x0000000F`.
- **в)** Смещение **`0x12`**: 3 байта `mov r10, rcx` + 5 байт `mov eax` +
  8 байт `test` + 2 байта `jne` = 18 = `0x12`.
- **г)** В `RCX` будет адрес инструкции **после** `syscall`, то есть
  `ret`: `00007FFA12340000 + 0x12 + 2` = **`00007FFA12340014`**. Двойка —
  длина самой `syscall` (`0F 05`).

Какой это функции номер, по одним байтам сказать нельзя: номера зависят
от версии Windows. Узнать можно в x64dbg — посмотреть, возле какого
имени стоит эта заглушка.

### 28.2. Несуществующая папка

**Предсказание:**

| Где | Что будет |
|---|---|
| `LastStatus` | `C000003A` — `STATUS_OBJECT_PATH_NOT_FOUND`, «путь не найден» |
| `LastError` | `3` — `ERROR_PATH_NOT_FOUND` |
| Procmon, **Result** | `PATH NOT FOUND` |
| вывод программы | `CreateFileA failed, GetLastError = 3` |

Рассуждение. Ядро ищет имя по частям, от корня: сначала диск `C:`,
потом папку `no_such_dir`, потом файл в ней. Спотыкается оно **на папке**:
её нет, и до файла дело не доходит. Поэтому ответ не «имя не найдено»
(`C0000034` — так было, когда папка есть, а файла в ней нет), а «путь
не найден». `kernelbase.dll` переводит `C000003A` в Win32 `3`.

Урок: по коду ошибки видно, **где именно** оборвался поиск. Реверсер
часто так и выясняет, что ищет программа: смотрит в Procmon, какие пути
дали `NAME NOT FOUND`, а какие — `PATH NOT FOUND`.

### 28.3. Выбросить `mov r10, rcx`

Сломается передача **первого аргумента**. Инструкция `syscall` сама
пишет в `RCX` адрес возврата (раздел 28.5), и старое значение `RCX`
пропадает. Ядро знает об этом и берёт первый аргумент из `R10`. Без
`mov r10, rcx` в `R10` окажется то, что там лежало случайно, — мусор.

Для `NtCreateFile` первый аргумент — адрес, куда записать дескриптор.
Ядро получило бы мусорный адрес. Проверка указателя (раздел 28.6)
почти наверняка его отвергла бы, и вызов вернул бы ошибку
вроде `C0000005`. Файл не открылся бы ни при каких условиях.

Урок шире: в заглушке нет лишних инструкций. Каждая там потому, что
без неё что-то ломается.

### 28.4. `RSP` и флаг `IF` при `syscall`

**`RSP` — в пользовательской половине.** `syscall` не трогает `RSP`
(раздел 28.5), поэтому в первый миг после входа в кольцо 0 процессор
всё ещё стоит на стеке программы.

**`IF` сбрасывается**, чтобы до переключения стека не пришло аппаратное
прерывание. Прерывание в кольце 0 не меняет стек: процессор положил бы
данные ядра — адрес возврата, флаги — прямо на текущий стек, то есть
на **пользовательский**.

**Что могло бы случиться.** Стек программы программа и контролирует.
Её другой поток мог бы в этот миг читать эти данные ядра или подменять
их. А если программа нарочно поставила `RSP` на мусорный адрес, ядро
получило бы сбой прямо в обработчике прерывания — в самом уязвимом
месте. Поэтому правило такое: пока ядро на чужом стеке, никаких
прерываний. Переключило стек — `sti`, прерывания снова разрешены.

### 28.5. Адрес ядра вместо адреса дескриптора

**Ядро откажет**: вызов вернёт ошибку (обычно `C0000005`, нарушение
доступа), и ничего никуда записано не будет.

Рассуждение. Вызов пришёл через `syscall` из кольца 3, поэтому
`PreviousMode = UserMode` (раздел 28.6). `NtCreateFile` проверяет
указатель: лежит ли он в пользовательской половине? `FFFF800000001000` —
нет. Проверка не пройдена — ошибка.

**Почему нельзя просто записать, раз ядру можно.** Потому что тогда
ядро стало бы **руками программы**. Программа не может сама писать
в память ядра — это запрещает процессор (глава 27). Но если ядро пишет
куда скажут, программа получила бы эту возможность через ядро:
подобрала бы адрес, и ядро само испортило бы свои данные. Защита колец
потеряла бы смысл. Такую ошибку в ядре (или в драйвере) называют
уязвимостью, и в части IX ты будешь учиться их **не допускать**
в собственном драйвере.

### 28.6. `Nt` и `Zw`

- **а) В программе — разницы нет.** В кольце 3 `NtClose` и `ZwClose` —
  одна и та же заглушка в `ntdll.dll`, по одному адресу. Проверить
  можно в x64dbg: **Ctrl+G** → `ntdll.ZwClose`, потом `ntdll.NtClose` —
  адрес будет одинаковым.
- **б) В драйвере — вероятно, `PreviousMode`.** Драйвер работает
  в потоке, который пришёл в ядро из программы, поэтому `PreviousMode =
  UserMode`. `NtCreateFile` проверяет буфер как пользовательский,
  а буфер лежит в памяти ядра, в верхней половине, — проверка
  проваливается. **Исправление:** звать `ZwCreateFile`. Она
  устанавливает `PreviousMode = KernelMode` и говорит ядру: параметры
  пришли из ядра, им можно верить (раздел 28.8).

### 28.7. Заглушка `NtUserGetDC`

**Похожа** на заглушку `NtCreateFile` устройством: `mov r10, rcx`,
`mov eax, число`, проверка флажка по адресу `7FFE0308`, `syscall`,
`ret`, запасной `int 0x2E`. Это тот же механизм, та же дверь.

**Отличается:**

1. **Библиотекой** — `win32u.dll`, а не `ntdll.dll`.
2. **Номером**: он **`0x1000` или больше** (точное число зависит от
   версии Windows). Это не случайность: по номерам от `0x1000` ядро
   понимает, что просьба к `win32k…sys` — к графической части ядра,
   а не к `ntoskrnl.exe` (раздел 28.9).

Если не нашёл `win32u.NtUserGetDC`: проверь, что программа именно
`box.exe` (с `MessageBoxW`) и что ты дошёл до `entry breakpoint` —
раньше `user32.dll` и `win32u.dll` могут быть ещё не загружены.
Попробуй и форму `win32u:NtUserGetDC`.

## Глава 32. Страничная память

### 32.1. Режем руками

**PML4 = 0, PDPT = 1, PD = 511, PT = 480, смещение = `0x000`.**

Ход работы. В Калькуляторе (режим «Программист», HEX) вводим
`7FFE0000` и смотрим строку BIN. Для удобства дополним нулями слева
до 32 битов и разобьём справа налево:

```
0111 1111 1111 1110 0000 0000 0000 0000      ← 0x7FFE0000

справа 12 битов:   0000 0000 0000            → смещение 0x000
следующие 9:       1 1110 0000               → PT   = 0x1E0 = 480
следующие 9:       1 1111 1111               → PD   = 0x1FF = 511
следующие 9:       01 (дальше нули)          → PDPT = 1
остальное:         нули                      → PML4 = 0
```

Проверка формулой: `0x7FFE0000 >> 12 = 0x7FFE0`, младшие 9 битов —
`0x1E0` = 480. Сходится с выводом `pagewalk.exe` в разделе 32.8.

**Почему адрес не меняется.** `KUSER_SHARED_DATA` Windows ставит
по **постоянному** адресу `0x7FFE0000` во всех процессах (глава 26):
программы и `ntdll.dll` читают её по этому числу, зашитому прямо
в код (помнишь `test byte ptr [0x7FFE0308], 1` в заглушке из главы 28?).
Если бы адрес двигался, этот код бы сломался. А `main` лежит в образе
`.exe`, и образ ASLR при каждом запуске ставит в новое место (глава 4).

### 32.2. Сколько весит дерево

**а) 1 ГБ.** Одна запись PD покрывает 2 МБ (раздел 32.3), записей
512: 512 × 2 МБ = 1024 МБ = 1 ГБ. Или через биты: целая таблица PD
отвечает за всё, что ниже индекса PDPT, — это 9 + 9 + 12 = 30 битов,
2³⁰ байт = 1 ГБ.

**б) 4 таблицы, 16 КБ.** Чтобы процессор дошёл до одной страницы,
нужна одна таблица **каждого** уровня: PML4 → PDPT → PD → PT. В каждой
заполнена всего одна запись, остальные 511 — с P = 0. Каждая таблица —
одна страница, 4 КБ. Итого 4 × 4 КБ = **16 КБ**.

Сравни: плоская таблица — 256 ГБ, дерево — 16 КБ. Разница в
шестнадцать миллионов раз. В этом и смысл дерева: платишь только за
ветки, где что-то есть. (Настоящему процессу нужно больше таблиц —
у него десятки областей в разных местах, плюс общие таблицы ядра, —
но всё равно это мегабайты, а не сотни гигабайт.)

### 32.3. Спуск по дереву

Сначала индексы. `0x403ABC`:

```
PML4 = (0x403ABC >> 39) & 0x1FF = 0
PDPT = (0x403ABC >> 30) & 0x1FF = 0
PD   = (0x403ABC >> 21) & 0x1FF = 2      ← 0x400000 — это ровно 2 × 2 МБ
PT   = (0x403ABC >> 12) & 0x1FF = 3      ← 0x403 & 0x1FF = 3
смещение = 0xABC
```

Подсказка, как считать в уме. `0x400000` = 4 МБ, а одна запись PD
покрывает 2 МБ, значит, 4 МБ — это начало записи PD номер 2. Остаток
`0x3ABC` — внутри неё: `0x3ABC >> 12 = 3` (третья страница),
смещение `0xABC`.

Теперь адреса записей по правилу «таблица + индекс × 8»:

```
PML4E:  0x5000 + 0 × 8 = 0x5000
PDPTE:  0x7000 + 0 × 8 = 0x7000
PDE:    0x9000 + 2 × 8 = 0x9010
PTE:    0xB000 + 3 × 8 = 0xB018
итог:   0x42000 + 0xABC = 0x42ABC
```

Частая ошибка — прибавить индекс без умножения на 8 (получится
`0x9002` вместо `0x9010`). Запись занимает 8 байт, и индекс — это
номер **записи**, а не байта.

Кстати, `0x400000` — не случайное число. Это стандартная база образа
старых 32-битных программ Windows. В 64-битных программах её сменила
`0x140000000` — та, что ты видел в Ghidra в главе 14.

### 32.4. Читаем записи

**а) `0000000076543025`**

Младшие 12 битов — `0x025` = `0000 0010 0101`:

| Бит | Значение | Смысл |
|---|---|---|
| 0 (P) | 1 | страница есть |
| 1 (R/W) | 0 | **только чтение** |
| 2 (U/S) | 1 | пользовательская, доступна из кольца 3 |
| 5 (A) | 1 | к ней обращались |
| 6 (D) | 0 | в неё не писали |
| 63 (XD) | 0 | старшая цифра `0` — **выполнять можно** |

Физический адрес: `0x76543000`. Читать и выполнять можно, писать —
нет, пользовательская. Это права `PAGE_EXECUTE_READ` (раздел 32.6):
типичная страница **кода**, секция `.text` программы или библиотеки.
D = 0 тоже логично: в код никто не пишет.

**б) `0000000ABCDE0006`**

Младшие 12 битов — `0x006` = `0000 0000 0110`: бит 1 и бит 2 равны 1,
но **бит 0 (P) равен 0**.

Это главное: **P = 0 — страницы нет**. Все остальные биты процессор
при этом **не смотрит вовсе** — ни R/W, ни U/S, ни «адрес»
`0xABCDE000`. Любое обращение — страничный сбой. Что значат остальные
биты, знает только Windows: там могут лежать её пометки — например,
что страница выгружена в файл подкачки и где её там искать (раздел
32.7). Это ловушка упражнения: не надо разбирать права у записи с P = 0.

### 32.5. Канон

Правило: смотрим на бит 47 и старшие 16 битов. Если адрес начинается
на `0000` и следующая цифра от `0` до `7` — канонический (нижняя
половина). Если начинается на `FFFF` и следующая цифра от `8` до `F` —
канонический (верхняя половина). Всё остальное — нет.

| Адрес | Канонический? | Почему |
|---|---|---|
| `00007FFFFFFFFFFF` | **да** | последний адрес пользовательской части |
| `0000800000000000` | **нет** | бит 47 = 1, а старшие биты — нули |
| `FFFF800000000000` | **да** | первый адрес половины ядра |
| `FFFF7FFFFFFFFFFF` | **нет** | старшие — единицы, а бит 47 = 0 |
| `0001000000000000` | **нет** | единица в бите 48 — в «запретных» битах |
| `FFFFF78000000000` | **да** | бит 47 = 1, старшие — единицы. Это половина ядра |

Для неканонических адресов процессор **не начинает** спуск по таблицам
и сразу вызывает общее нарушение защиты (#GP, раздел 32.10). Программа
в кольце 3 получит `C0000005`.

Что будет при чтении канонических? `00007FFFFFFFFFFF` — скорее всего,
тоже `C0000005`: адрес допустимый, но там почти наверняка ничего не
выделено (P = 0, настоящий страничный сбой). `FFFF800000000000`
и `FFFFF78000000000` — `C0000005` из-за U/S = 0 или P = 0: это половина
ядра. То есть **исключение одно и то же**, но у процессора это три
разные причины: #GP, страничный сбой без страницы и страничный сбой
по правам.

Любопытный факт: по адресу `FFFFF78000000000` ядро видит ту же
страницу `KUSER_SHARED_DATA`, которую программы видят по `0x7FFE0000`.
Одна физическая страница — два виртуальных адреса в разных половинах.
Так тоже можно: две записи PTE указывают на одну физическую страницу.

### 32.6. Эксперимент с шагом

**Предсказание:** сбоев станет больше примерно на **8 192**, рабочий
набор вырастет примерно на **32 МБ** (32 768 КБ).

Рассуждение. 64 МБ = 16 384 страницы. С шагом 8192 цикл трогает каждую
вторую: 16 384 / 2 = 8 192 страницы. Нетронутые страницы остаются
с P = 0 — физической памяти у них нет, сбоев по ним тоже нет. Каждая
тронутая — один сбой и 4 КБ в рабочем наборе: 8 192 × 4 КБ = 32 МБ.

Второй проход, как и раньше, сбоев почти не добавит: тронутые страницы
уже на месте.

Если реальные числа отличаются от предсказания — вспомни оговорку
в разделе 32.9: точная арифметика зависит от внутренних хитростей
Windows. Главное — чтобы прирост был примерно вдвое меньше, чем
с шагом 4096. Напиши мне свои числа.

**Звёздочка: только `MEM_RESERVE`.** Программа упадёт с `C0000005`
на первой же записи `p[0] = 1`.

Почему. Процессор в обоих случаях видит одно и то же — P = 0,
страничный сбой. Разница — в том, что **Windows записала у себя**.
При `MEM_COMMIT` она обещала память (глава 26), и сбой для неё —
«первое касание, выдать страницу». При `MEM_RESERVE` адреса только
забронированы, памяти за ними нет и не обещано. Сбой в такой области
Windows считает настоящей ошибкой и отдаёт программе исключение.
То есть **процессор не знает разницы между резервом и выделением —
её знает только Windows**.

### 32.7. Строгий побеждает

**а) Нет, не выполнится.** Для выполнения нужно, чтобы XD = 0
**на всех** уровнях пути. В PD стоит XD = 1 — и это запрещает
выполнение для всех 512 страниц под этой записью (2 МБ адресов),
что бы ни было записано в их PTE.

**б) Биты 0, 2 и 4.**

| Бит | Значение | Почему |
|---|---|---|
| 0 | **1** | страница **есть**, не подошли **права** |
| 1 | 0 | это не запись |
| 2 | **1** | сбой случился в **кольце 3** |
| 4 | **1** | процессор пытался **выбрать инструкцию** — выполнить |

Код ошибки = `0b10101` = `0x15`. Windows по нему поймёт: программа
попыталась выполнить неисполняемую память — это срабатывание DEP
(глава 11). Программа получит `C0000005`.

## Глава 33. Привилегии и системные регистры

### 33.1. Разбор CR0

`80000011`:

```
80000011
      11  = 0001 0001  → биты 0 и 4
8         = 1000       → бит 31
```

- бит 0 — **PE**: защищённый режим включён;
- бит 4 — ET, пережиток математического сопроцессора, не важен;
- бит 31 — **PG**: страничная память **включена**.

А вот бит 16 (**WP**) — **ноль**. Цифра на позиции 4 (биты 16–19) — `0`.
Значит, код ядра **не защищён** от записи самим ядром: кольцо 0 может
писать в страницы с R/W = 0. Ошибка в драйвере, которая пишет в код
ядра, не упадёт сразу, а тихо его испортит. Сравни с обычным для
Windows `80050033`: там на позиции 4 стоит `5` = `0101`, биты 16 и 18.

Метод тот же, что с PTE в главе 32: каждая hex-цифра — четыре бита,
цифра на позиции *k* справа (считая с нуля) отвечает за биты
с 4*k* по 4*k* + 3.

### 33.2. Ступени загрузки

**б → г → в → а**, причём **г** и **в** можно поменять местами:

1. **б) `CR0.PE = 1`** — из реального режима в защищённый. Без этого
   нет колец и таблиц.
2. **г) `CR4.PAE = 1`** — записи таблиц по 8 байт (64-битному режиму
   нужен именно такой формат). Заодно в `CR3` кладут адрес PML4.
3. **в) `EFER.LME = 1`** — «разрешаю длинный режим».
4. **а) `CR0.PG = 1`** — включить страничную память. Именно в этот миг
   процессор видит, что всё готово, и переходит в 64-битный режим.

Бит, который процессор ставит **сам**, — **`EFER.LMA`** (Long Mode
Active): «длинный режим работает». Его не пишут, его читают, чтобы
проверить, что переход удался.

Почему PG — последним? Как только страничная память включена, каждый
адрес идёт через таблицы. Если бы таблицы или формат записей ещё не
были готовы, процессор на следующей же инструкции переводил бы адреса
по мусору.

### 33.3. Свой `cpuid`

Правильного ответа здесь нет — есть **твой**. Как читать вывод:

- **а)** строка `vendor`: `GenuineIntel` — Intel, `AuthenticAMD` — AMD.
  Строка `brand` — полное название.
- **б)** на Intel смотри `VMX`, на AMD — `SVM`. Бит чужого производителя
  будет 0 — это нормально: у Intel нет AMD-V, и наоборот.
- **в)** `hypervisor 1` — Windows работает гостем. `hv vendor` скажет
  чьим: `Microsoft Hv` — это Hyper-V, скорее всего включён VBS
  (целостность памяти, глава 27). `hypervisor 0` — гипервизора нет,
  место «ниже нуля» свободно.

Возможная неожиданность: `VMX 0` на Intel при `hypervisor 1`. Это
не значит, что процессор не умеет VT-x: гипервизор Microsoft может
прятать этот бит от своего гостя, как KVM на моём сервере
(раздел 33.5). Пришли мне вывод с обоих компьютеров — по ним решим,
как будем испытывать гипервизор в части XI.

### 33.4. Допиши вопрос

После строки с LA57 (там `r` уже содержит ответ на лист 7) добавь:

```c
    printf("SMEP       %d\n", bit(r[1], 7));
```

`r[1]` — это `EBX`: порядок в массиве `EAX, EBX, ECX, EDX` = `r[0]…r[3]`.
Частая ошибка — написать `r[2]` по привычке: LA57 лежал в `ECX`,
а SMEP — в `EBX` того же листа.

Если хочешь, чтобы вопрос стоял отдельно, повтори `ask(7, r);` перед
`printf` — лишний `cpuid` ничего не испортит. На современных Intel
и AMD ты увидишь `SMEP 1`.

### 33.5. Селекторы

Формулы: `index = селектор >> 3`, `TI = (селектор >> 2) & 1`,
`RPL = селектор & 3`.

| Селектор | Двоичная запись (младший байт) | index | TI | RPL | Что это (раздел 33.7) |
|---|---|---|---|---|---|
| `0x2B` | `0010 1011` | 5 | 0 | 3 | данные и стек программ |
| `0x23` | `0010 0011` | 4 | 0 | 3 | код 32-битных программ (WoW64) |
| `0x18` | `0001 1000` | 3 | 0 | **0** | данные и стек ядра |
| `0x53` | `0101 0011` | 10 | 0 | 3 | сегмент для `FS` |

Для кольца 0 — только `0x18`: у него RPL = 0. Проверка через деление:
`0x53` = 83; 83 ÷ 8 = 10 (остаток 3) → index 10, а остаток 3 = TI 0
и RPL 3.

Заметь закономерность: у всех селекторов кольца 3 младшая hex-цифра —
`3` или `B` (`0011` и `1011`), у селекторов кольца 0 — `0` или `8`.
Увидев в отладчике ядра `CS 0010`, сразу понимаешь: ядро.

### 33.6. Попытка стать ядром

Процессор **откажет**: общее нарушение защиты (#GP). Программа увидит
`C0000005`.

Ход рассуждения. При дальнем переходе процессор находит в GDT
дескриптор записи 2 (`0x10 >> 3 = 2`), читает его DPL — это 0, код ядра.
Текущее кольцо — 3. Прямой переход в более привилегированный код
запрещён. Не помогает и то, что RPL в селекторе мы можем написать любой:
решает DPL в дескрипторе, а дескрипторы пишет только ядро (`lgdt` —
привилегированная).

Законные пути в кольцо 0 — только через адреса, которые ядро заранее
записало само: `LSTAR` для `syscall` и таблица IDT (глава 34).

### 33.7. Два рубильника

Ошибка в том, что **`CR4.VMXE` — рубильник Intel**. У Ryzen — процессор
AMD, и его виртуализация называется AMD-V (SVM). Для неё нужно:

1. проверить `cpuid` лист `80000001`, `ECX` бит 2;
2. убедиться, что в MSR `VM_CR` бит 4 (SVMDIS) равен 0 — прошивка
   не запретила;
3. поставить **`EFER.SVME = 1`** — рубильник AMD лежит в MSR `EFER`,
   а не в `CR4`.

Скорее всего, у друга всё сломалось ещё раньше: в документации AMD бит
13 регистра `CR4` описан как зарезервированный, а запись единицы
в зарезервированный бит `CR4` вызывает исключение. Урок для твоего
гипервизора: код включения для Intel и для AMD — **разный**, и выбирать
ветку надо по `cpuid`, лист 0 (`GenuineIntel` или `AuthenticAMD`).

## Глава 34. Прерывания

### 34.1. Адрес шлюза

Правило: **адрес шлюза = база IDT + вектор × 16**.

- Страничный сбой — вектор 14: 14 × 16 = 224 = `0xE0`.
  Адрес: `FFFFF80012340000 + E0` = **`FFFFF800123400E0`**.
- `int 0x2E` — вектор `0x2E`: `0x2E` × 16 = `0x2E0` (умножить на 16 в hex —
  дописать ноль справа, как умножить на 10 в десятичной).
  Адрес: **`FFFFF800123402E0`**.
- Вся IDT: 256 × 16 = **4096 байт** — ровно одна страница.

Частая ошибка — умножить на 8, как в GDT и таблицах страниц. Шлюз IDT
в 64-битном режиме вдвое больше: в нём 64-битный адрес обработчика.

### 34.2. Предскажи коды

Сверься с таблицей раздела 34.5. Главное, что стоит проверить в своём
выводе: в **каждом** запуске строки `address` и `expected` совпадают.
Для пяти сбоев это естественно: процессор сохраняет адрес виновной
инструкции. Для `int3` — благодаря поправке Windows (раздел 34.3).

Если какой-то код у тебя отличается от таблицы — пришли вывод целиком,
это интересно разобрать. Например, если Windows когда-нибудь поменяет,
как переводит вектор 13 в коды.

### 34.3. Сбой или ловушка

| Событие | Вид | Сохранённый `RIP` |
|---|---|---|
| а) деление на ноль | **сбой** (#DE) | на **ту же** `div` |
| б) `int3` | **ловушка** (#BP) | на инструкцию **после** `CC` (Windows потом сдвинет на 1 назад) |
| в) первое касание страницы | **сбой** (#PF) | на **ту же** инструкцию — её повторят после подстановки страницы |
| г) шаг F7 | **ловушка** (#DB) | на **следующую** инструкцию: та, что с `TF`, уже выполнена |

Как рассуждать: «можно ли после обработки просто повторить
инструкцию?» Для страничного сбоя — да, и это нужно: запись должна
пройти. Для `int3` и шага — нет: событие — это сама выполненная
инструкция, повторять нечего.

### 34.4. Стек после прерывания

Таймер застал программу в кольце 3, обработчик — в кольце 0, поэтому
процессор перешёл на стек ядра из `TSS.RSP0` и положил:

| Поле | Значение |
|---|---|
| `SS` | `0x2B` — стек программы (глава 33) |
| `RSP` | **`000000A3B2DFF800`** — старый, пользовательский |
| `RFLAGS` | флаги программы (`IF` в них = 1: прерывания были разрешены, иначе таймер не пришёл бы) |
| `CS` | **`0x33`** — код программы, кольцо 3 |
| `RIP` | адрес следующей не начатой инструкции программы |

**Кода ошибки нет**: у аппаратных прерываний его не бывает.

Если бы вместо таймера был **страничный сбой** — всё то же самое, но
`RIP` указывал бы на **ту же** инструкцию (это сбой), и сверху лёг бы
**код ошибки** с битами из главы 32. Бит 2 в нём был бы 1: сбой
случился в кольце 3.

### 34.5. Запретная дверь

Всё решает поле **DPL шлюза**: инструкцией `int n` можно вызвать вектор,
только если текущее кольцо не слабее, чем DPL (CPL ≤ DPL).

- **`int 0x0E`** — у шлюза страничного сбоя DPL = 0. Программа в кольце 3
  не имеет права. Процессор вместо этого выдаёт **#GP**. Программа,
  скорее всего, увидит `C0000005`.
- **`int3`** — у шлюза вектора 3 DPL = 3. Разрешено: обычная точка
  останова, `80000003`.
- **`int 0x2E`** — DPL = 3. Разрешено: это старая дверь для системных
  вызовов из главы 28. Ядро выполнит системный вызов с номером из `EAX`.

Зачем такой замок? Иначе программа могла бы изобразить страничный сбой
или любое другое событие, и ядро приняло бы подделку за настоящее
сообщение процессора, со всеми вытекающими.

### 34.6. Почему IST

`RSP0` из TSS процессор берёт **только при переходе из кольца 3
в кольцо 0**. А double fault чаще всего случается, когда процессор
**уже в ядре** — и именно потому, что стек ядра испорчен. В этом
случае без IST процессор остался бы на текущем, сломанном стеке,
попытался бы положить туда пять значений, получил бы ещё одну ошибку —
и третья подряд (triple fault) просто перезагружает компьютер.

Поле IST в шлюзе заставляет процессор **всегда** переключиться на
отдельный, заранее выделенный и заведомо исправный стек. Поэтому ядро
успевает хотя бы показать синий экран с понятным кодом.

### 34.7. IRQL

Цепочка:

1. Драйвер на `DISPATCH_LEVEL` читает переменную.
2. **Сегодня** страница с ней в оперативной памяти: `P = 1`, сбоя нет,
   всё работает.
3. **Через неделю** памяти стало мало, и Windows выгрузила эту страницу
   в файл подкачки: `P = 0` (главы 26 и 32).
4. Чтение вызывает страничный сбой. Чтобы его обработать, ядро должно
   прочитать страницу с диска и **подождать** — переключиться на другой
   поток.
5. Но на `DISPATCH_LEVEL` переключать потоки нельзя. Ядро видит
   нарушение правила и останавливает систему:
   `IRQL_NOT_LESS_OR_EQUAL`.

**Почему не всегда.** Ошибка в коде есть всегда, а **проявляется** она
только тогда, когда страница случайно окажется выгруженной. Это зависит
от нагрузки, объёма памяти, других программ. Такие «плавающие» ошибки —
самые коварные. Поэтому у Microsoft есть Driver Verifier — инструмент,
который нарочно выгружает память драйвера, чтобы такие ошибки
проявлялись сразу. Им мы воспользуемся в части IX.

## Приложение П1. Си: от чтения к письму

### П1.1. Размеры

| Значение | Тип | Почему |
|---|---|---|
| а) `CR3` | `uint64_t` | регистр 64-битный, в нём физический адрес |
| б) селектор `CS` | `uint16_t` | селектор — 16 битов (глава 33) |
| в) байт шифра | `uint8_t` | ровно байт, без знака (глава 17) |
| г) половинка MSR в `EAX` | `uint32_t` | `EAX` — 32 бита |
| д) результат `sizeof` | `size_t` | так его объявляет язык; печатать через `(unsigned long long)` и `%llu` |

Ловушка — выбрать `long` для а): в Windows он 4 байта, и старшая
половина `CR3` пропала бы.

### П1.2. Рецепты

```c
cr4 |= 1ULL << 13;                  // а) поставить VMXE
pte &= ~(1ULL << 1);                // б) снять R/W
if (efer & (1ULL << 12)) { ... }    // в) есть ли SVME
uint64_t pd = (va >> 21) & 0x1FF;   // г) индекс PD
```

Проверь себя по г): сдвиги индексов — 39, 30, **21**, 12 (глава 32,
раздел 32.5). Маска `0x1FF` — девять единиц.

### П1.3. Найди ошибку

`1` — это `int`, 32 бита. Сдвиг на 63 выходит за его ширину: результат
не определён, и бит 63 так не поставить. Исправление: **`pte |= 1ULL << 63;`**

Компилятор для Windows с `-Wall` скажет (я проверил):

```
warning: left shift count >= width of type [-Wshift-count-overflow]
```

«Величина сдвига больше или равна ширине типа». Если видишь это
предупреждение — почти наверняка забыт суффикс `ULL`.

### П1.4. Выравнивание

`struct C { char a; uint64_t b; char c; };` — **24 байта**:

```
a — смещение 0   (1 байт, потом 7 пустых: b должен начаться с кратного 8)
b — смещение 8   (8 байт)
c — смещение 16  (1 байт, потом 7 пустых: размер кратен 8)
```

Переставим: `struct D { uint64_t b; char a; char c; };` — **16 байт**:
`b` на 0, `a` на 8, `c` на 9 и 6 пустых байт в конце. Правило: **большие
поля — первыми**, мелкие — в конец, тогда дырок меньше.

Проверочная программа (числа выше — её настоящий вывод):

```c
#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

struct C { char a; uint64_t b; char c; };
struct D { uint64_t b; char a; char c; };

int main(void)
{
    printf("C: size %llu, a %llu, b %llu, c %llu\n",
           (unsigned long long)sizeof(struct C),
           (unsigned long long)offsetof(struct C, a),
           (unsigned long long)offsetof(struct C, b),
           (unsigned long long)offsetof(struct C, c));
    printf("D: size %llu\n", (unsigned long long)sizeof(struct D));
    return 0;
}
```

### П1.5. Своя запись

В `pte.h`:

```c
typedef union {
    uint16_t value;
    struct {
        uint16_t rpl   : 2;    // биты 0–1
        uint16_t ti    : 1;    // бит 2
        uint16_t index : 13;   // биты 3–15
    } bits;
} SELECTOR;
```

В `main.c`:

```c
_Static_assert(sizeof(SELECTOR) == 2, "SELECTOR must be 2 bytes");

void show(uint16_t v)
{
    SELECTOR s;
    s.value = v;
    printf("selector %04X: index %u, ti %u, rpl %u\n",
           s.value, s.bits.index, s.bits.ti, s.bits.rpl);
}
```

и вызовы `show(0x33); show(0x10);`. Вывод:

```
selector 0033: index 6, ti 0, rpl 3
selector 0010: index 2, ti 0, rpl 0
```

Совпадает с разбором в главе 33: запись 6 GDT, кольцо 3 — код программ;
запись 2, кольцо 0 — код ядра. Обрати внимание: поля объявлены
**`uint16_t`**, а не `uint64_t`, — иначе объединение раздулось бы
до 8 байт, и `_Static_assert` это поймал бы.

### П1.6. Таблица обработчиков

```c
void on_negative(int value) { printf("negative: %d\n", -value); }

HANDLER table[] = { on_hello, on_double, on_square, on_negative };
```

В проверке границ менять **ничего не нужно**: `COUNT` вычисляется
через `sizeof(table) / sizeof(table[0])` и сам стал 4. В этом и смысл
такой записи. Если бы границу написали числом `3`, новый обработчик
никогда бы не вызвался — и такую ошибку легко не заметить.

### П1.7. Проект дальше

Один из вариантов `main.c`:

```c
#include <stdio.h>
#include <string.h>
#include "pte.h"

int main(int argc, char **argv)
{
    int verbose = 0, first = 1, ok = 0, bad = 0;

    if (argc > 1 && strcmp(argv[1], "-v") == 0) {
        verbose = 1;
        first = 2;                  // записи начинаются со второго аргумента
    }
    for (int i = first; i < argc; i++) {
        PTE e;
        if (pte_parse(argv[i], &e)) {
            pte_print(e);
            ok++;
        } else {
            printf("not a hex number: %s\n", argv[i]);
            bad++;
        }
    }
    if (verbose)
        printf("parsed: %d, errors: %d\n", ok, bad);
    return 0;
}
```

Ход мысли: ключ стоит **первым**, значит, проверяем только `argv[1]`
и, если это `-v`, начинаем разбор с `argv[2]`. `strcmp` возвращает 0
при равенстве (глава 5) — отсюда `== 0`. Сборку без аргументов (где
программа строила запись сама) можно оставить: добавь её снова в начало,
если хочешь сохранить.
